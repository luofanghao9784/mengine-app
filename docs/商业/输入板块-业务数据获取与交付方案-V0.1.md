# 输入板块：业务数据获取与交付方案 V0.1

日期：2026-09-28。状态：用户认可讨论逻辑，并要求固化为输入板块的业务方案。本文记录客户选择、获取路径与交付边界；渠道为按场景选择的方案，不代表全部进入首期，也不代表已有连接器实现、客户数据授权、供应商选型或收费承诺。

关联：[基础流程与输入设计](../技术/梦核引擎-基础流程与自进化接入讨论稿-V0.1.md)、[服务与收费边界](服务与收费边界.md)、[产品需求基线](../产品/产品需求基线-V0.1.md)、[开发决策记录 DEC-081](../技术/开发决策记录.md)。

## 1. 业务判断原则

按目标任务的数据可获得性选择切入点，不以企业有无 API 作为唯一客户门槛，也不默认先为客户建设管理系统。

从要交付的成果倒推必需事实、历史跨度、更新频率和业务口径，再调查现有来源、核验依据、读取权限、负责人及持续成本。有稳定报表导出的企业可以先做日度或周度工作；存在 API 不代表数据完整、口径一致或有人维护。

AI 可以帮助获取、提取、映射和检查已有证据，不能可靠补出从未记录的业务事实。接入成功、结构化成功与事实核实分别表达；例如收款记录不必然包含完整订单、退货或库存事实。

## 2. 三类数据条件与交付路线

| 数据条件 | 首选处理方向 | 业务边界 |
| --- | --- | --- |
| 已有系统和可信记录，但没有合适接口 | 寻找导出、文件交付、经授权的数据库或界面操作渠道 | 先判断能否持续获得任务所需数据，不承诺接通所有封闭系统 |
| 没有统一系统，但有表格、单据、文档等记录 | 汇集现有记录，建立映射、校验和更新责任 | 确认覆盖范围和缺口，不将零散证据包装为全企业完整数据 |
| 关键业务没有持续记录 | 用既有表格或现成表单建立任务所需的最小记录流程 | 企业明确记录和确认责任；不以模型推断冒充缺失历史 |

无可靠来源且不愿承担记录责任时，缩小该任务的承诺范围，转向可由现有资料支持的工作，或不承接该数据驱动场景；不因此判定该客户不能使用任何 AI 功能。

## 3. 可选获取方式

以下是调查和选型清单，不是所有客户必须依次执行的流程。具体系统能否提供相应能力，需要在实施时核实。

| 方式 | 适用条件 | 持续运行要处理什么 |
| --- | --- | --- |
| 官方 API、Webhook 或供应商合作接口 | 接口覆盖目标任务，取得必要授权 | 数据口径、覆盖范围、限额、供应商变更和费用 |
| 客户可控制的数据库只读视图或报表库 | 自建或本地部署系统，有明确管理与读取权限 | 表结构、读取范围、系统负载和维护责任；不假定 SaaS 数据库可直接访问 |
| 定期文件导出与交付 | 有 CSV、Excel 等报表或现有台账 | 固定格式、业务周期、交付负责人、遗漏与重复核验；可从人工上传逐步转为文件目录或 SFTP 等自动交付 |
| 浏览器或桌面自动化下载报表 | 仅有可操作界面，具备相应账号和运行条件 | 优先复用已有报表导出；处理登录、页面变化、执行环境、失败通知和人工补交 |
| PDF、图片、扫描件等内容提取 | 原始记录只有非结构化材料 | 保留证据，检查遗漏、识别错误和业务含义；不因提取完成直接标记事实正确 |

初次建立时可由 AI 辅助理解字段、识别口径和生成映射；稳定方法经核验后优先由程序复用。新格式、歧义和异常按需调用模型或交由负责人处理，不要求每次取数都调用主模型。

人工、半自动和自动交付都可以成为正式来源，后续替换获取渠道时复用来源与数据说明。自动化失败可采用获准的同口径文件补交，并保留批次与核验记录，不掩盖实际人工成本。

对外部客户系统的读取由接入适配和平台授权边界承接，不赋予独立引擎直连平台业务数据库的权限。客户本地采集器或自动化机器属于需单独评估的交付方式，不自动改变云端优先的部署范围。

## 4. 无系统企业的最小记录与额外业务

先定义完成一个任务必须记录什么、由谁记录、何时更新和如何确认，优先利用客户已有表格或现成工具；AI 可辅助将文字、语音或单据转为待确认记录，具体能力随场景实施。

最小记录不等于完整管理系统。若需要订单流转、库存事务、应收核销、审批及多岗位状态协同等经营系统能力，应作为本产品之外的独立系统建设项目或合作伙伴服务，另定范围、费用和验收。本文不新增梦核自建表单平台、ERP、CRM 或客户业务系统的首期承诺。

## 5. 产品、接入实施与系统建设的分工

| 层次 | 负责什么 | 交付与计费边界 |
| --- | --- | --- |
| 标准产品能力方向 | 来源登记、可复用导入/映射、校验、版本与更新状态、异常和任务影响提示 | 具体页面、渠道和首期切片继续设计；不声称已实现通用接入平台 |
| 有边界的 FDE 接入实施 | 调查资料、协调供应商、建立初始口径、清理约定范围历史数据、培训及约定维护 | 单独说明首次投入、持续支持、客户责任、变更与退出条件，不承诺无限人工追数和适配 |
| 独立管理系统建设 | 客户确需的新业务系统或完整事务流程 | 额外业务或合作伙伴交付，不纳入默认产品包 |

相同场景重复出现且维护方式稳定后，再把接入方法沉淀为可复用连接器或实施模板。初始模板可以通过正常开发和审阅建立，不依赖独立自进化模块。

成本同时计入 FDE 和客户员工时间、工具与机器费用、失败恢复和持续维护。具体收费、工时上限及服务时效继续按项目约定；未在本轮冻结金额或承诺。

## 6. 来源管理与三个端的边界

每个业务来源应能说明：覆盖的业务与口径、企业/空间及授权范围、获取方式、责任方、更新频率、数据截至时间、最后成功批次、质量缺口、失败后的责任人与替代交付方式。具体字段按来源适用性设计，不强制普通文稿填写业务表指标。

- 客户端承担获准资料的提供、补交、核验和纠正，以及在任务中了解数据缺口。
- 企业管理端配置本企业来源用途、更新责任和运行状态；管理连接不自动获得内容读取权限。
- 平台总台管理连接能力版本及技术运行状态，沿用首期无客户内容排障入口的边界；日志、评测与未来自进化不能绕过它。

沿用三端，不新增第四端。接入状态、质量状态和业务覆盖范围分别表达。来源陈旧或覆盖不全时，输入提供准确状态，处理限制结论，输出向获准接收者说明依据范围。

## 7. 可按客户任务采用的验证办法

建议先选择一个没有 API 的目标任务，以获准真实资料或明确标注的合成样例，完成下列清单。未得到真实数据时，合成验证不能代替客户交付证明。

| 清单项 | 要回答的问题 |
| --- | --- |
| 目标成果 | 谁使用，完成什么工作，所需时效是什么？ |
| 必需事实 | 哪些字段、时间范围和口径缺一不可？ |
| 现有证据 | 记录在哪里，覆盖哪些业务，谁可授权提供？ |
| 交付责任 | 谁提供和确认，多久更新，失败由谁处理？ |
| 核验方式 | 如何发现遗漏、重复、格式变化与口径冲突？ |
| 持续成本 | 首次配置、每周期人工、工具费用和故障恢复各有多少？ |
| 降级或退出 | 能否降低频率、缩小范围、替换来源，何时转入额外项目？ |

建议先用必要人工或现有工具跑过至少两个业务更新周期，观察覆盖、时效、异常、维护成本和实际用途，再自动化稳定瓶颈。周期数量和通过阈值是待场景确定的验证建议，不是合同指标，也不是基础系统开发或自进化接入的统一前置条件。
