## 3. 表关系与连接方式

数据库声明的外键列映射完整保存在结构文件。它们和源码逻辑关联分开处理；不因两列都叫 `source_id` 就建立通用关联。下表中的 1:N 是业务结构描述，未声明唯一性及空值例外仍需在接入批次全量检验。

| 主链 | 连接键与粒度 | 必须避免的错误 |
|---|---|---|
| 门店 → 教练/会员/业务 | 各表 `store_id` 等 → `stores.id`；人员用 `coach_id/member_id` | 主带门店、实际授课门店、销售门店、财务归属门店不可混用 |
| 会员 → 课程权益 | `member_courses.member_id → members.id`；一会员多课程 | 课程数不等于会员数，续费和待开课不能去重成一个当前状态 |
| 产品 → 历史课程/订单 | `course_product_id` + 各自购买时快照/版本 | 不只联当前产品表覆盖历史规则；JSON 仅白名单拆取 |
| 草稿 → 完整订单 → 收款/分期 | `full_orders.pending_order_id`、`payment_orders.full_order_id`、分期中的订单键 | 先按订单聚合收款，禁止订单金额随收款明细重复累加 |
| 课程权益 → 课时 | `session_records.member_course_id → member_courses.id`；一课程多课时 | 汇总需排除作废并识别待跨店认领、代课替换；不用设备抓拍次数代替课时 |
| 课程 → 退款 → 资金 | 退款的 `member_course_id`、`approval_request_id`；`t_course_refund_finance_entry_links` 衔接财务流水 | 不按会员姓名关联；退款出款、收入冲减、费用影响不重复扣减 |
| 审批 → 动作/业务效果 | 动作的审批键；各业务表 `approval_request_id/source_approval_id`；类型化 `payload_json` | 审批动作不是多笔业务，通用审批 JSON 不整段导出 |
| 课债 → 收款分段 → 提成 | 课程/快照日期/运行批次；分段的 `payment_order_id`；月度收入增量 | 日末余额不能按天相加；累计收入不能当每天收入；缺日不自动补零 |
| 工资 → 调整/发放 | 人员、工资月、工资条版本；调整项、承接记录、源财务事件 | 工资条确认不是发薪，发薪对应财务事实，不重复叠加工资合计与组件 |
| 财务主体 → 流水/支付账户 | `finance_ledger_entries.account_id → finance_accounts.id`；支付账户键；`reversal_of_entry_id` 自关联 | 核算主体与实际支付账户不是同一粒度；内部调拨两腿不计公司外部收入 |
| 对账批次 → 账户余额/主体快照 | 批次 ID + 截止时刻；基线/修正批次自关联 | 不跨多个截止时点相加银行余额；不将预计流水视为已确认现金 |
| 分红权益 → 发放分配 | `dividend_payout_allocations.source_event_id → dividend_entitlement_events.id`，`payout_line_id → dividend_payout_lines.id` | 一权益可多次结算，一发放可分摊多权益；直接 join 会放大金额 |
| 体验课 → 首次转化 | `trial_course_conversions.opening_id/full_order_id/payment_order_id` | 使用转化事实，不把会员所有正式订单都算体验课转化 |
| 转店 → 课程/结算/门店历史 | `member_store_transfer_courses.transfer_id`、`member_course_id`，配套分段/结算/冲回 | 转店剩余价值不是新销售；会员当前店不能替换历史归属 |
| 合同/公告/手册 → 文件/版本 | 业务对象键与文件引用，继承各自可见范围 | 文件 ID 不等于允许读文件；历史版本、未发布版本不自动公开 |

课债、收款分段和部分 `source_type/source_id` 关联并未都声明数据库外键。首轮治理必须补充“无对应项/重复对应/失效引用”的全量检查，不能把本次结构盘点写成所有关联已通过。

## 5. 接入前必须补齐的技术条件

当前上线的是三表固定投影适配器，不是全库通用导入工具：

1. **完整取数容量**：现有 Wiki 部署适配器每表最多 10000 行/30 列，输出约 20MiB；正式课债快照 14283 行，历史参考快照 16925 行已超限。实现带稳定分页、同一快照/批次一致性、数量校验与原子发布的受限采集；也可按经确认的历史分区拆分，但不静默丢弃早期数据。知识统计必须覆盖该数据集完整范围。
2. **宽表投影**：8 张非备份源表超过 30 列，其中会员课程 40、课时 44、工资 46、课债 42、转店 32、退款 41。先按用途分成稳定关联的语义投影，必要时提升有界容量并测试。拆表不得把一笔业务重复算多次。
3. **逐链注册与原子发布**：分批注册固定查询/列；保留已接三表 ID、历史快照与权限。现有部署包每批最多 20 个数据集，拆批需先落关联维度，再落事实与知识；跨批不能出现半套新口径对外可用。
4. **历史和当前双层**：经营查询区分当前有效、作废/撤销、历史证据。课债全历史保留按日语义；统计“当前”选择有完整性依据的对应日期，不能为省容量只取最新一天又称全量。
5. **权限映射**：所有门店是建议业务范围，不表示给所有员工看所有门店。沿源业务职责、目标企业/空间授权和服务端行列约束；B 类需验证负责人/财务/人事与普通成员的正反例。不能给管理员自动补内容权。
6. **数据源更新与模型接续**：沿现有调度；记录变化由服务器模型更新统计知识，部署规则保持；字段/状态规则变化转为待复核。同步、检查、知识三个状态分别可观测，失败保留上版且标识过期。

这些是新范围的实施前置项，本次只发现并列出，没有声称已实现。

## 6. 建议分批顺序与验收

建议批准 **A+B 共 106 张源表的固定投影范围，所有门店、源库现存历史**；原有三表算已接基础，新增候选 103 表。只取获准列并按链形成数据集，表数不作为知识成果数量。C 类默认不独立接入，若某批必须读取 C 类依赖元数据，应在该批清单列明，得到范围确认后执行；D 类不接。

| 批次 | 业务链与依赖 | 首轮知识成果 | 验收重点 |
|---|---|---|---|
| 0 范围/底座 | 冻结本清单、权限与历史范围；先补容量/分页/投影 | 全局词汇、门店/人员/时间/状态约定 | 超限整批失败、只读、跨企业与越权拒绝、完整页数和行数 |
| 1 基础经营链 | 组织/产品 → 会员/课程 → 原订单/收款/退款扩展；审批基础元数据 | 会员生命周期、产品版本、成交与收款口径 | 原三表不重复建；成员/课程/订单/款项关联；作废与草稿独立 |
| 2 履约与转化 | 课时/费率 → 体验课/转化 → 特殊课/体验官 → 转店归属 | 课消、营业日、跨店、体验转化与权益使用 | 同日有效性、代课/作废、转店前后归属、转化不重复 |
| 3 收入与资金 | 课债/历史参考 → 财务流水/头寸/备用金/储备 → 渠道与对账 | 实收、收入释放、课债、资金、对账差异分别建知识 | 历史完整、日余额不累加、现金/预计区分、调拨/冲销、空渠道事实 |
| 4 人事与分配 | 工资/提成 → 分红权益/历史期初/发放；依赖 2/3 | 工资组件、收入分期提成、可分配与已发放区别 | 锁定期/版本、应付与已付、权益与现金、源引用去重、受限权限 |
| 5 合同与组织知识 | 合同状态/事件 → 已发布公告/员工手册 | 合同履行状态、制度版本与生效范围 | 原文及附件单独授权；未发布/过期版本不可冒充现行制度 |
| 可选后续 | C 类设备运行、标准动作/器械知识、脱敏用量等 | 运维或教练标准知识 | 单独明确用途及正文来源；不导入私人健康/会话/图片 |

每批均执行：固定投影 → 本地全量取数 → Codex 逐列说明及关系/质量检查 → 首轮规则知识与事实分析 → 独立副本中制造明确的合成新增/修改/撤销并验证服务器模型接续 → 备份与线上发布 → 原有账号实际可见性及调度验收。模拟/真实来源/真实模型/线上验收分别记录。

待确认只涉及业务范围，不需要确认技术细枝末节：

- 是否采用上述 **106 表候选、全部门店、全部现存历史** 的分批范围？敏感字段始终按固定投影排除，不将确认解释为整库正文授权。
- B 类建议先限**已获该类内容权限的负责人及相应财务/人事岗位**；普通成员只访问明确授权的门店/聚合成果。具体目标账号映射在发布前验证，未映射不开放。
- AI 教练个人健康、私人会话、图片，以及合同/凭证原件不进入本轮默认范围；标准动作/器械等 C 类作为可选后续。

用户确认后进入第 0/1 批；本报告不将建议自动升级为已确认需求。
