## 1. 目标与责任

输出负责让适当的人，在适当的入口和时间，获得其有权接收且对当前工作有用的结果，并留下可核对的交付与反馈记录。输出包括直接交付，也包括画报中的主动推荐，不以“产出更多卡片”作为完成目标。

处理负责形成有依据的结论、建议、成果及真实执行结果；输出负责受众适配、呈现、选择和交付；可信平台继续执行权限、保存版本和实际状态。三者是逻辑责任，不要求部署三个服务，也不要求输出另设专用模型。

用户请求的普通回答可以直接返回；现成文件可以直接下载；需要摘要、角色化表达时再按需调用模型。内容在处理阶段已达到交付要求时，输出无需重复改写。没有独立自进化板块，以上能力也应正常运行。

## 3. 本轮讨论：结果与各交付入口的关系

建议先区分信息含义，再决定如何复用现有对象；下表不指定新表、独立服务或每项任务必走的流程。

| 概念 | 解决的问题 | 关系与限制 |
| --- | --- | --- |
| 处理结果 | 实际发现、生成或执行了什么，还有什么未完成 | 可以包含回答、分析、产物和执行回执；部分完成、无新发现和失败也有真实结果，不都适合推荐 |
| 工作成果 | 哪些内容需要长期保存、编辑、引用或交付 | 可成为版本化文稿、表格、报告等；普通回答无需先转换成文稿，任务日志也不自动都是工作成果 |
| 会话回答 | 当前用户请求如何得到答复并继续工作 | 可直接呈现结果、引用成果和报告真实状态，不强制经过候选池或推荐评分 |
| 画报内容 | 哪些获准内容值得被发现、阅读或持续关注 | 可引用成果，也可承载有依据的资讯、数据、洞察和建议；保留来源和版本，不另造一套事实 |
| 通知 | 是否需要在特定时间和渠道提醒某人 | 可以指向会话、成果或画报，无需先创建画报；正文、接收者、渠道和回执可追溯，不代表对方已阅读 |

同一份项目周报可以在会话中直接交付、保存为成果、按授权成为画报内容，并在有发送依据时通知相关人员。这些是对同一成果的不同使用方式，不是必须顺序执行的四个步骤。共享工作动态继续记录真实事件，可链接相应成果，但不重复承担推荐和消息发送责任。

### 3.1 直接交付与主动推荐

- **明确请求和已约定交付**：回答、指定文件、定期报告、需要用户处理的确认等，应有稳定可找到的入口，并按约定反馈完成、缺口或失败；推荐评分低不能使它们消失。普通任务无需用户逐项验收才算完成。
- **主动发现与额外曝光**：有依据的发现可形成候选，结合当前工作价值决定是否呈现、合并、延后或不展示。内部候选不必全部出现在用户界面，也不因生成就自动发布或通知。
- **职责内的重要事项**：按已生效职责和授权提供稳定入口或相应提醒，具体事项及优先级在后续排序/推送专题确定；不能把所有模型标记“重要”的内容都变成强制提醒。
- **等待与失败**：任务等待补充、授权或外部结果时，在原任务中说明真实状态；部分成果可先交付，但不能包装成全部完成。是否额外进入画报或通知由对应策略决定。
- **无新发现**：主动分析可以不新增卡片；已承诺定期反馈的任务仍应按约定说明结果或缺口。“少打扰”不自动取消既定交付。

隐藏画报、取消关注和关闭某类通知各自控制展示、关注或提醒；不默认删除成果、停止持续任务或撤销业务承诺。三者具体联动在后续讨论中明示，不能靠用户猜测。

### 3.2 一次分析怎样服务多个用户

可以复用共同获准的事实和成果，再按岗位与偏好调整重点、详略和形式，无需机械地为每个人重复完整分析。先确定可交付内容，再决定是否需要生成不同表达；相同表达可以复用，确有需求时再产生版本化视图。

例如项目周报：项目负责人需要风险和决策事项，执行人员需要其负责事项及下一步。若双方都获准阅读同一周报，可以从同一成果形成不同视图；若某员工无权获得其中的经营数据及其结论，就不能把完整分析交给改写模型后只删数值或来源来分发。应使用其获准的依据重新处理，或使用按系统发布规则明确授权给该范围的内容。发布仍不等于自动脱敏。

岗位、偏好和信息密度可以改变表达，不能把未知改成确定、将未完成写成完成，或省略影响当前判断的重要限制。纯排版和摘要可留在输出；新增计算、因果判断或建议依据需要相应处理和检查，并关联新的结果或成果版本。可以由同一模型完成，不要求跨服务来回调用。

## 4. 受众、权限与发布依据

平台依据当前身份和访问规则确认可交付范围。企业档案、用户偏好、模型建议的受众用于适配和选择，不授予访问权限；“企业管理员”“平台管理员”也不自动获得私人会话和所有企业内容。

### 4.1 两类现有成果继续使用不同访问规则

| 类型 | 访问依据 | 输出使用时的要求 |
| --- | --- | --- |
| 私人会话及随来源权限的派生成果 | 当前所有者、企业/空间与必要来源权限 | 来源撤权后按现有规则阻止后续访问、生成视图和交付；历史版本不保留已撤销的访问权 |
| 明确发布的独立企业副本 | 有效发布记录和目标空间权限，沿 DEC-066 | 读者不需要原私人来源权限；原作者离职、停用或来源撤权不自动撤回企业副本。读者自身撤权及企业停用仍阻止访问 |

发布副本仅包含已选择发布的内容，不因此开放私人会话、原件和内部来源关系。输出可引用获准的公开于该范围的版本信息；不能附带私人来源 ID、可绕过鉴权的链接或附件。副本正文中的来源说明与读者是否有权打开原件分别处理，不能承诺每个引用都可下钻。

发布时检查读取来源和维护目标的相应权限，后续读取按已形成对象的访问规则进行，避免将两类权限混为一谈。个人文稿的明确发布/更新动作继续沿原规则；未来主动共享若要采用预先委托，须另行明确范围、责任和授权机制，不能从允许分析推导出允许发布。

### 4.2 权限检查覆盖整个输出

标题、摘要、图表、缩略图、来源名称、附件、数量、搜索结果及通知预览都可能包含内容。检索、候选筛选、个性化生成及交付必须在适用访问范围内进行；最终读取/发送时复核当前权限和确切版本，不能只在首次生成时检查一次。

跨用户复用视图或缓存时，需满足相同的可交付内容范围及有效版本，不按角色名称或同一企业简单共享。权限过滤先于面向用户的计数和分页；被过滤内容不以标题、数量或空占位泄露存在。

系统能阻止后续读取和发送，不能把已经展示、下载或被外部渠道接收的内容声称为已远程撤回。对已交付内容发现错误或越权风险时，应留存实际记录并按获准方式处理；具体更正和通知策略在后续专题细化。

## 5. 内容合并、版本与阅读上下文

建议围绕业务事项和成果版本组织内容，避免同一事项每运行一次就重复生成一张新卡。事项如何识别和合并属于可替换方法；首次可复用任务、成果、持续关注等已有关系，不要求现在建立通用业务本体。

- 同一请求或逻辑交付动作按幂等标识避免重复发送、发布或新增卡片，实际尝试与回执仍留记录。用户明确要求再次交付同一报告属于新动作，不能仅因成果版本和接收者相同就拒绝。不同事项、相冲突结论和不同授权范围不能仅因标题相似而合并。
- 来源新版本、重新分析和用户修订可能形成新成果；排版、打开、关注和刷新不伪造新的业务时间，也不把旧事实包装成新发现。
- 内容版本与呈现版本分开理解：内容更正可能改变事实或结论；同一内容的短摘要、图表或移动端布局属于呈现变化。反馈和阅读上下文须能指回当时实际看到的版本，不要求复制每次页面全文。
- 当前浏览、历史回看及从卡片发起会话应保留确切阅读依据；新版本可提示并按具体入口切换，不能把用户针对旧版本的反馈误记到新内容。完整历史快照的保存范围和周期仍待确定。
- 个人文稿修改不自动更新已发布企业副本；企业版本更新沿明确更新与并发检查规则。成果更新也不自动重发所有旧通知。
- 已排队交付应在执行前检查对象可用性、授权和版本变化；是继续交付固定版本、换成新版本还是停止，应符合原任务承诺，不能静默替换。

发现重要错误时，先标记受影响的候选、成果和待交付项，避免继续传播失效结论；已交付内容的更正记录、新版本及再次通知分别管理。是否影响独立发布副本需按它的维护规则处理，不能用“回退推荐算法”代替修复已发布内容。

## 6. 与处理、输入及平台的交接

下表定义应说明的信息，不冻结 API 字段或新增状态枚举。

| 交接 | 需要说明 | 责任边界 |
| --- | --- | --- |
| 处理 → 输出 | 任务/尝试及目标，结果/成果和依据版本，实际完成范围，未解决事项，建议受众与交付方式，已有授权/发布依据及真实工具回执 | 拟受众不是授权；输出不得把部分结果改称完整完成，不重复执行已经有回执的发送动作 |
| 输入/平台 → 输出 | 当前成员与内容访问范围、有效档案和偏好、资料/成果可用性及版本 | 事实、偏好与权限来源分开；输出不另建一套相互覆盖的企业档案或权限 |
| 输出/工具 → 平台及任务 | 确切交付内容/呈现、受众、入口或渠道、真实执行状态及失败/未知原因 | 同一实际发送能力统一执行并回写，不由处理和输出各发送一次 |
| 输出 → 反馈与评估 | 关联内容/呈现/任务版本、实际曝光或打开事件、明确评价及纠正 | 无展示不能当作没用，无反馈不能当作满意，打开不等于理解、采纳或经营改善 |

生成、保存、发布、渠道接受、送达和打开表示不同事实，各按实际能力与回执记录；渠道无法证明送达时保留未知。并非每种交付都经过所有阶段，也不要求每次用户查看都运行评判模型。

任务是否完成仍由平台结合目标判断：要求草稿时提供草稿即可；要求发送报告时还需真实发送结果。外部发送超时或响应丢失时先核对已有记录，不盲目重发；取消/重试沿处理任务的真实状态与幂等机制衔接。

## 7. 拟开发任务、管理责任与分期

沿用 AI-01、AI-11—AI-13、WS-06—WS-14、DASH-01—DASH-04 等既有需求及最新覆盖决定。模块编号复用总任务书，不在本轮把全部能力承诺进同一版本。

| 范围 | 拟交付工作 | 复用与依赖 |
| --- | --- | --- |
| M4 / M6 与 M5 交接 | 明确回复、成果和画报引用关系，保留任务、权限、版本及实际状态；直接交付不依赖推荐 | 现有任务、文稿、文件与共享发布能力；处理第 7、11 节 |
| M5 输出与呈现 | 主动候选入口、事项更新和去重、受众视图、排序与个性化，接入已设计的画报交互 | 输入档案、授权内容与真实成果；第 10 节补充排序与表达建议，首版范围仍待汇总 |
| 平台交付与 M7 观测 | 首版站内交付/提醒记录、失败恢复与版本追溯，保留后续接入其他渠道的边界 | 第 11 节补充交付/提醒、接收范围、节奏与恢复建议；系统外触达明确留到后续 App 版本（DEC-088），当前不开发外部消息通道 |
| 反馈接口 | 将画报/会话反馈关联到正确对象和版本，区分评价、纠正及实际生效结果 | 第 12 节补充当前任务纠正、偏好及经验候选的不同去向，复用既有机制；高评价不直接发布经验 |

三端仍按既定分工：员工客户端阅读、交付、维护本人偏好并作获准共享；企业管理端维护企业可管理的输出策略与采用范围，不因此查看所有私人内容；平台总台管理通用方法版本、兼容与运行状态，不提供客户内容旁路。具体页面和角色动作在三端专题汇总，不新增第四个端。

基础阶段应能完成站内直接交付和获准主动呈现，并留下必要的版本、状态和反馈依据。系统外触达按 DEC-088 后置到 App 版本；具体首版候选类型、排序方法、规模和站内提醒频率待后续讨论及全局汇总，不以建立通用推荐平台或学习型算法作为简单交付前置条件。

未来独立自进化可以优化候选提炼、合并、排序、表达及推送方法，经对应范围的评估和授权生效；不能自行扩大受众、修改真实回执或静默撤销用户承诺。日常反馈记录、获准偏好维护和正常内容更正无需等待自进化上线。

## 8. 后续验收场景建议

以下是统一执行阶段应取得的证据，本轮未运行验收。

1. 用户要求一份报告，实际在会话/成果入口得到它；即使未被推荐或画报被隐藏，交付及任务仍可找到。
2. 一份共同获准的报告形成不同角色视图，事实和限制一致；某用户无权获得的内容不通过标题、图表、附件、计数或缓存泄露。
3. 来源撤权后私人派生成果拒绝后续访问；既有明确发布的企业副本仍按目标权限读取，且不暴露私人会话和来源关系。读者自身撤权仍拒绝访问。
4. 同一交付动作的重复回调或重试不重复发卡或发送，实际尝试仍可核对；明确要求再次发送可形成新动作。有新版本时保留正确关联，用户的历史反馈及会话仍指向实际阅读版本。
5. 任务仅生成通知文案时未显示“已发送”；渠道只返回接受请求时不标记“已阅读”。未知外部结果不会直接触发重复发送。
6. 待授权、部分完成、无新发现和失败各按实际状态反馈；生成卡片或关闭通知不冒充任务完成或取消。
7. 个人修订不静默覆盖企业版本；发送前发现权限撤回或内容失效时按正确规则停止/复核，已交付内容仍保留真实记录。
8. 无自进化服务时直接交付与基本画报正常工作；输出无需第二次模型调用的路径能够独立完成，确需新分析时留下处理依据。

## 10. 本轮讨论：价值排序与个性化呈现

2026-09-30 接续。以下为第二轮设计建议，沿用[输入第 8 节档案原则](输入板块-开发任务书-V0.1.md#8-本轮讨论企业与用户档案)、[处理第 4 节目标与冷启动](处理板块-开发任务书-V0.1.md#4-任务从哪里开始)和本稿第 3—6 节；不改变已确认的前端布局或自动启用行为学习。排序目标是帮助用户理解与当前工作有关的变化、完成已承担工作、发现有依据的机会，并控制阅读和处理负担。具体业务价值随企业、岗位及当前目标而定，不统一等同于营收、点击率或内容数量。

### 10.1 明确交付、职责事项与一般推荐怎样协调

这三类是选择和交付时的语义，不要求新增三个页面分组，也不恢复已隐藏的“正在跟进”栏。

用户已决定将待办卡片放在智能画报板块内，采用可折叠待办区：概览最多显示两排，可完全展开，也可完全收起（DEC-093），见[管理任务书第 14.8 节](三端管理与共用平台-开发任务书-V0.1.md#148-智能画报内的可折叠待办卡片)。两排限制只作用概览，展开后可查看完整的当前获权待办；收起只改变展示，不结束责任。普通推荐排序、已读折叠或一般推荐开关不删除待办及重新展开方式，同一事项跨入口共用真实状态。区域位置、首次默认状态及偏好记忆仍为设计建议；不恢复旧会话类型/分组，尚未改变当前实现。

| 情况 | 判断依据 | 建议处理 |
| --- | --- | --- |
| 明确请求或已约定交付 | 当前任务、有效委托及明确交付要求 | 在相应会话/成果入口按约定交付；是否额外出现在推荐流另行选择，不参与“评分不足就不交付”的竞争 |
| 职责内需要处理的重要事项 | 有效职责、未完成任务、明确截止或生效策略及相应证据 | 保留可找到的处理入口；推荐中是否突出、何时提醒结合真实状态与策略判断，不因已读或较少点击自动当作已处理 |
| 一般推荐与探索候选 | 与当前工作有关的有依据发现、参考或待验证方向 | 在获准范围内按价值选择、合并、延后或不展示；用户可以关闭这类推荐，不借“重要”标签绕过其选择 |

模型可以识别风险和建议优先级，但“经理通常关心营收”不等于赋予一条内容强制待办身份。职责来源不明或归属存疑时，作为可纠正候选处理，不能仅凭岗位推断给人派任务。重要事项也不能无限置顶：完成、取消、转交、有效期或重要变化须依据实际任务/策略更新，具体提醒节奏留到推送专题。

目标或职责发生实质冲突时，沿处理侧的目标冲突机制解决；排序不能通过把某一方的事项藏到后面替代业务取舍。关闭推荐不自动终止已约定任务，任务仍按自己的入口和通知约定运行，也不能伪装成推荐反复打扰。

### 10.2 先判断是否适合向这个人呈现

权限、发布依据、内容有效性和必要来源按第 4 节核对。重要性分数不能弥补越权、错误状态或不存在的证据。发现明确错误或已失效的结论时，先进入纠正/复核，不把它继续作为有效建议竞争曝光；历史记录仍按其规则留存。

有依据但尚未核实的风险、资料缺口及需要进一步调查的方向可以有价值，不要求所有内容完全确定后才允许呈现。应说明已知事实、待验证判断和可能需要的下一步；“可能存在问题”不能变成“已经造成损失”。模型自报置信度不独立构成证据。

候选可引用任务、成果和来源版本，按需补充适用对象、关联目标/职责、业务时间、变化、状态、重复关系及价值理由。信息由已有记录和处理结果提供，缺失就保持缺失或补充核对，不为填满字段编造截止时间、负责人或收益。此处定义信息含义，不要求首版建全套字段或每项都增加模型调用。

### 10.3 排序主要考虑什么

建议保留以下可解释的考虑维度，允许 AI 和后续实现根据任务选择方法，不把它们固定成一条全行业通用的加权公式。

| 维度 | 需要判断的问题 | 容易误判的情况 |
| --- | --- | --- |
| 当前工作关联 | 与此人的当前任务、明确关注或真实责任有什么关系 | 职位相同不代表任务相同；阅读兴趣也不自动形成业务责任 |
| 影响与必要性 | 可能影响什么决定、进度、协作或风险处理，影响范围和依据是什么 | “预计节省很多钱”等模型估计不能当作已实现收益；抽象大主题不自动优先 |
| 时间与事项状态 | 截止是否临近、机会是否仍有效、事项是否已解决 | 今天刚生成的内容不一定比昨天未处理且今天到期的任务更重要 |
| 信息增量 | 是否出现关键变化、纠正或新的可用证据 | 改标题、换模板、重复抓取不构成新发现；已读后发生实质变化仍可能值得再看 |
| 依据与适用性 | 来源是否支持结论，口径是否适合当前场景，哪些限制影响决策 | 信息多、措辞肯定、点赞多不代表质量高；有依据的疑点也不必被一律排除 |
| 理解与处理负担 | 此刻需要知道什么，是否有合适的下一步，怎样减少重复阅读 | 无须行动的知情信息也可能有价值；不能为了降低负担隐藏必须面对的问题 |

近期生成、用户偏好和阅读行为可以作为辅助信息；不规定“越新越优先”“越爱看越重要”或所有候选必须打出精确数值。不同类型难以可靠比较时，可结合目标、事项类别和理由进行选择，不制造可比性的假象。

### 10.4 不只排单条内容，还要考虑整次阅读

同一个事项产生多条相近洞察时，可以合并主线并保留重要差异和可核对来源，避免一个活跃主题占满画报。不同授权范围不混并；互相矛盾的证据不能为简洁而被拼成单一确定结论。多样性围绕用户相关工作展开，不按固定比例塞入无关资讯。

允许没有新推荐，或只出现少量有价值内容，不设“每次必须几张”的任务。用户正在阅读时应避免无实质原因的反复跳位；状态或重要内容变化可以提示，具体刷新方式与当前交互衔接。

沿用推荐自动补齐中间空位、关注独立手动布局。**新增设计建议是：排版补空位不能使需要优先看到的事项长期被普通卡片挤到后面。** 后续可采用同等优先程度内调整、适当尺寸适配等方式验证；不要求现在更换网格或锁定算法，旧 Demo 也不视为已经证明这项保证。

现有普通已读内容刷新后后置的体验保留。业务处理状态与当前内容版本已读分别判断：重要未完成事项应仍有稳定入口，重大变化不能继承旧版本已读而被忽略。具体显著程度及再次提醒进入下一专题，不承诺所有未处理事项始终置顶。

### 10.5 个性化分别影响内容选择与表达

内容选择可以利用获准的当前任务、工作责任、明确关注与业务背景；表达可以利用语言、详略、结构、术语和文字/表格等偏好。岗位是相关性线索，不是固定模板或授权来源；同一用户在不同任务中也可能需要不同表达。

| 上下文 | 建议作用方式 | 生效边界 |
| --- | --- | --- |
| 权限及有效的强制业务要求 | 确定可提供范围与必须保留的信息 | 不与兴趣分数加权抵消；具体要求及维护权来自已生效记录 |
| 本次明确要求 | 决定当前交付的主题、详略和形式 | “这次只用表格”仅用于本次，不自动改长期偏好 |
| 本人同场景明确偏好 | 按输入既有机制复用，支持查看、纠正和撤销 | “以后周报先结论”按本人、企业及场景范围生效，不扩展给全员 |
| 空间或企业默认 | 缺少更具体要求时提供适用的默认表达与关注方向 | 默认与强制要求区分；个人偏好不能改写全企业配置 |
| AI 推断或行为线索 | 可供讨论有限的推荐试探，不冒充明确事实或永久偏好 | 新的行为采集、自动画像和自动学习范围尚未确认，不随本稿启用 |

表达沿输入已讨论的顺序处理：满足权限和有效强制要求后，再考虑本次要求、本人同场景明确偏好、适用空间默认和企业默认；推断不压过明确要求。重要冲突回到相应业务机制，不把所有企业默认都当作不可覆盖的命令。

例如“喜欢简短”可以得到结论、关键依据及必要限制，并按需展开完整成果；不能因此省去会影响决策的条件或把不确定说成确定。无行动要求时不强行生成待办，复杂决策也不被强制压成一句话。颜色、版式等可调整，但不以夸大标题或警示样式制造紧迫感。

同一账号跨企业的工作背景与记忆分别使用，私人偏好不自动向管理员公开。共享表达或缓存继续满足第 4 节的内容与权限范围；不因两个用户属于同一岗位就共用高权限上下文。

### 10.6 冷启动与反馈不足时怎样工作

结合处理侧的冷启动方案，从已有背景、实际获准资料和经核对的方法形成少量相关候选，说明它与当前工作有什么关系。没有足够依据时可指出最有价值的资料缺口或调查方向，不用通用行业资讯填满空白，也不要求先完成一份完整用户画像。

用户可以围绕实际成果纠正“这不是我的职责”“这个问题已解决”“信息重复”“希望先看结论”等。分别影响职责核对、事项状态、合并和表达；单次反馈不自动同时改目标、偏好和全局方法。具体记录及生效方式留到两类反馈专题，低风险明确长期偏好继续沿输入既有授权处理。

未展示、未点击、读过但没有反馈是不同情况，不直接推断无价值。点击和停留可能是为了核查错误或理解复杂内容，也不独立证明喜欢或有效。候选来源不能永久收窄为曾获点赞的同类内容；有限探索仍须与当前工作相关，并遵守用户选择的范围与资源约束。

### 10.7 程序、模型与未来自进化怎样分工

建议先建立可解释、可替换的基础选择与呈现方法。身份权限、真实状态、时间版本、幂等和可明确识别的重复关系由可信平台/程序处理；语义相关性、事项归并、影响判断和表达适配可按需要使用模型。复杂排序是否再调用主模型或其他模型，依据实际质量、延迟和成本决定。

不必每次页面打开都重新分析全部历史原文。可复用仍有效的结果和摘要，在内容、权限、任务状态或相关上下文变化时按需要更新；读取必要来源继续受权限约束。基础规则能够确定的结果可以直接交付，不强制每个候选都走一遍完整模型评分流程。

语义排序或个性化服务暂时不可用时，在满足当前权限和有效性检查的前提下，仍可访问既有成果与明确任务，按可信时间/状态作有限展示，或暂缓缺乏依据的主动推荐。不能回退成演示内容，不能使用撤权缓存，也不能声称已完成未执行的价值评估。

以上约定写入输出职责和评估依据，不逐条堆成主模型的常驻规则文档。具体排序、合并、摘要和布局方法保留版本及替换边界；未来自进化可提出改进并按影响范围验证和发布。正常读取偏好、接受获准纠正及更新呈现属于基础运行，不等待自进化上线；自动调整跨用户通用方法的授权另行讨论。

### 10.8 怎样观察排序是否有效

先分别观察“候选有没有覆盖应该发现的事项”“选择与呈现是否合适”“交付后是否有实际帮助”。关键事项未进入候选池时，仅优化候选池内排名解决不了遗漏，应回到输入、处理或职责覆盖排查。

建议保留受权限控制的必要依据：内容/呈现和方法版本、相关目标或职责、使用的上下文版本、展示或暂不展示的主要理由、可取得的曝光/阅读事实及明确反馈。可向用户用一两句真实依据解释“与哪个任务有关、发生了什么变化”；不能在事后生成一段听起来合理但与当次选择无关的解释，也不暴露私人来源或内部隐藏推理。

后续评估结合关键事项遗漏、误报、重复/过时、事实或表达纠正、用户完成工作的负担、延迟与成本；点击率、停留和卡片数量仅作辅助。没有证据时不把推荐后发生的经营变化当作推荐造成的收益。具体指标、规模、观测范围和保留周期在评估/运行专题确定，不在本轮承诺百分比提升或新增全量行为采集。

### 10.9 任务与验收补充

M5 继续承接候选适用性、选择/合并、排序和表达，以及现有画报交互的真实接入；M4/输入提供目标、职责、依据、状态和获准档案；M7/评估承接版本与运行效果。复用原有资料、任务和档案，不另建一份用户画像或业务完成状态。排序不负责擅自启动下一次分析、建立持续目标或扩大数据获取，发现需要追加工作的机会交由处理侧在现有授权内推进。

本轮提出基础方法和降级要求，固定权重、默认候选数量、强制提醒清单、行为学习、每用户独立模型及全行业画像都未因此纳入已确认首版。统一执行时，除第 8 节场景外建议补充：

1. 未被推荐或推荐关闭时，明确交付仍可找到；有来源的重要事项不因少点击而被当作已完成，模型自称重要也不能新增强制义务。
2. 昨日未处理且即将到期的事项，与今天生成的一般分析按真实上下文处理；重排版、重复抓取和旧内容换标题不刷新业务新鲜度。
3. “这次用表格”只改变本次；明确长期周报偏好按范围复用且可撤销，同一账号跨企业不串用工作背景。
4. 资料不足的风险以有依据的待核实判断呈现，不伪造事实；已知失效内容不因高相关性继续作为当前结论推荐。
5. 同一主题多条重复内容得到合理合并，保留关键差异；用户没有点击不会导致永远只剩容易获赞的内容，无有效候选时也不凑数。
6. 推荐补空位、普通已读后置与优先事项可见性共同验证；关注手动布局不改变其他视图的业务排序或内容版本，不恢复隐藏的会话类型和“正在跟进”栏。
7. 模型或个性化服务不可用时，可信任务与成果仍可访问，无法完成的推荐明确降级；权限撤回后不借复用视图或缓存继续交付。
8. 使用代表性样例检查应发现的事项是否进入候选，并区分候选遗漏、选择错误及表达问题；评分、点击或内容增长不能单独作为改法有效的证据。

上述为未来验收依据，本轮仅更新文档。下一轮按第 9 节讨论交付和推送，之后再细化反馈如何作用于当前任务、个人偏好、经验库及后续方法优化。

### 10.10 补充讨论：现在确认到什么程度，后续能否自主优化

用户追问是否需要当前确定具体推荐算法，以及自进化能否自行优化机制。本节说明建议边界，不将这次提问记为已批准自动实验或发布。

**当前确定目标、用户可见行为、业务边界和评价方向，具体算法在统一执行时由 AI 设计初始版本。** 明确交付不能因排序被隐藏、关闭推荐的含义、可用资料和探索范围等仍需讨论；权重、候选选择、合并/排序方法、模型分工与缓存更新方式可以按实现和验证选择，无需用户逐项指定，也不必现在设计成最终算法。

统一执行阶段仍要交付真实可运行的初始方法，记录适用范围、版本、代表场景表现和必要的恢复方式。具体评价口径随评估专题收口，形成可供后续比较的基础；不能把基本可用性留给将来的自进化解决。基础系统完整开发后，再接入并测试自进化，沿 DEC-079、DEC-083，不提前开展相关实验。

**未来优化范围可以覆盖参数、局部流程以及整个推荐方法的替换。** 例如调整时效处理与选择策略、改进事项合并、改变程序和模型的分工，或改用新的排序方法。第 10.3 节的考虑维度是初始设计依据，不是永久固定的特征清单；AI 可提出增删或重组依据的候选，说明变化和适用条件，并检查与现有内容/版本/交付接口的兼容性。

“自行优化”可以包含自动发现问题、设计候选、修改方法、运行比较及在授权范围内采用。未来在预先批准的作用范围、资源和质量条件内，可以自动试验并启用通过验证的改法，无需每次等待人工点击；超出授权范围或改变业务承诺、权限、费用等时，再由有权主体决定。自动类别、条件和停止机制仍在后续自进化及管理专题确定，当前没有获得实际执行这些动作的授权。通用版本发布与企业实际采用继续区分，沿[跨板块更新管理方案](新架构下开发范围与管理端规划-讨论稿-V0.1.md#61-补充讨论跨板块更新与自进化管理)。

验证深度按改动影响安排，不要求每次小改都重测全系统；涉及用户实际曝光的试验同样需要适用授权。比较覆盖真实价值、关键遗漏、事实与权限、用户负担和资源代价，不能只证明点击增加。改法可能无效或变差，应允许拒绝候选、停止试验或恢复已验证的兼容方案，不承诺每次自动优化都有效。

业务目标和评价方法本身也可以提出改进，但应作为有依据的独立变更管理。一次效果比较使用一致口径；评价口径确需变化时，对原方法和候选重新建立可比依据，不能通过放宽标准、删除反例或改写真实结果证明排序进步。权限等业务边界按相应授权调整，推荐方法不能通过自行修改规则扩大权限。

## 11. 本轮讨论：交付和推送

2026-09-30 接续。本节明确交付、提醒及恢复的业务含义，具体频率和自动策略仍为建议；用户随后确认首版不开发系统外触达，留到后续 App 版本（DEC-088）。下文关于外部渠道受理、送达、跨渠道恢复等内容保留为后续设计依据，不属于首版开发或验收任务。当前真实能力主要是会话/成果读取、明确共享发布和工作动态；画报转发仍为 Demo，实际消息推送尚未接通。

### 11.1 先说明什么算本次交付完成

用户要求“生成报告”，可按约定在会话/成果入口提供报告；要求“把报告发给指定同事”，则还要完成对应获准发送动作。成果形成、共享发布、站内可访问、发出提醒是不同事实，具体需要哪些步骤取决于任务目标。

建议每项交付按需要关联：任务和交付目的、确切内容/成果版本、接收范围、约定入口或渠道、时限及时间依据、已有授权和实际回执。普通会话可由当前请求和身份提供这些信息，不增加每次都要填写的表单，也不要求用户重复批准已授权的动作。

可用可靠方式证明的状态决定完成范围：只得到渠道受理回执时，记录“渠道已接受，送达未知”；如果任务明确要求确认对方收到，则该条件仍未满足。交付成功不自动证明用户阅读、理解、采纳或业务事项完成。

### 11.2 哪些情况需要额外提醒

| 情况 | 建议的基本行为 | 是否需要额外提醒 |
| --- | --- | --- |
| 用户正在会话中等待的回答或文件 | 在当前会话提供结果及真实状态 | 通常无须同时再产生多个提醒；明确要求另行发送时按委托处理 |
| 异步任务完成、失败或需要补充 | 在原任务保留结果、缺口及可继续的入口 | 根据事先约定的通知方式提醒发起者或已明确的相关人；失败不保持假性运行状态 |
| 定期报告或已约定交付 | 按约定入口、时间和接收范围交付 | 提醒与报告交付要求分别执行；合并或免打扰不能悄悄取消承诺 |
| 需要决定、临近截止或重要变化 | 关联真实事项、责任和依据 | 在有效策略内提醒实际需要知情或处理的人；模型标记“紧急”本身不授予越过限制的权利 |
| 一般推荐、普通资料更新 | 更新获准范围内的画报或动态 | 默认设计建议是不逐条外发、不默认通知全员；可按明确关注和订阅汇总 |

画报中的高排名不自动触发外部发送；关注一个主题也不默认订阅所有渠道。没有新发现时，可以保持安静；已经约定的定期报告仍需按约定反馈“暂无重要变化”或说明资料缺口。关闭一般推荐与取消报告委托是不同选择。

### 11.3 接收人、转发与内容范围

接收人可来自当前用户的明确请求、有效任务责任或获准订阅策略，在发送时解析成明确对象并复核当前身份、企业、内容及渠道授权。模型可以建议谁需要知道，不能仅凭职位推测、资料中的地址或历史经验里的联系人自行发出消息。

现有权限内的明确委托可以直接执行，不要求每条通知重新审批。发送者能读某份资料不等于可任意分发；接收者需要有对应内容的访问依据。转发可指向对方已经有权访问的成果；若需要新共享或企业版本更新，则沿有效发布规则和委托范围办理，不能靠转发按钮绕过。明确发布的独立企业副本继续按目标空间权限管理，不因私人来源撤权自动撤回。

接收群体与工作空间成员不必相同。群、部门或职责成员发生变化时，按委托的接收范围解析和检查，不能把人员新增当作自动补发历史内容的依据。无法确认受限内容的接收范围时，应停止该项受限发送或采用已经获准的交付方式，不能只检查发送者。

正文、标题、预览、附件和链接都属于交付内容。建议提醒优先提供完成目的所需的简明信息，并指向受控成果入口；确需正文或附件发送时，按该渠道与接收范围授权使用确切版本。通知链接不携带可绕过身份检查的私人访问凭据，读取时仍鉴权。企业外收件人、公开链接和自动全员广播需要另行明确业务范围，不因本轮加入首版。

### 11.4 首版范围已确认：站内交付，系统外触达后置

2026-09-30，用户明确“首版暂时不开发系统外的触达，那个是后续 app 版本的功能”，记录为 DEC-088。此前“首版是否要求离线触达待确认”由本决定替代，不再作为首版待决项。

首版输出限定为站内会话、任务、成果、画报及相应提醒；具体交互仍按各节的确认状态理解。复用现有入口，不以新增一个通知中心为前置。交付状态、偏好和未读等按实际业务设计持久记录，不能把 Demo 浏览器内的转发记录迁成真实交付。

用户未打开系统时，不承诺通过系统外渠道主动触达；系统可在已有授权内继续后台任务、保存成果和站内提醒，用户返回后再按当前权限及实际状态查看。关闭页面不自动停止后台任务，也不意味着成果已经被用户阅读。

首版不接入业务邮件、企业协作工具推送、短信、浏览器/操作系统通知等系统外触达，也不提前建设对应供应商适配、外部账号绑定、多渠道重试或真实送达验收。站内共享与获准转发仍按现有成果发布/访问规则设计，不因外部触达后置而取消。

这些系统外触达能力放入后续 App 版本规划，具体渠道、接入条件、费用和支持范围到该阶段再确定；不代表届时必须一次支持全部渠道，也不是认定 Web 技术无法触达。现在保留任务、内容版本、接收范围及交付记录的可扩展边界即可，不为未来渠道预先搭建空服务。

后续渠道不可用时，备用方式及跨渠道回执仍按本节其他设计建议细化。当前用户请求尚未支持的系统外发送时，应在站内说明本版本能力范围并提供已有成果入口，不宣称已安排外部发送。此决定针对本轮讨论的业务成果/画报触达，既有身份邀请与账号安全流程按其独立范围维护。

### 11.5 时机、合并、免打扰与再次提醒

提醒时机可选择及时告知、在约定窗口汇总、等有重要变化再提醒，或仅保留站内入口。采用哪种方式由交付要求、事项状态、用户偏好和生效策略决定；具体间隔、每日数量、窗口和上限留待使用场景与运行成本确定。

- 同一事项短时间内反复变化，可以合并有用变化并保留依据，避免每次刷新都发送；明确要求逐次告知或固定时间交付的任务不能被合并策略静默延后。
- 计划应使用明确时区和时间依据；错过窗口、连接恢复或服务重启后，按时效与承诺选择补交、汇总或标记过期，不把积压提醒一次性全部重放。过期不代表任务成功，未完成的交付责任仍可见。
- 免打扰影响告知时机，不阻止成果按约定准备和保存。明确发送时限与免打扰冲突时，按已生效的例外规则处理；没有规则时保留冲突状态并在可用入口说明，不悄悄改时限或默认绕过用户选择。
- 企业默认与强制要求分别登记。模型不能把普通默认升级为强制，也不能仅凭内容评分忽略个人设置。哪些事项可以例外提醒、谁能制定、用户能控制什么，后续在管理专题明确。
- 再次提醒应有未完成的责任、截止变化、实质更新或已约定节奏等依据。已读仅说明打开了相应版本；“稍后提醒”改变下一次告知时间，不等于完成任务。实际完成、取消或转交应阻止旧状态继续催办。

多渠道告知应属于同一可追溯的交付意图，按约定协调，而不是某渠道暂无已读就向所有渠道再发一遍。用户正在处理事项时是否暂缓重复提醒可作为后续优化，不依赖持续监视用户屏幕或新增全量行为采集。

### 11.6 关闭、暂停和取消分别影响什么

以下为拟设计的行为含义，不表示现有页面已经有这些开关。

| 用户动作 | 建议影响范围 | 需要保留的区分 |
| --- | --- | --- |
| 关闭一般推荐 | 停止相应可选推荐曝光及其提醒 | 明确任务、已有成果和约定交付仍可访问，不伪装成其他类别继续发同样推荐 |
| 关闭某类/某渠道提醒 | 阻止该范围后续告知，等待和重试时也复核 | 分析和成果可继续；若该渠道承担唯一明确交付，应显示不可按原方式交付并按有效约定处理，不能自动改渠道或宣称已完成 |
| 稍后提醒 | 调整这次事项的告知安排 | 不自动改业务截止时间、内容事实或任务状态 |
| 暂停持续任务/关注计划 | 沿处理侧规则阻止后续触发，并说明对在途任务的影响 | 旧队列不继续产生新催办；已完成成果保留，已约定但尚未交付的成果怎样处理按暂停范围说明 |
| 取消某次待发交付 | 阻止尚可取消的发送及其重试 | 不默认删除成果或撤销已经发生的发布；若渠道已接受或结果未知，记录实际情况，不保证撤回 |

画报“取消关注”继续只表达相应呈现偏好，不自动等同于停止一个同名的持续任务；需要停止工作时指向该任务的明确操作。关闭渠道、撤权和取消在排队及恢复时继续有效，不能因为曾经生成了通知就保留永久发送资格。

### 11.7 真实回执、失败恢复和内容更正

复用平台任务、计划和执行基础统一安排交付，模型不需要为了等待发送而持续运行。处理和输出引用同一个交付动作及真实回执，避免分别发送一次。

| 情况 | 建议恢复方式 |
| --- | --- |
| 明确尚未发送或可证明被拒绝 | 按失败性质处理：暂时故障可在原授权、时限和次数范围内重试；无权限、对象失效或永久配置错误需先解决原因，不无限重试 |
| 请求超时、响应丢失，可能已经发送 | 保留结果未知，优先查对应动作、回执或渠道记录；具备可靠幂等能力时按该能力恢复。无法核实时不盲目重发或换渠道，在任务中说明未知状态 |
| 渠道已接受、送达情况未知 | 记录已接受，不伪造送达或已读；后续有可靠回执再更新，陈旧/重复回执不重复触发业务动作 |
| 同一请求或回调重复到达 | 避免重复发送、发布和增加待办，实际尝试仍留记录；用户明确要求再次发送属于新动作，不被按成果版本简单拒绝 |
| 部分接收人或部分渠道失败 | 分别记录各目标状态并反馈实际完成范围；重试针对符合条件的失败部分，不重新发送给已完成部分，也不因一部分成功就报告全部完成 |

发送前复核权限、接收范围、事项状态、取消/停用和确切版本。排队内容出现新版本时，按交付约定决定继续固定版本、采用新版本或暂停核对，不能把用户批准过的内容静默换成另一个结论。

发现错误时，先阻止尚未发出的失效内容继续传播；原成果、更正版本和已发生交付分别留存。是否再次告知原接收者，结合错误影响、当前权限和有效通知授权处理，不自动向所有历史用户群发。已发布企业副本沿其独立维护规则更正，不能仅修改私人原稿就宣称共享内容已修正。已经外发或下载的内容不能被平台方法回退视为已撤回。

### 11.8 三端管理、观测与后续自进化

客户端承接本人通知偏好、交付/失败状态、获准转发和当前事项操作；企业管理端维护其有权维护的默认策略、接收规则与渠道配置；总台维护通用交付能力和运行状态。具体角色动作仍待管理专题确定，配置通知策略不授予读取私人内容或代他人发送的权限，不新增第四个端。

观测应区分生成、发布、站内可用、渠道受理、可证实的送达、打开及实际业务完成，并记录等待原因、失败、未知、重试、取消和更正。可评估承诺范围内的及时交付、重复/遗漏、无效打扰、恢复效果及成本，不以消息条数或打开率单独证明价值。总台只取得获准的运行信息，不靠通知正文、接收名单或原始错误形成客户内容旁路。

未来自进化可在第 10.10 节及跨板块更新机制内，优化汇总、节奏、内容长度、已支持且获准渠道的选择及恢复方法。允许在预授权范围内自主试验和采用，不要求每次小调都人工批准；不能自行增加接收者、开通新渠道、突破免打扰规则、改变交付承诺或篡改回执。具体自动采用类别、阈值和停止条件在后续自进化专题确定，当前不执行试验或真实发送。

### 11.9 拟开发任务与后续验收

首版拟开发工作是：复用 M4 的任务/计划与 M6 的成果/发布，补齐站内交付记录和恢复；M5 承接站内呈现、提醒与用户选择；M7 承接实际状态和运行观测。系统外渠道、外部账号绑定、多渠道恢复及真实发送验收留到后续 App 版本，不作为首版前置。不把邀请邮件、账号安全消息与业务推荐混为一种可关闭设置，也不在本轮改动身份通知模块。

统一执行阶段建议补充以下站内验收；涉及渠道已接受、跨渠道重发及外部送达的分支明确后置到 App 阶段，不计入首版交付要求。本轮均未运行：

1. “生成报告”和“按指定方式发给同事”分别依据其完成条件结束；未发送的文案、站内可用成果和渠道受理不冒充更后阶段的事实。
2. 普通资料更新不默认全员通知；高分推荐和模型“紧急”标签不绕过真实接收范围、关闭设置或免打扰规则。
3. 排队后成员撤权、离职或接收范围改变时正确停止或重新核对；明确发布副本继续遵守目标空间权限，不误套私人来源规则。
4. 合并、延后和过期处理不静默取消明确交付；恢复联网或服务后不重放全部积压消息，未完成承诺仍能找到。
5. 已读不等于已处理；任务完成/取消后旧队列不再催办。“稍后提醒”不改变任务截止时间。
6. 关闭提醒与停止分析分别生效；待发送及重试复核最新设置。取消已被外部渠道接受的请求不报告虚假撤回。
7. 明确失败、结果未知、重复回调和部分成功采用对应恢复方式；未知结果不盲目跨渠道重发，明确再次发送可形成新动作。
8. 内容更正阻止未发失效版本，必要再交付有依据和授权；方法回退不抹去真实发送记录，也不声称已同步更正独立企业副本。
9. 首版明确只有站内交付与提醒，关闭页面后不声称可系统外触达；用户返回时按当前权限查看已有成果与有效提醒。请求未支持的外部发送时不伪装已安排，Demo 转发和模拟回执不计入真实验收。真实外部发送及异常留到 App 阶段验证。

首版未决项包括：站内共享与接收范围的具体操作、企业和个人可管理策略、站内提醒例外、时间窗口/上限及失败处理责任，随管理、运行及全局汇总确定。外部渠道、账号绑定、跨渠道备用和外部结果未知的恢复进入后续 App 规划，不再列为首版待决。下一轮讨论画报反馈与会话反馈如何分别作用于任务、档案、经验和方法优化。

## 12. 本轮讨论：画报反馈与会话反馈

2026-09-30 接续，用户随后认可两类反馈、当前纠正/长期积累分别处理及作用范围的大方向（DEC-089）；具体选项、时机、权限动作、保留政策和自动程度仍为设计建议。沿[输入档案维护原则](输入板块-开发任务书-V0.1.md#84-ai-怎样维护哪些情况需要业务确认)、[处理经验候选与维护](处理板块-开发任务书-V0.1.md#83-本轮讨论候选归档质量核验发布与失效维护)及[画报反馈既有交互](../产品/画报详情与反馈前端验收-2026-09-24.md)衔接。首版全部在系统内进行，不追加 App 或系统外索评（DEC-088）。当前 Demo 有反馈交互、浏览器保存及预设调整回复，不代表真实反馈归因、自动记忆、经验入库或会话满意度机制已经完成。

### 12.1 两类反馈的对象与含义

| 反馈 | 主要回答什么 | 需要关联的对象 |
| --- | --- | --- |
| 画报反馈 | 这条内容对我是否有用，内容、时机和表达哪里需要调整 | 实际阅读的内容与呈现版本、画报入口/推荐上下文、当前企业成员及获准范围 |
| 会话反馈 | 这次工作是否达到目的，结果或过程哪里需要改进 | 本次任务及目标、回复/成果/交付版本、明确评价范围和当时实际完成状态 |

同一成果可能同时收到画报评价和会话评价，它们可分别反映发现/阅读体验与任务体验，不合并成一个含义不明的总分，也不把同源结果重复累计为两次独立成功案例。

评价、执行确认和业务结果分别记录。有用或满意不等于允许发布、执行工具、建立长期任务或提炼共享经验；AI-12—AI-13 的确认卡片仍需表达具体动作及对应授权。用户说“很好，下周继续”可以同时含有评价与新委托，分别识别，明确且在权限内的委托沿处理机制推进，不因它出现在反馈入口就忽略，也不只靠“很好”推断授权。

### 12.2 画报沿用现有交互，补齐真实语义

- 有用/没用互斥，关注独立；认为本次内容没用，仍可关注这个事项。没用不自动隐藏、不取消关注或改变任务状态。
- 没用保留四个快捷原因：“与当前工作无关”“已经知道或内容重复”“内容不准确或已过时”“分析或建议没帮助”，加“告诉 AI 如何优化”自填入口。不是五个固定原因类别；旧原因按已有兼容规则读取。
- 选择快捷原因即提交相应反馈；只打开或取消原因面板不提交、不覆盖原评价。自填进入该卡的独立调整会话，带入实际阅读快照、呈现配置、空间、来源版本及既有历史，用户发送具体说明后才记录；继续对话保留前后关系，不覆盖最初原文。
- 普通业务会话与卡片调整会话继续各自复用。调整会话不新增活跃会话画报，也不把一次排版修改算作新的业务成果数量；仍保留必要的真实执行与资源记录。
- 关闭详情、隐藏、阅读、关注和转发不是有用/没用评价；读取旧快照不改变新版阅读事实，纯排版不伪造新的业务时间或内容发现。

以上沿用现有前端交互，不扩大为已有服务端能力。真实提交失败时应保留可恢复输入并说明未保存，不能显示“AI 已学习”；保存评价与调整内容分别取得实际结果，不能因为评价写入成功就声称内容已更新。

### 12.3 会话怎样邀请评价

建议在有意义的交付或阶段结束时适度邀请评价，例如询问“本次交付是否达到你的目的”，可采用“已达到 / 部分达到 / 未达到”并允许补充说明。选项和文案仍为设计建议，不直接加入当前界面；用户可以跳过，未评价不阻塞使用或正常任务结束。

评价对象应明确，例如“这份报告”或“本次资料核对”，避免让用户为整个长期会话一次性打分。部分交付、失败及等待补充也可接受反馈，但须标明实际评价范围，不能为发满意度卡片先把任务改为已完成。

不在每条模型回复后追问，不因用户跳过就重复弹出。用户已在自然语言中指出问题时优先处理，无需再重复填写评价卡；频率、采样和暂停索评方式在后续体验/运行专题确定，不以反馈数量作为目标。首版只在站内邀请，不通过系统外渠道追评。

用户可对当前回复、具体成果或任务结果自然表达反馈。上下文足以定位时自动关联；仅在歧义会实质影响纠正对象或动作时澄清，不把所有评价变成问卷。自然语言理解存在不确定时保留原意及归因候选，不编造满意程度。

### 12.4 反馈怎样分流到合适的处理

原因是问题线索，不保证诊断已经正确；AI 可结合当前目标、实际资料和执行回执分析。一个反馈可以包含多个含义，分别记录并按各自范围处理，而不是同时修改所有模块。

| 用户表达或反馈 | 建议去向 | 生效范围与限制 |
| --- | --- | --- |
| “与我当前工作无关” | 输出检查受众/相关性，必要时核对档案背景 | 可以调整本人的相关推荐；不据此修改组织职责或访问权限，也不抹去真实业务义务 |
| “已经知道，内容重复” | 输出检查重复、事项合并与信息增量 | 不直接判定内容错误，也不永久屏蔽以后出现的重要变化 |
| “数字错了 / 资料过期” | 处理核对具体依据和版本，必要时反馈给输入质量维护 | 可按用户提供的纠正注明依据并修订当前结果；修改权威资料仍需相应维护依据与权限，不由一次差评直接覆盖源数据 |
| “分析没有帮助 / 漏了关键条件” | 处理检查目标、信息缺口、推理与方法适用性 | 明确的当前改进请求可在已有授权内执行；只有负面评价时不自动开启无限重做或停用通用方法 |
| “没用，改成表格” | 保存评价，并承接本次表达修改请求 | 修改当前结果，原结果与新呈现可追溯；不自动形成永久偏好 |
| “以后我的周报先给结论” | 输入档案的低风险明确偏好维护 | 按本人、当前企业及周报场景记住，轻提示并可撤销；不扩展给全员，不等待自进化服务 |
| “这项工作已经线下解决” | 处理核对相应事项和允许确认其状态的主体 | 有权人员的确认可作为业务状态依据并注明来源；不将线下完成改写为系统工具执行成功，不直接抹掉失败回执 |
| “以后持续关注这个问题” | 处理侧的持续目标/任务机制 | 依据明确委托与已有授权安排，不仅保存为表达偏好；目标范围和运行状态可查看 |
| “这次效果很好，这套方法可复用” | 经验维护接收候选线索及真实任务关联 | 核对可复用条件和实际证据，再按提取/发布策略处理；高评价本身不授予跨空间或跨企业复用权 |

共享成果的不同用户可有不同意见。个人表达偏好分别生效，事实争议结合来源、时间与适用条件核对；不能用票数、职位标签或最新一条意见自动修改共享事实。用户可评价其获准阅读的内容，不因此获得维护共享成果、查看原私人会话或读取他人私人反馈的权限。

### 12.5 当次纠正与长期积累分别完成

明确的当前纠正应在既有权限内尽快处理，不等待满意度分析、经验归档或自进化模块上线。涉及共享文稿修改、源资料维护、持续计划或发布的动作沿对应权限和版本规则执行；同一已授权动作不重复索取确认。

长期偏好按输入既有机制维护；经验候选按处理第 8 节整理。高满意度可以成为触发线索，但任务真实完成范围、所用方法、人工贡献、适用条件和后续效果仍需核对。失败后的有效恢复、重要纠正与反例也可以成为候选，不只收集好评。

经验提取只读取获准用于相应用途的必要会话、成果和记录，不默认复制全部会话或模型隐藏推理。候选清洗、核验、去重、入库及发布复用已有设计；在预授权的来源、类型和范围内可以自动完成，不要求每条都人审；仅有提取权时保留候选，去敏也不自动扩大发布资格。

用户看到的结果应反映真实阶段，例如“评价已保存”“本次内容已更新”“已记住周报偏好”；只有实际形成经验候选时才记录该状态，发布/索引就绪继续单独判断。后台整理失败不回写成原任务失败，也不反复要求用户重评；纠正失败保留具体问题和可恢复入口，不使用一个笼统“已优化”掩盖。

三端处理入口及责任衔接见[管理任务书第 14 节](三端管理与共用平台-开发任务书-V0.1.md#14-运行与改进工作区及待处理流程)：能按授权自动处置的直接处理，需要人补充/决定的才进入相应待处理视图，个人提醒状态与处理进展、实际解决依据分别记录。分派事项不扩大反馈原文或源会话读取权，具体交互仍为设计建议。

### 12.6 版本、改评、撤销和重复处理

建议复用一套可追溯的反馈关联：反馈来源与当前成员身份、对象/任务及内容/呈现版本、明确评价及原文、原因或待核对归因、提交/修改关系、衍生动作与其实际状态。不同入口保持自己的业务含义，不要求建立一套独立流程引擎或把所有字段交给用户填写。

- **改评与撤销**：当前有效评价随用户修改变化，历史关联按权限与保留政策维护。撤销后不继续把旧评价作为有效支持；不能靠删除所有历史证明当时没有发生过处理。
- **衍生动作**：若一条待执行调整或个人偏好仅依赖被撤销的反馈，应停止继续据此生效或重新核对。已有独立明确确认的决定、已经发布的企业副本和已完成业务动作不机械回滚；撤销评价、撤销偏好和取消任务仍是不同操作，向用户说明实际影响。
- **晚到反馈**：先定位其对应的旧版本，再判断问题是否仍影响最新内容或方法；新版已经修复时不重复修改，旧版仍暴露通用问题时继续核对。不能直接用旧反馈覆盖新成果。
- **重试与重复来源**：同一提交的重试不重复改偏好、启动纠正或产生案例。用户在会话中说有用后再点卡片，保留关联与各自评价含义，不自动当作两个独立成功证据；无法确定是否同一含义时保留来源差异，不凭文本相似删除评价。
- **归因可修正**：用户可以纠正系统对原因或作用范围的理解。原文、AI 归因和实际采用分别可追溯；原因不明时保持未知，不能用推断冒充用户明确要求。

涉及本人纠错与历史反馈管理的访问范围按其身份和现行保留规则落实，不通过反馈记录继续取得已撤权源内容；内容删除、审计保留及已脱离私人来源的独立发布副本仍按各自规则处理，不承诺一次撤销清除所有已交付字节；跨对象保留、导出与恢复建议见[管理任务书第 15 节](三端管理与共用平台-开发任务书-V0.1.md#15-数据保留删除导出与恢复)，具体期限及动作授权仍待收口。

### 12.7 权限、观测与自进化的分工

反馈默认在其业务对象和目的所允许的范围内使用，卡片被共享不自动公开评价人的原文或私人调整会话。客户端提供本人的反馈与更正入口；企业侧获权维护者处理相应业务问题；总台只接收获准的运行信息和必要汇总，不获得全量客户会话/反馈正文。小范围汇总也需避免反推私人内容，具体可见字段和保留期限在管理/评估专题收口。

评价是证据之一：打开、停留、跳过和无回应不等同于满意；高分不覆盖真实执行失败，低分也不单独证明方法失效。观察应包含纠正是否真正完成、同类问题是否复发、反馈处理负担、关键遗漏和不同场景差异，不能只看满意率或入库数量。用户目标变化、资料变化与方法缺陷分别归因，缺少依据时保留未确定。

当前任务纠正、明确偏好维护、按已生效策略整理经验都属于基础系统能力。独立自进化后续改进的是索评时机、归因方法、推荐/表达及经验维护方法；在预授权范围内可自动试验和采用，但不能自行改用户评价、编造好评、扩大数据用途或用更改统计口径证明提升。具体机制沿第 10.10 节及跨板块评估/更新规则，不在本轮运行。

### 12.8 拟开发任务与验收补充

拟由 M5 复用画报交互并接入真实反馈保存、版本及修改/撤销；M4 承接任务级索评和获准纠正；输入档案与处理经验库分别接收适用变更；M7/评估串联反馈、衍生动作和实际效果。避免另建一套偏好库、经验库、权限或任务完成状态，日常交付不等待全部归档结束。

统一执行阶段建议验证以下行为，本轮未实现或运行：

1. 有用/没用互斥，关注独立；取消原因选择和只打开自填入口不提交负反馈，具体说明发送后才记录，保存失败不冒充成功。
2. 评价定位用户实际阅读或收到的内容版本；画报评价与会话任务评价可区分，满意不自动触发发布、执行确认或共享经验。
3. “没用，改成表格”既保存评价也处理本次明确修改；“以后周报先结论”按范围维护长期偏好，“很好，下周继续”按评价和新委托分别处理。
4. 用户提出事实错误时核对依据并处理当前结果，不直接覆盖无维护权的来源；共享成果多人意见不按多数票修改事实或泄露私人反馈。
5. 改评、撤销、重复提交和晚到反馈正确关联对象及衍生动作；既不重复创建案例，也不把新版已修复问题再改坏，独立发布和真实执行事实保留正确状态。
6. 失败、部分交付和无反馈如实记录；索评可跳过、不阻塞使用，已明确指出的问题不用再填写重复评价，也不发生系统外追评。
7. 高满意度仅形成适用候选线索，真实纠正和反例也能进入获准整理；提取、发布及索引状态分别验证，归档失败不改变原任务完成事实。
8. 撤权后不从反馈/缓存泄露源内容，个人反馈不自动公开给其他成员或总台；自进化停用时，当前纠正、明确偏好维护及获准经验维护仍正常运行。

待后续收口：会话评价卡的具体选项与时机、可关闭的索评设置、反馈可见范围/保留/删除、用户自述与业务事实的核对主体、自动维护类别和验收指标。本节已汇入第 13 节，最新接续按 DEC-090 先评估与运行观测、再独立自进化，之后统一三端管理；不以本节讨论完成代替用户确认、功能实现或质量验收。

## 13. 输出板块阶段汇总与管理衔接

2026-09-30 汇总第 1—12 节。本节整理下一阶段能够据以分工的范围、依赖与未决事项，不新增功能实施授权。具体开发任务在各板块讨论完成后统一安排；初始算法由 AI 在执行阶段设计和验证，后续独立自进化再优化。

### 13.1 确认状态与当前基础

- 已确认首版只做站内交付、画报和相应提醒，系统外业务触达留到后续 App（DEC-088），不再把是否接外部渠道列为首版待决项。
- 用户已认可两类反馈的对象、按原因分流、当前纠正与长期积累分别处理、偏好/经验的作用范围和真实处理状态方向（DEC-089）。具体评价选项、索评节奏、可见/维护权限、保留与自动采用条件继续待定。
- 输出对象、排序依据、个性化、站内提醒及恢复等已形成设计建议；不以本次认可推定整份输出稿或所有功能均已冻结。基础系统独立运行、自进化后接入和先讨论再执行的决定继续有效。
- 现有可复用能力沿第 2 节：私人成功任务画报投影、文稿/固定版本导出、独立企业副本及更新、共享资料动态，以及完整 Demo 的画报/会话交互。真实客户端、Demo、合成模型响应及历史本地验证继续分开，不能用界面已有按钮证明真实推荐、反馈或提醒已实现。本轮未重跑功能验证。

### 13.2 建议纳入基础交付的能力

下表是待全局汇总收口的能力范围，包含旧能力复用与新增工作；逻辑分工不要求增加六套服务，也不等于同时上线全部内容类型。

| 能力 | 复用与主要增量 | 关键验收落点 / 模块 |
| --- | --- | --- |
| 直接交付与成果引用 | 复用会话、任务、文稿、文件和发布；补齐处理结果到不同入口的确切版本与完成范围关联，站内转发衔接已有访问/发布能力 | 用户要求的交付可找到，不因未推荐而消失；部分/失败如实，私人和独立发布副本权限各自正确，转发不自动增权，具体操作在管理专题明确；M4/M6 与 M5 |
| 获准主动内容与基础推荐 | 从真实获准任务、资料及成果形成候选，补必要的适用性、去重、事项更新和初始选择方法 | 不只有成功回复截断投影；无价值候选可不展示，重要事项依据可核对，旧内容不伪装新发现；M4/M5 |
| 个性化与真实画报接入 | 复用已确认的画报详情、关注、日期及会话衔接，接入可信数据与受众表达 | 本次要求/长期偏好分开，事实和必要限制保留，标题/摘要/附件同样守权限；无需每次二次模型调用；M3/M4/M5 |
| 站内提醒与恢复 | 复用已有任务、成果及当前入口，衔接处理侧待补的持续计划机制；补持久交付/提醒状态、适用策略、关闭和恢复 | 页面关闭后成果仍可保存，返回后按当前权限查看；关闭提醒与停止工作分开，不重复提醒或虚假已读，不新增系统外触达；M4/M5/M7 |
| 两类反馈及实际处理 | 衔接画报已有交互，新增真实保存、任务级评价、改评/撤销、原因与衍生动作关联 | 当前纠正、明确偏好和经验候选各走已有机制；满意不自动授权或成为成功案例，归档不阻塞交付；M3/M4/M5/M7 |
| 版本、观测和故障下的可用性 | 关联任务/成果、内容/呈现、方法及反馈版本，明确失败与恢复 | 排序/个性化/归档故障时仍可提供有权访问的直接成果和任务；无法核验权限时不复用旧缓存绕过；方法可替换且效果有依据；M5/M7 |

基础推荐和反馈应能用代表性的真实链路验证，不以空接口、纯规则说明或 Demo 状态代替交付。候选来源、提醒事项和评价场景从已纳入的获准业务样例起步，无需先覆盖所有行业与岗位。

### 13.3 明确后置与继续可替换的部分

已后置：系统外业务触达及其渠道绑定、供应商接入、多渠道恢复、外部送达验收进入后续 App；独立自进化在基础系统完成后接入并验证。基础阶段不建设空推送网关或独立实验门户。

不作为当前首版前置：全行业推荐体系、大规模行为画像、每用户独立模型、全量历史内容重处理或复杂推荐训练。保留后续需求评估空间，不以算法复杂度定义首版完成。正常授权内的偏好维护、当前纠正和经验整理属于基础运行，不因自动发生而一并后置。

候选选择、合并、排序、摘要、角色化表达、索评时机、模型/程序分工及缓存方式保持可替换。需要确认的是业务范围、用户可依赖的行为、资源和质量条件；具体公式、权重及实现细节可由 AI 在统一执行时选择、记录并验证，不逐项要求用户指定。

| 对接方 | 共同明确的内容 | 保持的责任 |

### 13.6 整体验收怎样串起来

统一执行时从第 8、10.9、11.9、12.8 节选取代表场景，至少串起：

1. 用户请求报告 → 基于获准来源形成真实结果 → 会话/成果直接交付 → 适用时进入画报，不因未推荐而丢失交付。
2. 获准主动检查 → 有依据候选或无新发现 → 合理选择/合并 → 站内提醒及返回查看；旧状态、重复事件和任务取消不产生反复催办。
3. 同一获准成果向不同用户呈现 → 当前权限、私人来源或独立副本规则正确 → 原有详情/会话交互可用，表达不改写事实。
4. 用户针对确切版本反馈 → 明确的当前纠正、长期偏好或经验候选分别处理 → 用户可看到实际结果；改评、撤销、晚到和重复反馈不会重复动作或覆盖新版本。
5. 排序、个性化或归档失败 → 原有合法成果及任务仍可访问 → 未完成部分和恢复有记录；撤权时旧缓存及反馈关联不能绕过权限。

验证关注实际业务行为，贯穿企业隔离、权限变化、版本兼容和恢复，不以测试数量或生成内容数量代替证据。首版不验收系统外送达，本轮也没有运行上述检查。
