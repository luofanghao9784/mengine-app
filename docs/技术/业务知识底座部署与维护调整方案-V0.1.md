# 业务知识底座部署与维护调整方案

版本 V0.1，2026年10月16日，待用户确认。本次仅新增方案文档，不修改代码、既有部署协议、线上知识、自动任务或运行配置。本文所有新增机制均为拟议设计，不代表已经实现或获准上线。

目标是让首次部署形成可核验的业务认识，让同一板块的知识围绕业务问题汇总，并让后续运行维护这些知识，而不是按每张表持续生产统计文章。首个验证范围仅为 9POP 订单、收款、退款；通用机制不硬编码 9POP 的具体规则。

## 一 结论和本次范围

建议保留现有采集与字段治理底座，调整知识层的部署契约、存储组织、生成调度、权限依赖和检索消费。页面汇总是其中一部分，不能代替后端调整。

本期形成一个业务板块总览，包含订单与付款、收款确认、退款流程、退款计算、退款财务处理、核对与历史例外等专题章节。章节多少由业务问题决定，不按数据表数量配额。数据说明、业务规则、经营观察分开维护，能够相互引用。

不在本期展开全企业知识重建、复杂图谱平台、新向量数据库、任意 SQL、客户人工建表或新增审批系统。现有画报生成也不整体重做，只调整知识与经营观察的归属和消费边界。

## 二 当前实现与问题对应

以下代码核查针对当前主目录；线上193条知识等数量来自2026年10月16日上一轮只读核查，不代表已验证当前主目录的全部代码均在线上部署。

| 当前实现 | 已核查的位置 | 实际影响 | 拟调整 |
| --- | --- | --- | --- |
| 部署包要求每张表提交1至10篇知识；知识必须引用本表字段 | `deployment-governance.ts` 的 `importDeployment` | 即使几张表属于同一业务，也倾向重复生成；无法直接表达多来源专题 | 数据集治理与板块知识分开提交，数据集允许没有独立文章 |
| 数据知识按单表统计，每表最多3篇；输入是字段和最多60项统计事实 | `business-knowledge.ts` 的 `profile`、`learn`、`publish` | 擅长占比、范围和分布，缺少流程及适用条件 | 作为经营观察能力保留，退出正式业务规则的默认生成入口 |
| 发布检查侧重数字和事实编号存在 | `business-knowledge.ts` 的 `publish` | 数字正确不代表状态翻译和推论正确，如 applied 被误译 | 增加状态语义、推断性质、结论支持范围和规则冲突检查 |
| 每份原资料独立生成一篇，按单一 sourceId 保存 | `learned-wiki.ts` | 来源摘要直接占据知识位置，跨资料整合不足 | 保留为内部来源摘要或候选输入，发布知识按专题组织 |
| 数据知识与资料知识统一拼接为卡片；结构化知识按同源事实连线 | `scene-knowledge.ts` | 同名碎片混排，来源关系被当作主要知识关联 | 输出板块、专题、章节和待处理问题；关系区分业务依赖与共同来源 |
| 页面15秒轮询期间可调用 sync，后台也每60秒检查并调用 sync | `knowledge-api.ts`、`SceneInputWorker.java` | 两个触发入口均围绕待学习来源推进；单改定时器不够 | 页面读状态，显式操作提交请求；维护执行统一到持久任务 |
| sync 优先取一个待分析数据集，再学文档或生成图 | `scene-knowledge.ts` | 系统的工作单位是来源，而不是需要维护的业务专题 | 工作单位改为专题及其受影响章节 |
| 中央服务逐卡同步为资料，知识元数据以展示用 kv 为主 | `SceneService.java` | 页面合并不会自动改变AI看到的碎片；规则依赖不完整 | 同步正式专题版本和结构化来源依赖，按规则片段建立引用 |
| 当前检索以片段包含查询词筛选，按选中和解析时间等排序；工作空间工具路径一次取3条 | `KnowledgeService.java`、`AgentTaskService.java` | 没有专门按业务板块、有效规则和例外组织召回 | 增加业务主题检索与必要关联章节获取，不依靠关键词命中旧碎片 |

当日193条知识由106条部署口径和87条模型统计文章组成；106条口径去掉源表标识后有19种不同主体正文，订单收款退款相关14条口径同名。55条星图连线均在同一来源内部。这说明调整不能只改标题或增加分类。

## 三 首次部署怎样增加业务梳理

### 先按业务链建立认识

Codex在接入目标业务链时先收集以下内容，形成可读的业务简报，并保留结构化依据。不是要求客户填一份长表，也不要求先梳理整个企业。

| 梳理项 | 应得到的结果 | 9POP本期例子 |
| --- | --- | --- |
| 目的与问题 | 企业希望AI完成什么，什么不在范围内 | 解释收款与退款、核对差异；不代替批准退款 |
| 业务对象及粒度 | 对象关系、一对多、唯一性和重复计算风险 | 一个订单多笔收款，退款沿课程关联 |
| 流程与状态 | 状态定义、进入条件、动作、结果及分支 | 暂挂 active 与 applied 的不同含义 |
| 金额与时间 | 指标、单位、计算依据、归属日期 | 订单约定、登记收款、实际出款、收入冲减分开 |
| 岗位与权限 | 哪些角色可读取、处理、确认和发布 | 从权限配置与服务端检查核实，不凭岗位名称猜测 |
| 例外与历史 | 取消、撤回、软删除、迁移、旧字段缺失 | 历史财务类型为空不代表未退款 |
| 依据与适用范围 | 来源版本、定位、确定性、生效区间 | 源码实现、正式制度、执行记录分别表达 |
| 未解决问题 | 区分可继续查证和需用户决策的问题 | 净收款月份口径待决定；上课限制先查代码 |

来源有冲突时，分别记录“制度如何要求”“系统如何执行”“记录实际发生什么”，不能用源码自动覆盖制度，也不能因一次样例就推成通用规则。

### 部署流程与交付物

1. **确定授权范围。** 保留现有只读身份、固定投影和企业空间绑定。把当前业务链、允许读取的来源及用途写入部署简报。
2. **整理业务背景。** 先读规则和流程，再结合真实schema、状态机及获准样例核验。列出待补证与待决策项，不猜状态和业务口径。
3. **完成数据说明。** 继续交付现有逐字段依据、关系、不可加约束、空值处理和检查规则。未知含义不因导入成功变为已核实。
4. **形成板块总览与专题。** 多来源共同支持规则；没有新增业务价值时不生成文章。统计结果不作为流程规则依据。
5. **分别预览校验。** 数据校验验证结构、关联和精度；知识校验验证条件、例外、证据和问答。可先完成获准数据接入，但知识保持草稿或部分可用。
6. **确认真正需要决定的内容。** Codex能核实的技术事实主动处理；只将冲突、管理指标或责任承诺等决定交给用户。确认必须记录对象和版本，不能因用户确认整套方案就推定所有未知口径均获确认。
7. **版本化发布与接续。** 对已具备依据的章节发布，未确认部分明确保留缺口；发布前复核全部依赖与权限，输出可追踪回执、验证记录和后续维护范围。

首次部署交付应包含：业务简报、来源与字段说明、板块知识包、问题清单、问答验收与发布回执。数据已接入、规则已核实、知识已发布、模型问答已通过四项状态分别记录。

### 部署契约建议

新增版本化知识部署契约，保留原数据治理契约兼容入口。拟议结构为 `datasets`（字段治理）、`businessModules`（业务范围及背景）、`topics`（专题章节与依据）、`openQuestions`（缺口）、`acceptanceCases`（验证用例）。命名是实现建议。

移除新版契约中“每表至少一篇知识”的要求；一张表可以没有文章，一个专题可以依赖多张表和多份资料。数据集治理与专题发布可以分步完成；只有全部依赖已满足的专题版本才能发布。超过现有每批20张表的部署限制时，可先逐批治理，再基于已发布来源版本发布专题，不强行扩大一笔事务。

保留preview、幂等请求、版本令牌、权限复核、原子发布和审计。新专题使用稳定ID及独立版本，不以模型返回数组下标作为长期身份。业务内容包不接受模型或浏览器提供的SQL、命令或数据库凭据。

## 四 同板块知识怎样汇总

### 内容结构

| 对象 | 内容与作用 | 默认呈现 |
| --- | --- | --- |
| 板块总览 | 目标、业务对象、核心流程、专题导航和关键未决项 | 知识库板块入口 |
| 业务专题 | 规则章节、条件、步骤、例外、示例、关联与证据 | 员工阅读和AI回答的主内容 |
| 数据说明 | 字段、状态、关联、单位和来源版本 | 按需展开，供取数与核查 |
| 经营观察 | 指定期间和版本的分布、变化、异常 | 板块内次级页或现有分析入口，不混入规则正文 |
| 工作材料 | 来源摘要、候选解释、冲突、验证失败 | 维护者按权限查看，不作为已确认事实检索 |

板块按业务关系确定，部门仅是标签；不按department字段自动决定板块或访问权。不把所有表拼成超长文章：面向读者是一套连贯知识，底层以可独立更新和引用的章节或规则片段保存。

### 拟新增的知识信息

专题与章节保存稳定ID、标题、正文、适用条件、业务板块、关联规则、生效范围、证据性质和发布版本。依据保存来源ID、版本、字段或段落定位、摘要及相应权限依赖。经营观察另保存统计期间、采集时点、计算回执和指标定义。

发布状态与事实确定性分开：草稿、当前发布、待复核、被替代、下架是生命周期；来源明确、部署推断、证据不足、用户已确认是依据性质。发布了一篇有“待确认”章节的专题，不代表该章节已成为可执行规则。

拟议新增表可包含 `business_modules`、`business_topics`、`business_topic_revisions`、`business_topic_dependencies`、`business_knowledge_questions`、`business_knowledge_jobs`；名称可在开发时调整。Wiki维护规则源，中央平台维护受控消费投影，不形成两套可互相覆盖的业务规则权威。

### 阅读体验

知识库首屏按板块展示总览及有效专题，不默认展示所有单表文章。进入板块后先读业务介绍与流程，再按问题展开专题；“数据依据”“经营观察”“待确认事项”在相关位置进入，不增加多组独立后台菜单。

同一规则保留一个权威版本，多个专题引用它；共同来源只作为依据关系，不包装成业务依赖。星图后置为可选视图，不以节点数、连线数衡量知识价值。

## 五 后续自动维护怎样运行

### 按变化类型决定动作

| 触发变化 | 自动动作建议 | 是否修改正式规则 |
| --- | --- | --- |
| 新订单、新收款等普通行变化 | 更新数据版本；按已启用的分析策略评估是否值得生成或刷新经营观察 | 否，不因占比变化改业务规则 |
| 相同内容的周期采集 | 更新必要运行记录，按内容指纹去重 | 否，不重复模型调用 |
| 字段结构、投影或字段解释变化 | 标记依赖受影响，等待部署工具治理，阻止使用不再成立的规则计算 | 不由运行时模型重写字段解释 |
| 制度、源码版本或正式口径变化 | 定位受影响章节，生成差异和候选修订，运行验证 | 业务含义变化需相应维护确认后发布 |
| 已确认内容的排版、无语义改动 | 确定性更新及版本记录 | 可以自动；语义不确定时转候选 |
| 原来源补充了明确事实 | 形成章节补充候选，并检查与已发布规则是否冲突 | 首期不让模型自行把候选升级为制度 |
| 问答未能作答或引用不足 | 在允许范围内记录问题类别与缺口，合并同类项 | 不把模型回答自动回灌为规则 |
| 来源撤权、删除或确认错误 | 立即停止受影响内容的读取、检索、引用和缓存使用 | 立即失效，不等待人工确认或重新生成 |

这里的“自动维护”包括识别、定位、候选修订、验证与状态更新，不等于自动决定业务。现有正式规则仍有有效依据时，新候选生成失败不覆盖旧版；原依据已失效时，不能因为生成失败又恢复旧规则。

制度或源码变更必须有可观察输入：首期由部署工具提交带版本的变更清单，或现有资料更新事件触发。没有接入版本事件时，不能声称系统已自动察觉源系统行为变化；应展示最后核验时间和版本。

### 调度与更新可靠性

复用现有服务调度，不另建cron。由服务端持久任务统一执行；页面只读取状态，用户主动“重新核验”时提交幂等请求，不因打开页面自动发起生成。

任务按企业、专题、依赖版本和任务类型去重，合并短期连续变更，设置并发、预算、重试退避及失败原因。处理开始和发布前均复核版本与权限；旧任务晚到不得覆盖新版本。进程重启后能恢复任务，不能只依赖进程内Set或busy状态。

规则依赖要区分数据行版本、字段语义版本、政策版本、原始资料版本和权限版本。规则可在行数变化后继续有效；经营观察依赖固定数据版本。结构未变但源代码行为改变，也必须能触发业务规则复核，不能仅用schema指纹判断知识正确。

## 六 AI怎样读取这些知识

1. 根据问题及当前获权范围定位业务板块和专题，优先读取当前有效规则，必要时补板块总览。
2. 同时取得与本题相关的例外、待确认项和依赖规则，不能只取主结论。
3. 需要数据时，再读取字段解释和获权固定快照，复用可信计算或已核验跨表配方。
4. 回答引用具体章节或规则版本，检查引用ID真实存在，并检查其是否支持该结论。引用存在检查是硬校验，语义支持另需规则校验及评审，不能用模型自评分冒充已证明。
5. 来源冲突、指标未定或证据不足时，指出缺口；已有明确范围的子问题仍可回答，不因为一个未决项而把整篇知识判为无用。

中央同步应把正式专题版本、章节与依赖作为结构化资产保存和索引，不能只拼接展示kv生成文本。旧版统计文章不得和正式规则同级排序；一般聊天不得把仅供维护的候选摘要当正式事实。

首期优先扩展已有检索，加入板块、知识类型、有效版本、规则编号与别名的过滤和排序，并按需要补取关联章节。不承诺立即换向量库；用真实召回结果决定是否需要更复杂检索。

## 七 多来源权限与失效

专题整合不会扩大来源权限。首期采用保守的章节级依赖控制：用户必须满足一段内容全部必要来源的读取条件才能看到它；若章节不能安全拆分，则该章节整体不可见。不能把多个来源权限做并集，也不能让管理员资格自动替代内容读取权。

标题、摘要、导航、检索片段、下载、任务上下文、引用与缓存都执行同样的权限规则。对无权内容返回通用不可用状态，不能通过标题或缺口提示透露敏感业务。不同人员可能看到同一板块的不同获权章节，但界面不得虚称已经提供完整业务全貌。

目前平台桥会过滤部分restricted来源后同步到共享空间；此机制不能直接承担多来源知识的全部授权。新专题必须携带每项来源依赖与权限版本，中央读取和发布前复核。必要的权限隔离在本切片实现，不后置到上线后。

## 九 旧知识怎样迁移

1. 只对订单收款退款范围建立旧知识ID、来源、正文和状态的清单，保留可追溯版本。其他板块保持原状。
2. 将重复口径归入共同规则，把有关表的不同说明留在数据层；有效经营统计转入观察；已核实错误列为待纠正对象，不机械拼接到专题。
3. 以当前样稿形成专题候选，保留缺口；先在隔离环境发布新版知识并运行对照。只拿本地样稿问答通过不等于迁移完成。
4. 上线前输出明确清单：新专题、将被替代的旧文章、观察归类、受众及失效变化。按届时授权范围切换。
5. 正式切换时发布新版、更新检索投影、撤下被替代碎片及相关缓存；旧资料保留历史记录，默认检索不再召回旧正文。
6. 回退只切到仍满足当前权限且没有已知错误的有效版本；旧错误文章不能因回退自动重新成为权威。不能通过数据库整体还原覆盖后续业务写入。

升级后的新板块不再启用旧的逐表知识发布循环，避免迁移完又自动长出重复文章。仍可沿既有获准策略生成有价值的经营观察，不自动增加模型预算或生成频率。

## 十 分阶段实施与验收

按本目录main顺序推进，不并行开worktree。每阶段通过相关验证后再进入依赖阶段，不一次展开全企业。

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 1 业务包与存储 | 首次部署规范、新契约、专题版本及依赖、订单链导入预览 | 多表不要求逐表出文；重复请求幂等；来源变化拒绝旧发布；原字段治理不回归 |
| 2 阅读与AI消费 | 板块页面、章节引用、中央投影和检索 | 用户能读完整专题；AI能召回规则和例外；无重复新旧知识混用 |
| 3 维护闭环 | 变化分类、持久任务、候选修订、复核和失效传播 | 普通行变化不改规则；并发旧任务不覆盖新版；失败不伪造成功；权限撤销立即生效 |
| 4 试点迁移 | 当前业务链转换清单、本地证据、上线和回退计划 | 正式发布须另有授权；上线后按实际账号验证，不把管理员可见当全员可见 |

业务验收包括原六题回归，以及未用于样稿编写的新案例：同一退款混合财务处理、退款跨月、部分收款待审核、历史空字段、已取消订单与历史收款、暂挂撤回与生效混淆。未知题应先由源码或业务负责人建立答案依据，不能让同一模型同时出题、自答和判定通过。

验收同时检查：主要结论、适用条件、未知说明、引用真实性及支持程度。不能出现已申请/applied误译、金额重复累计、统计比例替代规则、未确认口径被当成默认值。不能用一个总分掩盖关键题错误；保留每题原答、证据和评审。

必须分开验证三层：直接提供知识的内容能力；真实用户会话的检索和工具调用；源变化、撤权与任务重试后的维护行为。既有六题样稿测试只覆盖第一层且为已知题回归，不是整体上线证明。

权限测试至少包括同企业不同来源授权、跨企业、生成中撤权、发布后撤权、标题摘要泄露、历史版本与缓存、来源清理及中央同步延迟。业务更新测试覆盖行变化、语义变化但schema不变、多来源仅一个失效、连续刷新和失败重试。

确认方案后，应在既有MAINT-08、MAINT-10及相关资料权限验收依据下记录调整，重要架构选择写入开发决策记录；当前不修改这些文档的已确认状态。

## 十一 本次建议确认的范围

建议整体确认以下方向后，再进入具体实施：

1. 首次部署必须交付目标业务链的业务简报、专题知识及缺口，而不是以按表知识数量作为完成标准；未知事项不阻止其他已核实部分接入。
2. 知识库按业务板块和专题呈现；字段解释保留底层，统计文章转为经营观察，工作摘要不自动公开为正式知识。
3. 自动维护按变化生成候选、验证和更新状态；首期业务含义变化经相应维护确认，模型不擅自修改字段解释或制度；已知错误与权限失效立即退出当前使用。
4. 第一轮只完成订单收款退款及其必要机制，不重建全企业知识库；实际代码实施与线上发布分别按后续授权执行。

“净收款”具体定义、月份归属等仍在[业务知识样稿](../产品/9POP订单收款退款业务知识样稿-V0.1.md)保持待确认。认可本方案不等于认可这些业务口径，也不等于本次已经授权代码或线上变更。
