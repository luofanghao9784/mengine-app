## 2. 已确认主路线与架构落实

**多个客户端 → 统一业务 API → 业务模块与数据；业务任务 → 独立引擎服务 → Agent 运行适配与工具。**

业务平台采用 Java＋Spring Boot，按模块化单体组织，必要的耗时工作放后台进程；网页继续 React＋TypeScript＋Vite。梦核引擎从第一版就通过进程间的版本化契约接入，拥有独立构建产物、启动入口、配置和升级流程。引擎实现语言与 Agent 运行时分别选择，不受 Java 限定。代码可以先在同一仓库维护；单独的目录或包不能代替独立部署边界。

| 必须共用 | 可以各端不同 |
| --- | --- |
| 账号身份、企业、空间、权限与成果发布规则 | 登录跳转、凭据安全存储及设备权限交互 |
| 资料身份、版本、会话、消息、任务和成果 | 页面布局、导航、手势、键盘和文件选择器 |
| 引擎能力、工具授权、业务状态和用量口径 | 推送接收、下载/分享、相机、系统集成 |
| API 契约、卡片/动作含义、来源引用 | 卡片的具体组件和平台原生渲染 |

“后端通用”应验收为同一业务资源与规则可由不同客户端调用，不能解释为后续绝不新增接口。设备管理、推送渠道、应用版本兼容等可能需要后端扩展，核心业务不复制成五套。

## 3. 已确认技术主线与配套候选

主后端比较已完成，用户选择 Spring Boot＋独立梦核引擎，网页继续 React。第 9 节保留比较依据。下表的业务后端、React 网页与独立引擎边界为已确认方向；协议、数据库、队列等配套仍按工程建议记录，不因主路线确认而自动成为用户逐项确认。

| 部分 | 推荐候选 | 本项目中的用途与取舍 |
| --- | --- | --- |
| 网页 | React＋TypeScript＋Vite；延续现有组件/CSS，响应式适配 | 复用 Demo；将浏览器业务状态逐步替换为服务数据，完善手机布局和触控 |
| 业务 API | Java＋Spring Boot，用户已确认 | 模块化业务平台，通过通用接口服务全部终端；不复制其他项目的业务权限与数据模型 |
| 接口契约 | HTTP/JSON＋OpenAPI，独立 API 客户端层 | 为 Web 和后续各语言客户端提供稳定约定；服务端仍执行运行时校验和授权 |
| 回复与进度 | SSE 优先，状态查询及按游标补取兜底 | 流连接中断不影响后台任务；各平台实现不同的接收适配 |
| 业务数据 | PostgreSQL＋数据库迁移 | 企业、权限、资料、版本、任务、事件、用量；数据库约束和租户隔离验证 |
| 检索 | 元数据/简介定位＋关键词＋pgvector | 按真实中文与表格样本验证；嵌入模型独立选择 |
| 文件 | 云对象存储＋平台文件服务 | 原件、解析结果、预览和成果；用文件 ID/版本定位，客户端下载方式可不同 |
| 队列 | 按后端及执行边界确定；TypeScript worker 候选 BullMQ＋Redis | 异步解析、调度和事件处理；业务事实和幂等结果保存在数据库；Java 不直接操作 BullMQ 私有队列结构 |
| 梦核引擎 | 独立服务/进程，HTTP 或消息契约；首个实现可用 TypeScript | 后续团队可用 Python 等重写实现；不绑定 NestJS 内部类或业务数据库表 |
| Agent | DeepSeek Harness 优先原型验证，封装适配 | 锁定可运行版本；引擎团队与平台通过统一任务/结果契约协作 |
| 文件计算 | 需要时使用独立 Python 处理进程/容器 | 文档解析、表格处理、OCR与导出，工具库随格式选型，不占用 API 主进程 |
| 部署 | Docker；开发与试点采用 Compose；数据库/文件托管与否随预算决定 | API、worker、engine 可分别部署；日志、备份、告警和回滚从初期加入 |
| 验证 | 接口/权限/状态测试＋引擎契约测试＋Playwright＋代表性真机 | 模拟浏览器检查不能代替 iOS/鸿蒙设备与后续原生 App 验收 |

后端通用性由协议和业务边界保证；Java API 与 React 网页通过语言中立的接口描述对齐，运行时输入校验和授权由服务端执行。

### 后端路线比较留档

| 路线 | 适合条件 | 需要承担的取舍 |
| --- | --- | --- |
| TypeScript＋NestJS | 希望延续前端语言、小团队统一开发习惯；引擎与 API 分离 | CPU 密集文件计算独立运行；类型共享不代替运行时校验 |

## 5. 现在就要建立的多端约定

1. **稳定业务 API。** 浏览器也使用公开约定的业务接口，不依赖只能在特定网页框架里调用的服务函数。统一 ID、时间/时区、分页、错误码、幂等、并发版本和权限检查。
2. **统一身份、多种登录适配。** 网页可采用安全 Cookie 会话；原生端接入适用的令牌与系统登录流程。使用标准授权登录时，遵循原生端外部浏览器及 PKCE 等约定，见 [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)。不自行发明授权协议；设备会话可撤销，客户端不能自报企业即获得权限。
3. **任务独立于页面生命周期。** 提交后返回任务身份；断网、关页、切后台不等于取消任务。事件可补取，状态可查询，重复发送有幂等保护。系统推送是通知渠道，不是任务事实源。
4. **文件使用通用流程。** 上传创建文件/版本身份，解析有状态，下载重新检查权限。支持普通文件选择和上传下载作为基础能力；文件夹访问、相机和系统分享通过端适配层接入，不让后端依赖浏览器对象或本地路径。
5. **卡片和动作使用结构化协议。** 引擎返回文本、数据系列、来源、文件、允许的动作及卡片类型/版本；前端用自己的组件渲染。不要把 React JSX 或任意 HTML 当作所有客户端必须执行的结果。未知卡片有可读降级展示，动作必须仍经服务端核验。
6. **客户端版本兼容。** App 升级不同步；接口和卡片协议保持明确兼容窗口，采用增量字段/能力协商及必要降级。过期或不兼容客户端明确提示，不能静默错误执行。
7. **设备能力可替换。** 通知、凭据存储、上传下载、打开链接、分享和未来本地执行单独封装。后续增加推送连接器和设备注册，不复制业务服务。
8. **跨设备数据一致。** 已发送会话、资料和任务以服务端为准。用户已选云端为主，先支持草稿恢复和文件上传下载；草稿的本机恢复与跨设备恢复、并发编辑冲突需要分别定义。本轮不建设完整离线编辑同步或本地任务执行。

本轮重点是建立接口和数据边界；尚无对应业务时不提前建设完整推送网关、离线同步引擎和本地 Agent。

## 6. 独立引擎升级的验收条件

- 引擎可单独构建、启动、升级、回滚，升级不要求所有客户端同步发布；业务 API 保持兼容。
- 引擎对接版本化的上下文、任务、事件、成果与用量协议；引擎不直接改业务表或绕过业务授权。
- 新旧版本可短期并存，新任务按策略选择；运行中任务固定版本，恢复/迁移有明确策略。
- 平台保存业务事实、资料、来源、反馈和成果；引擎私有状态定义迁移/重建方式，不把版本回退等同于数据库自动回退。
- 有契约测试、代表性回放、健康检查和失败回退。回放/影子运行不能重复实际业务写入。
- 提交重复、引擎超时/重启、失联、取消、部分产物和权限撤回均有明确处理；不因进程返回成功就认定业务完成。

可以在一个仓库里由不同负责人开发，通过契约而非源码内部调用协作。首个实现的语言只是当前工程选择，不限制后续算法团队。

## 7. 网页端的实际兼容工作

第一阶段同时设计桌面和触屏布局，核心会话、画报、资料、任务和确认流程在目标移动浏览器可操作。手机可使用单列/分页卡片，桌面保留横向阅读，视觉结构不要求完全相同。

建议覆盖 Safari、Chrome、Edge、Android 主流浏览器和 HarmonyOS 浏览器；明确最低浏览器/系统版本后形成测试矩阵。iOS 和鸿蒙使用代表性真机验收，不能只用桌面 Chromium 缩窄窗口宣称全端通过。

重点检查中文输入法、软键盘与安全区、触摸/长按、文件选择和下载、滚动与卡片拖动、流连接中断、切后台返回、登录过期和低性能设备。关键动作不能只依赖鼠标悬浮或桌面独有文件 API；动画和非核心浏览器特性允许降级。

浏览器“可访问”与承诺支持所有历史版本分别表达；本轮确认的是目标系统覆盖范围，最低版本待工程基线和试点设备清单确定。

## 9. NestJS 与 Spring Boot 的详细比较

### 9.1 本地已有事实

2026-09-21 只读核对了两个项目的说明和依赖声明：

- 9POP 的[后端构建文件](<../../../9POP 2.0/backend/pom.xml>)声明 Spring Boot 3.5.14、Java 编译目标 21，包含 Spring Security、MyBatis-Plus、Flyway/MySQL、Actuator 等；这是已有构建事实，不是本轮生产运行环境验证。
- 群力的[依赖声明](../../../群力AI工作台/pyproject.toml)已有 FastAPI、SQLAlchemy、Alembic、PostgreSQL/pgvector、Redis/Celery 和文件处理依赖。其 React/TypeScript 前端已与 Python 后端分离。
- 本项目当前只有 React/TypeScript 前端，没有需要保留的真实后端实现。因此选 NestJS 需要新增一套后端工程体系，选 Java/Python 有现存项目可参考；可直接复用多少尚未做代码抽取评估。

没有读取生产数据、调用两个项目的模型或修改其文件；不能把业务权限、数据库、凭据与部署资源直接沿用到新产品。

### 9.2 比较矩阵

| 维度 | TypeScript＋NestJS | Java＋Spring Boot | 对梦核的实际意义 |
| --- | --- | --- | --- |
| 所有客户端共用后端 | 通过 HTTP/OpenAPI 服务各端 | 同样通过 HTTP/OpenAPI 服务各端 | 没有决定性差别 |
| 与网页一起迭代 | 同语言，纯数据类型和工具可复用；运行时仍校验 | 通过契约生成/维护客户端类型；多一套语言与构建链 | NestJS 有便利，但用户接受重制前端，权重降低 |
| 模块化业务 | 模块、依赖注入、Guard、校验；选择数据库/事务等配套 | 模块、依赖注入、安全、事务、校验与监控生态组合 | 两者可实现；9POP 已有 Spring 实践可参考 |
| 事务和权限 | 依靠明确业务授权、数据库事务和所选 ORM/驱动 | Spring 提供统一事务及安全集成，但仍须写正确业务规则 | Java 并非天然杜绝漏洞，TS 也能实现严格隔离 |
| AI/引擎集成 | TS 适配代码便利，但引擎依旧进程隔离 | 经稳定协议调用引擎，算法和运行时可用其他语言 | 引擎独立升级后，同语言的重要性进一步降低 |
| 流式消息与并发 | 异步 I/O 适合网络等待；CPU 重活不能阻塞事件循环 | 可使用异步请求/流式响应及合适的线程模型 | 两者可做；数据库、模型服务、并发策略需实际测量 |
| 长任务与重试 | TS worker 可用 BullMQ；任务事实独立持久化 | Java worker 或通过可靠任务提交协议交给引擎；调度另定 | 任一框架都不自动提供业务幂等和长任务恢复 |
| 文件与算法计算 | 放独立工具进程，必要时用 Python | 同样可放独立工具进程，也有 Java 文件处理库 | 首批文件样本比后端语言更影响难度 |
| 开发与发布 | Node/npm/TS 构建链；需要依赖更新与边界治理 | JDK/Maven/JVM 构建链；需要配置、依赖和运行参数治理 | 不预设某条路线必然更快，按现有工程与维护者判断 |
| 运行成本 | 与依赖、进程数、负载和配置有关 | 同样取决于实际负载与配置 | 本轮无基准，不编造内存倍数或月费差额 |
| 接手维护 | 更适合希望统一 JS/TS 的维护者 | 更适合已有 Java 工程经验的维护者 | 当前尚未指定团队，不能拿假定招聘情况作定论 |
| 已有资产 | 当前网页可复用；会新增第三类业务后端技术栈 | 9POP 的工程模式可参考，仍须新建多企业业务模型 | 属于项目组合层面的取舍 |

Spring 的[事务管理](https://docs.spring.io/spring-framework/reference/data-access/transaction.html)、[安全体系](https://docs.spring.io/spring-security/reference/servlet/architecture.html)与[运行监控](https://docs.spring.io/spring-boot/reference/actuator/index.html)提供相应基础；NestJS 的[输入校验](https://docs.nestjs.com/techniques/validation)和[队列集成](https://docs.nestjs.com/techniques/queues)同样可用于这些场景。对本项目适配优劣的判断属于工程建议，官方能力说明不等于项目性能对比。

Node 官方强调避免阻塞事件循环，见[并发设计说明](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)。因此无论选哪种 API 框架，本方案都将耗时解析和算法计算移入独立工作进程。原生端和 AI 长连接也都要处理重连、补取和背压。

### 9.3 选择依据与最终决定

结合“引擎独立升级、前端可重制、平台长期维护”和已有 9POP 工程，建议调整为 **Spring Boot 业务平台＋独立引擎服务**，用户随后明确确认，并决定前端继续沿用 React。选择依据是现有工程经验和平台职责；Java 没有独占多端或企业能力。

NestJS 的统一 TypeScript 开发优势作为比较依据保留，当前不再作为并行待选主后端。系统采用一套 Spring Boot 主业务后端。

群力已有 FastAPI/PostgreSQL/文件协作工程，可作为文件处理、算法和工程模式的参考；Python 不再作为本项目待选主业务后端。若抽取相关能力，需单独评估通用部分；本轮只核对元数据，不能承诺整套搬用或给出节省工期。FastAPI 支持异步 I/O，见[官方说明](https://fastapi.tiangolo.com/async/)。

选择 Spring Boot 不意味着复制 9POP 的 MySQL 及门店权限模型。本项目仍建议独立 PostgreSQL、对象存储和租户设计。API/引擎通过可靠提交、任务 ID、幂等与状态查询衔接；如果执行端使用 BullMQ，由其适配服务管理队列，不让 Java 依赖 BullMQ 私有 Redis 数据结构。

下一步按已确认路线完成工程基线和引擎契约，随后贯通数据库、登录、文件、任务与真实会话的最小工作流程。具体 JDK/Node/框架版本在实施前按维护状态和兼容性选定，不直接复制旧项目版本或盲目追最新。
