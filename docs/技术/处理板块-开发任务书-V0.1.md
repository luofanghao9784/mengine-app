## 1. 目标与责任

处理板块根据用户请求、已生效的基础职责/场景策略或获准持续目标，形成当前任务，分析资料、发现相关问题与机会、生成成果，并通过工具执行已授权动作；向输出交付成果、依据、实际执行结果、限制和任务状态。目标可在获准探索和互动中逐步形成，不要求用户先配置完整业务目标。分析、建议和执行可出现在同一任务中，不要求拆成三个模型或三套服务。

建议明确当前目标及来源、授权、资源与完成责任，记录目标调整，保留模型自主选择方法的空间。资料检索、经验调用、规划、工具执行、检查和改写可以按需要交替进行；简单问题可直接回答，不强制所有任务走一套步骤或生成多份候选。

- 输入提供当前可访问的数据、确切版本与缺口；处理判断这些依据是否足够支持当前目标，必要时继续读取。
- 平台持有身份权限、任务与尝试、成果版本、实际回执；独立引擎经版本化接口运行，不直接操作业务数据库，也不能自行扩大执行身份。
- 输出负责受众、表达、排序、交付与反馈；任务若明确要求发布或发送，处理须追踪相应交付回执，不能在“内容生成”时就宣告整个目标完成。能力按现有接口复用，不建设两套发送器。
- 一次任务内调整计划、尝试其他工具及获准记忆维护属于基础运行；独立自进化后续改进跨任务共享方法，停用自进化不影响正常任务。

### 2.1 Harness 已有能力与平台待接入的区别

2026-09-29 用户追问后补充：上表中的缺口指梦核当前业务链路未提供完整能力，不代表 Harness 缺少底层机制。先核对和复用框架，再补适配与产品规则，不预设重新开发一套 Agent 循环、会话日志或恢复引擎。

本机实际安装的 `@deepseek-ai/dsh-agent`、`agent-loop`、`session`、`session-persistence`、`user-approval` 均为 `0.1.5-rc.2`，与锁定版本一致；本轮只读核对发布包说明及类型，没有升级或运行恢复试验。

| 能力 | 固定版本 Harness 已有机制 | 梦核仍需接入或定义的部分 |
| --- | --- | --- |
| 继续交流与途中补充 | `followup()`、`steer()`，Agent 收件箱与轮次机制 | 与产品会话/任务/目标版本关联，哪些补充改变目标、怎样反馈状态 |
| 等待工具批准 | `user-approval` 提供请求、决定、取消与审计；需要部署组合应答者，服务本身不展示人类 UI | 确认卡片、确认者权限、决定适用对象；长期等待及跨重启恢复另验，普通资料补充也不等同于工具审批 |
| 取消 | `cancel()` 与协作式中止；本项目已通过 AbortSignal 和 Agent cancel 接入 | 平台任务终态、停止传播及实际回执；已完成业务动作的核对或补偿 |
| 会话恢复 | `ctx.agents.resume()` 加载持久日志重建 Agent，需挂载持久化后端；支持处理中断轮次的日志收尾 | 任务/尝试与 Harness 会话映射、隔离存储、恢复前权限及业务条件检查；不等于任意外部进程原地暂停/续跑 |
| 请求重试 | `agent/request-error` 提供处理模型请求错误并决定 retry 的接口 | 是否启用及次数/费用限额；业务动作的去重和未知结果核对不由模型请求重试代替 |

本项目[Harness 适配器](../../engine/src/runtime/harness.ts)当前每次执行创建独立 Context 和随机会话，执行后释放；已使用 `followup()`、`whenIdle()` 和 `cancel()`，未挂载会话持久化/审批服务，也未接入 `resume()` 或 `steer()`。安装或锁定某个包不等于已启用其功能。Harness 会话持久化与平台任务记录各有职责，接入时映射统一身份与结果，避免两个系统各自决定业务任务成功。

产品会话是交互容器，可包含多个业务任务；一个业务任务可跨多轮交互和执行尝试。Harness 会话用于执行上下文与事件，不能未经设计就与产品会话或业务任务一一等同。第 5 节讨论的是业务任务的状态语义，其中运行能力应优先由上述框架机制承接。采用和恢复保证以固定版本实际验收为准，不将最新上游文档的能力自动视为当前集成事实。

## 3. 每项任务最少明确什么

| 信息 | 作用及来源 |
| --- | --- |
| 目标与交付 | 用户请求，或系统依据生效职责/场景策略形成的问题、草稿、文件或动作目标；说明目标来源及必要完成条件，用户无需预先逐项配置 |
| 发起与责任 | 用户请求、获准探索、事件或时间条件；企业、执行身份、责任及作用空间由平台提供 |
| 可用依据 | 指定资料及版本，或允许检索的范围；上下文、经验和公开资料按需取得，来源限制随输入传递 |
| 可执行范围 | 可用工具、读取/修改/发布范围、已有授权及仍需确认的事项；模型不能把目标本身解释为无限权限 |
| 资源与时效 | 当前生效的调用/工具/时间限额，必要的截止与优先级；默认配置可继承，不要求用户每次填写表单 |
| 关联与变化 | 所属会话/持续目标、请求与尝试关系、用户补充、采用的目标版本及成果版本 |

AI 可根据自然语言、已有配置与获准资料形成或补齐任务说明。只有缺失信息实质影响当前工作的关键判断或授权时才提问；尚无明确经营重点时，也可在生效策略内先开展有界探索，提出可解释的候选方向，而非一律等待用户设目标。可合理推定的低影响细节由 AI 决定并按需说明。明确授权在未改变的范围内继续有效，不因多次调用工具反复确认。

用户在运行中补充约束，应能关联原任务并调整尚未执行的工作；已完成动作与旧成果保留事实。目标、接收对象、资料范围或拟发布版本发生实质变化时，检查原授权是否仍覆盖；不能把旧确认套用到另一项动作。普通补充沿 AI-08—AI-10 支持自然语言和批量处理；重要权限或关键确认沿 AI-12 的明确确认卡片原则，具体动作分级留待管理专题。

## 4. 任务从哪里开始

建议让不同入口共用任务运行基础，而非各自维护一套引擎和状态。

| 入口 | 任务形成方式 | 边界 |
| --- | --- | --- |
| 用户会话 | 用户提问、要求分析、生成成果或执行动作 | 简单请求直接开展，复杂目标可由 AI 拆分；不强制先填完整计划 |
| 默认职责与冷启动 | 按已生效的基础策略、企业背景、职责和可用资料形成有限的初始分析 | 在既有权限/资源范围内先分析再校准，不要求每个候选先取得确认；策略范围可见、可调整及停用 |
| 已有任务继续 | 用户补充资料、回答问题、确认动作或要求修改 | 关联原任务和真实结果；恢复权限及条件需重新检查，不盲目重跑 |
| 获准时间或事件 | 约定周期、截止临近、相关资料更新触发一次检查 | 需要已生效目标/策略及执行身份，资料上传不自动授权无限后台分析 |
| AI 发现候选工作 | 在获准任务或探索范围中发现待办/机会 | 可记录建议；是否立即执行或成为持续目标按现有授权和预算判断，不自行设立永久职责 |

持续关注建议保存为可启停的目标，每次检查形成有结束条件的任务。事件先去重、合并，检查同事项是否已运行；记录自身动作的来源，避免“产出触发分析、分析再触发产出”的循环。此次检查未发现值得行动的变化，也可正常完成，不要求每次都生成画报或通知。

交互任务、已承诺截止工作、后台维护与探索按优先级、期限和资源分配；后台工作不能无限挤占交互资源，也不应永久饿死。具体调度算法、频率、额度、关注目标维护和首版触发范围在后续轮次细化，本轮不确定统一分数或固定周期。

### 4.1 系统目标：来源讨论与组织建议

来源：用户指定的任务《探讨梦擎的数据处理目标》，会话标识 `01a0ebd0-32aa-71e0-8431-e2a254c1d534`。2026-09-29 已完整读取其两轮讨论。用户明确提出：仅有企业背景和用户职责可能处于冷启动，应借助用户交互、流程设计、初始规则与行业经验库增强主动能力；本轮要求结合当前任务书主线考虑并入。默认职责表述、四层划分、首轮体验和验证方式来自该会话助手建议，本稿将其整理为待讨论方案，不直接升级为用户已确认的完整设计，见 DEC-086。

建议的默认职责是：**在获准范围内让资料保持可用，帮助用户理解变化，发现与工作有关的问题和机会，并推进已有工作目标。** 这既覆盖基础整理，也保留主动发现价值的空间；不把营收增长、利润最大化或内容数量设为所有企业共同的经营目标。

| 目标层次 | 来源与作用 | 如何形成和调整 |
| --- | --- | --- |
| 基础职责 | 生效的系统初始策略：资料可用性、关联/缺口/冲突、重要变化及工作相关发现 | 用户不必逐项填写；可见范围、资源和启停由平台配置，具体初始清单与默认开关待收口 |
| 场景关注 | 企业背景、已确认职责、空间用途、工作阶段及行业方法提供值得调查的方向 | 以候选/适用条件表达，可先在授权内核实；行业常见问题不直接认定为本企业实际问题 |
| 业务目标 | 有权者表达的重点、取舍和承诺，或从获准资料中取得的明确意图 | AI 可提取或提出建议，已有意图不要求重复输入；缺少依据的重大取舍保持候选，按范围由有权者明确 |
| 具体任务与子目标 | 围绕前述来源，由系统推演当次要调查、生成或执行的工作 | 形成可解释目标与结束条件，在既有授权内自主开展，随新依据和用户纠正调整 |

四层用于理解目标来源，不强制建立四套实体或依次通过四层审批。用户的一次提问可直接成为任务；候选问题可以先分析，不必先升级为正式业务目标。企业、空间和个人目标按作用范围与来源处理，冲突会改变重要取舍时明确呈现，不让最近一次点击或模型推测覆盖已生效方向。

例如同样出现业务量下降，系统可先核对口径和变化构成；在不知道企业当前取舍时，不直接宣布经营恶化或建议扩张。已有利润、交付质量或增长目标时，再判断该变化与目标的关系；必要时呈现不同解释及待补依据。

### 4.2 冷启动：先开展有限工作，再通过互动校准

以下为初始体验建议，不固定成所有任务必经流程：

1. **使用已知背景。** 从已有企业/空间/用户资料和当前授权取得必要上下文，可选地表达当前重点；不要求先填完整画像或目标管理表单。
2. **判断能做什么。** 查看获准资料的实际字段、时期和质量，按需检索相关行业方法。只有背景而无业务资料时，可先整理方法、准备工作模板，或在公开检索已获准时核对公开信息，再说明具体资料需求；不伪造已观察到的企业问题。
3. **做少量有依据的工作。** 在已有探索策略和预算内形成并核实候选，不逐项等待用户先批准；范围、深度和停止条件有界。没有适用经验时继续使用基础方法；没有有效发现时可结束。
4. **围绕成果获取反馈。** 提供来源、限制和必要的问题，让用户表达“继续关注”“这是主动调整”“当前更重要的是另一件事”等；只询问能改变当前判断或后续方向的问题。
5. **分别更新上下文和目标。** 事实纠正、表达偏好、本次任务要求与持续关注分别记录。用户未回应不算认可，单次点赞不自动成为永久目标；明确持续关注的表达按其作用范围及现有授权生效，无需重复确认同一决定。
6. **在后续资料中体现校准。** 使用新的企业证据、明确重点及纠正记录调整调查方向，保留来源及生效记录；更新不足或存在冲突时保持不确定。范围扩大、重大业务取舍或额外外部动作仍按对应授权处理。

这属于基础系统的正常目标形成、上下文维护和任务运行，不依赖独立自进化。未来自进化可优化初始策略、方法选择及互动方式；它不代替企业决定重要经营取舍，也不自行扩大数据或行动权限。

管理专题已在[第 13 节](三端管理与共用平台-开发任务书-V0.1.md#13-企业初始化与-ai-工作配置)补初始化交互和 AI 工作配置建议：按范围启用基础工作辅助、明确任务/持续关注/有限主动发现分别启动、配置和计划以实际保存为准。具体默认策略仍待确认，本轮没有启用任何实际后台工作。

### 4.3 经验库及跨板块任务

冷启动不应等待本企业先积累大量成功会话。经验库可从少量经核对的行业/岗位方法起步，说明适用场景、所需资料和口径、分析方法、反例/失效条件及能支持的结论范围。方法参考、待验证假设和有结果证据的成功案例分别标注；通用方法不伪装成当前企业事实，跨企业来源继续遵守授权与去敏规则。无需首期建成所有行业资料库。

| 板块 | 并入当前主线的任务 |
| --- | --- |

## 5. 任务运行、等待与结束

下表定义需要表达的业务含义，不是已实现状态枚举，也不要求每个任务逐项经过。底层运行优先复用第 2.1 节 Harness 能力；实现时决定哪些使用任务状态、等待原因或子动作状态表达，保持现有契约兼容。

| 情况 | 需要表达的含义 | 后续动作 |
| --- | --- | --- |
| 排队/运行 | 已接受目标，正在等待资源或执行获准工作 | 能说明当前实际阶段；网页关闭不等于取消云端任务 |
| 等待补充或确认 | 缺少必要资料、关键选择或该动作的授权 | 说明缺什么、由谁处理及影响；不反复调用模型等待用户；其他不依赖该项的工作可继续 |
| 用户暂停 | 暂停后续执行，保留已完成事实及可用进度 | 在安全边界停下并记录实际停机结果；恢复时复核权限、版本和时效，不能保证任意工具原地续跑 |
| 完成或部分交付 | 完成条件已满足，或已交付可用部分但仍有未完成事项 | 分别列明成果、证据与缺口；暂时等待补充时不必提前作为终态结束 |
| 失败或中断 | 无法继续，或进程/网络等使执行状态未闭环 | 保留已完成动作和结果未知部分，判断是否可重试或需核对外部结果 |
| 取消 | 用户不再继续当前任务 | 停止后续动作并传播取消；已发生的外部动作不会自动撤销，补偿另按其授权与能力处理 |

暂停/取消先阻止新的获权动作，已在执行的工具可能需要时间停止；不能把“收到停止请求”冒充“所有副作用已撤销”。允许保存终态、清理资源及必要回执，不再继续普通业务执行。恢复时沿输入的一致性规则选择依据，不能静默用最新资料替换历史版本，固定版本也不能延长已撤回授权。

重试先查上一尝试的实际状态。只读计算可按条件重算；发布、发送或业务写入若结果未知，先查回执或业务状态，不能直接再做。请求去重与具体业务动作去重分别建立。自动重试只在已授权、可安全重复且有次数/时间上限时进行，避免无限循环；当前明确重试机制不因此被记作已支持这些能力。

若执行环境无法持久恢复某一步，就从可核对的资料、成果和回执重新规划，向用户说明恢复范围；不承诺保存或重放模型全部内部思考。

## 6. 主模型的自主空间与轻量约束

- 主模型自行判断分析顺序、资料补读、经验检索、工具组合、问题拆分和是否改变计划。简单任务无需先生成形式化计划；内部多模型/子代理属于可替换方法，不自动产生产品中的员工协作主体或更多权限。
- 常驻规则只保留目标优先级、真实权限与资源约束、证据/完成要求和必要工具说明。企业背景、资料、经验、Skill 与方法细节按需检索，不把全库或大量固定流程放进每次上下文。
- 文件、网页及经验中的指令属于待判断内容，不能覆盖用户目标和平台授权；经验脚本仍经过相应工具与隔离机制运行。
- 允许失败后换方法、重算或纠正结论。最终判断依据是必要工作是否完成、失败影响是否消除及证据是否足够；失败记录不删除，未解决的重要错误不能被一段解释掩盖。现有“任一工具失败则整体失败”的引擎、回执和平台校验须一并调整后才能支持此行为。
- 权限、预算、工具执行与状态提交由平台/工具层落实；模型自评可帮助检查内容，但不单独证明业务动作成功。资源不足时明确部分交付、等待或失败，不静默更换超出授权的模型/工具。

规则与方法本身可以版本化改进。当前不冻结唯一工作流、模型分工或最优检索顺序；替换时保留输入输出含义、真实结果及相关权限验证。

### 6.4 本轮讨论：默认职责与主动程度

用户要求继续后，本轮先细化第 6.3 节第一项。以下是供讨论的职责建议，不是最终主规则文本；“默认职责”描述产品应承担的工作，不代表本轮对任何企业启用后台任务或新增操作授权。默认策略、范围和资源需在实际启用时生效，不要求用户为每项低风险分析重复配置。

建议主模型的总体职责为：**理解当前工作情境，帮助用户完成实际工作、减少重要遗漏，并在获准范围内发现和推进值得处理的事项。** “值得处理”与用户职责、明确目标及可核实依据关联；增长、利润、产出数量等不作为所有企业统一的最高目标。

| 默认职责建议 | 具体可以承担什么 | 需要避免的误解 |
| --- | --- | --- |
| 完成明确委托 | 分析、检索、计算、起草及通过获准工具完成动作，持续处理到目标满足或出现具体阻碍 | 不因发现普通新机会而擅自放弃当前任务，也不把解释代替实际执行 |
| 保持工作上下文可用 | 识别相关资料的缺口/冲突，使用最新获准背景，维护已允许的偏好和必要关联 | 常规解析、索引和同步可由程序/专项能力承担，不要求所有输入先调用主模型；普通整理不隐含删除或共享权限 |
| 跟进已有责任与承诺 | 按有效目标/计划关注待办、截止和依赖，检查已约定事项是否需要继续 | 一句讨论或模型推断不自动变成企业正式承诺；调度由实际保存的计划驱动 |
| 主动发现问题与机会 | 结合当前资料、行业方法和工作场景调查相关变化、异常、遗漏及改进可能 | 弱线索可以用于探索，但候选和已核实发现分开；不为了展示活跃而持续制造建议 |
| 帮助形成和校准方向 | 用小规模实际成果及必要互动帮助用户明确关注，吸收纠正并调整后续工作 | 未反馈不等于认可，个人表达不自动改变全企业目标，重要经营取舍保留有权者的意图依据 |

这些职责可在同一任务中共同发挥作用，不是五个固定步骤、模型角色或物理模块。企业和岗位可采用不同的适用范围，已生效目标及当前请求为当次工作提供方向。

不同起点下的建议行为：

| 当前条件 | 可以怎样开始或继续 |
| --- | --- |
| 用户有明确任务 | 直接推进任务；资料不足时先完成独立部分，再补问影响后续判断的关键内容 |
| 只有企业/岗位背景，缺少业务数据 | 形成带适用条件的调查方向，准备模板、检查清单或资料整理方案；公开检索仅在已有授权和渠道内使用，不把通用认识说成企业事实 |
| 有业务资料，但没有当前重点 | 在已生效的探索范围内核对资料和变化，形成少量有依据的发现及相关解释，再通过反馈校准；不先要求用户填完整目标 |
| 有持续目标，但用户没有提问 | 依获准时间、事件或已保存计划跟进，每次运行有当前目标和结束条件；后台检查不默认变成对外通知 |
| 没有新变化或没有新发现 | 检查本轮约定是否仍需交付、期限是否临近；可以交付无新增发现的核查结果，也可以结束无须通知的检查，不制造内容 |

资源取舍建议：当前明确任务通常是本轮主要工作，已经承诺的期限和获准的重要紧急事项也需照顾；普通探索与维护使用相应额度，必要时排队或合并。对当前任务有实质影响的发现可及时说明，其他候选可另存后续处理，不随意改写原目标。具体冲突优先级在下一轮专题讨论，不先冻结一条覆盖所有场景的排序公式。

主动分析、内部整理、私人草稿和业务动作分别沿实际授权执行。已明确授权的业务动作可以自主完成，不要求每次再确认；缺少必要授权、超出现有资源范围或遇到无法自行解决的重要业务取舍时，才请求对应决定。可调查的范围、责任人与资源从平台取得，不能由模型通过措辞自行扩张。

**是否继续工作，需要有可解释的判断：**

- 目标尚未满足，且还有可行方法、新依据或可核实线索时，在剩余资源内继续。探索不要求预先证明收益；查证后排除问题也可能是有用成果。
- 等待用户资料或明确决定时，先推进不依赖它的部分，记录真正阻碍后续工作的缺口，避免重复询问或持续消耗模型资源等待。
- 等待时间/事件或外部结果时，保存等待条件与获准后续计划，由调度在条件满足时唤醒，不用无休止的对话循环维持任务。
- 本轮目标已经满足，或继续尝试不再增加有效信息时，交付结果及限制并结束。资源耗尽、资料不可访问或检查覆盖不足，应说明尚未完成的内容，不标记为“一切正常”。

具体重试次数、探索时限、候选数量与是否通知仍为可调方法，由后续策略和验收确定；判断继续的依据可使用目标相关性、可能影响、已有证据、进一步获得信息的机会及成本，不把模型自评或单一分数作为唯一依据。

未来验收补充（尚未执行）：无企业业务数据时仍能完成适用准备工作；弱线索允许调查但不伪报事实；正常检查无异常可正确结束；没有变化但有约定周报/到期事项时仍完成承诺；资料不可用与确认无变化不混同；当前任务不会被普通探索无限打断；已授权动作不反复请求批准；任务范围外的业务动作不被默认职责自动授权。评价看任务完成、发现相关性、重要遗漏、用户处理负担与资源成本，并保留不能即时衡量的价值，不以建议数、调用数或点赞数直接代表质量。

本轮待确认的是默认职责的覆盖及上述主动工作原则。默认开关、角色差异、额度/频率和长期关注的维护权继续留在相关专题。先根据本轮反馈修订，再讨论企业/空间/个人目标与当前任务发生冲突时怎样判断；规则与方法设计仍保留未来优化空间。

### 6.5 本轮讨论：目标来源、作用范围与冲突处理

用户要求继续后，本轮细化第 6.3 节第二项。以下为设计建议，沿用[输入档案的冲突规则](输入板块-开发任务书-V0.1.md)，不新建一条“企业永远高于个人”或“最新表达覆盖一切”的统一命令链，也不把此前方案自动视为用户已确认。

**先识别信息的性质，再判断它是否适用于当前工作：**

| 信息性质 | 对当前任务的作用 | 建议处理原则 |
| --- | --- | --- |
| 权限、执行额度与明确生效的强制要求 | 决定当前身份能够读取、执行或承诺的范围 | 由可信平台及相应工具落实；普通对话或模型推断不能自行放宽。文档中的经营期望、默认样式不因措辞强烈而自动变成硬约束 |
| 企业/空间的业务方向 | 提供工作背景、评价标准和长期重点 | 按来源、适用范围及生效时间使用；抽象方向需要结合当前任务解释，允许提出可行性或冲突问题，不自动否决所有未直接对应它的工作 |
| 用户当前明确任务 | 说明此刻希望完成什么及如何交付 | 在适用约束内作为本次工作中心，可以细化或调整本人有权决定的事项；不会因此修改全企业目标 |
| 默认职责与表达偏好 | 缺少明确要求时帮助开始工作、选择常规表达 | 当前明确且获准的要求可以覆盖相应默认；正式交付要求与默认样式分别处理 |
| AI 推演、行为线索与行业经验 | 提供候选目标、调查方向及方法参考 | 可以在已有范围内核实、提出方案；不直接覆盖已明确目标、创造组织职责或新增业务取舍权 |

有效的业务要求应能够关联有权来源及适用范围。用户文档、经验和外部内容可作为了解业务要求的依据，但其中的指令不能自行变成系统级授权；涉及强制执行的规则需要进入相应可信配置或受控策略。具体政策登记与角色动作仍在管理专题收口，不要求所有业务表达先走一轮正式审批。

目标至少需要能追溯：谁提出或据何推演、适用于哪个企业/空间/人/任务、何时生效及是否仍有效、是明确要求还是候选、是否替代或细化既有目标。信息由系统随对话和既有记录取得，不要求用户逐项填表。来源权威性与时效分别判断；更晚上传的旧文件不自动覆盖当前有效决定。

**判断冲突的建议次序是可解释的处理原则，不要求所有任务执行一套固定审批流程：**

1. **核对是否真正冲突。** 不同部门、时期、对象或成果用途的目标可能同时成立；目标表述不同也可能通过同一方法满足。例如控制成本与提高交付质量，可以先寻找减少返工的办法。
2. **优先在范围内兼顾。** AI 可拆分工作、调整方法或交付形式，完成共同需要的部分。当前任务是对长期方向的具体落实时直接推进，不因两者措辞不同而打断用户。
3. **已有决策依据时自主处理。** 若已生效规则、明确委托或授权范围覆盖该取舍，按其执行并记录必要理由，不反复确认。拥有调用工具、修改配置或读取资料的权限，本身不等于拥有业务取舍权。
4. **真正互斥且缺少决定依据时提出具体方案。** 说明冲突目标、可选做法、各自影响及建议，由相应范围的有权者决定；在此期间继续不受影响的工作，不擅自降低已承诺的完成标准或替用户放弃重要目标。
5. **权限或执行条件不满足时处理受影响部分。** 不执行被阻止的动作，说明缺口并提供可行替代；仍可开展其他获准分析。目标冲突不能借模型推理绕过平台校验。

企业管理员、工作空间维护者、业务负责人和当前任务发起者不是同一个权限概念。谁能制定企业方向、修改空间目标、决定当前任务取舍，需有相应来源或授权；不根据管理员身份、职位自述或模型判断自行补权。拥有决策责任也不自动获得私人会话或全部来源正文：冲突说明按其实际可见范围提供必要信息，沟通渠道和动作沿输出及授权规则处理。

| 典型情形 | 建议行为 |
| --- | --- |
| 企业强调提高服务质量，用户要求先整理本周交付清单 | 通常可兼容，直接完成当前任务，并按需要突出延期/返工等相关内容 |
| 企业默认简短摘要，用户要求本次详细解释 | 在没有适用强制格式要求时按本次要求交付，不把它改成全企业新默认 |
| 两项已承诺工作在当前时间和资源内确实无法兼顾 | 先核实实际依赖、期限和已有优先规则；缺少取舍授权时展示排期/范围等具体选择，保留未受影响的进展 |
| 用户更新本人有权决定的当前目标 | 更新相应任务或关注范围，保留变更依据；不自动影响其他空间、其他人的目标或全部历史成果 |
| AI 发现新机会，但当前用户正在要求完成交付 | 先判断是否影响当前交付；一般机会可形成候选，实质影响目标的发现及时说明，沿已有紧急策略处理，不私自替换整个任务 |
| 新资料与目标依据矛盾 | 核对来源和适用时间，说明可能影响；可以建议调整目标，不为维持旧目标而忽略证据，也不自动把新资料当作变更授权 |

目标改变后，判断哪些待执行动作、计划与成果需要调整。已经完成的动作保留事实；历史结论不自动重写，明确承诺不能无记录消失。只有实质超出原授权范围的变化才需要补充决定：同一任务内调整措辞或排版通常不使全部授权失效，接收者、关键承诺或重要内容变化则需核对覆盖关系；若原授权已覆盖该变化，无需重复审批。

主规则保存判断原则及何时调用相关能力，平台保存目标来源、作用范围、生效版本、变更和必要决定记录；具体记录结构、角色配置及冲突卡片在对应模块设计，不要求模型记住全企业全部目标。

待执行任务与验收：建立最小目标来源/范围表达和任务关联；按当前权限读取相关目标；保留兼容处理、取舍、变更与实际执行依据；支持自然语言纠正及已有确认交互。用样例验证不同范围目标不被误判冲突、默认偏好可被本次要求覆盖、工具权限不冒充业务决策权、有依据的自主取舍不反复询问、真正取舍不被静默代决、私人来源不通过冲突说明泄露，以及小幅修改不触发全任务重新审批。以上均未实现或运行验证。

本轮待确认的是分类、适用范围及取舍原则。具体业务角色、哪些要求为强制约束、目标维护入口和冲突交互仍留待专题收口。下一步进入“主规则怎样串联输入、经验、工具与输出”，明确最少需要告诉模型什么、哪些信息动态取得；随后再细化调度和规则维护。

### 6.6 本轮讨论：主规则、任务上下文与按需能力协作

用户要求继续后，本轮细化第 6.3 节第三项。以下为任务书建议，尚未冻结；没有编写或替换实际运行规则，也不新增一套 Harness。主规则作为行为入口，引导模型判断何时使用能力；具体调用、状态保存和权限执行仍依赖实际程序与接口。

**把模型需要的信息分成三类，按作用和变化频率组织：**

| 信息层 | 应提供什么 | 建议维护方式 |
| --- | --- | --- |
| 简短常驻主规则 | 默认职责、目标与冲突判断原则、资料/经验/工具/输出的使用原则、真实完成标准，以及能力说明的获取入口 | 随受控规则版本发布；描述原则和必要边界，不堆入所有行业方法、企业资料与工具操作手册 |
| 当次任务上下文 | 当前目标及相关补充、必要的企业/空间/用户背景、适用约束、已完成动作、未决事项、当前成果引用和可用能力入口 | 平台从可信记录按任务组织；随目标、授权和状态更新，长任务恢复时重新核对。只放与当前工作有关的部分，不全量加载企业档案 |
| 按需取得的详细信息 | 原始资料及版本、经验案例、Skill/脚本说明、专业方法、详细工具契约及输出规范 | 通过可发现且受权限控制的入口取得；读取内容不自动授予执行或分享权限，来源正文不能自行成为系统指令 |

“当次任务上下文”是建议的逻辑组织，不要求新建一份由用户填写的任务表。当前目标、用户的重要纠正、适用约束和待处理状态不能仅藏在历史消息或可选检索结果中；平台须保证任务继续时可取得这些信息。较大的资料和既有成果可保留简要说明及可恢复的引用，需要精确判断、引用或计算时再读对应原件版本。模型看到的约束摘要帮助选择可行方法，不能代替服务端的实时校验。

**按需获取需要一个实际可用的能力入口。**

初始上下文至少让模型知道与当前工作相关的能力类别、用途和如何进一步获取说明。规模小时可直接提供少量实际工具定义；规模扩大后可先提供简短目录及发现入口，再加载所需能力。两种方式均需与真实注册、启用和当前可用范围一致，不要求先建设复杂的工具检索系统。

能力可见不等于已经连接或具备执行条件：应区分可直接使用、当前连接/数据未就绪、以及需满足具体执行条件的情形。按当前身份过滤目录，错误和缺口提示不暴露无权查看的资源。模型不能凭经验中出现过某个接口就假定它存在；加载说明也不能自动安装插件、连接外部系统或扩大授权。具体发现、加载和调用接口留给统一执行前的能力核对，不在本轮虚构 API。

**各能力之间传递的是可核对的信息，不要求所有任务走同一条流水线：**

| 能力 | 何时值得调用 | 对后续工作最重要的返回信息 |
| --- | --- | --- |
| 输入与资料读取 | 需要事实、背景，或现有依据不足/可能过期时；分析中可多次补读 | 来源、版本、适用范围、已覆盖部分及缺口；区分无匹配、尚未解析、连接失败和无权读取，不能都解释为“没有数据” |
| 经验库与方法 | 陌生、重复、复杂或已有成熟方法的工作，以及需要检查常见遗漏时 | 适用前提、方法/案例及其依据、依赖版本与已知限制；无命中可以继续独立分析，不强制每次回复检索，也不把过去成功当作本次事实 |
| 工具执行 | 需要检索、计算、生成文件或执行实际动作时 | 实际调用对象与回执、生成的成果、失败原因或结果未知状态；模型依据结果决定继续、换方法或等待，外部动作未知时先核对而非盲目重试 |
| 输出与交付 | 已有可交付内容，或需要向用户呈现进展、补充请求和结果时 | 成果版本、依据与限制、拟交付对象/形式，以及实际发布或发送回执；生成草稿和完成发送分别判断 |
| 状态、反馈与评价记录 | 发生目标补充、实际动作、等待、成果或反馈等有意义变化时 | 与任务、尝试、成果版本关联的事实；程序能确定的状态和用量由程序记录，反馈可作用当前任务，归档经验与跨任务方法更新另按各自规则处理 |

上表是逻辑协作关系，不对应五套新服务或五次必需模型调用。资料解析、数值核验、权限过滤、常规排序/展示等可由适合的程序或专项能力完成；需要语义判断和改写时再调用模型。经验中的脚本须经实际执行能力和当前授权使用，不能把检索到脚本视为已经执行；执行对象、参数和接收者按当前任务取得，不能沿用旧案例的业务对象。能力说明应讲清回执能证明的范围：文件已生成，不自动证明平台已保存、空间已发布或用户已收到。输出即使复用同一成果，也要按各接收者的权限处理内容、引用和附件，不能依赖排版或删去引用来消除正文中的越权信息。

例如，用户要求“将这段文字整理成三条待办”，模型可直接处理并回复；需要的权限和状态仍由平台保障，无须查经验或生成候选池。用户要求“根据现有资料分析本周项目延期原因并起草汇报”，模型可读取资料、发现缺口、选择是否参考相关方法、补充计算并形成有依据的草稿；未核实的原因标明假设，只有任务另含获准发布要求时才执行发送并核对回执。输入、经验、工具可交替调用，步骤由具体工作决定。

**上下文精简应保留工作连续性。**

长任务可以压缩过程和裁剪无关资料，但需保留当前目标及其变更、用户纠正、完成条件、明确禁止事项和接收范围、有效授权依据、实际已执行动作、未决事项及关键成果引用。摘要不能覆盖权威记录，例如“起草但不要发送”不能压缩成“完成并交付”；容量不足时优先裁剪历史和方法细节，必要时分段处理。执行结果不能只存在于模型摘要中；恢复时以平台与工具的真实记录核对，并刷新能力可用状态，无法核对的外部动作保留“结果未知”。引用失效或权限撤回时说明受影响部分，不能用旧摘要绕过当前访问限制。

按需加载和上下文组织本身是可替换方法，可在后续评估中优化选择、检索、排序、摘要和加载时机。保留必要的规则/能力/来源版本及调用结果关联，评估任务质量、遗漏、额外调用、延迟与成本，不单以提示词更短作为优化成功。正常任务内的补读、纠正与上下文维护不依赖独立自进化；规则跨版本发布及运行中切换另在维护专题讨论。

待执行工作：核对已有能力及真实契约，确定最小常驻规则和任务上下文组成，提供可用能力入口及按需说明，将资料/经验/工具/输出返回结果接入现有任务记录，并保证长任务继续时不丢失目标与实际进度。优先复用已有 Harness、工具注册和日志能力，仅补业务适配缺口。

验收建议：简单工作可跳过经验库；复杂工作可发现并正确使用未预加载的能力；无命中、未就绪、失败和无权访问得到不同处理；经验中出现的未注册工具不被伪装成已调用；加载说明不改变权限；任务压缩或恢复后保留目标纠正与真实动作，不因摘要遗漏重复执行；同一成果面向不同用户交付时分别检查内容权限；发送失败不被报告为交付完成。以上未实现或运行验证。

本轮形成能力协作与上下文组织建议，具体工具注册方式、字段结构、加载预算及物理文件拆分留待技术收口。下一步讨论“调度的模型与程序分工”：谁决定值得做什么、谁负责唤醒和排队、模型如何维护后续计划，以及等待/恢复/停止怎样与任务生命周期衔接。

### 6.7 本轮讨论：调度的模型与程序分工

用户要求继续后，本轮细化第 6.3 节第四项，承接[主动调度讨论稿](梦核引擎-主动调度与自进化机制讨论稿-V0.1.md)。以下为设计建议，未启用后台任务、定时器或真实模型调用；不将全部建议自动纳入同一交付版本。

**持续关注、调度计划和实际运行分别管理。**

| 对象 | 说明什么 | 生命周期建议 |
| --- | --- | --- |
| 持续目标/关注 | 为什么持续处理、作用范围、来源/维护责任、有效期和结束条件 | 可以关联多次运行；一次检查完成不等于关注结束，无反馈也不自动生成永久关注 |
| 生效调度计划 | 在什么时间、事件或条件下处理，获准执行到哪里，资源范围及何时失效 | 保存明确条件和版本，可在授权内调整、暂停或终止；只有平台已接受的计划才构成后续安排 |
| 本次任务及执行尝试 | 此次为什么启动、要完成什么、使用哪些依据、实际做到哪里 | 复用现有任务/尝试体系，表达排队、运行、等待及结束；失败重试不是新建一个长期关注 |

一次性请求通常直接形成任务，无须先建立长期目标或调度计划。这三个对象是逻辑责任，物理表结构和服务位置在技术收口时确定。持续目标可有多种触发条件，不需要维持一个永不结束的模型会话。

**由模型判断工作内容，由程序可靠执行已生效的安排。**

| 责任 | 主模型可以做什么 | 程序及运行框架负责什么 |
| --- | --- | --- |
| 开始工作 | 被唤醒后判断相关性、需要分析什么及完成方式 | 用户请求、获准事件或已保存计划发起首次运行；读取/解析/索引等确定性工作可直接执行，不要求先调用主模型 |
| 制定和调整计划 | 在已有目标与授权内选择检查时机、依赖、分析深度和后续步骤，说明必要理由 | 校验范围与可执行条件，持久化计划版本并返回接受/拒绝结果；按实际时间或事件唤醒 |
| 分配执行机会 | 提供影响、紧迫性、预计工作量及可延后部分的判断 | 按生效策略落实排队、并发、额度、最晚处理时间及公平性，不能仅因模型自报紧急就突破资源限制 |
| 执行与续接 | 根据真实结果继续、换方法、提出缺口或结束 | Harness 承接当次模型/工具循环及其可复用的恢复能力；平台关联任务、尝试、等待条件及真实回执 |
| 呈现和通知 | 判断成果价值、适合受众及是否需要及时告知 | 输出按受众权限和通知策略执行，保存真实交付结果；已运行检查不意味着必须推送一张画报或通知 |

模型提出“明天再检查”不等于安排成功；需要经真实接口保存并取得结果。计划未保存时如实说明，不对用户承诺已经安排。计划至少能关联目的和范围、责任/运行身份、触发条件、执行边界、期限/结束条件与资源策略；时间条件包含适用时区，事件条件指向实际支持的来源。资料范围和权限在执行时再次核对，历史计划不能延长已撤回的访问权。

平台按既定授权校验计划，并不要求每次模型调整都等待人审。已有授权覆盖的后续检查、资料补齐后继续、允许区间内的节奏变化可以直接保存；超出范围、增加未授权外部动作、改变明确承诺或提高资源上限时，才需要相应决定。增加临时子步骤、复制计划或新建关联任务不能规避原范围、有效期和共享资源约束。主规则描述调整原则，实际限额和生效计划由程序管理。

**触发与模型调用之间保留必要的程序判断。**

用户请求、资料/业务变化、截止与约定时间、缺少事件源时的周期核查，以及获准的有限探索，共用任务入口。首次部署的默认关注由已生效的场景策略和启用流程建立，不能等待尚未运行的模型“自行醒来”；不要求用户先配置完整业务目标。

平台先做能确定的检查，例如事件来源与版本、目标是否仍有效、是否重复、关联任务是否正在执行及资源是否可用。需要语义判断、无法排除重要影响或已有明确分析要求时，再调用模型；不能为了省调用而要求程序先证明存在业务价值。无法可靠判断相关性时可保留有限分析或按计划核查，也不能一律当作无关丢弃。

同一事项的一批变化可以合并，但需保留真实版本和处理覆盖；运行期间的新变化应成为本次获准补充或下一次待处理依据，不能因“已有任务”而永久丢弃。来自不同目标或授权范围的任务不因文件相同就直接合并内容。系统自身产生的资料/状态带有因果关联，阻止同一变化反复触发同一工作，同时允许确有必要的下游处理；不能简单屏蔽全部 AI 产物事件。

资源安排优先保护当前交互、明确期限及已承诺的重要检查，普通探索在相应额度内运行；保留防止长期等待的机制。重要目标发生真实冲突时沿第 6.5 节处理，不把全部场景固定为一条优先级公式。合并窗口、具体频率、额度、队列设施与排序方法留待统一设计；延后或漏检要保留原因和影响，不能以“没有异常”代替“没有执行”。

**等待、停止和恢复要明确作用对象。**

- 等待资料、决定、时间或外部结果时，保存真正的等待条件；不反复调用模型询问是否满足。能推进的独立部分继续，必要的外部轮询使用有间隔、期限和额度的程序机制。
- 暂停/取消本次任务，按第 5 节停止本次后续动作；不会无提示地取消所有长期关注。用户明确要求“以后不要再关注”时，应终止对应计划，并处理其已排队及正在运行的关联工作，防止旧触发重新启动。只在用户意图确实不清且影响不同对象时澄清，具体交互放入管理端专题。
- 关闭通知只改变告知策略，不自动终止分析；暂停持续计划阻止后续启动，并明确其对正在运行任务的作用。具体对象和实际停止结果应能查看，不使用一个模糊开关混合所有含义。
- 恢复前核对计划是否仍有效、当前目标与授权、数据版本、实际已执行动作和未知结果。复用 Harness 恢复能力并补平台关联；能力不足时按真实成果重新规划，不承诺任意外部工具断点续跑，也不盲目重复业务动作。
- 服务中断导致的错过触发，按任务性质补做：只需当前概览时可合并核查，每个期间都有独立义务的任务则保留相应缺口并逐项处理。不能重放全部旧触发，也不能一概跳过；具体补做策略须可查看和追溯。

取消和计划更新与排队/执行交错时，以当前有效状态校验新的动作，旧计划或旧尝试的迟到结果不能覆盖当前任务；并发修改计划须核对其依据版本，不能让较晚返回的旧方案覆盖用户的新决定。同一等待条件重复到达时只续接对应有效工作，避免重复启动整套动作；已经发生的外部动作保留事实。停止后允许保存真实回执、终态和清理结果，不将“停止业务执行”误写成“禁止一切状态写入”。

例如，用户要求“持续关注项目延期风险，先给我建议，不要发给团队”。计划可在相关进度资料就绪或约定检查时间启动，模型分析后交付给获准用户；缺少本周数据时保存缺口及后续检查条件，不持续空转。临近截止可在既定范围内调整检查节奏，无新发现时按交付约定选择安静结束或报告核查结果。停止此次检查与停止整个关注分别生效，生成建议不会自行触发对团队发送。

调整当前关注的后续计划属于基础运行，即使独立自进化停用也应正常工作。改变通用排序方法、跨任务调度策略或主规则版本属于方法维护，可由人工或后续自进化按评估和发布机制改进；模型不能通过普通计划接口改写全局硬约束。

待执行工作：复用现有任务/尝试与 Harness，补持续关注和生效计划的关联、触发接入、等待与唤醒、去重及覆盖记录、资源安排、明确范围的启停和恢复。三端只呈现各自有权管理的关注、计划、状态和必要原因；不因此新增管理端，也不向总台开放客户业务内容。

验收建议：模型未持续运行时计划仍能触发；保存失败不宣称已安排；范围内调整不反复审批，创建子任务不能绕开资源约束；一批重复事件不重复动作且执行期间新变化不丢失；自身产物不造成循环且合法下游能继续；无变化仍完成已约定交付；等待不空耗模型调用；取消本次、停止关注、关闭通知分别生效；撤权/终止后旧触发不启动新业务动作；中断恢复区分未知执行结果与未执行，并按各类任务补做错过的检查。以上均未实现或运行验证。

本轮形成职责和运行语义建议。默认主动策略的启用范围、长期关注维护权、具体频率/额度、暂停对在途任务的默认交互及首版交付范围仍待收口。下一步讨论“规则维护与评估”：规则和方法怎样发布、生效、试用与回退，以及换模型后怎样证明仍能正常工作；随后进入经验库细化。

### 6.8 本轮讨论：规则维护、发布、评估与回退

2026-09-30 用户要求继续后，本轮细化第 6.3 节第五项。以下为设计建议，承接[方法改进与独立替换讨论](梦核引擎-主动调度与自进化机制讨论稿-V0.1.md)。基础系统需要能由有权维护者更新方法并判断结果；后续自进化复用同一套版本、评估和生效机制。当前只形成任务，不修改运行规则、不开展模型对照或自进化实验。

**先分清维护对象，避免每次用户纠正都变成全局规则发布。**

| 变化对象 | 建议维护方式 |
| --- | --- |
| 当前目标、资料事实、明确偏好、任务计划 | 沿第 6.5—6.7 节及输入档案规则更新相关记录；在已有授权内作用于当前工作，保留来源、范围及必要的撤销能力 |
| 主规则、共享方法/Skill、上下文组织、检索/调度策略 | 作为可替换方法保存版本、适用条件和评估依据；变更是否试用及怎样生效，按影响范围和已有维护授权决定 |
| 模型、Harness/工具适配、平台代码、权限和资源配置 | 通过各自配置或研发发布机制维护，与方法版本记录依赖；方法更新本身不能扩大权限或替代必要的接口兼容验证 |

每次重要运行能够关联实际采用的规则、方法、模型标识及相关参数、工具/检索配置、来源版本和目标版本；按需要引用已有记录，不复制所有上下文或模型隐藏推理，也不承诺随机模型每次重放都输出相同文字。规则与方法可分别版本化，通过生效记录说明实际组合；不强制所有内容装进一个物理文件或每次共同升级。

企业/空间/个人配置只在相应范围生效，具体目标和业务要求沿第 6.5 节解释。全局方法维护权、企业业务规则维护权和个人偏好维护权分别定义，不能仅凭管理员身份推定其全部具备；维护通用方法也不自动获得客户内容。具体角色动作在管理端专题收口，沿用三端结构。

**共享方法变更建议使用以下路径，验证深度与影响相称：**

1. **提出候选。** 说明观察到的问题、依据、拟改对象、预期改善、适用范围及可能退化；先区分数据缺口、工具故障、错误目标和方法问题，避免全部通过增加提示词处理。候选尚未生效。
2. **与基准比较。** 提前确定比较样例、完成标准和评价口径，按同一目标、资料版本、可用工具与资源条件比较新旧方法；尽量隔离有意义的改动，多项协同改动则作为一组记录，不能把效果归给其中一项。并行候选及共享经验/索引变化应能隔离或明确记录；无法控制同时发生的变化时，说明归因限制。
3. **按需要限定试用。** 先限定场景或获准范围。需要影子运行时，候选只生成可比较结果，不执行真实发送、发布或业务写入；比较执行行为使用隔离环境或记录回放，不能让两套方案重复操作真实业务。正式试用也须明确同一业务动作由哪个有效任务/尝试执行。影子运行同样受数据访问和预算约束。
4. **按已有权限启用。** 保存采用哪个版本、对谁生效、从何时开始、观察什么及何种情况停止。已有授权覆盖的小范围调整可以直接处理，不要求每个微小变化重复审批；扩大范围或改变重要约束时再取得相应决定。
5. **观察并处理退化。** 对比真实任务结果和成本，按预先明确的条件停止扩展、停用候选或回退。低风险个人偏好和普通任务内纠正沿既有维护流程执行，不机械经过完整共享发布流程。

以上是可复用的职责和证据要求，不要求首版先建设复杂实验平台。具体样例规模、阈值、试用期限和自动程度在评估、管理及全局范围专题确定。

**评价围绕实际工作，并与改法生成保持必要区分。**

- 能由程序或外部结果核实的项目，使用实际证据，例如数值、来源定位、工具动作、权限和完成状态；相关性、表达质量、重要遗漏等结合明确标准、人工抽样和经校准的模型评判。模型自述“更好”或单个评判分数不足以证明提升。
- 同时观察任务完成与关键遗漏、事实/执行正确性、用户修改与处理负担、耗时和资源成本；按场景查看差异。平均改善不能抵消越权、重复业务动作或关键义务遗漏，提示词变短、调用减少、产出增加也不单独代表成功。
- 保留未参与候选调优的样例和反例，不能只用促成本次改法的成功案例验收；对关键或波动较大的结果进行必要重复比较并报告差异。模型评判需检查偏差，尽可能遮蔽新旧标签，重要分歧由适当人工核对，不强制每个普通任务都增加一次评判模型调用。
- 评价标准、样例和评判方法也需要版本及适用范围。AI 可提出改进评价系统的建议，但不能在同一次比较中自行放宽标准或删除失败样例后宣称方法提升；业务目标确实改变时应明确更新评价版本，并重新建立可比基准。

“未参与调优”要求在候选生成与最终检查之间保留实际数据边界；固定样例被反复用于修改后会失去这项作用，需要按评估计划补充新样例。评估数据同样遵守原有企业/空间权限，脱敏不自动获得跨企业复用权。无法从样本证明长期经营效果时，保留尚未验证的范围，不把满意度或短期变化冒充因果结论。

**发布与回退应说明对哪些任务生效。**

建议普通方法更新优先作用于发布后开始的新任务，运行中的任务保持可追溯的一致组合；等待或暂停后恢复的任务，按兼容性选择继续原组合或在明确记录迁移后重建上下文，不把新旧规则无记录混用。长期关注的后续运行可采用届时适用的新版本，当前目标和已作承诺仍需保留。

权限撤回、工具禁用和必须立即停止的缺陷不受上述版本固定限制，应及时阻止受影响的新动作，必要时暂停在途任务。回退通常恢复兼容且仍获准的旧方法组合，或转到已验证替代方案；同时核对受影响的排队任务、后续计划和在途工作，防止坏版本生成的安排在切换后继续执行。

回退方法不撤销已发送内容、已完成业务写入或用户决定。对受影响成果、待发布内容和执行结果保留版本及事实，识别需要复核、更正或补偿的事项，按其权限处理，不自动删除历史或重放动作。旧模型停用、接口变化或依赖缺失时，原版本可能已不可运行；不能承诺任意时刻原路回退，应记录已验证的替代方式，暂时没有可用方案时明确暂停受影响能力。

**更换模型同时检查方法是否仍然合适。**

比较可分两步：先在相近条件下观察模型更换本身的影响，再调整确有必要的规则和方法，分别记录结果。旧模型需要的长提示词或固定步骤可能不再有帮助，可通过适度删减的对照检验；保留目标、权限、真实结果和交付标准，允许模型采用不同的有效解法，不以是否复刻旧模型的每一步作为正确标准。

验证覆盖相关任务质量，也覆盖工具调用、结构化交接、长任务续接、取消/失败处理、延迟与用量记录等依赖。模型标识相同也不意味着服务行为永远不变，应记录供应方可取得的版本信息并结合运行信号发现退化；无法锁定底层版本时说明可复现性的限制。不要求每次小改都重测整个系统，按受影响范围选择验证，涉及共享基础能力再扩大覆盖。

待执行工作：梳理现有版本/发布记录，建立最小方法版本和实际组合关联、候选与生效范围、与共用评估模块的接口、在途任务切换原则以及停用/回退记录。基准样例、质量观测和发布依据归共用评估与运行能力，不在处理板块重复建设一套评测平台；自进化以后取得相应权限后接入。

验收建议：个人纠正不改全局规则；候选未启用时不影响真实运行；可以追溯实际方法组合；评测不重复真实业务动作，评价标准变化不伪装成方法提升；新任务/在途/恢复任务采用明确版本且撤权及时生效；方法回退不删除业务事实，旧模型不可用时有真实可行的处理方式；模型更换后允许有效的新解法，同时不丢失权限、工具和交付语义。以上均未实现或运行验证。

至此，第 6.3 节的五项专题均已形成讨论建议，具体业务选择、指标和首版范围仍待全局收口，不视为用户已逐项确认。原拟下一步进入经验库；用户随后要求深入讨论不同企业的规则差异、针对性评估及各板块自进化管理归属，先补第 6.9 节，再接经验对象、行业/岗位方法种子与历史案例。

### 6.9 补充讨论：多企业规则组合、评估范围与更新归属

2026-09-30 用户追问不同企业是否共用主模型规则、偏好如何单独维护、是否逐企业测试，以及经验库和其他板块的自进化由总台还是企业管理端处理。用户随后回复“可以的，继续下一步讨论内容”，认可共享基础规则、分范围配置/方法与评估、共用更新机制及三端分工的大方向，见 DEC-087。以下具体字段、权限动作、自动采用类别及参数继续待收口，不新增运行能力或自动采用权限。

**建议共享基础主规则，按任务组合企业差异，必要时扩展企业专属方法。**

| 组成 | 是否共用 | 维护与加载建议 |
| --- | --- | --- |
| 基础主规则 | 同一基础版本共用 | 职责、能力使用、证据/完成判断及目标处理原则由平台维护；不嵌入各企业全部背景和做法 |
| 行业/岗位方法及通用 Skill | 可选复用 | 有适用条件和依赖版本，按企业启用范围及任务需要获取；行业不同不要求复制整个引擎规则 |
| 企业背景、目标、正式业务要求与默认偏好 | 各企业维护 | 分别记录性质、来源、适用范围和生效状态；常用关键要求及时提供，其余按需取得 |
| 空间要求、个人工作上下文与偏好 | 对应空间/个人维护 | 保存相对适用默认的差异及必要来源，遵守内容权限；同一账号切换企业不串用工作记忆 |
| 企业/空间专属方法扩展 | 必要时独立维护 | 对独特口径、操作方法或场景要求形成有版本的增量资产，记录与基础规则/通用方法的关系，不默认整份复制分叉 |
| 当次任务与当前执行条件 | 每次动态取得 | 明确当前目标、接收者、实际状态及可用权限/工具，不因选定旧规则而沿用失效授权 |

这是逻辑组合，不是将六份全文拼接进每次提示词。不同企业可以使用同一基础版本而具有不同有效上下文；试用和升级期间，也可能采用不同但仍受支持的版本组合。应能解释某次运行采用了什么及原因，不要求所有企业在同一时刻升级。企业差异通常是可管理的配置和方法，不需要每家维护独立代码分支。

“偏好文档”可以作为可查看、自然语言维护的呈现，但不是所有企业差异的唯一存储，也不要求人工维护一份长 Markdown。复用[输入档案第 8 节](输入板块-开发任务书-V0.1.md)：背景事实、目标、默认偏好、正式业务要求和平台权限分别有来源与更新规则。例如“周报先给结论”是偏好，“本季重点降低返工”是目标，“使用本企业确认的交付验收口径”是业务要求，某人能否发布仍由平台权限决定。AI 可协助整理草案，文本本身不自动产生授权或企业级生效。

组合时沿第 6.5 节判断性质和适用范围，不采用“后加载的文本覆盖前面一切”的机制。适用默认可以被有权的当前要求细化，实际业务约束不能被普通表达偏好覆盖；企业专属方法替换哪个通用方法、适用于什么任务须明确。全局升级不能静默覆盖这些差异，也不能把原本可调整的默认全部升为不可覆盖的规则。兼容冲突无法自行解决时保留可用组合或停用受影响方法，说明原因，不悄悄删除企业要求。

**评估按改变的对象、依赖与影响范围展开，不机械按企业数重复全量测试。**

| 改动 | 推荐验证范围 |
| --- | --- |
| 个人表达偏好或局部默认样式 | 检查适用范围、效果和撤销行为；不触发全平台完整评测 |
| 企业专属口径、方法、数据映射或共享工作规则 | 在该企业获准样例上验证相关任务、依赖和影响到的空间/角色；不把本企业有效当作其他企业有效 |
| 通用主规则、检索/推荐方法或行业方法包 | 先验证通用行为及代表性任务/配置组合，识别受影响的企业配置与专属扩展，补兼容检查和必要的定向回归，再按范围逐步启用 |
| 模型、工具契约或共享底层结构 | 覆盖相关语义、权限、数据/索引迁移和恢复能力，不能只验证接口字段；特有业务依赖另补企业内样例 |

代表性组合应考虑任务类型、资料格式、已启用能力和企业扩展等差异，不只按行业抽样。受影响配置的兼容检查可自动开展，费用较高的效果评估根据差异和风险选择；未覆盖的特有做法明确标记，不能假称所有企业已验收。即使主规则相同，不同企业的资料和任务也可能导致不同效果，因此仍保留范围内的实际效果观察。

企业专属评测使用该范围内有权访问的数据和运行身份；平台共用计算基础设施不等于总台操作者可以查看原文。对总台仅提供获准的技术状态和必要汇总，完整样例、提示词、向量内容和错误正文不能作为默认上报材料。企业管理员若没有内容权，只处理其有权决定的范围、资源和采用策略；内容判断交给相应获权维护者，不能因需要评审而自动授予阅读权。

**跨板块共用变更机制，管理入口按对象归属划分。**

主规则、经验、输入、输出和评估方法都可引用同一套变更记录：修改对象及性质、归属/作用范围、来源与差异、依赖版本、评估依据、谁可维护/启用、实际采用范围、停止/恢复方式。共用的是记录、授权校验、版本及发布机制；各对象保留专门验证，如经验适用性、输入映射正确性、索引权限与检索覆盖、输出受众和交付效果。涉及结构变化时还需明确派生数据重建、迁移和兼容恢复，不能仅回退提示词版本。

经验库尤其区分三件事：新增/纠正具体经验内容，修改企业自己的分类与适用规则，改进通用索引结构或检索算法。它们可能使用不同维护权、验证和生效范围。普通经验归档或索引刷新属于基础维护；自进化以后优化归档、检索和使用方法，不能借算法升级扩大经验可见范围或自动将企业经验发布为通用经验。

三端的具体矩阵见[管理端规划第 6.1 节](新架构下开发范围与管理端规划-讨论稿-V0.1.md#61-补充讨论跨板块更新与自进化管理)。平台总台管理通用能力和技术发布；企业管理端管理本企业业务配置、专属优化与获准采用策略；客户端承接个人偏好及获权的空间/内容维护。自进化执行可复用同一服务和工作队列，但每项任务有明确身份、范围、数据与资源约束，不需要每个端各建设一套独立自进化引擎，也不要求每企业部署一个常驻模型。

提出候选、读取评估资料、运行试验、决定业务变更、发布可用版本、在指定范围启用、停用/恢复是不同动作；可由同一主体承担，也可在已有授权内自动完成，不机械增加多级人工审批。具体权限组合后续设计，不把现有企业或平台管理员直接升级为全部动作的有权者。

**平台发布与企业采用分别记录，但复用同一变更依据。**

例如总台发布新的检索方法：先验证通用效果与兼容性，再按企业实际配置检查其依赖，必要时在企业权限内比较召回结果；已有采用策略覆盖的兼容更新可以自动启用。若同时改变某企业的经验分类、业务映射或资料发送范围，应拆成相应企业变更，取得必要决定。无需每个兼容补丁都让客户点击批准，也不能把“通用版本已发布”当成所有企业已验证、已采用。

企业可在权限内停止本企业的可选优化或采用获准兼容版本；平台可停用有问题的共享能力。独立可选配置可按企业切换，共享数据结构或不可并行的组件升级则需平台统一安排迁移/恢复，不能承诺任意企业对所有底层组件单独回退。旧版本支持期限、强制缺陷修复与兼容迁移另立发布策略，不承诺永久锁定旧版本。

企业内得到良好结果的专属方法，默认仍属于原范围。推广为通用方法需要相应来源/复用授权、去除企业专有依赖及更广验证，不能通过复制提案或脱敏自动取得推广权。通用改进和企业自身优化可以并行，依赖冲突与切换沿第 6.8 节处理。

待执行工作：方法与配置标注作用范围/依赖，记录实际组合及企业采用状态，提供按影响选择评估的依据、范围内的候选/证据访问和相应三端操作；优先复用已有档案、经验、任务及发布记录，首版只做实际改动所需能力，不预建完整实验管理平台。

验收建议：两家企业共用基础规则仍保持各自目标/口径与偏好；个人偏好不改企业制度；企业方法不被通用升级覆盖或传播到别家；通用发布与企业采用可区分；兼容更新按既有策略执行，实质范围变化不被夹带；企业内评测不向总台暴露内容；经验内容维护与索引迁移各有真实验证；停用自进化后日常维护、发布及正常任务仍能运行。以上尚未实现或验证。

本节分层与分工方向已获认可，不扩大为此前所有目标/规则细节均已确认。待收口事项包括：首批可配置/可扩展对象、各范围维护权、自动采用条件、版本支持策略及企业专属评测的最小样例。接续进入第 8.1 节经验库细化，其检索/归档设计沿用本节的范围与管理分工。

## 7. 怎样判断完成，并交给输出

完成判断应与目标对应：要求草稿时，提供符合要求的草稿即可完成；要求执行动作时，需要真实执行结果；要求发布时，还需对应发布/交付回执。业务长期效果可能需后续观察，不能因任务执行成功就宣称经营改善或建议正确。

建议交给平台和输出的信息包括：任务/尝试及目标版本、成果和依据版本、完成范围、检查结果、未解决事项、工具及交付实际回执、拟交付范围和当前权限依赖。是否已交付、是否被采纳及实际效果分别记录，用户未反馈不视为满意。

可以确定验证的项目使用程序或外部真实结果，如产物存在、数值计算、来源可定位、接口动作回执；内容相关性、表达和建议质量使用适当评估，允许不确定结论。不要求每次简单回复再调用一个评判模型，也不要求用户逐项点击验收才能结束正常工作。

例：用户要求“根据现有资料整理本周项目进展，缺失项标明”，AI 可在资料有限时完成一份注明缺口的报告。若目标是“核齐所有部门后形成正式报告并发布”，则缺少部门数据时继续等待或部分交付，不能把草稿当完整完成。上传了新版本是否重做，按用户目标与输入一致性规则判断。

## 8. 经验库与反馈

经验库属于独立维护、按需检索的复用资产，不依赖某个模型的内部记忆。模型/检索实现更换仍需验证适用性和质量，不承诺换模型后所有经验都无需调整。

结合第 4 节冷启动建议，经验还承担帮助形成调查方向的作用，不能只收录本企业历史成功任务。少量行业/岗位方法可先行，但须区分方法依据与实际成功证据，并说明适用前提、输入需要和反例。

- 执行中可先检索经验摘要，再按需读案例、Skill 或脚本；无相关经验时继续使用获准资料和工具。只有当前任务必须依赖的能力缺失才构成阻塞，不强制每次回复都查库。
- 任务实际记录与“可复用经验”分开。高满意度只是候选信号，还需核对结果、适用前提、依赖版本和来源范围；失败与人工纠正也可帮助说明适用边界。
- 私人、企业和通用经验分别授权；清洗脱敏本身不自动授权跨企业复用。新增共享经验或脚本不因为来源任务成功就自动发布生效。
- 输出采集的会话/画报反馈关联任务与具体版本；区分事实错误、执行问题、目标变化和表达偏好，分别交给处理、输出或经验维护。正常纠正可立即作用当前任务，方法的跨任务自动优化留待自进化方案。

上述为前期接口边界。2026-09-30 从第 8.1 节开始细化经验库，后续继续检索、质量、清洗归档、发布/失效和维护；不把存下全量会话视为完成经验沉淀。

### 8.1 本轮讨论：收录对象、种子方法与最小使用闭环

用户认可第 6.9 节大方向并要求继续后，本轮进入经验库首个专题。以下为设计建议，尚未生成正式经验条目、归档用户会话、发布 Skill 或接入新的存储/检索服务。

**经验库保存可复用的做事依据与方法，资料库和任务记录继续保有原来的责任。**

原始文件说明当时的事实，任务记录说明实际发生了什么，经验条目提炼什么条件下可以借鉴哪些做法。经验可引用获准来源、成果和执行证据，不复制整段聊天或隐藏推理；企业实时数据、组织权限和当前目标仍从相应权威记录取得。用户偏好沿档案维护，不因重复出现就在经验库中另建一份互相覆盖的偏好。

**建议先支持四类可关联的内容，不必建设四套库：**

| 内容 | 收录重点 | 如何使用 |
| --- | --- | --- |
| 方法参考 | 要解决的问题、适用条件、所需数据、关键做法、检查要求及限制 | 帮助开始任务或提出调查方向；有依据的方法可先用作参考，无须伪装成已实测成功案例 |
| 任务案例 | 当时目标、条件、实际采用的方法、结果证据、人工修正及未验证效果 | 帮助判断某种做法在什么条件下有效；一次任务成功不自动证明长期业务收益 |
| 失败与纠正经验 | 可核对的错误、遗漏、不适用条件、修正方式及结果 | 帮助识别反例、检查前提和恢复；原因未确认时保留为假设，不以一次失败否定所有场景 |
| Skill、脚本及模板等复用资产 | 用途、输入/输出、依赖、实际版本、可执行范围或生成规范 | 引用能力目录或对应资产的受控版本，按当前任务选择使用；检索到代码不等于具备执行能力或授权 |

同一方法可以关联成功、失败和不适用案例，一次任务也可能组合多种方法。新增案例是补充证据，不直接覆盖已发布方法或 Skill；有改进价值时形成对应资产的新版本候选，沿第 6.8—6.9 节发布。经验条目优先引用已存在的工具、脚本和模板，避免相同代码在多个案例中形成无法同步的副本。

“案例完成”“方法经过验证”“用户满意”“取得业务成效”分别表达。例如员工修正了 AI 初稿后才完成任务，应记录修正点及最终结果，不能归档为原方案独立成功；后续效果尚未观察则保留未知。重复任务、重复引用或同一用户多次点赞不自动算作多份独立验证。

**条目的可信程度、适用条件、发布状态和可见范围分别管理。**

最少能回答：适合解决什么问题、需要哪些前提、具体可借鉴什么、依据是什么及验证到了哪一步、不能据此得出什么、依赖哪些版本、谁可以读取/维护/执行、何时需要复核。提取和结构化可由获准 AI 辅助，不要求用户手填全部字段；具体存储形式后续设计。

方法参考没有本系统实测案例，仍可明确身份供模型参考；经验证的案例也可能只适用于特定企业、资料口径和工具版本。候选、已发布、停用是生命周期，私人/空间/企业/通用是作用及访问范围，不能因为“验证成功”就自动扩大可见性。待验证的 AI 方法草案须标明候选和依据限制，不混成权威经验。

目录、标签、摘要和证据链接同样按权限提供；对来源的继续访问与独立发布副本分别沿既有资料规则处理。检索到方法不授予工具执行或对外分享权，也不将历史案例中的客户、路径、接收者和参数当成本次默认值；敏感原值不因案例成功而进入可复用模板。

**初始种子从少量适用方法起步，按实际任务补充。**

来源可以包括获准的企业操作方法、有来源且允许使用的行业/岗位资料、经核对的工具用法，以及已有授权范围内的真实任务记录。AI 可帮助整理和提出候选，但自身生成的做法不冒充外部权威来源或真实企业实践。引入外部材料时核对适用版本和使用范围，后续实施再确定首批来源与内容，不在本轮搜集或批量复制行业材料。

初期可围绕实际工作反复出现的资料核对、进度汇报、表格汇总等任务选少量种子，再增加企业专属方法；这些是候选方向，不冻结数量或首期行业名单。通用方法提供可能的调查路径，只有当前企业资料能支持实际发现；缺少数据时可以帮助准备清单或模板，不生成并不存在的企业问题。

收录价值要能说明，例如避免已知遗漏、复用已验证工具配方、保留特殊口径或减少重复试错。对模型已能稳定完成的常识性任务，不为增加条目数量而不断改写入库。后续在普通质量评估中比较采用经验与未采用时的完成质量、遗漏、耗时和成本，不能先承诺经验库必然更快更准；这不要求现在提前验证独立自进化。

**最小使用闭环建议如下，步骤按任务需要选用：**

1. 模型根据当前目标判断是否值得检索，取得当前身份可见的少量摘要及关键适用条件。
2. 判断数据、业务口径、工具版本和场景是否匹配；按需读取详细方法或证据。不适用时可补查、调整或不用，经验为空也能继续基本工作。
3. 用本次真实资料和当前授权执行，检查结果。方法参考可调整；已生效的正式业务要求沿相应配置执行，不因“参考方法”而被忽略。
4. 记录实际采用的经验及版本、重要调整、执行结果和相关反馈；区分检索命中、实际采用与效果证据。偏离方法本身不判为失败，以任务结果及必要约束判断。
5. 有复用价值的结果进入候选整理，提炼、核验及发布可在任务完成后异步进行，不让普通交付等待经验归档。哪些来源可自动提取、如何入库与发布在后续专题明确，不以满意度一项信号自动公开全量会话。

例如，一条“项目周报核对方法”可说明需要计划、实际进度和变更记录，并提醒区分事实与原因假设。某次任务缺少实际进度记录，适当结果可能是完成带缺口的汇报或请求必要资料；不能因为相似案例曾发现延期，就推断当前项目也延期。后来有人补充并纠正原因，该纠正关联本次案例，核实后再判断是否值得更新通用检查方法。

经验条目的获取、引用、日常纠正与获准发布属于基础运行；独立自进化以后优化提炼、分类、检索和使用方法。任务复用经验不要求先启动自进化；更新方法也不改变第 6.9 节的企业边界和维护责任。

### 8.2 补充讨论：标准结构、检索规模与使用后的维护

**规模目标是增加有效覆盖和可靠证据。** 更多独立、有依据且条件多样的经验可以扩大覆盖；重复、过期或错误内容也会增加检索和判断负担。库规模增长不保证效果单调改善，检索速度并非唯一限制，还需观察适用性误判、证据质量、时效及上下文负担。比较扩库前后相关经验能否找到、误用和关键遗漏、任务完成质量、检索/读取耗时、模型用量及维护成本，不单看条目数或命中数。

| --- | --- |
| 身份与结构 | 稳定标识、对象类型、内容版本、结构标准版本、关联方法/案例/资产；不同类型按需扩展字段 |

- 缺失分类不一律排除，必要时在授权内扩展查询。相似度和行业标签只提供候选，不能证明适用；排序不单靠热门程度，保留有效替代方法与关键反例。目录、摘要、片段和缓存均执行权限限制，不能先把越权内容交给模型再过滤输出。
- 实际采用前，程序检查可确定的状态与依赖，模型结合目标、数据口径和条件判断“可直接采用、需调整、条件未知、不适用”。判断可以融入已有分析，不要求每次额外调用评判模型，也不要求预先证明一定成功才允许探索。
- 当前仅有部分资料时，可以采用完整分析方法中的资料核对步骤，但不能给出只有完整资料才支持的结论。可补读、使用有效部分、明确假设或换方法。目标、关键依据或依赖实质变化时再核对相关条件，不对每个小步骤机械重复；自检通过不产生新权限。

**使用后的积累分成三类动作，避免经验正文无限增长。**

1. **使用事实：** 保留必要的任务/方法版本、适用判断、实际采用或调整、结果及反馈关联；区分命中、采用与有效证据。遵守当前授权与保留政策，不无限复制会话。
2. **案例候选：** 出现新条件、重要结果、失败、人工纠正或新的适用边界时，提炼独立案例；普通重复使用保留简要事实即可。业务效果尚未出现时保持待观察，不在任务结束时提前判断。
3. **方法维护：** 案例关联到当时使用的方法版本，推荐案例/统计可作派生视图。改变方法结论、适用条件、脚本或 Skill 时形成候选新版本，沿第 6.8—6.9 节核验和生效，不让一次满意反馈直接覆盖原文。

同一任务的总结、派生方法和后续引用保留共同来源，不能算成多份独立成功证据；热门程度不自动变成可信程度。新证据推翻旧判断时，在授权内标记限制、停用或提出修订，保留历史采用事实。企业或私人案例关联不自动扩大共享范围；独立案例如何清洗、发布及回溯影响在下一专题细化。

**两类库都预留方法改进能力，日常运行不依赖独立自进化。** 正常资料解析/更新、经验适用判断、使用记录和获准修订属于基础维护。自进化未来可优化分类、切分、摘要、索引、检索/重排、适用判断及经验提炼，也可提出结构标准升级，按范围评估后生效。

### 8.3 本轮讨论：候选归档、质量核验、发布与失效维护

2026-09-30 用户要求继续后，本轮细化经验从使用记录到可用条目、再到持续维护的过程。第 8.2 节的结构、算法和规模设想仍为研究建议；以下不构成已启用的自动归档或发布策略，也不读取/归档真实用户会话。

**先判断是否值得提炼，再判断是否可以发布。**

完成任务、用户明确推荐、关键人工修正、工具失败后的有效恢复、出现新条件或后续真实效果，都可成为候选线索，不要求必须先获好评。重复排版、重复使用已知方法等通常只需保留必要使用事实；新增证据可关联已有方法，不为每次使用复制新条目。差评也不直接证明方法错误，应区分目标变化、表达不合偏好、资料缺口与实际执行问题。

候选提取复用第 8.2 节使用记录，在获准来源、目的、范围和资源内异步开展。读取会话用于当前任务，不自动授权把私人内容提炼为企业或通用经验；来源是否允许提取、保留及发布需要由适用策略提供。提取失败不回写为原业务任务失败，正常交付不等待归档结束。

**候选整理应提炼可复用条件，并保留证据。**

1. 确定要整理的是新案例、既有方法的补充证据、失败/反例，还是方法修订候选；先查重复来源与已有条目，避免把同一次结果重复计数。
2. 提炼目标、必要背景、所用方法、关键调整和结果。去除无关对话及敏感原值，将可变对象改为有含义的参数；保留会影响适用性的时期、口径、条件和限制，不能清洗到无法解释为什么有效。
3. 关联必要的来源版本、工具/成果回执、人工纠正及后续反馈。区分实际观察、当事人反馈、AI 推断和未知事项，不用流畅摘要代替结果证据，也不复制模型隐藏推理。
4. 形成适用范围和推荐发布范围内的候选，按来源与内容权限查看和修改。脱敏只是处理步骤，不自动取得跨空间或跨企业发布权；脚本中的凭据、真实接收者和环境私有路径不进入可复用默认参数。

清洗、去重和提炼方法可以优化，不固定成所有类型必走同一工作流。语义相近但口径或条件不同的条目可以共存并标明区别；自动检测出重复不等于自动删除原始证据或合并不同版本。无法在不暴露受限信息的前提下保留必要条件时，留在原授权范围，不强求整理为通用经验。

**核验标准与条目类型相称。**

| 核验方面 | 需要确认什么 |
| --- | --- |
| 依据和结果 | 方法参考来源是否可信且可用；案例的完成范围、人工贡献和结果是否与真实记录一致；未观察到的长期效果保持未知 |
| 适用性与复用价值 | 需要哪些资料/条件、哪些情形不适用、比已有条目补充了什么，是否过度概括一次结果 |
| 方法及执行依赖 | 所引方法/Skill/脚本的版本和依赖是否明确；执行资产沿相应验证和发布机制，案例成功不代替当前可执行性检查 |
| 范围与发布资格 | 当前来源允许怎样提炼、谁可读/维护、拟发布范围是否获准，摘要、附件和证据链接均不越权 |
| 与已有内容的关系 | 是独立证据、同源派生、反例、替代版本还是重复；结论冲突需保留条件与证据，不能只选票数多的一方 |

有依据的方法参考可以按“参考”身份发布，不必伪造成功案例；证据不足的案例可补证或降低结论范围，不能以一项模型自评分补齐缺失事实。程序检查明确字段、关联和真实回执；模型辅助提炼与语义判断，重要且尚无依据的分歧由适当有权者处理，不要求每条候选都增加一次完整评判模型调用。

**自动维护按动作和已有授权划分。以下是可配置策略的建议，不是本轮新增授权。**

| 动作 | 建议的自动处理方式 |
| --- | --- |
| 记录真实采用、形成候选、补充可重建标签/摘要/索引 | 在已有来源、用途、资源和维护授权内执行，保留依据与修改记录；标签变化不改变内容权限 |
| 追加已核对的案例或结果关联 | 在已有发布/维护策略覆盖且不改变方法结论、范围时，可自动关联；效果未知和同源证据如实表达 |
| 发布方法参考或案例 | 满足该类型质量条件和目标范围的发布策略时可自动生效；仅有提取权限时保留候选，不默认所有条目必须人审或都可自动发布 |
| 修改方法步骤、适用条件、脚本或 Skill | 形成新版本并验证；已有自动升级授权覆盖的范围内可启用，超出授权或遇到重要未决取舍时取得相应决定 |
| 扩大共享、改变业务口径、引入新数据/执行范围 | 使用对应范围的真实授权与发布机制；去敏、好评或模型认为有用均不能代替 |
| 已撤权、已失效或明确不兼容的条目 | 按生效维护策略停止受影响使用；不因需要后续人工复核而继续绕过已生效限制 |

这些动作可由同一系统执行，主规则只说明原则，实际权限与发布条件由平台落实。企业/空间/个人及通用经验继续沿 DEC-087 分工，不把所有候选送到总台，也不让企业管理员自动取得私人证据。对缺少必要决定的候选，说明具体缺口并留在对应范围，不能以积压为由自动批准。

**候选、可用与停止使用分开表达。**

候选默认不混入日常检索的可用经验；核验或已有授权的探索需要读取候选时，明确其状态及限制。核验通过且发布条件满足后，形成可用的确切版本与范围；“参考方法”也可以是可用内容，其证据强度继续单独表达。字段结构、状态枚举与过渡细节留待实施收口，不把所有维度压成一个“可信分”。

需要复核的条目按受影响情况缩小适用范围、降级为带限制参考或停止使用；明确错误、执行不兼容或不允许继续访问时，停止相关使用。低使用率不直接判为无效，新证据有分歧时保留反例和条件；未找到错误原因不自动宣判整套方法永久失效。发布、停用、归档和删除分别记录，停用不代替实际删除及保留政策处理。

发布时再次核对当前来源授权、所依据的方法版本、企业规则及发布条件；整理期间发生实质变化的候选转为待调整或按现有依据重新核验，不能沿用过期条件覆盖当前决定。已有授权仍适用时继续自动处理，不因这项校验增加逐条审批。

平台记录发布状态和版本，索引记录检索就绪情况。保存或发布成功不等于已可检索；索引同步失败保留真实待处理状态并可重试。读取候选摘要或正文前核对当前权威状态和权限，旧索引不能让已停用/撤权条目继续被使用。归档、索引及证据关联重试按同一来源/版本/动作去重，避免重复发布或重复累计证据；并发修订核对所依据版本，不覆盖较新的决定。

**失效处理要能追溯受影响的使用。**

新反馈推翻原结果、企业口径改变、工具依赖升级、有效期到达、来源失效或权限撤回，都可能触发相应条目复核。已发生的使用事实和实际业务动作保留真实记录，不因为方法停用而伪装从未使用；对受影响的待执行任务和待交付成果重新判断，必要更正或告知沿其授权及输出策略处理，不自动向所有历史用户推送通知。

来源删除、独立发布副本、审计保留及索引/缓存清理沿输入和运行规则执行，跨对象保留与删除建议见[管理任务书第 15 节](三端管理与共用平台-开发任务书-V0.1.md#15-数据保留删除导出与恢复)；原始会话、候选、正式方法及案例证据分别处理，不以未来自进化为无限保留依据。来源权限变化不必然等于内容事实错误，但会改变可继续访问和使用的范围；确切删除要求也不能仅以“保留历史证据”为由无限保存正文。

例如，某次汇报获用户好评，但后来发现日期筛选遗漏部分记录：好评保留为当时反馈，案例补充真实纠正及影响；同一方法是否需要新版本取决于问题来自方法、参数、数据还是工具。不能直接删除失败记录，也不能让原“成功案例”继续无条件支持旧结论。

维护任务使用相应资源额度，可合并相近变化、延后低价值整理和限制候选积压；不以候选/入库数量作为优化目标，也不让归档挤占明确交付。具体触发频率、保留期限、优先级和自动发布条件在管理/评估/运行专题收口。日常维护在自进化停用时仍可运行，未来自进化优化这些方法时复用现有评估和发布边界。

待执行工作：补来源使用策略与提取触发、候选和证据关联、核验结果、分范围发布/维护、索引就绪状态与重试去重、失效传播及受影响使用查询；复用已有任务/队列、版本权限和反馈机制，不在本轮另建整套工作流引擎。

验收建议：没有好评也能从真实纠正形成候选；重复事件不重复证据；清洗保留关键条件且不携带敏感执行参数；仅有读取/提取权不能扩大发布；已预授权的正常维护无需逐条审批；候选和正式可用内容可区分；发布与索引失败分别呈现；晚到反例可影响当前适用性；撤权/停用在旧索引中也有效；方法停用不删除真实业务事实，删除要求按实际政策处理。以上尚未实现或运行验证。

下一步做处理板块阶段收口：汇总职责、现有缺口、拟交付范围和跨板块依赖，列清主动调度资源/频率等剩余决策，再进入输出板块。处理侧范围先作建议，待所有板块及全局依赖讨论完成后统一确定并执行。

## 10. 验收方向与后续讨论

尚未执行的验收场景：

1. 简单请求可直接完成；复杂请求可多次读取/试错，不受固定步骤限制，过程中权限与预算持续有效。
2. 工具首次失败、换方法后完成必要工作可正确交付；未解决的关键失败不可被正常文字回复掩盖。
3. 补充资料/确认只恢复对应工作，重复提交不重复执行；目标或对象变化不误用旧授权。
4. 暂停、取消、租约中断和权限撤回分别保留真实状态；迟到结果不覆盖新尝试，外部未知结果不盲目重放。
5. 来源不足可如实部分交付或等待；任务完成、发布成功与业务效果不混为一谈。
6. 经验为空仍可运行；错误/过期或跨企业未授权经验不被当作可靠依据，脚本不能绕开工具边界。
7. 重复事件和系统自产事件不无限触发；预算耗尽不冒充完整检查，后台分析不自动发送通知。
8. 正式调用、合成验证、用量未知与真实回执分别呈现；新旧引擎及契约切换保持结果和权限语义。
9. 按第 4.4 节验证冷启动与目标校准，不把无反馈、行业常见现象或模型建议当成已确认企业目标。
10. 按第 6.4 节验证默认主动工作在不同起点、承诺、信息缺口与资源条件下的继续/等待/结束行为，不把无变化当成所有任务的统一停止条件。
11. 按第 6.5 节验证目标范围、来源及冲突处理；角色、工具权限和业务决策权不混同，已有授权的小幅变更不触发全量重审。
12. 按第 6.6 节验证能力发现、按需加载、缺口区分及跨轮上下文连续性；目录与实际能力一致，经验/说明不改变权限，真实动作和交付结果不被模型摘要替代。
13. 按第 6.7 节验证计划实际保存、无常驻模型的触发、去重及变化覆盖、等待/启停作用范围和中断后补做；动态调整不能绕开原授权、期限与资源约束。
14. 按第 6.8 节验证候选与生效版本、评价依据及适用范围、任务切换与回退语义；评价口径变化不冒充提升，模型更换不以复刻旧步骤作为唯一标准，方法回退不冒充撤销业务动作。
15. 按第 6.9 节验证多企业规则/方法组合、评估范围及通用发布与企业采用；差异保留、隔离与各范围维护权不能被共用更新服务绕过。
16. 按第 8.1 节验证经验对象及证据范围、冷启动方法与真实案例区分、适用性判断、实际采用记录及反馈关联；成功案例不自动修改方法、扩大可见性或授予工具权限。
17. 按第 8.2 节验证标准结构/属性、检索与适用性、使用事实与案例/方法版本分离及扩库效果；历史引用、独立证据及当前权限不因重建或优化而丢失。
18. 按第 8.3 节验证候选价值与证据、清洗及范围、发布时版本/授权复核、自动维护边界、索引就绪与幂等，以及晚到纠正、依赖失效和撤权后的影响处理；正常交付不等待经验归档。

上述场景作为后续验收候选，第 11 节按能力与交接汇总。当前没有执行新的运行验收或自进化实验；进入下一板块不代表这些场景已通过或全部纳入同一交付版本。

| 成果与输出交接 | 交付确切成果、依据/限制、任务完成范围及待执行动作；接收输出回执与关联反馈 | 草稿、发布、送达分别判断；任务包含发送时须跟踪真实交付，复用发送能力；M4/M5/M6 |
| 方法版本与运行依据 | 保存实际模型/规则/方法组合、授权范围、回执、用量及反馈，支持有权维护者正常更新与停用/恢复 | 能解释实际采用内容，未知用量不填零；基础质量和发布管理可运行，自进化停用不影响正常工作；M7 联动各模块 |

任务执行仅使用届时已接入且获准的能力；缺少外部业务工具时如实说明，不能用模拟动作冒充执行。当前“任一工具失败即整体失败”的实现限制、平台任务与 Harness 会话的映射、恢复时的权限与实际结果核对，需要在统一执行阶段作为明确增量处理。

经验首版不能只有一个空接口，但也不要求建立全行业大库。主动工作首版应有可验证的触发和结束行为，不必同时支持所有外部事件。具体场景、工具及来源在全局范围表登记，未纳入的能力不得在界面表现为已可用。

### 11.3 后续扩展与可替换方法

建议留到后续范围评估的内容包括：全行业经验覆盖、复杂的组合检索与自动价值排序、广泛跨员工协作、任意外部业务系统接入、复杂实验管理门户，以及独立自进化服务及其效果实验。已确认独立自进化在基础系统完成后接入，其余条目保留需求方向，不承诺同一版本全部上线。

正常任务的重新规划、已获准计划调整、档案/索引维护、经验积累及有权维护者的方法发布，属于基础能力，不因自动发生就一并延后到自进化。底层库结构、字段实现、队列设施、上下文组织、检索/重排和模型分工保持可替换，先满足接口含义和实际验收，不预先锁死算法。

### 11.4 跨板块需要共同完成的交接

| 对接方 | 应共同明确的内容 | 责任边界 |
| --- | --- | --- |
| 输入 | 可访问资料及确切版本、时效、解析/质量状态、覆盖与缺口；背景/目标/偏好的来源和适用范围 | 输入负责可取得什么，处理判断够不够完成目标；未解析、无命中、无权和读取失败分别解释 |
| 输出 | 成果版本、事实/分析/假设、完成范围与限制、拟交付对象/用途、下一步建议；交付回执和反馈引用 | 处理形成有依据的成果，输出按权限决定具体呈现/排序/交付；包含发送的任务由处理继续跟踪，平台持有真实状态，不重复建设发送器 |
| 三端管理 | 持续关注维护权、业务取舍权、工具/数据范围、预算、经验发布及版本采用策略 | 管理配置与内容读取分权；个人/空间/企业/平台各自有明确生效范围，使用者不必操作所有技术参数 |
| 评估 | 任务完成、主动发现与遗漏、经验误用、纠正吸收、恢复与隔离、质量/成本及方法版本比较 | 复用一套评估依据，按影响范围验收；程序成功不等于业务价值，基础验收不依赖自进化实验 |
| 运行与平台 | 模型/工具依赖、实际执行身份、资源、等待/恢复、记录保留、引用/索引迁移和停止传播 | 平台负责持久状态和约束，引擎经版本化接口运行；真实模型、部署及客户体验需各自证据，模拟不替代 |

这是交接语义，不是最终接口字段或数据库设计。复用平台现有身份、任务、原件、成果和记录作为权威依据，避免输入、处理、输出各自保存互相冲突的任务状态或权限。

### 11.5 未决事项放到哪里收口

| 待确定事项 | 当前建议 / 下一步责任 |
| --- | --- |
| 默认职责、冷启动和主动开关 | 明确请求直接处理；已生效职责/持续目标可在范围内运行。哪些角色默认启用哪些关注、首批触发源和探索范围，由管理端与具体场景确定，不推定企业一开通就扫描全部资料 |
| 调度频率、资源和优先级 | 支持每项关注按事件/时间运行、在允许区间调整节奏，交互及明确承诺有资源保障；具体间隔、额度、并发和等待上限结合模型成本、规模及运行专题决定，不设全企业统一固定频率 |
| 经验种子和维护策略 | 明确首批任务/方法与来源、自动提取/发布类别、维护主体和失效政策；结构/属性标准及 WeKnora 采用范围通过相应技术研究与获准样例核对 |
| 输出与反馈 | 当前结果怎样进入会话/成果/画报，主动候选是否展示、何时通知、反馈怎样作用于任务/偏好/经验，以及错误更正是否重新交付，由下一输出专题明确 |
| 角色、重要取舍和外部动作 | 在管理专题落到具体权限动作、已有委托及发布范围；不把“管理员”作为所有事项的默认决定者 |
| 质量、规模与恢复承诺 | 在评估/运行专题确定代表任务、规模、可接受成本和关键失败标准；安排获准真实模型及实际集成验收，不能仅引用历史本地测试 |

这些未决项不阻止继续输出等板块讨论；依赖它们的实现/交付在统一执行前按需要明确。可逆的内部技术选择由开发结合真实框架与验证决定，实质影响业务范围、权限、费用或承诺的选择保留相应决定，不反复询问已经明确的方向。

### 11.6 后续验证与进入输出的起点

从第 10 节选取覆盖实际行为的代表任务，至少串起以下情形：简单任务直接交付；资料不足时补充或明确部分成果；工具失败后有效恢复；计划等待后被真实事件/时间唤醒并可停止；经验空库/命中/不适用及用后候选；包含发送的任务按真实回执结束。将跨企业隔离、撤权、重复触发与未知外部结果贯穿相关场景，不以新增测试数量代替行为证据。

以上仍是未来验收范围建议，本轮仅整理文档。模型选型、真实调用、集成、部署和客户验收按全局任务书分阶段取得证据。

接下来进入输出板块第一轮：先确定处理结果、可交付成果、画报内容与通知之间的关系，讨论哪些结果直接交付、哪些形成候选，如何合并/更新，以及受众和权限怎样贯穿呈现。随后再细化价值排序、个性化表达、推送与两类反馈。输出继续复用同一引擎和平台能力，不要求每次交付都再调用一个模型。
