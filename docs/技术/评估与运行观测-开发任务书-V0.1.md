## 1. 目标与职责

这一能力为系统提供可核对的运行事实及质量判断，既服务日常维护、内容纠正和人工研发更新，也供未来自进化使用。自进化未部署、停用或失败时，基础系统的运行观测、必要检查和评估仍可使用；自进化通过已有授权读取证据和申请评测，不拥有唯一评价权。

三项责任分开：**运行观测记录实际发生了什么；评估按明确目标判断结果是否达标及改法是否有效；采用变更由相应授权和发布机制决定。** 评分通过本身不产生读取资料、改业务事实或发布方法的权限。可以共享存储、页面和执行设施，不要求另建物理服务、独立模型或第四个管理端。

本轮先梳理讨论框架，保留模型自由选择有效解法的空间。评价以结果及约定约束为主，不把是否复刻固定步骤、检索次数、思考长度或输出篇幅当作通用正确标准。

## 3. 建议区分四类判断

| 判断层次 | 要回答的问题 | 主要证据 | 容易混淆的信号 |
| --- | --- | --- | --- |
| 运行健康 | 任务是否正常启动、推进、结束，资源是否可控 | 平台任务/尝试状态、实际工具回执、等待与执行耗时、错误、用量及计量覆盖 | 服务能访问、模型返回了文字，不等于完成任务 |
| 任务与内容质量 | 是否满足具体请求或职责，事实/计算/执行是否正确，有无关键遗漏 | 当前目标与完成标准、固定来源和结果版本、程序检查、按标准评判及必要复核 | 工具成功、文件生成、格式整齐，不等于内容正确 |
| 用户与业务价值 | 是否帮助了适当的人，纠正与处理负担是否合理 | 针对确切结果的反馈、明确采纳/修改记录、获准且可取得的后续业务结果 | 点击、停留、满意度、产出数量，不单独证明业务收益 |
| 变更收益 | 某项方法调整在什么范围真正改善了结果 | 版本化基准与候选、可比较样例和条件、质量/成本/耗时差异、关键退化及证据限制 | 自评更好、单次成功、只看平均分，不证明普遍提升 |

四类判断相关但分别记录，不先压成一个覆盖全系统的总分。某类任务可以按明确业务目标选择主要指标及辅助指标；权限、真实执行正确性等基本要求不能被更快、更便宜或平均满意度提高抵消。具体关键要求随场景定义，不把一切瑕疵都升级为全系统停止条件。

例如销售周报：文件已经生成是运行事实；计算与来源正确且没有漏掉约定的重要异常是质量判断；负责人认为可用、减少了修改是价值信号；经营改善是否由报告促成仍需更多证据。新版本更快，但漏掉关键异常，不能仅凭耗时降低判断优化成功。

## 4. 最少应能关联的证据

按需要引用已有业务对象，建议形成以下关联，不要求集中复制全部会话、原件、提示词或隐藏推理：

| 证据组 | 建议记录的含义 |
| --- | --- |
| 工作依据 | 企业/空间及授权范围、任务或持续委托、触发原因、当时目标与适用完成标准；内部关联标识不因此向总台公开 |
| 实际条件 | 使用的来源/成果版本、主规则与方法组合、模型可取得的版本信息、工具与检索配置、资源约束 |
| 实际过程与结果 | 任务和尝试关联、关键动作与回执、产物、失败/取消/待补充/部分完成、等待与执行耗时、已知用量及缺口 |
| 交付与反馈 | 内容/呈现版本、获准受众、实际展示或站内交付记录、用户原始反馈与后续改评；未观察到的行为保持未知 |
| 评价记录 | 评价对象、样例及标准版本、检查/评判方法、评价结果、证据引用、分歧和未验证范围 |

业务结果与评价结论分别保存，并区分模型原始产出、人工修正后的成果和最终业务结果，避免把人工补救归为模型直接完成。任务执行成功后抽查发现错误，应保留成功执行的历史及新增质量问题，不能悄悄改写历史为“从未成功”；纠正、停用或补偿沿相应业务权限执行。评价失败也不触发重复真实任务。

统计必须说明**统计单位、时间窗口、入选条件、分母、证据覆盖率和排除项**。一项任务重试三次仍是一项业务任务，但有多次尝试及实际资源消耗；等待、取消、部分完成、未评估与评估未通过分别处理。质量样本只覆盖一部分任务时，结论须标明样本量、选取方式和适用范围，不能把样本通过率直接命名为全系统准确率。

无用户反馈不等于满意或不满意，未曝光不等于内容无用，无模型用量回执不等于零消耗。无合法资料或证据不足时，诚实说明缺口、请求补充或正确停止可能符合任务要求；不能为了提高“完成率”鼓励编造或越权。

## 5. 各板块需要提供什么观察面

| 板块 | 首轮关注问题 | 归因时需要区分 |
| --- | --- | --- |
| 输入 | 来源可用/新鲜程度、解析与同步结果、版本和权限、与当前任务有关的数据缺口 | 企业本来没有数据、未授权、尚未接入、解析失败及检索未找到，不都算模型能力差 |
| 处理 | 目标理解、引用与计算、工具执行、关键任务完成、等待/恢复、经验适用性及资源 | 不合理目标、资料不足、外部工具故障、方法不适用及模型错误；允许暂时无法确定原因 |
| 输出 | 直接交付、候选覆盖、排序与表达、受众适配、站内可达、重复/过期及打扰负担 | 应有内容未生成、候选未选中、呈现不清楚、未展示和确实无帮助；不能只看推荐点击 |
| 资料库与经验库 | 检索相关性与遗漏、索引可用性、经验适用条件、复用后的真实结果与维护状态 | 命中不等于适用，引用不等于有贡献，收录更多不等于效果更好；失效和负例也有评价价值 |
| 冷启动及持续工作 | 能否提出有依据的初始帮助、识别缺口、吸收纠正并履行已生效委托 | 主动内容多不等于有价值，暂不推荐可能合理；已承诺检查未运行与检查后无新发现不同 |

全链路结果与具体环节共同观察，局部指标改善不能掩盖下游退化。原因判断区分事实证据、模型推断和待核对，不强制每个问题立即归到唯一责任方。

## 6. 评价怎样执行及如何为自进化预留

建议按成本与影响分层使用，避免让每个普通请求增加一次评价模型调用：

1. **随实际操作完成必要检查。** 权限、状态、结构、数值可核对项、真实回执等优先使用平台或工具能力；属于动作前提的检查不能后移到异步抽查。
2. **运行后按需评价。** 对代表场景、失败、纠正、重要交付和适当正常样本做质量检查；自然语言质量可用明确标准、模型评判及必要人工抽样。用户满意度是一个来源，人工也不应逐条检查所有任务。
3. **变更前作针对性比较。** 人工研发和未来 AI 提出的候选均可使用同一基础评估能力，按影响范围选择案例，记录基准与候选的差异、退化和不确定性。当前先设计接口与证据，完整自动试验和采用由自进化专题继续设计，基础系统完成后再接入验证。

客观事实能用程序及原始证据验证时，不以另一个模型的赞同替代；开放任务允许多种有效答案，不以字面相同作为通用标准。模型评判需有明确量表及与获准人工/已知样例核对的依据，关键分歧可进入复核；换一个模型评判也不自动消除共同偏差。

承接[处理任务书第 6.8 节](处理板块-开发任务书-V0.1.md#68-本轮讨论规则维护发布评估与回退)：基准与候选尽量在相同目标、来源、工具和资源条件下比较；保留未用于调优的检查样例和负例，必要时观察重复运行差异。多项一起修改则评价组合效果，不能任意归因到某一项。样本过少、条件不同或经营结果尚未成熟时，结论可以是“证据不足”，无需强行选出赢家。

评价标准、样例和评判方法本身也可维护、提出优化，但有独立版本和变更记录。不能在同一轮放宽标准、删掉失败样例或针对已知答案调优后，将分数上升宣称为方法提升。业务目标改变时明确更换评价口径并重建可比基准。独立性主要体现在证据、数据使用边界和生效权限，不预定必须购买另一个模型。

评测任务与正式业务区分标识和计量，不能让合成成功、额外评价调用或重复样本混入业务完成量。影子比较或重放不得重复真实发布/写入；执行验证在相应隔离或受控条件下进行。评价服务只有评价任务授予的数据和工具范围，不继承原任务的全部执行权限。

## 7. 日常运行、异常与恢复

运行观测需要帮助使用者理解异常的影响、当前状态及可执行动作，而非只呈现日志数量。普通错误、等待、主动无新发现、用量未知与系统不可用分别显示；失败已恢复后保留必要事件与尝试依据，不能仅因当前状态成功就从长期分析中抹去曾经失败。

建议区分三类失败处理：

- 统计页面、非关键质量抽查或观察消费者暂时不可用：显示不可得/待评价，可在已有资源和权限范围恢复，不因此丢弃正常业务结果。
- 可信业务状态、动作授权或执行前必须保存的记录无法确认：按原任务要求停止相应动作，不能以“观测可降级”为理由继续执行。
- 评价结果提示质量或运行退化：关联受影响对象及证据，按既定维护/发布权限处理；评价模块本身不偷偷改配置、自动重发成果或重跑真实写入。

日常基础计量和异常可用性不能依赖自进化运行。更细的事件保存、聚合性能、容量指标、观察开销与保留期限按首版规模继续确认；不先承诺全面行为追踪或永久保存原文。新增用户可见提醒沿 DEC-088 限定系统内，后台异常也不在本轮自动扩展成外部业务通知渠道。

## 8. 先登记管理交互需求，后统一分配到三端

以下是需要承接的动作与信息，不是新增菜单或已授予的角色权限。管理端专题结合全部板块再确定页面归属、复用、角色和操作路径。

| 交互需要 | 需要使用者理解或完成什么 | 初步使用者与权限限制 |
| --- | --- | --- |
| 运行概览与异常 | 查看范围、时间口径、状态、用量覆盖和异常影响，刷新及跟踪处理状态 | 企业/平台运行维护者按既有汇总范围；平台无客户内容入口，不因排障获得私人任务详情 |
| 单项任务质量说明 | 区分执行状态、质量问题和未知项，定位本人有权读取的依据，提出纠正或复核 | 本人或有权协作者；对成果有读取权不自动有私人会话、反馈及源资料读取权 |
| 评价标准及样例维护 | 维护适用场景、完成标准、版本、来源与用途，查看候选和生效状态 | 获相应维护授权者；企业业务标准和平台通用方法分别授权，管理员头衔不直接决定业务标准 |
| 评测发起及进度 | 选择获准对象和版本、核对范围与预计资源、查看排队/执行/失败/取消 | 具备相应范围评测和资源使用权者；取消评测不等于取消原业务任务 |
| 基准/候选对比 | 查看收益、退化、样本覆盖、无法判断项及证据，形成采用建议 | 对对应方法和范围有权的维护者；看见比较或评分通过不代表有发布/采用权 |
| 反馈与评价争议 | 区分原始反馈、推断原因及处理结果，处理改评、撤回、错误评价 | 原反馈者及获准处理者；不把企业汇总变成员工个人表现排名或私人内容列表 |

评估处理企业内容须在原授权范围内进行。平台通用评测优先使用合成、公开或明确允许此用途的案例；脱敏不自动取得跨企业复用权。企业内部结果若需形成平台可见统计，也必须明确字段和聚合范围，避免小样本、自由文本、提示词、样例或错误详情泄露内容；本轮不新增这种数据上传权限。

展示证据引用时复核当前权限。原文删除或撤权后，不可通过评估副本、报告、缓存或导出恢复原本不能读取的内容；保留必要审计与删除要求的具体协调在管理/运行专题明确，不承诺永久完整重放。

| 建立最小样例与评价流程 | 选代表任务、来源与预期要求，先覆盖客观检查和必要语义评价；提供版本化结果、证据、分歧和复核，不要求首先建完整实验平台 |
| 支持受影响范围的版本比较 | 可区分当前基准、候选、样例和评价口径；业务动作隔离，资源独立计量，结论不自动触发生效 |
| 承接管理交互及权限 | 将第 8 节与自进化的后续管理需要交给三端专题统一设计；沿已有管理端扩展，不新增第四端 |

统一执行阶段拟以以下场景验收，本轮没有运行：

1. 同一任务失败后重试成功：业务任务数、各次尝试、耗时和未知用量分别可信，质量判断不从执行成功状态直接推导。
2. 文件成功生成但包含错误或关键遗漏：评价能够记录具体问题和依据，不改写执行历史、不擅自覆盖成果；数据不足且正确说明时不误报为编造。
3. 画报未曝光、未反馈、有用但内容有误或两入口重复反馈：分别保留事实，不虚构满意、不重复计算独立成功样本。
4. 候选更快但关键质量下降，或样例/标准发生变化：对比明确展示退化或不可比，不能被单一总分掩盖；评测不重复真实业务动作。
5. 企业停用、来源撤权、私人反馈、跨企业样例及小样本汇总：读取和展示保持权限，评测和总台不能成为内容旁路。
6. 自进化未启用、质量抽查失败或观察页面故障：基础任务按其必要检查继续或明确停止，系统不伪造零值、合格结论或已完成评价。

## 10. 首轮结论与接续

已确认的既有原则是基础系统可独立运行、自进化后接入、先讨论任务书后统一执行，以及本专题在自进化和三端管理之前展开。本轮提出四类判断、最少证据与分层评价方案，不视为用户已确认具体指标、自动处理或首版范围。

首轮提出继续讨论本板块的**评价标准、样例和判断权**，现已在第 11 节展开：通用底线、任务要求、企业业务目标和个人偏好如何分别形成标准；什么适合程序判定、什么交给模型或人工；样例怎样积累并保留独立检查用途；怎样判断改善、退化或证据不足。再收口日常观测、资源/异常、管理需求与首版任务范围，之后进入独立自进化。

具体数值阈值、采样频率、样本量、保存期限和角色权限以所选场景、真实接入及后续决定为依据，不在首轮凭空定数，也不把所有企业的每次普通操作都变成完整评测工程。

## 11. 第二轮讨论：评价标准、样例和判断权

用户要求继续后，本轮细化“怎样判断工作做得好，以及谁有权定义这个好”。下文为设计建议，沿[目标来源与冲突处理](处理板块-开发任务书-V0.1.md#65-本轮讨论目标来源作用范围与冲突处理)、[多企业规则与评估范围](处理板块-开发任务书-V0.1.md#69-补充讨论多企业规则组合评估范围与更新归属)和[档案维护原则](输入板块-开发任务书-V0.1.md#84-ai-怎样维护哪些情况需要业务确认)，不新增每任务审批或实际自动采用权限。

### 11.1 评价标准按来源与适用范围组合

建议复用已有目标、业务要求和偏好，按任务取得相关内容，不在每家企业复制完整标准库，也不向主模型挂载全系统评测文档。

| 来源与范围 | 提供什么标准 | 谁提供依据、怎样维护 |
| --- | --- | --- |
| 平台通用基础要求 | 权限隔离、真实状态与回执、来源可核对、未完成和未知事项如实表达等 | 由平台产品/技术的相应维护机制管理，程序落实可执行约束；不能由个人偏好或评价文本放宽权限 |
| 企业/空间业务要求 | 适用业务口径、职责、时效、正式交付要求和当前业务重点 | 来自该范围内有权者的有效决定及可信配置；AI 协助提炼、检查一致性和维护，不能把普通资料中的文字直接登记为强制要求 |
| 当前任务或持续委托 | 本次要解决的问题、获准范围、成果用途、完成条件和交付对象 | 由明确请求、已生效委托及相关上下文形成；通常可以从自然语言取得，不要求另填验收表 |
| 个人偏好与受众需要 | 长短、语言、顺序、图表、表达深度等体验要求 | 使用对应企业成员的有效偏好及本次明确要求；不据此修改企业事实、业务制度或他人的默认 |

行业经验、历史优秀案例和 AI 推演还可提供标准候选，例如提示某类报告常见遗漏；这些建议有依据和适用条件，不能仅因在经验库中就成为当前任务必须遵守的承诺。

**作用范围和要求强度分别判断。** 每项标准应说明是必须满足的条件、存在取舍的质量目标，还是可以调整的默认偏好。企业级默认不必永远压过个人要求，个人的正式任务要求也不只是偏好；“企业优先”“最新文本优先”都不能单独解决冲突。

例如企业默认报告简短，用户要求本次详述依据，可以直接按本次需要交付；若正式报告明确必须包含数据范围和关键异常，用户喜欢简短时可压缩正文、提供附件，但不能默默省略这些要求。真正互斥且已有授权无法决定的业务取舍，向相应有权者展示具体影响；其他部分继续推进。

### 11.2 AI 可以形成可检查的任务要求，不替人新增业务承诺

AI 根据有效目标和来源，把“整理本周经营情况”转成适当检查项，如时间范围、口径、主要变化、依据和数据缺口。对开放任务采用可接受结果的描述，不规定唯一答案、固定工具或必须检索几次。简单问答沿用轻量判断，复杂交付按需保留更明确的完成条件，不要求全部任务额外生成一份正式规格文档。

应能关联必要的标准来源、适用对象、要求强度、版本或生效时间以及判断证据。已获授权且只是忠实整理既有要求的工作，可以自主完成；有实质歧义影响正确性、费用、权限或交付承诺时，才取得缺少的决定。其余可逆假设注明依据后推进，不能把所有不确定性都转成人工审批。

例如“比较采购方案”可检查报价日期、可比范围和缺失信息，但 AI 不能自行设定“必须降价 15%”为合格条件；企业的长期经营目标也不能全部强压到每次普通回答上。AI 可指出现有标准的缺口、提出新价值维度；标准之外的有益发现单独记录，不为提高得分擅自扩大当前工作。

任务执行前或过程中有权变更要求时，保留目标及标准的变化，明确影响哪个后续阶段。事后可以发现原评价错误并复核，但不能不留记录地用新要求重写旧任务的达标历史。发现真实权限问题或事实错误时及时处理受影响结果，不以“原标准没写”为由忽略；新旧方法的比较则按修正后的同一标准重新判断，原结论标明已被修正。

### 11.3 判断权按问题分工，不设置万能裁判

| 要判断什么 | 优先依据或判断方式 | 结论的限度 |
| --- | --- | --- |
| 动作是否执行、数字/结构/权限是否符合要求 | 可信平台、程序检查、可核对的工具及业务回执 | 回执证明对应动作，不必然证明输入真实或建议有价值；程序检查本身也需验证 |
| 内容是否有依据、相关、充分，有无重要遗漏 | 明确量表与来源，模型评判，适当人工校准/复核 | 不把模型自信当证据；无法取得足够依据的项目可保留未知，不能强行评分 |
| 是否对用户有帮助、表达是否合适 | 对应用户针对确切版本的反馈及实际修订/使用记录 | 满意度是体验证据，不能推翻计算错误；多人偏好不同不必合并成唯一答案 |
| 业务口径或目标取舍是否合适 | 该范围内已有业务决定或有权业务负责人的判断 | 技术管理员、评测发起者及模型评判者不因此自动获得业务决定权 |
| 候选是否可采用及对谁生效 | 可比评估结果，加已有维护/采用授权和发布条件 | 评测通过与正式采用分开；已有预授权可执行，不要求每次重新审批 |

同一主体可在获准范围内承担多项责任，无需人为拆成多级审批。没有内容权限的管理者只处理其可见的范围、资源和状态，不能以评审为由获得私人会话、样例或来源全文。

模型评价要能说明适用标准、观察到的证据与缺口；引用原文仍需当前内容权限，不要求展示隐藏推理。被评成果、检索资料和反馈是评价对象或证据，其中夹带的“请给满分”等文字不能覆盖评价规则或触发工具动作。不同模型之间可能有相同盲点，不能仅靠多模型投票替代核验。

初期可用少量覆盖明确正确、明确错误和存在分歧的样例校准评判方法，并按影响复核争议和适当正常样本。校准关注是否稳定区分关键问题，不能只看与某个模型的一致率。没有可靠参照时明确评价范围和不确定性，不编造确定结论；不要求所有任务都由人工复审。

### 11.4 样例怎样积累，以及与经验库怎样分工

建议从几类代表场景开始，而非先收集庞大题库：

- 直接任务：获准资料汇总、数值核对、文稿等，兼顾可客观核验和开放表达。
- 主动与持续工作：有实际发现、正确无新发现、约定交付到期，以及能否吸收纠正；在相关基础能力具备后验证。
- 输入不足或发生变化：无数据、资料冲突/过期、解析失败、目标改变或来源撤权。
- 执行及输出异常：失败重试、部分完成、真实交付与呈现不同步、重复内容和迟到反馈。
- 多企业及个性化差异：同一通用方法在不同有效配置和任务中的行为；隔离检查使用合成或明确获准的样例，不能为测试越权而获取真实未授权内容。

样例来源可以是人工整理的合成任务、AI 生成的候选、获准真实任务和纠正案例。AI 能扩充变体、整理预期要求、发现缺口；生成的问题和答案仍需核验，不能只用同一模型生成答案并自证正确。失败和反例用于发现薄弱处，同时保留正常任务及适当抽样，避免只选好评案例。

一个样例至少能说明：任务/场景和适用范围、输入及依据时间/版本、可用能力和权限、关键要求与可接受结果、检查依据、未知项、来源/用途和当前有效状态。可以引用已有记录，不必另存所有原件；涉及工具动作时使用适当隔离或受控条件。开放任务可保留多个合格示例及其理由，不把某次历史文字、旧流程或一个工具序列写成唯一标准答案。

**经验库帮助完成任务，评测样例帮助判断完成质量。** 二者可以引用同一次获准任务、共享检索或文件设施，但分别记录用途、访问权限、版本和是否参与过调优。优秀经验不自动成为正确答案；用户好评也不是样例核验完成。经验的发布/失效、评测样例的启用/修正分别维护，不能通过更换标签绕过来源用途和复用授权。

来源撤回、业务口径变化或已知答案错误时，标记相关样例的适用变化及受影响评估，保留修正依据。可疑样例可以暂停用于结论，不能只因候选没通过就删掉；正常维护不依赖自进化，也不机械要求每条候选人工审批。内容读取和删除仍沿第 8 节边界处理。

### 11.5 调优、回归和独立检查分别说明用途

建议区分三种使用目的，而非必须建设三套物理库：

| 用途 | 怎么使用 | 能说明什么 |
| --- | --- | --- |
| 开发与调优样例 | 可查看问题、预期和评分反馈，据此修改方法 | 能帮助修复已知问题，不能单独证明对未见任务也有提升 |
| 回归样例 | 保留重要历史问题与基础要求，检查是否再次出现 | 能说明已知行为仍符合要求，即使它曾用于调优也仍有回归价值 |
| 独立检查样例 | 在该轮候选确定前不向候选生成/调优过程暴露具体题目、预期答案及逐题评分反馈；由有权评估过程运行 | 补充对未直接用于本轮修改案例的证据，仍受覆盖、规模和真实性限制 |

正常任务允许读取的资料和经验，本来可能就是受测能力的一部分，不能因它们与评测共用来源就禁用检索。需要识别的是具体问题、答案和评分反馈是否已用于调整被测方法；同一任务的改写、拆分片段和人工修正版也可能同源，不能仅凭文件名或记录编号不同就视为独立样例。

区分候选生成者与评估执行者所能读取的内容；最终检查样例及其预期不能作为普通经验被候选检索命中。针对已知评分反复调整后，该样例继续可用于回归，但不能保持“未参与调优”的标记。即使只反复查看汇总得分，也可能逐渐适配同一组样例，需要记录使用情况并按计划补充新检查样例。

真实运行抽样也应说明选择依据及观察窗口。为排障集中挑出的失败案例与代表性业务样本分开报告，不将其平均分直接当作真实总体水平；同一来源任务的多次运行及多入口反馈也不充当多份独立业务证据。只验证合成样例时，结论限定为相应检查，不扩写为真实企业效果已证明。

### 11.6 怎样判断一次调整值得采用

比较前明确受影响场景、主要改善目标、必须保持的要求、可接受取舍和观察方式；数值阈值按业务影响与测量可行性确定，本轮不凭空规定通用及格分、固定样本量或统一权重。只涉及个人排版的小改不必使用共享算法升级的全套验证。

同一轮固定可比较的标准、样例与条件；模型、来源、规则和检索同时变化时可以比较组合，但不把组合差异单独归功于某一项。观察必要的重复运行差异及分场景结果，不凭挑选最好的一次宣告提升；若继续试验或变更样例范围，保留安排及依据，避免只在出现有利结果时结束检查。

| 比较结论 | 建议表达 |
| --- | --- |
| 有改善依据 | 明确哪些场景、维度改善，关键要求是否保持，有哪些未覆盖范围 |
| 未见明确改善 | 证据范围内没有足够的实际收益，不因此必须替换现有方法 |
| 发生退化 | 指出质量、权限、执行、负担或资源上的问题及受影响范围；必要处理沿维护机制执行 |
| 存在取舍 | 例如质量提高但耗时增加，按已生效目标及授权判断是否接受，不能自行用任意权重算成赢家 |
| 证据不足或不可比 | 样本不足、数据不同、评价失效或业务结果未成熟，说明缺什么，不假定成功或失败 |

结论允许同时出现，例如“普通摘要更快，但复杂表格退化”，不只输出一个全局标签。价值还未体现不等于没有价值；已知严重问题也不能因为整体样本少就消失。上线后的实际观察可以补充或纠正结论，但时间前后差异并不自动证明因果关系。

评价标准、量表或模型评判方法改进时，作为独立变更验证。若发现原标准错误，需要在新口径下重新评价相应基准和候选，并标明旧结论不再适用；不能把两个口径的分数连起来展示成能力持续提升。新增价值维度可形成后续标准候选，不限制 AI 提出更有效的方法及目标改进建议。

### 11.7 管理需要、待执行任务与验收补充

本轮补充到第 8 节的管理需要：可查看适用标准及来源/版本、区分必须项与偏好、提出和处理标准修正；维护样例用途/状态及同源关联；展示评价分歧、证据不足和旧结论被修正；按权限发起复核，并查看候选与基准的分项比较。角色、入口和首版操作在三端专题统一设计，不新增总台客户内容入口。

提出标准候选、改变业务标准、读取样例、运行评测、修正评价和采用方法分别核对已有权限，可由同一有权主体或其获准 AI 代理完成。评测资源使用权不等于内容读取权，内容读取权也不自动允许跨企业复用；平台通用发布与企业采用继续分开。

待统一执行时，优先补最少的标准来源/范围及任务关联、带用途和版本的代表样例、程序检查与按需模型评判、分歧复核及对比记录。具体存储、检查脚本和模型选择由后续实现决定，复用原任务/目标/资料/经验/反馈及发布记录，不新建第二套事实真相。

未来验收补充（本轮均未运行）：

1. 企业默认简短、当前请求详细时可以自主适配；明确业务要求不会被表达偏好覆盖；AI 提炼标准不自行增加利润、期限或执行承诺。
2. 标准由自然语言和有效上下文形成，普通任务无需逐项人工审批；实质互斥的业务目标不会被管理员头衔或模型评分擅自裁定。
3. 多种有效解法、数据不足时正确说明和适当停止能够通过相应判断；生成了文件但事实错误、人工大量补救的结果不会被误归因。
4. 经验引用本身不影响独立性判断；已用于调优的题目、答案、反馈及同源改写不会被伪装成未见案例；被评文本不能修改评价规则。
5. 样例/标准修正保留依据并重算适用对比；只用失败集或合成样例时不伪报全业务效果；有分歧或证据不足时不强行给出通过结论。
6. 无权管理者无法读取私人样例和详情；评价通过不自动发布方法、改变权限或重跑真实动作；全部能力在自进化关闭时仍可维护使用。

本轮没有冻结行业指标、评价模型、数据规模、自动维护类别或具体审批角色。后续已在第 12—13 节展开**日常运行观测、异常处理与资源边界，并汇总评估板块的首版任务**；之后按 DEC-090 单独展开自进化，最后统一三端管理和全局依赖。

## 12. 第三轮讨论：日常观测、异常处理与资源边界

本轮把前文评价方案衔接到日常运行和维护。以下均为拟开发设计；复用现有任务、尝试、权限、计量和发布机制，不因增加观测再建一套业务状态真相，也不把普通维护后置到自进化上线。

M7 承接运行汇总、评价及管理信息，M4 和可信平台负责原任务调度、执行控制及其资源限制，M2 承接相应身份与权限。观测提出的暂停、重试或资源调整通过原控制入口执行，不在评估模块再造一个调度器。可恢复暂停、等待唤醒、计划补做和跨任务资源公平性仍属处理板块待建设能力，不把现有显式重试或刷新后查看任务视为断点续跑。

### 12.1 日常需要看见哪些信息

建议按实际问题组织信息，而非先建一个塞满技术指标的仪表盘：

| 观察面 | 最少说明什么 | 必须保留的区别 |
| --- | --- | --- |
| 基础运行可用性 | 相关服务或能力是否可用，任务是否能被接受和推进，最近核对时间及证据缺口 | 页面能打开、模型能响应与完整工作链路可用不同；未检测不能显示正常 |
| 工作进度与积压 | 排队、执行、等待、部分完成及结束情况，等待原因/时长，已生效交付是否延迟或漏做 | 运行慢、等资料、等决定和计划未触发不同；无新发现与未执行不同 |
| 质量与反馈 | 检查覆盖、关键错误/遗漏、纠正与复核、反馈适用范围及仍未知的价值 | 业务成功、评价通过和用户满意分别展示；没抽查不算通过 |
| 资源使用 | 按任务/尝试及用途核对请求、已知用量、执行资源和存储口径，当前限制及受阻工作 | Token、实际费用、估算与未知不同；原件字节不等于系统总磁盘占用 |
| 维护与变更 | 当前生效方法/版本、异常影响、处理进展、恢复结果及仍需复核的成果 | 服务恢复、方法回退与业务后果修复不同，不能一键标记全部已恢复 |

沿第 4 节说明统计单位、时间窗口和覆盖。成功率、延迟等按有意义的任务类别及条件观察，保留未完成、超期、取消及未知事项，不通过排除这些任务制造良好表现；关注长时间等待和较慢任务，不能只展示总体平均值。样本不足时不制造精确趋势或稳定性承诺。

当前运行概览主要是选定窗口内任务的当前状态，新尝试计量补充部分过程证据；完整历史异常、持续计划漏检、跨环节耗时及质量趋势仍需增量开发。尚未实现的计划/等待语义随处理板块接入后再观察，不能在页面用模拟数字补齐。

### 12.2 异常按原因和影响分流

异常首先需要说明受影响对象、实际现象、范围和紧迫程度、已有证据及下一项可执行动作。原因尚未确定时保留待核对，不把模型推断写成已证实根因。权限正常拒绝、用户主动取消及合理等待不自动升级成平台事故。

| 情形 | 建议处理方式 | 不应发生的行为 |
| --- | --- | --- |
| 资料缺失、目标不清或等待决定 | 记录具体缺口，继续可独立完成的部分；必要时在当前任务中提出补充 | 反复调用模型、把缺资料误报为模型故障，或为提高完成率编造 |
| 可恢复技术故障且确认重做安全 | 在已有授权、次数/期限及资源范围内重试、延后或使用已验证获准方案 | 无限重试、重新申请不受限预算，或所有错误都重新启动整个任务 |
| 超时、断连后业务动作可能已发生 | 先核对原动作标识、已有成果和实际回执；仍无法确认时保留待核对结果 | 将未知当未执行，重复发布、写入或生成业务承诺 |
| 已交付结果存在质量问题 | 关联确切版本、受影响范围和证据，按内容维护权限更正或复核 | 改写用户原评价，静默覆盖共享成果或抹去历史执行事实 |
| 权限撤回、企业/工具停用、重要依赖失效 | 阻止受影响的新动作，按当前有效授权处理在途工作及可用替代 | 用旧缓存、旧任务令牌或备用模型绕过限制；直接停掉无关企业全部工作 |
| 观察、统计或非关键评测故障 | 标明数据不可得/滞后/待评价，按上限恢复；保持可用的基础工作 | 显示零错误/零消耗或评价合格，或者因统计页面失败阻断一切任务 |

必要的授权、去重、资源许可和可信任务记录属于执行前提，不能套用“观测故障可降级”放行。若动作已经发生而回执保存失败，应保留核对路径；恢复时确认原动作，不能修改历史为未发生或直接重做。失败影响限定到相关能力或动作，能够安全继续的部分仍可推进。

异常处置可以记录“待处理、处理中、等待条件、已恢复、仍需业务复核”等含义，具体状态字段由实现和交互设计决定。它关联原任务事实，不代替任务生命周期。关闭提醒、确认已看见或暂缓处理不等于故障解决；恢复结论需有相应检查或真实回执，不能只依赖 AI 说已修好。

管理专题已在[第 14 节](三端管理与共用平台-开发任务书-V0.1.md#14-运行与改进工作区及待处理流程)细化三端视图、责任分流、原对象操作和实际解决依据；包括跨端同步、多人部分处理及平台技术恢复与企业业务复核的区别，均为待实现建议。

同一故障造成多项任务失败时可合并提醒、抑制重复，并保留范围和次数变化。不能跨权限展示关联私密信息，也不能因静默提醒而丢失新影响。首版新增用户业务提醒均在系统内，沿 DEC-088；不因称作异常提醒就加入邮件、短信或其他系统外触达。部署基础设施的技术监控若有需要，在实际部署方案中另定，不在本轮承诺外部通道。

### 12.3 日常恢复与方法优化怎样分开

恢复执行既有策略，方法优化改变未来工作的做法。两者可衔接，但不要求处理每个运行问题时先生成一项自进化提案。

- 已授权的安全重试、恢复等待任务、暂停异常能力、限流或使用已验证且获准的备用方案，属于基础运行处置；由相应控制机制校验并记录实际结果，不逐次增加人工批准。
- AI 可在当前任务权限内诊断、提出修复建议，执行已获准的维护动作；观测信号本身不赋予修改共享规则、代码、索引结构或企业业务标准的权限。
- 改变共享方法、模型采用策略或通用流程，沿版本、比较、授权和发布机制处理。人工研发可以使用这些机制，后续自进化也复用它们。
- 备用方案改变模型/工具或能力条件时记录实际组合及影响；没有合适授权或兼容方案就如实受阻，不暗中使用更昂贵的模型、未经验证的替代或降低交付要求。

方法回退后仍需识别旧版本已经生成的计划、成果和真实业务后果。恢复某个方法不能自动删除错误成果、撤销已执行动作或保证旧模型永远可用，沿[处理任务书第 6.8 节](处理板块-开发任务书-V0.1.md#68-本轮讨论规则维护发布评估与回退)处理兼容、复核与必要补偿。

### 12.4 资源按用途记录，共同受实际总量约束

建议至少区分正常业务工作、资料/经验等基础维护、质量评测，以及将来的自进化试验。用途分别记录不要求物理隔离四套资源；同一实际消耗不重复累计，无法精确分摊的共享成本标明口径，不伪造每任务准确费用。

当前请求次数、Token 回执及技术上限可以复用，但它们还不是企业商业额度和费用封顶机制。已有的每次尝试上限属于当前实现配置，不在新架构中永久固定为所有任务的能力上限。未来按任务类别及授权配置并验证适合的限制；本轮不改现行限制、不授权真实付费调用，也不承诺无上限探索。

资源控制建议同时考虑平台实际容量、企业适用范围和任务/委托限额。重试、子任务、关联评测及后续步骤不能通过新建编号绕过所属资源约束；过去已经消耗或结果尚未知的请求不能在取消后当作从未发生。控制器可区分预留、已知使用与尚未核清的占用，具体算法后续实现；没有可靠费用数据时不得宣称已实现货币硬封顶。

排队与并发沿[处理调度原则](处理板块-开发任务书-V0.1.md#67-本轮讨论调度的模型与程序分工)：保护当前交互和明确期限/承诺，同时防止后台任务、资料维护或某些企业长期拿不到执行机会。不固定为“前台永远优先”，不允许模型仅自称紧急就插队或突破上限；具体队列和公平性方法可以由 AI 在开发阶段选择并验证。

资源不足时，在已生效策略内延后可延后的抽查、探索或试验，保留排队原因和观察覆盖变化；动作前必要的权限/正确性检查不能因此跳过。将影响明确交付期限或质量要求时，呈现受阻部分和可选安排，按已有业务取舍权限处理；不能静默把正式交付降级或把未执行检查写成一切正常。

评测和自进化以后也有预算、并发及停止条件，不能挤占已承诺的业务资源；长时间推迟评测应显示覆盖不足，不能继续对外声称质量已得到验证。等待资料、决定或未来时间时保存等待条件，不用持续模型循环消耗预算。达到限制时停下相关新动作，允许必要的真实回执补报和清理，但不能借清理名义继续业务执行。

### 12.5 记录保留、观测开销与恢复依据

建议把业务事实/必要审计、可重算汇总、受权限保护的评价证据及临时诊断分开维护。优先引用已有来源及版本，记录关键行为；不要求保存全部提示词、隐藏推理、屏幕行为或永久全文副本。详细内容和自由文本不进入总台运行汇总，脱敏仍不自动获得跨企业用途。

观测本身需要有读取、采样、存储、重试和积压的上限：可重算汇总或非关键详细诊断允许延后、合并或按既定保留规则清理，必须显示缺失及最近更新时间；不能为了限流静默丢弃业务授权、去重或关键执行事实。处理积压时不因重放观测事件重做业务动作，重复或迟到事件按原版本关联。

[管理任务书第 15 节](三端管理与共用平台-开发任务书-V0.1.md#15-数据保留删除导出与恢复)已补按用途保留、关联删除、三端导出及恢复的设计建议。具体保留期、删除、导出、备份覆盖及恢复权限仍在管理汇总/全局专题收口，依赖这些决定的新数据保存功能在相应实现前明确。撤权或原文删除后，评价详情及副本不能继续成为内容读取旁路；必要审计与业务恢复需要保留什么，应有明确对象和依据，不承诺无限重放或立即抹除所有历史备份。

已有本地备份、新目录还原和引擎切换演练可以作为工程基础，但仍限于各自验证范围，见[本地备份边界](M7-A1本地备份与还原边界.md)、[最新计量与备份增量](M7-A1模型尝试计量与执行限制.md)及[升级边界](M7-A1引擎升级与回退边界.md)。观测增加“备份成功”标记不能代替真实还原检查；云灾备、生产容量、恢复目标及任意版本回退不因本轮任务书而完成。

## 13. 评估板块阶段汇总与自进化衔接

本节汇总第 1—12 节，形成后续可分工的任务范围；新方案仍为设计建议，未全量冻结或执行。沿 M7 及相关 M2/M3/M4/M5/M6 组织增量，不新增独立管理端、运行时或完整实验平台作为基础系统前提。

### 13.1 首版拟交付的最小完整能力

| 拟交付能力 | 复用与新增任务 | 完成依据 |
| --- | --- | --- |
| 可解释的基础运行观测 | 复用任务/尝试与用量账本、已有管理端汇总；补相关等待/耗时、异常影响和必要版本关联 | 范围、窗口、状态及未知数据可核对，真实运行与合成评测不混计 |
| 异常定位及受控恢复 | 复用原任务取消/重试和发布机制；补异常关联、处理责任、恢复依据及受影响成果复核 | 区分缺资料、技术失败、质量问题和结果未知，安全恢复不重复业务动作 |
| 最小质量评价 | 复用目标、来源、成果及反馈；建立代表样例与标准关联、客观检查和按需语义评价/复核 | 真实错误、重要遗漏、人工修订及证据不足能够呈现，评价不改变业务历史 |
| 针对性方法比较 | 关联基准/候选、适用范围、样例/标准/方法版本及分项结果 | 能区分改善、退化、取舍和不可比；在所测范围提供人工更新或后续自进化采用的依据 |
| 有边界的资源使用 | 复用现有技术限制与计量；补用途、所属任务/委托关联、总量约束、排队与受阻说明 | 重试/子任务不能绕过限制，正常业务与评测消耗可区分，未知不冒充零值或账单 |
| 获权查看和管理 | 将第 8、11.7、12 节需要合并到三端专题；复用现有页面和身份边界 | 使用者能理解影响及可做动作，总台仍无客户内容入口，管理头衔不自动获得业务决定权 |

“最小完整”指代表任务能够从运行事实、评价到问题处理闭环，不要求首版评估所有行业、所有业务结果或每一次模型步骤。异步抽查可以只覆盖部分任务，但覆盖程度真实可见；已实现的前端 Demo 或本地合成验收不替代真实模型和实际使用验证。

### 13.2 首版暂不扩展的内容

暂不以全量逐步打分、每任务人工验收、综合企业价值评分、大规模在线实验、完整供应商账单/商业计费、永久全量日志、通用自动修复平台或独立评测门户作为首版要求。更完整成本能力按真实需要另行确认；现有技术限制和未知消耗处理仍必须保留。

系统外业务触达沿 DEC-088 后置 App。独立自进化的自主诊断、生成候选、试验和采用在基础系统完整开发后接入测试；基础质量检查、正常维护和人工研发所需评估不一并后置。当前不创建后台定时任务、空自进化服务或真实实验。

### 13.3 跨板块依赖与最少交接

| 对应板块 | 需要提供或承接什么 | 边界 |
| --- | --- | --- |
| 输入 | 来源/解析/索引状态，实际版本、范围与缺口 | 不把资料不存在、未授权与处理失败混为一类；原文权限随评价引用继续生效 |
| 处理 | 有效目标、任务/尝试、关键动作与真实结果、实际方法组合、等待和计划覆盖 | 任务状态及调度事实由原模块负责，观测不另造成功状态或默认新增持续计划 |
| 输出 | 成果/呈现/站内交付版本，实际曝光与反馈、纠正记录 | 没反馈不等于满意，提醒失败与结果未生成不同，未记录的历史行为不倒造 |
| 三端及共用平台 | 运行/评价查看，标准和样例维护，资源/异常处理及范围内采用权 | 查看、执行、决定、发布和采用分别校验；具体页面在后续统一落定 |
| 独立自进化 | 通过获准入口读取运行证据、提交候选评估、取得比较与持续观察结果 | 不能自行放宽同轮标准、获得全部客户内容、改业务事实或绕过发布；停用它不影响基础观测与维护 |

交接首先约定这些含义，物理表、事件系统、接口细节和产品模型由后续实现及验证决定。优先复用现有平台事实和版本化契约，不要求先开发完整通用框架才交付代表任务。

### 13.4 尚需后续专题及全局汇总明确的事项

| 未决项 | 后续收口位置及实施边界 |
| --- | --- |
| 首批代表任务、资料及评价依据 | 全局汇总选择获准场景，区分合成与真实验收；与相应输入/处理/输出切片一起落实，不等齐所有行业题库 |
| 可接受延迟、资源限制、评测频率和观察窗口 | 管理/全局按规模、任务承诺及真实测量明确；不得把当前技术默认值自动升级为商业承诺 |
| 运行/内容/业务标准的维护者和可自动处置范围 | 三端专题分别确定范围和动作，复用已有授权；对实际新增的权限在相关功能启用前明确 |
| 数据保留、删除、导出和备份恢复 | 三端/全局明确对象、期限和权限；生产恢复目标及真实演练随部署方案落实 |
| 方法采用、并行候选及停止条件 | 自进化专题补独立运行与试验生命周期，三端确认采用策略，全局处理兼容/迁移；本轮不授予自动试验或采用权 |
| 真实供应商、容量和用户体验验收 | 沿已有接入边界，在相应统一执行切片取得证据；历史本地检查不作新功能已通过依据 |

这些未决项不阻止进入自进化讨论，也不意味着相应业务决定已由实现自行确认。具体算法和组件选择可由开发在已授权范围内自主验证；实质权限、费用和交付承诺依赖的决定须在受影响动作前明确。

### 13.5 整体验收如何贯通

统一执行时结合第 9、11.7 节，至少贯通以下场景；本轮没有运行这些检查：

1. 获准任务完成 → 真实结果与用量可核对 → 按适用标准评价 → 反馈/人工修订关联确切版本，不能把合成运行或补救成果算成原模型直接成功。
2. 写入或发布后回执丢失 → 核对原动作及成果 → 记录恢复结果；确认不了时保持待核对，无关获准工作仍能运行，不重复业务动作。
3. 同一依赖异常影响多个任务 → 合并范围内提醒 → 按既有策略处置 → 核对服务及成果恢复；静默提醒、技术恢复与业务复核各有真实状态。
4. 持续交互与后台承诺并存、资源不足 → 按已生效策略安排且后台不过度等待 → 评测覆盖/受阻影响可见；子任务、重试和评测不能绕过总量约束。
5. 非关键统计或评测不可用 → 显示缺失并按上限恢复，正常任务不被额外阻断；授权/去重等必要前提不可确认时，只停止受影响动作。
6. 代表样例比较候选 → 明确质量/成本取舍和证据限制 → 有权者按范围采用或不采用 → 后续观察能发现退化；自进化全程未部署也能完成基础流程。
7. 企业停用、资料撤权或用户删除内容 → 任务、评价引用、缓存与管理展示一致处理；总台及备份管理页面不能成为新的客户内容入口。

### 13.6 最新接续：统一三端管理

评估和[独立自进化](独立自进化-开发任务书-V0.1.md#12-自进化板块阶段汇总与三端管理衔接)均已形成阶段汇总；自进化触发与分范围预授权方向获认可（DEC-091），具体策略未全量冻结。现已进入[三端管理与共用平台任务书](三端管理与共用平台-开发任务书-V0.1.md)，首轮归并对象/动作/范围、页面及共用能力，下一轮细化组织角色及授权生命周期。自进化复用本板块的证据、评估和正常发布能力，仍在基础系统完整开发后接入并测试效果。

自进化任务书同样登记需要查看和操作的对象、状态、范围、证据与使用者，随后将全部板块一起映射到三端管理，再完成全局任务汇总。阶段汇总不等于全部设计获确认，也不改变当前只讨论与文档整理的授权边界。
