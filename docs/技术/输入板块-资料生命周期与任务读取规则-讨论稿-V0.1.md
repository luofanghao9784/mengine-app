## 1. 示例与设计目标

采用合成业务情境：企业成员在获准共享空间提供一份“9 月 21—27 日销售报表”，希望 AI 整理本周情况，并在有可比较上周数据时分析变化。随后补交同一周期的修正版，再提供下一周报表。文件可来自人工导出，本文不实际上传或接入客户系统。

输入对任务负责的是：在当前权限内提供所需内容及其确切依据，说明时间、口径和缺口。资料不足时仍可交付可用部分；是否继续分析、补查或请用户补充，由处理板块结合目标决定。

本文约束业务结果与交接含义，解析、分类、索引及工具组合可调整，不把示例步骤强制应用于所有输入。

## 2. 最少区分四种信息

| 信息 | 示例 | 保存与变化规则建议 |
| --- | --- | --- |
| 业务来源说明 | 销售周报来源，提供人、用途、覆盖范围、周期和已知口径 | 一个来源可以持续提供多份资料；来源不是某一份文件，连接管理与内容权限分开 |
| 原始依据及版本 | 本周报表 v1，同周期修正版 v2 | 保留具体原件/获准引用、版本、平台确认的归属、提供时间和摘要；上传时间不充当业务发生时间 |
| 解析或整理结果 | v2 的表格提取、字段映射、核验结果与检索索引 | 关联原件版本、解析批次和方法版本；改进解析方法不冒充原件发生变化，可在资料规则允许时重建 |
| 任务实际使用记录 | 本次分析实际读取了哪份报表、哪一版本和哪些派生结果 | 按任务/尝试记录实际读取依据与缺口；选中资料、交付字节和内容核验分别表达 |

这是逻辑区分，不要求创建四个新服务、四张表或复制既有平台记录。归属、权限和版本标识由平台确定，正文和模型提取的值不能自行扩大读取范围。

“任务实际使用”依据工具实际交付记录和成果引用表达，不推断模型内部究竟理解或依赖了哪段文字；工具交付、成果引用和事实核验分别记录，不为此保存完整模型上下文或隐藏推理。

下一周报表属于同一业务来源下的另一周期资料，不能自动当作上周资料的修正版覆盖。需要区分“同周期修正”“新周期数据”“累计快照或增量记录”；日期或文件名不足以确定时，保留候选关系，由维护者在必要时确认。

## 3. 首次进入：先保存依据，再逐步提高可用性

| 发生什么 | 输入应保存或返回什么 | 谁负责 |
| --- | --- | --- |
| 成员上传本周报表 | 校验维护权限；保存原件、确切版本、上传回执和已有来源说明 | 平台执行权限与持久化；成员或既有配置提供来源信息 |
| 系统读取格式与内容 | 解析批次、实际读取范围、成功/部分/失败及警告；字段、表头与原文位置 | 已有解析工具或获准模型，保留证据 |
| 识别业务含义 | 如金额单位、业务周期、门店范围、是否包含取消记录；明确已知、候选或未知 | 优先复用已核验口径；AI 可提出映射，影响结论且无依据的歧义交业务方澄清 |
| 任务开始使用 | 按该任务需要返回片段、受控原件或查询结果及缺口 | 平台复核当前权限，处理模型按需读取 |

不要求每份资料所有字段都人工审批。既定来源、格式和口径可复用；普通文稿不强制填写销售字段。未知金额口径可能影响精确统计，但不一定妨碍读取文字备注，应按使用目的表达限制。

“已保存”“已解析”“统计所需信息齐备”“已有人核验”具有不同含义，不合并成一个通用可信分数。AI 填写的置信度也不替代核验依据。

## 4. 更新：区分修正、重复和新周期

### 4.1 同一周期修正版

成员明确更新本周资料，保存 v2，保留 v1。v2 的解析、索引和业务检查独立记录，不能复用 v1 的“已完成”状态。

建议明确展示最新收到版本与其当前可用能力。v2 尚未完成解析时，仍可说明原件已保存；如当前任务获准读取原件，可尝试其他适用方法。需要已解析数据而 v2 暂不可用时，返回具体原因。

若任务允许使用较早数据，处理可以明确选择仍获准的 v1，并记录日期和限制；不得把旧版标成最新已核实数据。用户指定 v2 时不能静默替换为 v1。这里的旧版选择能力是新增设计建议，不描述为当前已有自动回退。

### 4.2 重复交付与覆盖关系

- 同一次请求因断网重试，复用原请求标识，不产生第二次有效导入。建议回执能定位该次成功保存的确切版本，并将其与资料当前版本区分；当前接口重试返回当前资料状态，尚不具备这个固定回执语义。
- 不同请求提交相同字节，可在同一企业、同一来源和目标范围内提示候选重复；文件摘要相同不自动证明业务周期和用途相同，不跨权限合并资料或泄露重复关系。
- 两份不同文件包含相同业务记录，不能只靠文件摘要去重；汇总前需根据来源口径识别业务主键、周期、快照或增量含义。无可靠依据时提示可能重叠，不默认全部相加。
- 同周期修正取代的是该周期分析的有效数据依据，不将 v1 与 v2 当作两批新增销售记录；若目标是比较修订差异，可明确同时读取。

### 4.3 下一周期及历史成果

下一周资料复用来源和已验证映射，但形成新的周期记录。月累计报表、周明细和修正版可能覆盖相同事实，需要按任务选择兼容依据。

已有会话回复和画报保留生成时使用的确切版本，不自动改写历史结论。后续重新分析形成新的任务/成果记录并说明依据变化。自动重算、通知或重新推送由处理/输出的触发规则另行决定，不因输入更新而新增全员通知。

## 5. 任务读取：先找范围，再固定实际依据

示例任务是“整理本周销售情况，并与上周比较”。任务说明表达目标周期、允许的数据范围和必要结果，输入据此在当前授权内寻找资料；主模型不需要一次接收全企业数据。

### 5.1 版本选择建议

1. 用户指定原件版本时，保持该确切选择，沿用现有原件授权规则。
2. 自动检索先发现候选资料；准备将某份资料用于本次分析时，记录确切版本与派生批次，后续补读同一资料保持一致。新上传不在一次分析中静默替换它。
3. 任务需要刷新到更新资料时，明确记录重新选择的依据和受影响计算；不把新旧版本混合算作同一批事实。重试应保留已确定的输入选择；需新数据时明确刷新并记录与原尝试的区别。
4. 多个来源分别记录周期和采集时点；版本固定不意味着不同系统天然具有同一时刻的完整快照。跨周期或口径不可比要作为缺口返回。
5. 每次读取仍复核当前权限。版本固定不延续已撤回授权，已进入执行环境的字节也不承诺瞬时收回。

第 2—4 项为待实现/验证的目标规则。当前未选原件时的默认检索并未提供整个任务一致的版本快照，详见第 8 节。

### 5.2 输入回执示例

下表是信息含义，不是最终 API 字段或要求用户填写的表单。示例假设本周修正版已完成适用解析，但上周资料不存在。

| 信息 | 本次返回的示例 |
| --- | --- |
| 实际依据 | 本周报表 v2、对应解析批次、原始记录定位或受控读取入口 |
| 时间与范围 | 业务周期为 9 月 21—27 日；覆盖门店范围和上传时间分别记录 |
| 业务含义 | 已有依据的金额口径、单位和状态含义；没有依据的部分明确未知 |
| 已完成检查 | 已读取的工作表/行范围、格式与必需字段检查；如未做业务复核，明确未做 |
| 任务缺口 | 未取得可比较的上周资料，无法据此计算环比；检索覆盖不足时也说明限制 |
| 当前可继续的工作 | 可以基于本周现有证据整理情况；是否补充上周资料由处理结合任务决定 |

“未检索到匹配内容”“相关资料尚未解析”“解析只完成一部分”“所需周期缺失”要能分开说明。输入应依据实际检索范围和状态记录报告，不把检索无命中解释成企业没有这类业务。

## 6. 异常与责任

| 情况 | 系统应如何表现 | 后续处理 |
| --- | --- | --- |
| 上传失败或回执丢失 | 尚未成功与已成功但客户端未知分开；用原请求核对/重试 | 平台与客户端处理，不要求重新造一份数据 |
| 原件已保存但解析中/失败 | 保留原件状态，返回具体不可用能力；不显示为没有资料 | 系统按既定重试策略恢复，维护者可补交；获准任务可换方法读取 |
| 只读到部分表或字段 | 返回可用部分、未读取范围与警告 | 处理限制统计范围，不能把局部汇总冒充完整总计 |
| 字段或业务口径变化 | 区分格式变化和影响结论的含义变化，保留已知部分 | 复用或调整映射；真正缺少业务含义时由来源负责人说明 |
| 缺少上一周期或某门店 | 标明缺口及已覆盖范围，不填零 | 处理完成可做部分或请有责任的人补充 |
| 同周期多份冲突数据 | 返回候选关系和冲突依据，避免重复计入 | 按已确定来源优先级选择；尚无规则时由业务方确认 |
| 撤权、停用或来源被判定不可用 | 拒绝后续不再获准的读取及使用，依当前规则处理结果访问 | 技术修复不能绕过业务授权；独立发布副本沿既有授权规则管理 |

任务反馈、错误说明和来源名称自身也遵守权限。平台总台可观察去敏技术状态，不因此获得客户文件、聊天或提示内容；企业管理员配置来源不自动获得内容读取权。

## 7. 三个端只呈现各自需要的动作

- 客户端：上传/更新资料，查看所选及实际使用版本，了解解析和任务缺口，按权限补交或纠正。员工不必先配置完整数据源才能使用普通文件。
- 企业管理端：对需持续交付的来源配置用途、范围、更新责任和频率，查看获准状态；具体配置权限随切片落实，不让管理员设置检索步骤和模型分工。
- 平台总台：维护解析/连接能力版本，查看技术失败与运行指标；继续不提供客户内容排障入口。

这些是操作职责建议，不新增第四端，不把全部来源治理页面作为第一个增量的前置条件。

| 业务来源与口径 | 现有资料/知识契约没有完整的来源更新责任、业务周期、口径和核验表达 | 按目标任务补最少信息，自动候选与已确认事实分开；不先建全企业标准库 |

首个增量建议聚焦“任务知道自己用了什么，以及还有什么没拿到”：沿 M3/M4 补读取回执、自动选材的版本一致性与异常解释，并在已有客户端显示必要信息。上传回执沿 M2-C1 的既有请求幂等补齐确切版本关系；跨文件业务去重与持续来源管理随确有需要的后续切片接入，外部自动连接器不作为本轮前置。

具体契约版本、存储迁移、默认刷新方式和页面布局在实现切片中确定，本文没有直接修改协议文件。验证环境与正式入口沿[原件授权边界](M4-A1原件授权与版本边界.md)和当前配置分别核对。

## 9. 后续实现的验收实例

以下是应证明的行为，尚未执行：

1. 成功上传并解析 v1 后，任务回执能定位实际版本、解析批次和业务周期，未知口径保持未知。
2. 上传 v2 但尚未解析时，任务收到暂不可用原因；指定 v1 的任务仍使用 v1，指定 v2 不偷偷读取 v1。
3. 自动选材已经采用 v1 后上传 v2，同一分析后续补读保持一致；明确刷新与重试能解释使用版本。
4. 解析只完成部分内容时，警告进入任务依据，结果不把局部统计声明为完整总计。
5. 同请求重试不重复导入，能分清原成功版本与后续当前版本；业务来源适配时，进一步验证同周期修正版、下一周期、重叠累计报表不被默认重复相加。
6. 缺上周资料时允许交付本周有依据部分，不能编造环比或把上周值当零。
7. 读取期间撤权或停用后拒绝后续访问；跨企业、跨空间、私人资料及错误信息没有旁路泄露。

自进化后续可评估取数成本、解析质量、映射和检索方法；本轮先通过正常工程方法建立这些行为与证据，不验证自进化效果，也不限制模型在既有授权任务内选择工具和处理方法。

## 10. 首批开发任务说明：输入依据与异常可见

2026-09-28，用户认可三项能力可被自进化优化并询问下一步。本节将设计收敛为一项跨 M2-C1/M3-A1/M4-A1 的输入增量候选，保留原需求编号；状态为任务定义完成、运行实现未开始。现有模块的其余待办不因本节划分而消失，具体协议和迁移版本在实现时核定。

### 10.1 本批完成后应有的行为

成员上传资料后，能分清本次保存的版本与资料当前版本；AI 任务取得授权片段时，同时取得真实的解析状态和限制；一次分析补读同份资料时，依据版本可解释。用户在现有资料/会话界面看到必要版本及异常提示。

首批沿现有上传、解析片段检索和任务链路交付，不以正式开放原件读取、代码执行或新增业务系统连接为前提。验证模式下的原件工具继续单独标明，不把合成模型响应当作真实模型质量验收。

### 10.2 三项工作与完成依据

| 工作 | 本批具体内容 | 关键验收 |
| --- | --- | --- |
| A. 最小输入回执 | 保留现有片段、引用和受控句柄，补关联资料/版本、解析批次与方法、解析状态/警告、查询范围及可解释的缺口；平台记录实际交付，引擎将限制随内容交给模型，客户端显示必要提示 | PARTIAL 警告不丢失；解析中/失败与无匹配内容可区分；服务端异常不转换为空数组成功；撤权后的错误与元信息不泄露 |
| B. 已取得依据的一致性 | 对本任务已实际取得的资料记录版本与解析批次，后续补读保持关联；允许继续发现其他获准资料。刷新/比较产生明确的依据变更记录；重试不丢失已确定关系 | 上传新版或重解析时不静默混用；历史原件选择继续有效；无法恢复旧依据时明确失败或要求刷新，不假装读取成功 |
| C. 上传请求的确切版本回执 | 保留已有幂等防重复能力，将本次成功请求与确切版本关联；重试返回原成功版本及可见的当前状态，两者含义分开 | v1 上传成功、随后 v2 更新，再重试 v1 请求仍能定位 v1；相同请求改内容仍拒绝；失去当前访问权后不能借旧回执读取资料 |

业务周期、指标口径、事实核验等有权威记录时可以随回执带出，未知保持未知。本批不要求模型自动理解所有报表或为所有资料建立业务字段。

尚未解析的文件不能仅凭查询词就认定与任务相关。系统可以报告“所选资料尚未就绪”或“本次获准检索范围内有尚不可检索资料”；未判断相关性、未扫描全范围或结果分页时明确边界，不将范围状态包装成具体业务缺失结论。

### 10.3 接口与实现责任

| 边界 | 本批需要定义的信息或行为 | 现有承接位置 |
| --- | --- | --- |
| 上传入口 → 平台 → 客户端 | 原请求成功版本、当前版本、重复请求和冲突含义；保持客户端兼容或明确配套升级 | `MaterialService`、资料公开契约、`src/material/` |
| 解析/检索 → 任务授权层 | 内容、确切解析批次、警告、分页/覆盖限制和暂不可用原因；只返回当前可见范围 | `KnowledgeService`、知识契约、`AgentTaskService` |
| 平台 → 引擎检索工具 | 回执结构校验、限制随内容交付、服务失败与无匹配分开 | `engine/src/runtime/agent-task.ts` 的 `search_sources`；随实际变化核定平台回调版本 |
| 任务记录 → 会话界面 | 实际交付/引用依据及必要警告，模型不得自报成功来覆盖平台状态 | 会话公开契约、任务查询和 `src/conversation/` |

首个实现动作是写出上述回执的合成样例及兼容规则，再改平台持久化和查询、引擎解析及客户端展示，最后联调。上传回执与检索回执可在明确文件责任后并行；涉及共享契约和迁移由同一集成者协调。

语义名称先定义清楚，再选择最终 JSON 字段、表结构和发布版本；本稿不直接修改现行 schema 或虚构已存在的统一回执接口。旧引擎不具备新能力时明确兼容行为，不能声称它已获得警告与版本保证。

历史上传若只存资料 ID、无法可靠确定原请求对应版本，保持“未记录/不可确定”；不根据当前版本倒填历史。迁移以追加事实和兼容读取为主，不能修改已成功原件内容或重写历史成果。

### 10.4 本批验收包

使用两家合成企业及共享/私人资料，覆盖：正常读取、部分解析、新版排队/失败、同版重解析、读取后上传新版、显式刷新与重试、v1 上传回执丢失后 v2 更新、并发版本冲突、读取中撤权/取消、旧协议兼容。

平台与引擎的集成测试证明“实际回执和警告正确传递、版本关系正确、重复请求不重复导入”；客户端验证用户能辨认版本与异常。合成模型响应只能验证链路，不能证明真实模型一定尊重警告或业务结论正确；真实模型效果在获准资料、配置和预算后单独验收。

记录必要的查询耗时、回执大小、解析状态覆盖及重试结果作为初始运行基线；不把这一批扩成统计平台，也不预设没有测量依据的性能达标数字。本文第 9 节的跨文件业务去重和自动周期识别场景留给对应来源适配批次。

### 10.5 本批之后的范围

持续业务来源登记、自动同步、跨文件业务去重、周期识别、完整企业/用户档案及管理后台按后续任务推进。本批完成不等于输入板块全部完成；处理板块的经验检索与输出板块的交付规则可继续独立设计，不要求等所有外部渠道接通。

## 11. 三项能力与未来自进化的关系

用户已认可：质量回执、版本一致性和上传回执都可以成为自进化优化对象；具体算法、流程和数据结构允许替换。当前先建立初始实现及运行证据，基础系统完成后再验证自进化效果，见 DEC-079、DEC-082。

| 能力 | 可替换的方法 | 比较候选方法时应观察什么 |
| --- | --- | --- |
| 质量与缺口说明 | 异常识别、相关性判断、说明的组织方式、哪些处理提前做或按任务做 | 有标注样例上的漏报/误报、关键警告是否保留、查询耗时及上下文成本；未标注实际任务不能声称已有准确率 |
| 版本一致性 | 按资料/批次固定、变化检测、刷新时机、受影响部分重算及缓存 | 依据能否解释、是否混用不兼容版本、数据时效、重复读取与重算成本 |
| 上传与回执 | 幂等实现、事务/存储组织、回执查询与缓存方式 | 是否重复导入、原请求版本是否正确、并发失败行为、耗时与存储成本 |

权限、确切依据、不重复执行及不伪装成功是需要满足的业务责任。自进化可以提出改变业务规则或模块划分的方案，但其生效需要相应评估与授权；不能用提高平均效率来换取未获准的访问扩大或历史事实重写。

现在记录当前实现与方法版本、必要运行结果及可重复验证样例即可，不预建通用插件平台或自动发布服务。以后改变存储/协议需说明兼容、迁移与回退；替换后自进化服务停止，基础运行仍使用已经生效的持久方法。
