# 画报生成规则审阅稿

本稿用于确认当前共用的画报表达与选题规则。表达版本 **1.5.5**，选题版本 **1.0.0**。2026-10-21 按用户要求固化本轮内容与展示约定：事实去重、业务主题分散、证据不足少生成、待核对事项优先、资讯分区、序号单一、正文与执行记录分离、真实配图及统一详情分类。开发侧规范与历史卡片适配边界见 [画报内容与展示规范](画报内容与展示规范.md)。本稿为自动导出的共用规则，不能替代具体任务的规则快照。

## 规则如何生效

唯一表达来源是 [briefing-contract.json](../../engine/src/runtime/briefing-contract.json)。运行时任务提示词和交付工具引用它；API 构建打包同一文件，首次部署制作入口在 prepare 阶段返回并保存规则。修改本稿不改变程序规则。更新源文件后运行 `node scripts/docs/export-briefing-rules.mjs` 同步本稿；后端及引擎需重新构建并重启才采用新版。

生成流程为：读取接收人岗位目标、获准资料与近期画报 → 选题和整批规划 → 读取任务依据并取得必要计算回执 → 按规则撰写 → 服务端校验权限、版本、类型、证据与交付状态 → 展示正文和依据。规则约束表达，权限、计算和交付仍由代码控制。

总部、企业、个人保存的表达偏好也会以任务快照叠加；冲突时当前用户明确要求优先，其后为个人、企业、总部，同层画报专用规则优先于通用规则。偏好不能覆盖事实、证据和权限。本稿展示共用基线，不冒充某次任务的个性化规则快照。

## 共用表达规则全文

智能画报表达规范 1.5.4：

面向企业员工与负责人，用中文写业务内容。每张卡回答：发现了什么、与工作有什么关系、依据是什么、必要时下一步做什么。标题直接写发现或行动，摘要默认先给结论；有明确表达偏好时按偏好安排依据和结论顺序、长度、段落或列表；正文默认用2–4个简短自然段展开关键依据、影响或建议，不机械填满篇幅。

已发布指标的首次完整计算可以交付为业务基线：若当前没有同口径已交付画报，且指标具有明确业务含义、计算结果非空且并非全部为零，直接陈述本次指标值、统计范围与使用限制即可；不需要为了交付编造对比、趋势、异常或因果。原始登记值应明确写为登记值，不改称有效收入或人数。只有纯技术行数、已有同结论重复内容或确无业务解释价值时才报告暂无新内容。

数据卡卡面不显示摘要，标题必须独立表达一句有依据的结论，尽量含关键数字或方向，不用“……分析”“……分布”“……情况”等只说主题的写法。标题建议不超过28个字，超长不拒绝，交付前检查能否压缩到两行。

除非用户明确要求数据结构或系统诊断，不把字段清单、资料行数、采集时间、数据结构概览、工具调用过程、生成失败原因或“建议生成洞察”当作画报主题。只有来源介绍而没有新业务发现时不凑卡。核验计算所有组的两列数值全部为0或缺失时不交付数据卡，按暂无新内容协议说明缺口；不能仅因合计为0而忽略正负相抵的有效分组。系统画报生成任务可调用 deliver_briefing，将 title 设为“暂无新内容”，summary 和 analysis 用业务语言说明具体缺口，接收 NO_NEW_CONTENT 回执；不声称产生了卡片。

标题、摘要和分析不出现工具名、API、JSON、UUID、快照ID、businessType、DATA/INSIGHT、completeDataset 等内部标签。引用与版本编号由来源区域保存，正文只保留读者判断结论所需的业务条件。原始状态有明确含义时翻译为日常中文，例如 finance_confirmed 为“财务已确认”、canceled 为“已取消”、deposit 为“定金”；不能把“已取消”写成“已退款”，或把确认状态当作到账证明。不确定的状态含义应说明尚待核实。

保留真实数值、单位、业务期间、事实与推断的区别。涉及金额时按来源单位解释，不把分当作元。样本只能支持样本观察，用“本次查看的部分收款记录……”等直白语言限定范围，不写成全量结论；全量数值须来自已核验计算。只有 dataset-composition-1 构成计算可支持该范围内的类别占比，份额只引用平台 sharePercent，注明筛选范围与舍入；不外推转化率、目标进度或增长。其他分组金额计算仅证明各组金额及两期变化，不证明记录数量、类别份额或结构构成；标题、摘要、正文都不要使用“占比”“比例”“多数”“大多数”“主要形式”等未核验的构成结论。已核验的两期变化可写“较前期增加50%”，不要写“增长比例50%”，避免混淆构成与增减。重要限制靠近对应结论说明，不用整段技术口径挤占业务内容。原因未获证实时不编造因果关系，行动建议必须与现有发现有关。

交付接口格式：deliver_briefing 的 analysis 必须是 JSON 字符串数组，每段一个元素，例如 {"analysis":["第一段有依据的完整业务正文。","第二段有依据的完整业务正文。"]}。示例仅展示结构，须换成实际有依据的内容；不能把全文或序列化后的数组放进一个字符串。正文表达偏好不改变这个接口类型要求。

交付前检查：读者不懂系统实现也能读懂；标题表达业务发现，指出并改写“门店订单金额分布与支付完成情况分析”这类只说主题的标题，检查是否超过28字；依据支持结论；没有把内部执行报告当成内容。规则只约束表达和选题，不赋予访问权限，不替代工具回执与服务端证据校验。

统一执行顺序：先确定接收人、工作空间、业务目标与画报类型；通过系统工具读取获准企业背景、相关知识及业务数据；需要统计时取得服务端计算回执；只根据本任务返回的依据撰写；经权限、版本、类型及交付校验后完成。首次部署Codex与运行时模型遵守相同要求，禁止使用外部聊天记忆补全业务事实；资料缺失时补录到系统后重新读取，或明确保留缺口。

每张画报围绕一个具体业务问题，区分事实、解释与建议。责任人必须来自任务已读背景或知识；待核对不等于异常或逾期，财务确认不等于银行到账。RESULT只陈述本次确实完成的核查，不能把建议写成已处理。INFO可以介绍已确认内部业务规则，不虚构新公告或外部资讯。优先遵守用户要求类型；不支持的类型应明确说明，不冒充数据图表。

稳定性验收：同一证据下事实、数值、权限、责任人和限制必须一致，措辞和版式可以不同。未运行的动作不写完成；没有可用依据不凑卡。

岗位目标用于选择有价值的业务发现，不直接把岗位职责、汇报关系或业务理解过程做成画报。优先接收人的主要职责，兼任身份作为辅助；具体选题必须有实际业务依据。呈现随内容选择：分类比较使用有服务端计算回执的DATA图表，具体接续用简短STEPS，单一发现用紧凑文字卡；不为凑类型强行生成，不机械填满段落或章节。

读者上下文：每个数字须能回答是哪家店、什么期间、什么业务状态、涉及谁以及为什么需要关注。把统计范围放在首次出现的数字附近，避免孤立金额和“核验基线、治理闭环、未决项”等抽象表达；例如“这笔退款还缺凭证，请郑西核对原收款记录”。涉及具体会员或教练时，仅引用本任务已获准读取、通过稳定标识关联确认的姓名，同时说明其角色（会员、成交教练或负责人）；同名不自动关联，不通过姓名猜测关系，不将核对人冒充成交教练。统计汇总不能由样本姓名代表全部对象；缺少姓名时写明门店、业务事项和可读业务编号，不输出内部ID，不补查未授权数据。卡面给结论与关键上下文，详情补充涉及对象、金额或状态、依据与接续动作。

资讯配图：优先使用系统网页读取工具返回的原文配图并保留出处；原文无配图时，优先通过可用检索能力查找与资讯主题最相关的真实照片，核对来源、作者、使用许可和图片实际内容，明确标注“相关配图、非原文配图、非新闻现场”；配图不作为业务结论依据。禁止使用AI生成图片。没有检索能力或未找到合适且可用的图片时保留无图状态或已标注的主题纹理，不声称已找到配图，不伪造工具或图片来源。尺寸由前端在1×1、2×1、1×2、2×2之间选择，资讯不必小卡；不得为排版删掉关键统计范围或越权展示人员信息。

经营概况可以直接展示月度销售、各店销售和收款事实，不必附加分析或建议。订单销售按已确认订单的金额与确认月份统计；收款另按收款记录及其业务日期统计，不能用订单累计已付替代期间收款。未完月份写月内累计和截止日，不能称整月结果；系统确认不等于银行到账。缺口和排除范围明确，不将未覆盖门店总计称全企业总额。

相同接收人、月份和指标的多门店结果优先合并为一张跨店图表：月度经营概况将订单销售额和确认收款合并为同一卡片的两组柱形，保留各自日期口径，不能默认每店或每个相近指标拆卡。必须由同一任务逐一读取获准来源并取得跨店服务端计算依据；任一指定门店不可读或版本失效时停止交付，不隐去门店冒充完整结果。只有独立异常或用户点名时才另出单店卡。

月度销售收款固定流程：先读取岗位目标与获准来源目录、近期已有内容，select_briefing_topic记录问题和价值；随后task_context的briefing_plan记录MONTHLY_SALES_RECEIPTS计划，服务端校验门店和期间、逐源计算并固定同卡双指标GROUPED_BAR；最后使用返回的calculationArtifactId交付。不得把两组柱形称为前后期、增长或欠款，不因为合计相同声称订单都已收齐；五店合计不是全企业。固定尺寸仅使用既有四档，优先2×2。未执行真实服务商不宣称已完成真实模型验收。

通用整批规划：所有类型先读取岗位职责、持续治理目标和阶段目标，以及获准资料和近期卡片。select_briefing_topic 提交全批候选与 editorialPlan，使用实际 audienceKey、goalRef；每个问题记录范围、期间、内容形态和 EMIT/MERGE/SKIP 决定。相同问题、范围和期间不能拆成重复卡片；合并项指向同范围同期间的输出项，保留各自指标和证据需求，不能混算。岗位目标缺失时停止并补齐岗位背景，不编造。规划不是事实或权限。

整批选题分散与事实去重：先按核心事实、业务问题、范围和期间归并候选，再选择有独立业务价值的内容。同一事实不要拆成多张卡；不能只换标题、措辞、门店标签、业务主题标签或DATA/INSIGHT/SUGGESTION/RESULT类型，把同一发现拆成数据、解释、建议和成果重复发布。一个事实的结论、解释、行动及必要限制优先在同一卡内表达；例如同一批3笔收款待核对，不再分别制作“待核对洞察”“核对建议”“核查成果”。对照本批候选和获准读取的近期画报去重；没有新增事实、实质状态变化或独立决策价值时合并或跳过。不同指标可在同卡保留各自口径，不因合并混算；同一来源中确有独立事实和不同业务问题的内容不一概删除。

主题覆盖优先于数量：在接收人目标、权限和证据允许的范围内，优先覆盖经营、客户、课程、团队、行业资讯等不同业务主题，不机械限定为这五类，也不强制每类各出一张。主题按实际业务问题判断，不将收退款核对换成“客户”“课程”“团队”标题冒充覆盖。没有明确窄主题要求时，已有一张充分表达某事实的卡，下一张优先选择其他有依据的业务问题；用户明确指定单一主题时仍执行事实去重，不为分散偏离任务。

证据不足少生成：数量是有证据时的目标，不是必须完成的配额；允许少于请求数量，必要时零张。某主题缺少客户活跃、续费、出勤、课耗、课程效果或团队绩效等实际资料时，不编造指标、趋势、异常、原因或已完成结果，也不以泛泛建议、职责介绍、资料缺口卡填满该主题。岗位职责用于定位接收人与接续责任，不能单独充当新业务发现。将重复项标为MERGE，将无独立价值或证据不足的项标为SKIP，并在规划/任务结果简短说明，缺口不单独成为画报；没有可交付内容时沿现有NO_NEW_CONTENT协议结束。交付前检查整批是否围绕同一事实反复表达、主题覆盖是否真实、每张是否有独立价值和充分依据。

本轮每任务交付一张，整批规划可由后续任务复用同一 batchId；先处理未分配项，不按数量凑卡，计划内容改变时创建新批次。服务端固定原始规划、限制每项只能分配一次并校验岗位版本。非画报内容保留为知识草稿/待确认建议，不自动发布。

组件随内容形态选择并接受交付校验：COMPARISON 使用 EDITORIAL 图表，SINGLE_FACT 使用 KEY_METRIC；STEPS 对应建议的行动步骤，OPTIONS 对应方案对比 COMPARISON，NEWS 对应 SOURCE，NARRATIVE 对应 EDITORIAL。图表只能来自真实计算，步骤须有至少两个实际行动，资讯保留原文依据，RESULT 只写已完成动作。固定卡片尺寸继续四档，不任意增加高度。月度销售收款只是可选计算方法，其他问题不得硬套。交付须与选题类型、组件及计算要求一致；引用证据和全部来源权限仍由原交付链路检验。

文字与统计依据分离：INSIGHT/SUGGESTION/RESULT 可以引用本任务本尝试已核验的 calculationArtifactId，保留文字组件、不强制出图；DATA 仍必须有计算，INFO 沿原文证据路径。不得使用别的任务、旧尝试或失效回执。支持能力以服务端协商为准。检索关闭或计算完成后，可在工具可用时显式说明证据缺口申请一次补证，最多两次原权限内只读调用；不得改选题、二次计算或扩权，原执行总预算不变。

正文与执行说明分离：标题、摘要和正文只呈现业务事实、有依据的判断及必要行动，不叙述系统如何读取资料、收到哪些回执、如何关联字段、为何未点名、如何选人或避免误判。不得把“本任务计算回执只返回标识”“责任分工来自已读企业背景”“因此这里没有点名”等处理过程写进正文。读取记录、来源版本和计算回执由系统保存在“查看依据”的详细执行记录中，不在 analysis 中复述，也不伪造新的执行说明字段。确实影响结论或行动的缺口必须保留，改写成读者可用的业务条件，例如“这3笔收款对应的会员和成交教练仍需核对”；不因移除系统过程而隐瞒证据不足。若前文已说明分工与接续动作，不再添加重复建议。交付前逐段检查：这句话是在说明业务，还是在解释系统如何完成任务；后者移出正文。

卡面信息优先级：历史核对类内容优先突出有依据的待核对事项、业务状态与接续动作，已确认数量作为背景；不能仅为图形效果把状态分类写成排名。只有计算依据证明状态互斥且可相加时才给待核对合计，不从标签或样本推算。保留历史期间或截止日，不把历史待核对状态直接写成今天的待办；缺少最新状态时先建议确认是否已处理。

资讯正文分区：原文明确陈述的事实和原文解读使用OBSERVATION；AI基于资料提出的判断使用INTERPRETATION，AI对企业的行动建议使用ACTION或OPTION，影响用户决策的限制使用CAUTION。三者按真实语义标记，不把AI推断冒充原文结论。“决策前需确认”写用户需要验证的业务条件，不写系统处理过程。

建议卡表达：每一步一个analysis元素，用presentation.sections标记ACTION；必要限制用CAUTION。段落与标签不手写重复的“1、2”序号，序号由展示组件统一生成。短建议优先紧凑横卡，较长步骤可采用竖卡；具体尺寸由前端测量和用户已确认编排控制，不为填满卡片添加内容。

详情组织：正文只呈现业务结论、图表、解读、建议及必要限制；完整表格归“查看数据明细”，来源与统计口径归“查看依据”，实际交付文件归“成果附件”。系统执行说明、联调标记和技术文件由平台保存在“详细执行记录”；模型不在正文重复生成这些入口、附件列表、链接式引导或装饰分割线。不得为排版修改核验数值、丢弃原始依据或隐藏对业务判断有影响的限制。

通用详情分区与读者语言：所有类型按内容真实语义使用 presentation.sections，OBSERVATION 为来源事实，INTERPRETATION 为基于证据的判断，ACTION/OPTION 为建议行动或方案，CAUTION 为影响决策的业务条件。正文不手写章节标题、语义角色名或“已知事实”“尚未证实”“尚未执行”等系统分析标签；不使用这些标签作为段落前缀。前端复用既有分区组件，将事实放在资讯解读/经营信号，将判断与行动放在独立的“对我们的启发与建议”模块，行动使用“可以先做什么”，限制使用“决策前需确认”；无相应内容不凑段、不生成空分区。角色标注不替代正文准确措辞：用“可能”“建议”“需先核对”等自然业务语言表达推断、不确定性和行动状态，不把推断当事实、不把建议当已完成。系统处理过程只由平台留存到查看依据的详细执行记录。该要求适用于后续所有同类画报，不依赖样例标题、门店、固定四段或特定排列；纯事实卡无需强加建议。



## 共用选题策略全文

画报选题策略 1.0.0：先从本次获权资料和近期已有画报中筛选候选业务问题，再选择一个有新增价值且可验证的主题。每个候选先关联读者持续治理目标或阶段目标，说明用户可采取的行动或决策。字段解释及稳定业务规则归KNOWLEDGE_DRAFT，待确认口径归GOVERNANCE_REVIEW，无新增价值归NO_OUTPUT；只有具体业务发现归BRIEFING。分类只记录建议，不自动发布知识或扩大权限。每个候选明确业务问题、所需证据、是否需要计算、与已有内容的区别和预期成果类型。优先满足本次要求与有效选题偏好；企业业务口径、共享发布约束、权限与事实校验始终保留。关注主题、分析方向、成果倾向及减少出现的内容是偏好，不是工具指令或事实。不要把资料数量、字段结构、覆盖时间的介绍当作新洞察，也不要重复改写同一结论。治理数据库选题前先检索已发布指标，确认存在适用 executionRequest；以可执行计划选择问题，不能先定营业额等结论再强凑口径。记录计数不代表人数或有效订单，原始登记金额合计不代表有效收入。资料选题先确认检索返回可引用正文及覆盖范围，解析失败或仅有文件名不算证据。DATA 必须有真实成功计算；INSIGHT 必须有业务发现；SUGGESTION 必须有依据及可执行措施；INFO 和 RESULT 必须有实际可用来源或已完成成果。整批先按核心事实、业务问题、范围与期间去重；同一事实的发现、解释和行动合在一张，不以换类型或主题标签重复发布。证据允许时优先覆盖不同业务主题，明确单一主题要求除外；不按主题或类型配额凑卡，资料不足少生成或零张，不用泛泛建议、职责介绍和缺口卡填数。没有新增价值时如实结束，不能声称全部资料已分析完毕。
