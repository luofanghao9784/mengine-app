## 已确认的技术方向

开发主要使用 GPT-6 coding agent；下表的 AI 执行方向指产品运行时。两者分别选型，开发工具的选择不改变产品的模型与 Harness 意向。

| 方向 | 当前结论 | 尚未冻结的部分 |
| --- | --- | --- |
| 业务平台与网页 | Java＋Spring Boot 业务平台；网页继续 React＋TypeScript＋Vite | JDK/框架版本、持久层及普通依赖在实施中选择并验证 |
| 梦核引擎 | 独立服务、构建、发布与回退；会话和后台分析共用 | 实现语言、运行时版本、契约与升级验收细节 |
| 部署 | 租用云端服务器提供产品服务 | 云厂商、地区、规格、可用性目标和月度预算 |
| 企业隔离 | 多家企业共用基础设施，数据与任务按企业隔离 | 数据库、存储、检索、缓存与执行环境的具体隔离方案 |
| AI 执行 | 用户提出以 DeepSeek Harness 为产品基础方向 | 具体项目与版本、接入边界、许可条件、运行与恢复能力仍需验证 |
| 企业资源 | AI 直接调用企业资料环境，工作成果在云端处理与积累 | 检索、文件解析、结构化数据、工具接口的实现 |
| 客户端 | 网页先覆盖 macOS、Windows、iOS、Android、HarmonyOS | 最低浏览器版本、真机清单及响应式交互 |
| 后续扩展 | 网页成熟后开发 iOS/Android/HarmonyOS App，再开发 macOS/Windows App；后端共用，前端可分别适配 | 原生框架、端能力适配与分发；小程序本轮未排期 |
| 工作方式 | 云端为主，先支持草稿恢复和文件上传下载 | 草稿跨设备策略；完整离线同步及本地执行不在当前范围 |

2026-09-21 已只读核对 [DeepSeek Harness 官方仓库](https://github.com/deepseek-ai/deepseek-harness)、官网、架构和安全说明，确认官方项目及 MIT 许可标示；项目仍为开发者预览。具体版本/提交、依赖许可、实际接入、任务恢复与企业隔离仍待原型验证，未安装或执行 Harness。不据此宣称已具备完整办公文件处理或生产交付能力。

## 建议的能力边界

以下为实现建议，帮助后续选型保持职责清晰。

| 能力层 | 负责什么 | 不宜依赖什么 |
| --- | --- | --- |
| 网页交互 | 会话、空间、资料、任务与确认的界面 | 不把权限检查只放在浏览器中 |
| 企业业务服务 | 企业、成员、权限、空间、资料版本、业务记录与计费口径 | 不将企业核心数据仅保存在模型上下文或 Harness 会话中 |
| AI 执行适配 | 将任务交给 Harness，提供获准工具，返回状态与产物 | 不假定更换模型会自动解决工作流与数据治理 |
| 异步任务 | 调度、取消、等待确认、恢复与重复执行防护 | 不把“重新运行”视为必然安全的任务恢复 |
| 文件与检索 | 原始文件、解析结果、检索索引、版本与访问控制 | 不把向量索引当作唯一原始资料存储 |
| 隔离执行环境 | 文件处理及后续 AI 生成代码的受限执行 | 不让生成代码默认访问生产数据库、全部企业文件或主机凭据 |
| 事件与记录 | 记录真实操作，支持工作动态、追溯与故障定位 | 不用 AI 自述代替实际执行成功记录 |

个人仪表盘、空间仪表盘、后台整理和跨部门协作应复用上述能力，避免各自维护一套权限与资料体系。

## 按依赖推进的技术验证与交付验收

接入 Harness 前核实来源、版本、许可和实际接口；运行能力通过开发原型验证；交付前完成相关业务验收。“首期必要”表示首期交付需要具备的证据，不表示所有项目都必须在代码骨架建立前验证完毕。不依赖 Harness 的界面、业务接口和合成数据流程可以先行，模拟结果不得作为真实运行证据。

| 优先级 | 问题 | 建议验证方式 |
| --- | --- | --- |
| 首期必要 | Harness 究竟如何嵌入服务端，是否适合当前交付范围 | 接入前核实来源、版本、许可和实际接口；开发中用小型原型跑通接收任务、调用授权工具、返回产物 |
| 首期必要 | 不同企业与不同空间的数据能否真正隔离 | 用两家企业及不同成员的测试数据，覆盖检索、预览、下载、缓存和动态 |
| 首期必要 | 文件能否支撑选中的真实工作 | 开发可先用合成文件；交付前用获准使用的代表性文件检验解析、引用与生成质量，区分两类证据 |
| 首期必要 | 长任务和人工确认如何连续完成 | 验证网页断开、任务失败、确认等待、取消与重试时的实际行为 |
| 首期必要 | 单次任务与单客户成本能否记录 | 记录模型调用、执行资源、存储处理及人工复核投入，形成可归因成本 |
| 首期必要 | 服务终止或人员退出如何移交 | 明确资料、成果和责任归属，验证导出、撤销访问与交接 |
| 后续能力前 | 后台整理是否能减少维护负担 | 对小范围资料运行，比较发现的有效问题与新增人工确认量 |
| 后续能力前 | 跨部门请求能否在不扩大原始权限的情况下交付 | 分别检查请求许可、执行范围、结果审核和接收方可见内容 |
| 后续能力前 | AI 生成组件能否持续维护 | 验证预览、数据权限、发布、撤回、版本兼容与错误恢复 |

## 技术选型登记方式

2026-09-17 前端 Demo 已选择 React + TypeScript + Vite，Lucide 提供统一图标，localStorage 保留演示状态；选型原因与替换影响见 DEC-022。2026-09-21 用户已确认 Spring Boot 业务平台＋独立梦核引擎、前端继续 React，见 DEC-037。数据库、对象存储、检索、队列和执行隔离的配套选型继续细化。在已授权目标内，可先完成可逆的技术选择与验证，按需记录实现决定或暂定方案；无需等待全部技术栈冻结才开工。重要选择按下列口径记录：

1. 选择解决哪一项已确认需求。
2. 为什么适合两人团队维护，以及当前预计的费用与复杂度。
3. 使用哪个具体项目、版本和许可证；依据核验时间是什么。
4. 原型已经验证什么、还没有验证什么。
5. 如果不适用，替换影响是否局限在明确边界内。

后续客户端可以共享服务端业务接口与权限体系，但桌面、本地文件访问、移动端、小程序的界面与平台能力仍需分别适配，不把“后端可复用”表述为“所有端零改造支持”。

## 下一次产品讨论需要优先回答

- 第一项需要稳定完成的工作是什么，输入和交付文件分别是什么？
- 员工从会话进入空间，还是在空间内开启会话；私人会话如何转成共享成果？
- 哪些操作可以直接执行，哪些必须确认，失败或取消后如何处理？
- 第一版是否需要跨部门申请，还是在同一授权空间内先完成协作？
- FDE 在一次标准实施中交付哪些配置，后续由谁维护？

用户明确的业务决定应回写需求基线，再据此确定相关交付范围。未决事项只阻塞依赖其答案的实现；页面布局等可逆交互选择可在授权范围内先行，记录为暂定方案，不作为用户已确认的业务规则。
