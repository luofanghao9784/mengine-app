## 1. 设计判断

建议采用两套相互连接的循环：

- **工作循环：** 感知变化 → 判断是否值得处理 → 补齐上下文 → 核实与分析 → 在授权内推进 → 判断是否需要通知。
- **改进循环：** 收集纠正与实际结果 → 找到重复问题 → 生成候选改法 → 对照评估 → 按影响范围试用/启用 → 观察与回退。

最适合当前项目的起点是“有边界的动态机制”：允许 AI 选择内容、深度和节奏，同时由平台约束权限、费用、运行期限和发布范围。是否最优需要三个试点的数据来判断，当前不能预先宣称某种频率或自治程度最佳。

主要风险是两类反馈放大：无意义的变化不断触发分析、分析又产生更多事件；未经核实的经验进入记忆，随后被反复引用成为更确信的错误。设计必须能阻断这两种循环。

## 2. 主动性的四个独立决定

| 决定 | 含义 | 例子 |
| --- | --- | --- |
| 关注 | 哪些目标、责任或问题值得持续关注 | 某项目交付承诺、本周经营变化、岗位待处理事项 |
| 启动 | 什么变化或时间条件值得检查 | 新文件、状态变化、截止临近、资料长期未更新 |
| 执行 | 本轮可做到哪里 | 检索核实、生成草案、提交待确认动作、调用获准工具 |
| 告知 | 什么值得呈现给谁 | 只更新索引、合并进画报、提示负责人、紧急升级 |

四者不应绑定为一个“主动程度”开关。频繁检查可以保持少量提醒；低频检查也可能产生重要紧急提醒。获准自动分析不代表获准自动发布或对外发送。

## 3. 关注目标从哪里来

2026-09-29 补充：用户要求将《探讨梦擎的数据处理目标》会话并入当前开发讨论。默认职责、目标形成与冷启动的当前建议见[处理任务书第 4.1—4.4 节](处理板块-开发任务书-V0.1.md)，来源和确认范围见 DEC-086。用户不必先手动设定完整目标；系统可在已生效的基础策略和授权内先开展有限分析，通过初次成果与互动校准。以下三种关注来源继续适用，不要求每个候选在分析前单独确认；具体默认策略、长期关注及业务动作沿对应授权处理。

建议组合三种来源，减轻用户配置负担，同时保留责任依据：

1. **用户明确目标。** 例如“持续关注本项目需求变更对交付计划的影响”。可设置资料、负责人、结束条件和预算。
2. **岗位/场景默认关注。** 在用户已有职责和授权内，加载少量可解释的模板；首次让用户看见并调整。9POP 管理者和群力员工采用不同模板，共用引擎。
3. **引擎提出的新关注。** 从重复问题和新证据发现潜在主题，在允许的探索预算内准备依据。临时只读探索可预授权；成为长期目标、扩大资料范围或采取业务动作时按规则确认。

关注目标具有创建者、来源、作用范围、责任人、重要性、有效期、完成/终止条件。推测出的职责不自动升级为实际责任；不存在负责人时提示缺口。

## 4. 混合触发，而非每种事件都调用大模型

2026-09-29 接续建议见[处理任务书第 6.7 节](处理板块-开发任务书-V0.1.md#67-本轮讨论调度的模型与程序分工)：区分持续关注、生效计划和单次任务，补充模型/程序/Harness 分工、计划保存回执、变化覆盖、启停作用范围与中断后补做。以下机制按该职责细化，不代表已实现或启用调度；具体参数继续待确认。

| 触发方式 | 适用情况 | 处理建议 |
| --- | --- | --- |
| 用户请求 | 用户要立即分析或完成工作 | 优先执行，按需调用引擎环节；资源不足明确排队 |
| 资料/业务事件 | 新资料、有效版本变更、状态变化、反馈进入 | 先归并相关事件，再判定受影响目标 |
| 时间与承诺 | 临近截止、等待过久、约定回访、周期复盘 | 按实际时间约束检查；没有新文件也可能需要行动 |
| 周期兜底 | 没接事件源、漏掉变化、资料过期、任务遗漏 | 低频检查覆盖盲区，核对数据源是否更新成功 |
| 有界探索 | 新信息关联、潜在问题、可改进的方法 | 低优先级且有预算/时间上限，不挤占用户正在进行的工作 |

外部事件只作为不可信信号。每次读取和执行重新检查身份、企业、空间、当前权限与数据版本；事件携带的文本不能自行改变目标或授权。

### 4.1 一次触发怎样决策

1. 收到事件后记录来源、时间、版本、关联空间和可见范围。
2. 去重、合并同批变化，检查是否已有同一事项在运行；自身写入标识因果来源，避免无限自触发。
3. 通过元数据/版本差异判断是否真的变化，关联可能受影响的目标；无法可靠判断时保留周期核查兜底。
4. 先执行便宜且可核实的检查；只有确有分析价值或无法排除重要影响时调用更深入的模型/工具。
5. 按优先级、预算、并发和等待时间决定立即做、合并批处理、延后或本次不做；记录原因。
6. 产出后分别判断更新内部状态、画报内容、待确认工作还是提醒；同事项更新原记录。

用户应能按需查看：这次为何检查、使用什么依据、为何产生/没有产生提醒、下次何时检查。无需在日常页面暴露调度技术细节。

### 4.2 动态调节什么

建议每个关注目标有自己的调度策略，调整以下变量：

- 检查间隔：变化快、接近截止、有未解决关键问题时缩短；长期无有效变化时延长。
- 分析深度：先做增量检查；出现重大冲突再扩展上下文、交叉核验，避免每次全量分析。
- 批处理窗口：相近时间的一批更新合并；明确紧急事项不被普通批处理长期延迟。
- 资源预算：先预留用户交互和已承诺工作的资源，主动分析与探索使用独立额度。
- 提醒节奏：基于影响、紧迫性、责任和已处理状态；用户不点击不是自动降低重要性的充分证据。
- 模型/方法选择：仅在预先允许的供应商、数据地区及质量等级中调整，按版本记录。

可用的调节信号包括变化密度、任务截止、信息新鲜度、近期有效发现、误报原因、用户明确偏好和成本。首版建议规则可解释、上下限明确，模型可提出调整建议；积累数据后再评估更复杂的自动策略。

避免将所有信号过早压成一个貌似精确的“重要性分数”。首期采用明确优先级和排序理由，后续校准实际效果。

### 4.3 不能由模型自行调整的边界

企业/空间权限、允许的资料与工具、最大费用、对外行为限制、必要确认、明确的截止承诺和最低覆盖检查，由平台执行。模型可以提出变更申请，不能借调优自行突破。

为防止长期低优先级任务永远排不到，保留最晚检查时间；预算不够时明确报告未完成覆盖，不能显示“一切正常”。取消/暂停须区分本次任务与持续计划，按其范围阻止新的业务动作并传播停止；已发生的动作保留事实，允许保存终态、真实回执和清理结果。关闭通知不自动停止分析，计划停止后旧触发不得重新启动相关工作，具体行为沿处理任务书第 5、6.7 节。

## 5. 自进化具体改变哪些对象

自进化是多个可观察的改进对象，不应只有一段越来越长的“系统提示词”。

| 层次 | 改变对象 | 建议的自动程度，待确认 |
| --- | --- | --- |
| 个人适应 | 格式、信息密度、常用资料、已明确的偏好 | 延续低风险偏好自动记忆、可见可撤销；推测重要事实先确认 |
| 上下文维护 | 事实有效期、索引、冲突、过期关系 | 可重建索引可自动；有争议的企业事实保留候选及证据，不覆盖已确认事实 |
| 工作方法 | 分析步骤、核实清单、输出模板、统计口径引用 | 自动提出、离线验证；个人/共享方法分别决定试用与启用方式 |
| 运行策略 | 检索、上下文选取、工具顺序、调度与模型路由 | 在已批准范围内比较质量与成本，小范围试用，可自动回退 |
| 可执行工具 | 脚本、可复用操作、应用组件 | 在隔离环境测试，验证数据/执行边界；共享和发布使用相应授权 |
| 平台或模型研发 | 平台代码、全局策略、模型训练/微调 | 使用独立研发发布流程；是否开展模型训练依数据、成本和评估决定 |

进入自进化开发阶段后，其第一版可建立完整的“提改法—评估—启用—回退”流程，只支持有限改进对象。按 2026-09-28 决定，该验证安排在基础系统完成后；基础版本现在保留所需证据与接入条件。

## 6. 一次改进怎样成为可靠的方法

2026-09-30 接续建议见[处理任务书第 6.8 节](处理板块-开发任务书-V0.1.md#68-本轮讨论规则维护发布评估与回退)：基础系统由有权维护者使用版本、评估、发布和回退机制，独立自进化以后复用；本轮只形成任务，不启动实验。补充实际生效组合、评价口径独立维护、任务版本切换和旧依赖不可用时的恢复边界。

建议每项改进使用独立版本，经历：

**观察问题 → 解释原因 → 提出候选 → 离线对照 → 影子运行 → 有界试用 → 正式采用 → 持续观察/撤回。**

不要求每个个人偏好都经过全套流程；流程深度由影响范围和可逆性决定。

1. **观察问题。** 保存用户改了哪里、工具失败在哪里、结果是否采用、后续实际发生什么，保留原始证据。
2. **归因。** 区分数据缺失、错误口径、权限不足、检索失败、模型错误、执行错误及环境变化；不把所有失败都归因于提示词。
3. **候选改法。** 指定修改对象、适用场景、预期改善与可能退化；一次尽量只改变可解释的一组因素。
4. **离线对照。** 新旧方法用相同资料版本比较；保留未参与改法生成的样例、反例、异常和权限测试，防止只记住历史答案。
5. **影子运行。** 在真实新输入上产生候选结果，由系统/人工抽样比较；不执行真实外部动作，不重复发送提醒。影子运行也占用单独预算。
6. **有界试用。** 先限定个人、场景或获准的小范围。多个优化不要同时改变同一目标的重要变量，便于判断原因。
7. **启用与退化处理。** 使用者/负责人按影响范围预授权或确认；有明显退化时按既定条件停止扩展、停用候选或恢复到已验证且仍可用的组合。旧模型或接口不可用时，采用已获准的替代方案，或暂停受影响能力，不能承诺任意时刻原路回退。回退行为与已经产生的业务动作分别处理，不能用切换策略撤销现实副作用。

持续记录反馈并用于之后尝试的思路有已有研究基础，例如 [Reflexion](https://arxiv.org/abs/2303.11366)；研究结果不等于梦核在企业管理场景已经有效，本项目仍须建立独立评估。

### 6.1 什么算有效反馈

强反馈包括明确的事实纠正、确认的口径、人工审阅差异、工具真实结果和可核对的后续业务结果。点击、停留时间、继续聊天及没有投诉只作为弱信号。

采纳建议不一定证明判断正确；结果变好不一定由该建议造成。管理场景尽量保留同期背景、替代解释和反例，无法归因时明确“不确定”，避免把相关性写成经验规律。

一个目标的评价至少包含：事实/引用是否正确、发现是否有用、误报和漏报、人工总耗时、任务完成情况、模型与执行成本。重要权限和数据边界是必须通过的检查，不能用平均质量提升抵消失败。

### 6.2 遗忘、失效与范围

方法附带适用条件、维护者、依赖的规则版本和最近验证时间。企业制度、指标口径、数据结构变化时重新验证；过期内容先降级或停用，保留历史证据。

区分原始记录与当前生效记忆。整理和遗忘可改变检索优先级/生效状态，原始决策证据按保留规则管理。方法只在适用的企业/空间/个人范围生效；跨企业复用需要独立的资料授权与去敏处理。

### 6.3 建议的生效分级

- 低影响、可撤回的个人偏好和索引维护，可以在已授权范围自动生效。
- 调度、检索及运行参数，可在预先批准的上下限内自动试用；重要目标覆盖不能被优化掉。
- 影响多人判断的共享方法，默认先展示评估结果；负责人可明确授予有限范围的自动升级策略，不必每个微小改动重复批准。
- 权限、财务/业务写入、对外发布、平台代码等按各自发布与授权流程处理，不能通过“学习”获得额外权限。

以上是建议的分级方式，并非已确认的自动批准政策。

## 7. 与独立替换的关系

建议独立维护：目标与调度策略、上下文/记忆服务接口、分析方法包、工作提案契约、Agent 运行适配器、评估与发布记录。梦核引擎版本引用这些配置与方法版本，每次运行能够追溯当时实际采用的组合；记录存在不保证旧服务仍可调用或已撤权资料仍可使用，也不保证随机模型生成相同输出。重新执行前核对依赖、权限及实际业务状态。

平台保存中立的事实、反馈、来源、任务和成果；引擎可以维护私有缓存，但要说明如何重建或迁移。接口契约测试包括鉴权、来源、取消、错误、用量、版本兼容；不能仅测试返回字段相同。

替换验证至少包含：相同输入的旧/新结果可比、旧任务有明确恢复策略、历史结论仍可解释、数据/记忆可导出、某个租户可先试用、出问题可回退。重放只重算结果，不重放真实业务副作用。

## 8. 本项目自用的首个验证建议

本节为进入自进化阶段后的候选实验，不作为当前基础系统开发的前置条件，也不替代已确认的自用场景随开发探索原则。

选择“需求和决策变化对当前工作计划的影响”，以获准的项目文件和明确维护的任务记录为输入，先不假设系统可以自动读取开发工具的所有历史或执行代码发布。

流程示例：一项已确认需求修改 → 合并相关文档变化 → 检查已知依赖和未完成事项 → 发现与现有计划矛盾 → 呈现证据和受影响事项 → 用户纠正影响范围 → 引擎记录纠正 → 提出更好的识别方法 → 用原案例、未见样例和无影响反例验证 → 按确认的策略启用。

试验应主动包含：无实质影响的改名/排版、相互矛盾的材料、缺失依据、已过期承诺、权限撤回和重复事件。需要验证它何时保持安静，也要验证它能否发现问题。

内部自用用于验证工作与改进循环；9POP 再检验管理指标和判断口径，群力再检验多人职责与协作。不能用本项目单人使用顺畅代替企业隔离和多角色验收。

## 9. 接下来应确认的原则

1. 目标允许用户明确指定、岗位模板提供、引擎提出候选三种来源；候选可在探索预算内核实，长期关注与扩大范围按规则授权。
2. 允许动态调整频次、分析深度、批处理与提醒，平台保留权限/费用/截止/覆盖边界，变化都有可解释原因。
3. 基础系统完成后再验证自进化的顺序已于 2026-09-28 确认；自进化阶段的首批改进对象和自动生效程度仍按个人/团队/平台及影响分级讨论。
4. 首个自用场景是否采用上述需求—决策—计划核对，或改用用户更看重的实际工作。

第 1、2 项的具体机制、第 3 项的改进对象/生效规则及第 4 项的实验场景仍待细化，开发顺序以顶部最新决定为准。本稿不构成真实主动任务、模型调用、资料导入或自动升级的运行证据。
