# 梦核工作空间：Git 多人协作方案 V0.1

用户已明确两条开发线为“系统＋前端”和“梦核引擎”，两组均可访问整个项目源码，优先简单协作。本文据此推荐：**一个私有主仓库、一个长期 `main` 主线、按任务建立短期分支；两组按模块负责，通过版本化契约并行开发，平台与引擎分别发布。**

用户随后已确认按本设计初始化 Git。当前执行规则见 [COLLABORATION](../../COLLABORATION.md)，仓库与验证证据见 [初始化记录](../交接/Git初始化与验证-2026-09-21.md)。下文目标目录、后端/引擎契约与独立升级演练随相关代码落地，不因 Git 初始化自动成为已实现能力。

依据：[开发协作规则](../../AGENTS.md)、[整体开发框架](整体开发框架与待办-V0.1.md)、[多端架构讨论](多端架构与技术栈确认-V0.1.md)。技术栈与引擎具体机制继续沿用各文档的确认状态，Git 方案不替代这些决定。

## 1. 为什么先采用单仓库

| 方案 | 对本项目的影响 | 建议 |
| --- | --- | --- |
| 单仓库、模块分工、任务分支 | 接口、模拟实现和两侧测试可以一起审查；新人只需一个主项目；可以分别构建和发布 | 当前采用的推荐方案 |
| 平台与引擎两个仓库 | 便于隔离源码权限或对外独立交付；需要额外维护契约发布、依赖升级和跨仓库兼容测试 | 出现实际隔离或独立产品需求后再拆 |
| 同仓库长期 `system` / `engine` 分支 | 两侧重复保留共享文件、长期偏离，接口冲突与集成问题被推迟 | 不采用 |

当前判断建立在“同一产品、源码可互见、早期接口需要共同打磨”上。最强的反对理由是未来引擎团队可能独立对外提供产品；因此从第一版隔离接口、运行状态和构建入口，保留拆仓能力。多人或不同语言本身并不要求拆仓。

单仓库并不强制同步部署。源码仓库、服务边界、构建产物和发布版本分别管理；引擎独立升级主要靠接口兼容与独立产物实现。

## 2. 当前目录与建议布局

2026-09-21 初始化前检查事实（当前 Git 状态见上方记录）：

- 主目录尚未初始化 Git；现有源码在 `src/`，采用 React、TypeScript、Vite。
- 已有根目录 `package.json`、锁文件、单元测试、Playwright 测试与打包脚本；后端及引擎尚未落地。
- `website/` 已有独立 `main` 和 Sites 远端，检查时工作区干净。官网交付生命周期保持独立。

建议在后端骨架阶段形成以下布局；这是目标布局，本轮没有移动现有文件：

```text
梦核工作空间主仓库/
  apps/
    web/                     # 现有网页逐步迁入
    api/                     # 身份、空间、资料、会话、任务、成果
    worker/                  # 业务任务队列、重试、文件处理编排
  engine/
    src/                     # 梦核分析、策略、记忆与运行适配
    tests/
    evals/                   # 合成或获准且适合入库的评估样例
    README.md                # 引擎单独开发、构建与启动入口
  contracts/
    public-api/              # 客户端与平台的接口
    engine-api/              # 平台与引擎的双向协议
    fixtures/                # 两侧共用的输入、事件与结果样例
  packages/
    api-client/              # 由契约生成或封装的客户端
    ui/                      # 出现实际复用需求时再抽取
  tests/integration/         # 平台与引擎的共同验收
  ops/                       # 环境、发布、回滚和版本组合记录
  docs/
  .github/                   # 若采用 GitHub，放 CI 与审查配置
```

现有 `src/` 可先保留，不需要为了初始化 Git 立刻迁移。迁入 `apps/web/` 应单独做一个结构调整 PR，同步修正 Vite、测试、资源、Demo 打包和官网刷新路径，并验证现有 Demo。不要把全目录移动混进某项业务开发。

`engine/` 有自己的依赖清单、入口、配置与构建产物。当前即使采用相同语言，也不允许平台导入其内部源码。后续换成 Python 等实现时，平台仍通过协议接入。JS 工作区、锁文件数量和具体构建工具随技术栈落实，不为本方案预先更换包管理器。

### 官网仓库的处理

初始化主仓库时显式忽略 `/website/`，不把内层仓库误提交成 gitlink，也不引入 submodule。既有官网位置先保留，以兼容当前依赖父目录的刷新脚本。

新克隆的主项目默认不含官网。届时交接文档补充官网的单独获取方式；涉及官网的打包/刷新脚本先检查该目录，缺失时给出明确说明。主项目构建和测试不依赖官网。需要移动官网到并列目录时，再一起调整依赖父路径的脚本和文档链接。

## 3. 两条开发线如何分工

| 责任区 | 主责 | 边界 |
| --- | --- | --- |
| `apps/web`、`apps/api`、`apps/worker`；迁移前的 `src/` | 系统＋前端组 | 页面、业务事实、身份与授权、资料版本、任务持久化、成果发布、用量核算 |
| `engine/` | 引擎组 | 上下文分析、优先级与调度策略、方法与记忆、Harness/模型适配、算法评估 |
| `contracts/engine-api`、相关样例与集成测试 | 双方共同评审，指定一人整合 | 双向接口、任务事件、兼容窗口、错误与恢复语义 |
| `contracts/public-api`、API 客户端 | 系统＋前端组 | 网页及后续原生客户端与平台的约定 |
| 根配置、公共依赖锁、CI、`ops/`、公共文档 | 项目维护者整合，受影响方审查 | 避免双方同时大范围调整公共基础文件 |

业务队列负责可靠执行、重试和任务记录；引擎决定在获准目标内何时值得工作、使用什么策略。具体调度机制另行设计，避免两组分别建立互相竞争的任务事实源。

跨责任区修改允许发生，提交者须说明原因并邀请相应负责人审查。共同文件和数据库迁移先在任务中认领；迁移使用唯一标识，合并前检查重复、顺序及升级兼容。人工开发和 coding agent 遵守同一套规则，实际开发者负责审查及提交结果。

## 4. 分支与日常操作

`main` 是唯一长期主线，表示已经集成且通过当前阶段约定检查的源码，不等同于正在生产运行的版本。不开长期 `develop`、按人命名的永久分支或按环境维护的代码分支。

短期分支按“责任区＋任务号＋主题”命名，例如：

```text
codex/platform/WS-001-task-submit
codex/engine/EN-001-context-analysis
codex/contract/CT-001-task-events
```

前缀沿用项目现有 AI 开发习惯；`WS/EN/CT` 是建议的工程任务分类，任务正文仍引用产品原需求编号，不替代 AI-xx、WS-xx 等需求标识。分支名是示例，尚未创建。

日常流程：

1. 从最新 `origin/main` 建立任务分支，写明目标、负责目录、契约版本、依赖与验收。一个任务保留一个主要负责人。
2. 在自己的工作目录开发，尽早开 Draft PR，让另一组看到接口变化。尽量把工作拆成 1—3 天可审查的改动；这是建议粒度，不是交付承诺。
3. 提交只暂存本任务明确路径，并检查暂存差异；不使用 `git add .` 混入别人的改动、环境或输出。
4. 自测后发起 PR；同模块由另一位可承担该责任的开发者审查，跨契约改动由双方审查，再由指定维护者合并。
5. 默认以 squash 合入 `main`，保留任务、需求与验证证据。若出现冲突，在任务分支解决并重跑受影响检查。
6. 合并后删除已完成的远端任务分支；确认本地无未提交/未推送工作后移除对应 worktree。本地集成目录用快进方式跟进主线。

尚未共享的任务分支可 rebase 到最新主线；已经共享或多人基于其开发的分支优先 merge `origin/main`，避免改写协作者历史。`main` 不强推，已集成错误用新提交或 `git revert` 修复。

需要多分支提前联调时，可建一次性的 `integration/<主题>`，只做测试；正式修复回到对应任务分支，通过各自 PR 集成。不要让新任务依赖这一临时分支，也不要将它逐渐变成第二条长期主线。Git 官方介绍了[主题分支与临时集成分支](https://git-scm.com/docs/gitworkflows)。

### 不同电脑与同机并行

- 不同开发者各自 clone；不要通过共享网盘同步 `.git` 或使用同一个可写目录。
- 同一台电脑同时运行多个开发任务时，每个任务用一个独立 worktree 和分支；单一任务无需额外 worktree。[Git worktree](https://git-scm.com/docs/git-worktree) 允许同一仓库同时检出多个分支。
- worktree 只隔离工作文件。端口、环境文件、数据库/测试 schema、队列前缀、Compose 项目名和日志目录也要按任务隔离，防止代码分开而运行数据相互覆盖。
- 同机多个任务不并发修改公共 Git 配置、移动分支引用或清理其他任务目录；各自提交自己的分支，集成由维护者协调。

## 5. 能独立推进的关键：先形成最小契约

先共同完成一份小的 `engine-api v1` 草案和固定样例，再分别开发。契约是语言中立的 schema、接口说明和测试样例；TypeScript 类型可以由它生成，但不作为其他语言必须依赖的实现。

至少约定以下内容，具体字段与状态机在首个切片细化：

| 方向/内容 | 必须共同约定 |
| --- | --- |
| 平台发起运行 | 任务与请求身份、幂等键、目标、输入引用及版本、预算、时限、契约版本和能力 |
| 引擎读取上下文/调用工具 | 受限身份与授权范围、工具参数、当前权限验证、版本约束、明确的错误；由平台和工具服务执行授权 |
| 引擎报告进度/结果 | 运行身份、事件身份/顺序、文本或结构化产物、来源、实际执行记录、用量及失败原因 |
| 取消与恢复 | 重复提交、断线、乱序/重复事件、超时、取消、已产生的部分结果，以及终态判断责任 |
| 版本与追踪 | 引擎构建、方法/提示、模型与配置版本；兼容能力和可关联日志的追踪身份 |

客户端或引擎自报 `tenantId` 不构成授权。平台确认请求的企业与操作者，工具层在读取和写入时复核当前权限。引擎不直接修改业务表；结果先经过平台校验再变成正式业务事实。运行完成、成果保存、成果共享分别表示，不用模型自述代替成功证据。

双方分别拥有可脱离另一组开发进度的替身：

- 系统组使用 **模拟引擎**：固定样例、流式事件、失败、取消、重复回调等都可触发，明确标注模拟。
- 引擎组使用 **模拟平台/工具服务**：提供同一套获准资料与版本样例，也能拒绝越权、模拟撤权和工具失败。
- 两者执行同一份契约测试。依赖稳定测试样例或已发布兼容产物，不依赖另一位开发者“电脑上正在运行的最新版”。

算法内部改进且协议兼容时，引擎组自行推进；改字段含义、增加必须能力、调整任务语义时，先发契约 PR。可选字段增量也需要默认值与消费者测试；新增枚举/事件不自动视为兼容。

不兼容升级采用“先扩展消费者接受范围 → 发布生产者新能力 → 迁移与观察 → 结束兼容窗口后删除旧协议”，并验证实际版本组合。禁止双方在各自分支偷偷改同一接口，最后靠人工对齐。

## 6. 主线保护与 CI

托管建议使用团队拥有的私有仓库；若沿用 GitHub，可由 Organization 管理所有权与成员。托管账号、付费方案与权限需要在实际建立远端时核对，本轮不做购买或成员邀请。

建议主线要求 PR、至少一位非作者审查、必需检查通过、讨论已解决，并阻止删除和强推。规则应覆盖管理员，只有明确记录的紧急恢复流程可例外。多人提交后应验证合并候选与当前主线组合，避免两个单独通过的 PR 集成后失效。

`CODEOWNERS` 用于指定目录的审查责任，不提供目录级源码保密。契约必须双组同意时，**同一行列出两个 owner 并不会强制两人都批准**；GitHub 默认其中一人批准即可。初期由维护者核验双方已审查，后续确有需要再增加双方审批校验。见 [GitHub CODEOWNERS 说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)。

GitHub 官方当前列明：私有仓库的受保护分支需适用的 Pro、Team 或 Enterprise 方案，组织通常采用 Team 或 Enterprise。实际能力以建立仓库时的账号为准。若暂不可用，应标记“人工集成、无服务端强制保护”，本地 hook 只能辅助；不要为获取功能改成公开仓库。见[受保护分支说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。

CI 随实际代码增加，建议责任如下：

| 改动 | 必需检查方向 |
| --- | --- |
| 网页 | 类型/构建、相关规则测试、受影响的关键页面流程 |
| 平台 | 业务接口、企业/空间隔离、授权撤回、状态转换、重试幂等、迁移 |
| 引擎 | 引擎单测、契约、固定样例回放；方法改动增加对应质量比较 |
| 契约与双方边界 | 平台＋引擎消费者/提供者测试、兼容版本组合和完整跨服务流程 |
| 公共锁文件、基础配置、CI | 所有受影响模块的检查，不能只按提交者所属组选择 |

首次 CI 先接已有的 `npm run build`、`npm test` 与默认空谷场景 `npm run test:e2e:konggu`，核对所需 Node 与浏览器版本；旧通用场景脚本不能直接充当当前默认场景验收。上述为已有命令，不表示本轮重新执行通过。

使用按路径选择任务时，保留始终运行的汇总检查，核对该跑的任务确实成功，避免 required check 因整个 workflow 被跳过而挂起，或因为错误跳过而放行。开始阶段检查规模小，可以先全跑，复杂筛选以后再加。

普通 PR 默认使用合成数据和确定性替身。真实模型评估按涉及的能力和已授权预算单独触发；模拟通过、真模型通过、部署通过和客户验收分别记录。评估不能重复执行真实外部写入。

## 7. 平台和引擎分别发布

| 对象 | 建议版本标记 | 发布边界 |
| --- | --- | --- |
| 系统＋前端 | `platform/v0.1.0` | 网页、业务 API、worker 及兼容数据迁移 |
| 梦核引擎 | `engine/v0.1.0` | 引擎服务、运行依赖及方法配置 |
| 引擎协议 | `engine-api/v1` 等协议标识 | schema 与兼容规则；与软件发布版本分开 |

标签均指向主线中已验证的提交；一个提交可产生多个独立产物，也可只发布一个模块。CI 必须允许从不同提交构建平台和引擎，部署不采用含糊的 `latest`。

每次环境发布保存版本组合：平台提交/产物摘要、引擎提交/产物摘要、协议版本、方法/配置版本、数据库迁移版本和兼容测试证据。示例组合为“平台 0.3.0＋引擎 0.7.2＋协议 v1”，不是要求版本号同步增长。

引擎升级先验证已部署平台兼容；新任务可切向新版本，运行中任务记录并固定引擎与方法版本。回退选择已验证的旧产物组合；数据库及引擎持久状态单独设计迁移/恢复，不把 `git revert` 当作数据回滚。合并主线和创建标签也不自动授权生产发布。

## 8. 最小落地顺序与验证

1. **建立现状基线。** 核对正在进行的其他修改、敏感文件及大文件；完善忽略规则（含独立官网）、按路径建立 `main` 初始提交。保留当前 Demo 可运行，不在初始化时混做全目录重构。
2. **建立远端协作。** 确定私有远端归属、成员及合并维护者，配置可用的主线保护、PR 模板和第一批 CI；实际验证规则是否生效。
3. **建立工程边界。** 在专门 PR 中调整必要目录、添加模块开发说明与独立启动入口；已有脚本与文档链接同步修改。后端/引擎技术栈按其自身决定落地。
4. **共同完成最小契约与替身。** 以“提交一个合成资料任务 → 返回进度 → 返回带来源的草稿结果”为演练，再覆盖失败、取消和重复提交；不以此替代真实模型验收。
5. **做一次双线并行演练。** 两组各建任务分支，系统侧用模拟引擎完成界面与任务处理，引擎侧用模拟平台完成分析；分别合并，按契约联调并记录冲突点。
6. **验证独立升级。** 固定平台产物，仅替换兼容的引擎产物，再回到旧引擎；确认不用重编译平台、不会重复业务写入、可追踪任务与结果版本。

最危险的假设是“目录分开就能独立开发”。第 4—6 步是最小验证：若两组仍必须修改同一批业务文件才能交付，引擎边界没有成立，应先修正契约与调用关系。

只有当访问权限、独立对外产品或团队治理出现明确需求时，再将 `engine/` 拆成独立仓库；保留历史、发布语言中立的契约包、锁定版本或镜像摘要，并继续跑跨仓库兼容测试。主项目通过协议与产物引用它，不直接复制一份引擎源码。

## 9. 方案设计阶段完成范围

已检查主项目和官网的 Git 状态、当前代码布局、开发与架构文档，并核对 Git/GitHub 官方协作说明。已记录用户的源码互通与简单协作偏好，完成本方案与文档入口。

方案设计阶段未初始化主仓库、创建远端/分支、移动源码、配置 CI 或保护规则、提交/推送和部署。用户随后授权初始化，其实际结果单独记录；文档中的后端/引擎工程结构、契约与发布演练继续留在相关开发任务中落实。
