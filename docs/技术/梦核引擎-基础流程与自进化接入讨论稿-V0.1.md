# 梦核引擎：基础流程与自进化接入讨论稿 V0.1

日期：2026-09-28。状态：基础开发顺序已确认；外部业务数据获取讨论已另存为业务方案（DEC-081）。以下职责、交接信息和实现安排为设计建议，尚未冻结具体接口或验收阈值。

关联：[产品需求基线](../产品/产品需求基线-V0.1.md)、[开发决策记录](开发决策记录.md)、[既有主动调度与自进化讨论稿](梦核引擎-主动调度与自进化机制讨论稿-V0.1.md)、[实际协议与验证入口](../../contracts/README.md)。需求沿用 AI-01—AI-04、ACT-01—ACT-04、DASH-01—DASH-04、MAINT-01—MAINT-10，不将讨论稿中的建议自动升级为已确认业务规则。

## 1. 已确认原则与本轮范围

用户提出输入、处理、输出三个基础板块及独立自进化板块，并进一步明确：没有自进化板块，系统也必须正常运行；架构现在考虑其加入，基础系统完成后再测试自进化能力。用户已认可据此调整开发顺序，并要求继续细化。

据此延续以下原则：

1. 输入、处理、输出构成基础业务闭环，使用可运行的初始方法，不依赖自进化服务在线或先产生优化方案。
2. 当前落实可观测、反馈关联、关键方法可替换、版本可追溯/回退及调整边界；不要求现在完成自进化实验平台。
3. 基础运行评估随开发进行，判断任务是否正确完成、运行是否稳定及资源消耗；自进化效果评估在基础系统完成后开展，判断候选改法是否优于现有方案。
4. “基础系统完成”按一个明确的可交付版本落实，其实际范围与验收继续沿任务书确认；本轮没有宣告现有系统完成，也没有将全部远期功能列为接入前提。

第 2—8 节为实现建议。现在讨论板块职责和交接含义，不指定四个模型、四个服务、统一数据库或固定执行步骤；物理部署沿现有 Spring Boot 平台与独立引擎边界继续设计。

## 2. 三个基础板块的职责

| 板块 | 对其他板块负责什么 | 交出的信息 | 内部可以继续调整什么 |
| --- | --- | --- | --- |
| 输入：数据获取与核验 | 在当前授权范围内提供可追溯的数据，说明时效、口径、缺口与冲突 | 来源或数据引用、版本、必要内容、质量状态和缺失说明 | 接入方式、解析/映射方法、分类模型、缓存和索引 |
| 处理：分析与执行 | 根据任务目标选择方法，生成有依据的结论、建议或成果，并通过获准工具执行动作 | 成果、依据、执行回执、未解决事项和明确的任务状态 | 检索顺序、上下文选取、工具组合、分析步骤、模型分工 |
| 输出：交付与分发 | 在接收者当前权限内，把成果交付到合适入口，并收集与具体版本关联的反馈 | 会话回复、文件、画报或获准通知，以及实际交付/展示/反馈记录 | 内容排序、表达方式、模板、发送时机及是否调用模型 |

这是逻辑职责划分。模型生成文稿或表格可以发生在处理阶段，输出负责该产物的交付；不要求所有格式生成代码迁往输出服务。检索、读原件等工具在处理时可反复调用输入能力，不预先把全部资料塞进一个上下文。

简单会话可以直接交付答案；主动发现类任务可以产生有限候选，再由输出筛选。没有必要让每个任务都经过候选池、排序模型或画报。

### 2.1 输入的初始运行方式

建议保留“来源原件/引用 → 可重建的解析与结构化结果 → 面向任务的检索或数据读取”三种信息。统一来源、时间、版本和口径的表达，不强迫所有业务资料变成同一张表。

稳定数据通道优先用确定的解析、校验与计算程序。初次接入、新格式、语义歧义和异常可以调用模型；验证后的映射再固化为可复用方法。模型是否长期参与分类取决于实际效果，不在本轮预设专项模型。

字段、单位、统计区间和指标含义都需要来源依据。未知或矛盾的信息可以以缺口状态返回，由处理判断是否需要补充、澄清或给出有限结论；不能因入库成功而标记为事实正确。需要记录本轮确切读取版本，同时在每次读取时核对当前权限，版本快照不延续已经撤回的授权。

围绕当前任务逐步建立数据标准；基础使用不等待全企业数据治理完成，延续 POS-04。

### 2.2 处理的初始运行方式

每项任务需要形成可解释的当前目标：来源是什么、为谁工作、希望得到什么、允许使用哪些资料与工具、何时算完成。目标可由用户提出，也可由系统基于生效的基础职责、场景策略和获准探索推演；不要求用户先配置完整经营目标。2026-09-29 系统目标与冷启动讨论已并入[处理任务书第 4 节](处理板块-开发任务书-V0.1.md)，包括先开展有限工作、再通过成果互动校准的建议（DEC-086）。主动任务由获准策略、目标、事件或时间条件触发；具体调度算法继续细化。

主模型可自行选择补充资料、调用工具、检索经验、计算或组织成果的方式。常驻规则保持简洁，把当前目标、真实权限边界、结果要求和工具使用说明交给模型；详细方法按需加载。是否必须检索经验由任务需要决定，经验库为空也能依靠授权资料和工具正常工作。

经验建议以“问题、适用前提、方法、结果证据、失败/不适用情形、依赖版本、作用范围”组织。先检索摘要，再按需读取完整案例、Skill 或脚本。个人、企业及通用经验分别管理；跨企业复用需要明确授权和去敏，脚本使用沿工具执行边界核验。

模型可在一次任务内根据工具结果调整计划。保存明确偏好、更新资料索引等既有获准行为也可按现行规则运行；这些不要求独立自进化服务在线。跨任务修改共享工作方法的自动生效策略，留待自进化接入阶段设计。

### 2.3 输出的初始运行方式

输出消费带依据的成果和实际任务状态，先核对接收者与可发布范围，再进行价值排序、个性化表达和交付。用户直接请求的成果、职责待办与主动推荐分别处理，不让推荐偏好改变已承诺交付。

共同授权的事实和成果可复用，表达可按岗位、信息密度和偏好调整。高权限资料产生的结论不能只删敏感字段后默认分发；需要按现有成果发布规则释放，或基于接收者获准依据重新生成。表达产生新的事实判断时，需补充核验与来源，不能伪装成纯排版变化。

默认可以由程序和模板完成排序与呈现；需要语义改写时再调用模型。主模型或另一个模型负责表达属于后续可替换选择。对外通知必须经过对应工具及授权，记录实际回执，不能把“模型生成通知内容”算作已发送。

2026-09-30 分期确认（DEC-088）：首版仅系统内交付与提醒，系统外业务触达留到后续 App 版本。上述对外通知规则保留为后续接入边界，不要求首版实现外部通道或送达验收；后台任务和成果保存继续按授权运行，具体见[输出任务书第 11.4 节](输出板块-开发任务书-V0.1.md#114-首版范围已确认站内交付系统外触达后置)。

画报反馈关联内容版本、呈现版本及曝光上下文，会话反馈关联任务、回复和成果。反馈按事实、相关性、表达、执行等原因区分；满意度只作为经验候选证据之一，不直接授予通用经验资格。

## 3. 板块之间最少要交接什么

以下是信息含义建议，不是已实现的 API、JSON 字段或数据库表。实现时优先扩展既有契约，按受影响双方评审和版本兼容规则推进。

| 交接对象 | 谁提供，谁使用 | 最少说明什么 |
| --- | --- | --- |
| 任务说明 | 会话/调度入口 → 处理，按需传给输入与输出 | 目标、请求与任务标识、执行身份、企业/空间、完成条件、资料/工具范围、预算及时限 |
| 数据回执 | 输入 → 处理 | 来源标识与版本、时间及口径、内容或受控句柄、质量状态、缺口/错误、权限依赖 |
| 成果与执行回执 | 处理 → 平台持久化及输出 | 任务/尝试、成果版本、证据引用、工具真实结果、状态、待确认或未完成部分 |
| 交付记录与反馈 | 输出/工具 → 平台及获准的观测消费者 | 内容与呈现版本、接收范围、渠道、实际交付状态、用户反馈和后续结果 |
| 运行记录 | 三板块 → 平台运行观测 | 任务与尝试关联、所用版本、关键动作、耗时、用量、错误/取消/缺口 |

身份、权限与生效配置由可信平台记录提供，模型不能通过填写这些信息扩大授权。运行范围快照用来解释当时情况；任务继续、检索、产物读取与发布时仍检查实时权限。

共享基础建议分开保存事实资料、企业/用户档案、可复用经验、任务成果与生效方法版本。它们可以由现有平台和引擎适配能力承载，不要求新增一个包办所有内容的服务。事实、推断、偏好和权限各有来源与状态；企业画像不替代访问控制。

## 4. 当前保留的运行证据

运行观测首先服务基础系统排障与质量检查。建议按实际能力逐步补齐，不要求第一天存下所有内容或每条内部思考：

- **为什么运行：** 任务目标、触发来源、责任和授权范围。
- **基于什么运行：** 实际资料/经验版本、引擎/模型标识、已启用的工具或方法版本。
- **实际做了什么：** 关键工具调用、检查结果、取消/失败与重试关联、产物和外部执行回执；模型自述与真实状态区分。
- **付出多少资源：** 等待/执行耗时、模型请求/尝试、工具消耗；未知用量保持未知，不填为零或估作供应商账单。
- **交付与效果：** 成果和呈现版本、展示/发送状态、明确反馈、人工修改及可核对的后续结果；未展示不当作没用，未反馈不当作满意。

正常、失败、取消、无相关资料以及主动决定不通知，都应有可解释的结果。记录按需要引用原件或产物，不无限复制全文；错误文本去敏，不保存凭据，不要求记录模型隐藏推理。详细内容、经验候选与汇总指标分别授权，并在相关实现中确定保留期限、删除和撤权后的访问行为。

尝试记录不等于允许重复执行。发生超时或丢响应时，沿任务状态与工具幂等机制核对既有结果，避免重复业务写入或发送。

## 5. 自进化将来从哪里接入

2026-09-30 接续：[独立自进化任务书](独立自进化-开发任务书-V0.1.md)已单独展开职责、可优化对象、采用后的运行依赖和停止范围，触发/候选与分范围预授权方向获认可（DEC-091），第 11—12 节补并发/恢复及后接入范围，已形成阶段汇总并转入三端管理专题。下文保留基础预留依据；具体参数、自动类别及恢复方案未全量冻结，未开始实现或实验。

本节是预留职责，不要求现在建设空服务、通用插件市场或复杂参数管理平台。

| 接入面 | 基础系统现在保留什么 | 自进化阶段再实现什么 |
| --- | --- | --- |
| 观察 | 持久任务、版本与运行证据，按权限查询/导出 | 授权范围内的定期诊断、问题归因和改进机会识别 |
| 提案与试验 | 关键方法有边界，记录当前生效版本 | 候选改法、假设、适用范围、兼容要求、实验与独立评测 |
| 发布与恢复 | 正常工程升级和回退机制；当前生效版本不由自进化服务临时提供 | 根据授权和证据试用/启用候选，观测后保留或回退 |

自进化暂未部署或停止时，基础运行继续使用持久保存的当前有效方法。将来观察消费者滞后、实验失败或没有新提案，不得阻塞正常任务；观察产生的模型调用与实验资源需有独立额度，避免挤占业务任务。基础资料或工具本身不可用时，仍按正常任务规则明确报错或降级，不能假装完成。

自进化通过现有授权与发布入口提交变更，不直接改业务数据或所有租户配置。可以提出架构重组建议，具体实施仍须处理兼容、迁移和替换影响。切换策略不能撤销已经发生的业务动作。

是否允许自动改提示、检索、索引、排序、脚本或数据结构，按对象及影响继续决定；本轮未授予这些改动的自动发布权限，也未确认具体触发频率。

## 6. 一个基础工作示例

以“根据本周获准资料整理项目进展和待办”为说明，不冻结为唯一首发工作流：

1. 用户在会话提出目标，平台形成任务说明，记录当前身份、资料范围和预期交付。
2. 输入提供相关原件/解析片段的确切版本与时间；缺失进展或冲突记录一并说明。
3. 处理按需要检索获准经验、补充资料和核对进展，生成摘要、证据和待确认事项。
4. 工具生成文稿时保存真实产物回执；资料不足的事项保留未知，不用文字“完成”替代执行结果。
5. 输出交付给请求者；若有获准共享需求，再按受众与发布规则生成对应视图。普通会话不强制产生全员画报或通知。
6. 平台关联任务、来源、成果版本、耗时/用量及反馈。当前可用于人工排障、正常版本迭代；将来自进化在获准范围消费这些证据。

这条工作在没有自进化模块时即可独立成立。

## 8. 这轮之后的推进方式

2026-09-28 最新要求（DEC-083）：先讨论完整开发板块，每次形成或更新对应任务书，最终汇总后统一执行，当前暂不实现。讨论目录见[总任务书第 0 节](开发任务书-V0.1.md)，输入阶段成果见[输入任务书](输入板块-开发任务书-V0.1.md)。本节此前“选择下一开发切片”现指登记未来执行安排，不据此现在开始编码。

2026-09-28 接续：用户要求先确认现有开发内容与管理端的大体方向，再进入输入板块细化，随后认可保留三端、扩展两类管理职责及复用工程的方向。见[开发范围与管理端规划](新架构下开发范围与管理端规划-讨论稿-V0.1.md)和 DEC-080。新增菜单、具体权限和交付切片继续设计；当前进入下方第 9 节的输入范围讨论。

当前先用本稿细化各板块的职责与交接信息，对照实际契约登记候选任务和依赖，讨论结束后写入对应任务书。所有板块汇总完成再统一执行；具体方法和字段在已明确边界内保留实现调整空间。

基础版本的验收仍检查任务、资料、成果、权限、失败恢复、用量及目标场景的真实模型效果；无需先证明自动优化有效。待该基础版本完成后，再接入自进化观察和提案，开展独立效果验证，并按证据决定自动生效范围。

后续需要分别讨论的数据接入范围、经验入库/失效机制、企业与用户档案来源、推荐目标与主动触发策略，不因本稿写出建议而自动冻结。当前没有新增开发工期、调用费用或对外发布承诺。

## 9. 下一步：输入板块的范围与最小标准建议

本节为进入输入细化的起点，尚未成为用户确认的首版渠道清单或数据模型；先明确范围与交接，再落实管理操作及开发任务。

每次细化以一项实际目标任务和所需事实约束范围；本项目自用任务仍可随开发探索，不冻结唯一工作流。最小档案字段按任务需要逐步补充，不把自动画像或完整档案模块自动纳入首个切片。

### 9.1 先按来源明确数据范围

| 来源 | 第一版建议 | 归属和维护 |
| --- | --- | --- |
| 用户上传的文档、表格、图片等资料 | 复用当前原件/版本、解析和检索能力，保留格式差异；只按实际支持程度标明可用性 | 客户端上传维护，属于个人或获准共享空间 |
| 系统内已有记录 | 在任务需要时读取获准的任务、成果、版本和明确反馈，不全量复制到另一数据库 | 原业务模块持有事实，输入提供统一读取方式 |
| 企业与用户档案 | 补充最小档案表达：已确认背景/术语、系统权威身份与权限引用、明确偏好；推断与确认分开 | 企业档案由获授权者维护，个人偏好由本人维护；身份/权限沿平台事实 |
| 外部业务数据 | 按目标任务的数据可获得性选择少量接入方式；接口、文件交付、界面自动化或既有工具记录按条件采用，不预先覆盖所有 SaaS | 企业侧明确来源、用途、范围、授权及更新责任；产品与 FDE 分工见下方业务方案 |

2026-09-28 接续：用户已要求将外部业务数据获取讨论固化为[业务数据获取与交付方案](../商业/输入板块-业务数据获取与交付方案-V0.1.md)。该方案明确数据已存在但取不出、分散记录、从未记录三种情况，以及标准产品、接入实施和额外系统建设的边界；并不将所有渠道纳入首期或新增接入授权。当前回到输入整体职责及运行方式的细化，见第 9.4—9.6 节。

用户请求、工作目标、事件和时间条件作为任务的触发与上下文进入系统，不都转换成普通资料文件。既有获准的公开检索/网页阅读继续按任务使用；自动持续同步或定期抓取的新增范围在对应接入时确定。

任务状态和工具回执记录执行事实，生成成果中的判断另保留来源与核验状态；不能因为任务成功就把回答视为已核实业务事实。私人会话/成果也不自动转为企业公共输入，避免循环引用生成内容后误当成独立证据。

经验库作为共享资产提供按权限检索，不再复制为一套独立“输入经验库”；经验入库、有效性与失效规则另行细化。原始会话、工具输出和任务成果即使成为输入，也保持资料属性，不能自行修改系统指令或权限。

### 9.2 统一数据说明，按需统一内容结构

每项输入建议至少能回答六个问题：

1. **来自哪里：** 来源标识、责任方或连接渠道，能否回查依据。
2. **属于谁、谁可用：** 企业/空间归属和当前权限依赖；不由内容或模型自报。
3. **是哪一份、何时有效：** 稳定身份、版本、采集时间、业务发生/有效时间；未知时明确未知。
4. **具体表示什么：** 类型、必要单位与业务口径；普通文稿不强制转成业务表。
5. **处理到什么程度：** 原件是否取得、解析是否完整、是否过期/冲突/缺失；接入或解析成功不等于事实已经核实。
6. **怎样被使用：** 可检索片段、受控原件句柄或结构化查询结果，并保留来源依赖。

按资料规则保留可追溯的原始依据和版本，再生成可重建的解析、索引或结构化结果，最后按任务返回所需内容和状态。不同来源可采用获准快照或受控引用，不默认永久复制全部接口响应、网页或会话上下文；保存期限和来源失效处理随接入明确。模型可帮助建立映射、处理歧义；稳定路径由程序复用。不要求先选择专项分类模型，也不把全企业标准化作为开始使用的前置条件。

来源版本变化、删除或撤权时，应使相关派生结果和缓存的可用状态一致更新；历史引用仍按当前权限访问。失败、部分可用和资料不足需要明确返回给处理板块，避免把缺失当作零或把旧资料当作最新。

### 9.3 从范围讨论走到开发

下一轮按“数据范围与最小标准 → 获取/更新与按任务读取 → 企业侧管理动作及平台侧技术状态 → 对应源码/契约切片与验收”推进。先复用现有文件和平台事实，采用合成或明确获准样例验证；具体业务渠道、真实资料和外部处理范围随场景明确，不在本节自动接入。

这一轮的可审阅产出应是数据来源清单、最小输入说明、缺失/更新/撤权处理规则，以及三个端分别承担的操作。完成这些再选择首个开发切片，不先搭建全行业通用数据平台。

### 9.4 输入的运行职责建议：准备数据与按需读取

本节及后续两节是业务方案固化后的继续设计，尚未成为用户确认的固定流程。输入负责提供当前获准的数据、依据和可用状态；业务分析、行动选择与结论由处理板块负责。允许交付明确缺口，不承诺所有来源始终准确完整。

| 运行场景 | 输入应承担的责任 | 保留调整空间 |
| --- | --- | --- |
| 来源初次建立或发生变化 | 明确来源、用途、范围和负责人；按需要建立解析、映射与核验方法 | AI 辅助理解样例、提出方法；稳定映射可由程序复用，不要求每家企业完整治理后才能使用 |
| 文件到达、平台记录变化或获准同步 | 保存可追溯依据，识别版本、重复、缺失或异常，更新必要的派生结果 | 依据成本及时效选择提前解析、缓存、事件更新或定期同步，不要求全部来源持续抓取 |
| 任务执行时请求数据 | 核对当前身份与范围，提供所需片段、原件或查询结果，附版本、时间及缺口 | 处理可在任务内反复检索和补查；无需每次全量导入，也不一次塞入全企业资料 |

以上是职责场景，不是所有资料必须依次经过的固定流水线。输入的逻辑范围也不等于一个新服务或统一物理数据库；平台事实继续由原业务模块持有，通过受控接口读取。

模型可以在已授权任务内改选解析方法、补查资料和处理异常，属于基础运行能力，不等待独立自进化模块。跨任务改变共享接入方法、索引或结构的生效按正常版本和授权机制管理；未来自进化沿相同边界接入，不自行扩大渠道或资料权限。

### 9.5 以任务需要解释数据状态

不设置一个覆盖所有场景的“可信/不可信”总开关。来源可接通、内容可读取、业务覆盖是否足够、是否及时以及事实核验情况分别说明；同一份月度报表可能适合月度复盘，却不足以判断今天的实时情况。

| 情况 | 输入交给处理什么 | 后续责任 |
| --- | --- | --- |
| 所需内容可用 | 内容或受控引用、来源版本、业务时间、口径和已有核验依据 | 处理据此分析，仍不把解析成功等同事实正确 |
| 部分内容缺失、陈旧或存在冲突 | 可用部分及具体缺口、时间范围或冲突依据 | 处理判断是否补查、请业务方补充，或给出范围受限的结果；输出说明适用范围 |
| 获取或解析失败 | 明确错误与可用替代路径；旧版本可访问时说明其日期和限制 | 原来源负责人补交或修复，不默认为零、不把旧值伪装为本次成功数据 |
| 来源发生更新 | 新版本及其生效/采集时间，派生结果的更新状态 | 新任务按来源选择规则读取；旧任务保留确切依据，刷新或重算应明确记录 |
| 权限撤回或资料失效 | 当前不可用状态，停止不再获准的读取 | 按平台规则处理缓存、派生引用及结果访问；已有明确发布副本沿其既有授权规则执行 |

错误与缺口信息本身也遵守权限；不向无权者暴露来源名称、正文或受限业务细节。没有数据与无权读取在内部原因上区分，对请求者仅返回其可见的状态。

### 9.6 首个输入增量与管理动作建议

先复用现有原件/版本/检索和获准平台记录，补齐任务实际需要的输入说明与异常返回。企业背景、术语和个人偏好只补本轮工作必需部分，权威身份与权限继续引用平台记录；不自动建设完整画像或推断更新系统。

外部报表可作为同一输入说明的样例，具体格式和导入方法按选定任务落实；自动连接器、本地采集器和通用同步后台不因业务方案已固化而全部进入首个切片。

三个端先围绕必要动作承接：客户端提供/纠正获准资料并查看任务缺口；企业侧管理来源用途、更新责任及状态；总台维护技术能力和运行状态。数据范围管理与内容访问分权，尚未授权的角色或访问动作继续保持未决；无需让企业管理员配置解析算法、检索步骤或模型分工。

下一项具体设计产出是“来源/更新事件 → 最小输入说明 → 任务读取结果 → 缺口处理”的实例，并据此确定受影响的接口与验收。权限隔离、版本依据、重复导入不重复计入、陈旧/缺失提示按实际切片验证；不先固定表结构、专项模型或全部渠道的统一量化指标。
