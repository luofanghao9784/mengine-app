## 2. 总体开发方式

**按已确认主路线采用模块式开发：业务服务按模块组织、统一发布，梦核引擎通过独立契约接入，后台任务和受限执行环境单独运行。交付按完整工作流程逐段完成。**

“模块化单体”指账号、空间、资料、会话等业务模块有清楚的职责和接口，初期在一套 Spring Boot 后端中维护。耗时工作由后台进程承担。代码模块数不等于服务器数；是否进一步拆服务依据真实负载和团队维护能力决定。

| 部分 | 负责什么 | 与其他部分如何连接 |
| --- | --- | --- |
| 网页交互 | 延续现有画报、会话、资料阅读与成果交互 | 调用业务接口，接收回复与进度 |
| 业务平台 | 身份、企业/空间授权、资料版本、会话、任务、成果发布、用量 | 保存业务事实，核验每次读取、执行及发布 |
| 梦核引擎 | 企业上下文、变化识别、证据判断、影响与优先级、协作建议、反馈改进 | 只经稳定接口读取获准上下文、产生分析及工作提案 |
| Agent 执行层 | 模型调用、工具使用、执行循环、文件产物 | 优先验证 DeepSeek Harness，经适配器执行获准任务 |
| 后台调度与数据设施 | 异步/定时任务、受限工作目录、数据库、文件和检索 | 受企业、用户、任务授权与资源额度约束 |

梦核引擎解决“理解什么、如何判断、什么值得做、如何改善”；Harness 提供组织模型和工具执行的运行能力；业务平台负责“谁有权做、实际做了什么、成果属于谁”。三者可独立演进。

## 3. 梦核引擎基础机制建议

用户随后要求深入讨论动态组合触发和自进化，详见[专门机制讨论稿](梦核引擎-主动调度与自进化机制讨论稿-V0.1.md)。下表是拆解框架，不以固定周期或统一人工批准替代待讨论的机制。

会话与后台分析共用引擎、按任务调用所需能力已经用户确认。其余机制已由用户暂定沿讨论稿，细节在引擎迭代中继续验证，不再作为整体搭建的前置阻塞；保留“理解企业 → 有据判断 → 授权协作 → 验证调优”的既有方向。

| 环节 | 第一版建议机制 | 必须留下的依据 |
| --- | --- | --- |
| 输入与触发 | 手动会话、资料变化、周期检查调用同一套能力；主动任务绑定目标、资料范围和预算 | 谁/什么触发、检查范围、使用版本与时间 |
| 企业上下文 | 整理企业目标、组织职责、资源约束、工作承诺及领域术语；允许结构化设置与资料提取并存 | 事实来源、负责人、有效期、冲突与待确认项 |
| 发现与判断 | 对照既定目标和规则发现变化/冲突；模型提出候选判断，规则与计算工具核实可计算事实 | 问题成立条件、支持/反对证据、缺失信息；不能用模型自评代替核实 |
| 优先级与协作 | 结合影响、紧迫程度和责任范围，提出谁应介入及可采取的动作 | 排序理由、相关责任、受众和执行前置条件 |
| 工作与反馈 | 发现进入画报；会话承接核实/决策；授权工具执行后记录成果和实际结果 | 发现、决定、任务、成果、后续结果之间的关系 |
| 记忆与改进 | 记录用户纠正、误判及适用条件，形成候选方法；在样例上对照验证后按授权启用 | 新旧方法版本、评估样例、质量/耗时/成本与回退点 |

已确认会话与后台主动分析共用引擎，按任务选所需环节。简单问答不必执行全部流程。主动调度器决定何时唤醒，引擎在获准目标内决定本轮值得处理什么，工具层决定可实际执行什么。

### 3.1 上下文和记忆

建议分别保存：企业事实与工作约束、已确认的决策及其理由、个人偏好、可复用方法与评估案例。每条内容有来源、作用范围、时间/版本、确认状态及撤销或失效方式。

企业、空间、个人是不同作用范围。明确表达的低风险个人偏好延续原有自动记忆且可撤销的规则；推测出的重要事实和职责仍先确认。读取私人对话、发布团队结论及用于跨客户研发是不同动作。可共享的方法不得夹带其他企业资料、专有判断或可识别信息。

### 3.2 发现到执行的衔接

建议发现具有稳定身份，状态可分为候选、待核实、待决策、处理中、待验收、已结束/已撤回。具体状态机随首个场景确认。相同问题的新证据更新原事项，控制重复提醒；没有有用变化时允许不生成新画报。

工作提案与执行记录分开。提案包含目标、依据、资料范围、动作、预期产物和需要确认的事项；执行时重新检查当前权限与版本。读取权限不自动变成修改、共享或对外发送权限。

### 3.3 独立替换和迭代的落实方式

- **接口独立：** 定义版本化的上下文请求、分析结果、工作提案、反馈和评估契约；引擎不依赖页面组件或业务表的内部结构。
- **执行可换：** 梦核引擎通过运行时适配器使用 Harness 和模型；更换 Harness、模型或分析策略不要求重写业务平台。
- **数据可迁移：** 企业事实、决策、反馈、来源和成果使用平台管理的中立数据结构；引擎专用索引/缓存可重建。引擎状态需要导出、迁移和兼容策略，不能承诺任意实现无成本热换。
- **版本可追溯：** 每次运行记录引擎、模型、提示/方法、检索配置和来源版本。运行中的任务固定版本，新版本先用于新任务；旧任务明确恢复或迁移，不静默切换。
- **升级可比较：** 旧案例回放评估、只产生候选结果的影子运行、小范围启用和回退。回放不能再次执行真实发布或外部写入。
- **独立升级：** 初期可在同一仓库，但引擎有独立服务契约、构建产物、启动配置和部署/回退流程；不同负责人通过版本化协议协作。新旧版本和运行中任务的兼容须有测试，不把目录分开视为已经实现可替换。

建议暂将 AI 可变工作策略与确定性的权限/状态规则分开。自动优化不能自行改企业权限、计费边界和平台发布规则。

## 5. 已确认技术主线与配套候选

已确认 Spring Boot 业务平台＋独立梦核引擎，前端继续 React。数据库、检索、队列等配套仍是工程建议；具体版本在原型中锁定兼容组合并核验许可。

| 部分 | 推荐候选 | 选择原因及限制 |
| --- | --- | --- |
| 前端 | 保留 React + TypeScript + Vite、现有组件/CSS | 复用已确认界面；逐步把 localStorage 业务数据换成服务数据 |
| 业务后端 | Java＋Spring Boot，用户已确认 | 模块化单体，通用 API 服务网页及后续 App；比较依据见多端架构文档 |
| 引擎 | 独立服务/进程＋版本化契约 | 独立构建、部署及回退；实现语言不受主后端限定 |
| 数据库 | PostgreSQL＋显式迁移 | 保存关系、权限、版本、任务和事件；企业标识/约束及 RLS 加固需专项验证 |
| 资料检索 | 简介/元数据定位＋关键词＋pgvector | 原始资料保留；中文分词、嵌入模型、表格召回与重排用样本验证 |
| 文件存储 | 云对象存储，通过内部接口封装 | 厂商随部署地区选择；原件、版本与成果分开标识并授权下载 |
| 任务调度 | 按主后端和执行边界选型；TS worker 可用 BullMQ＋Redis | 数据库为任务事实源；不同语言经稳定任务契约交互，不依赖私有队列数据结构 |
| Agent 运行 | DeepSeek Harness 优先验证，外接运行适配器 | 开发者预览，具体版本、接口、恢复、文件工具和隔离尚需原型 |
| 模型 | 模型 API 适配；对话、嵌入、视觉分别选型 | 不因采用 DeepSeek Harness 自动限定只用 DeepSeek 模型；供应商、型号和费用待定 |
| 文件处理 | 按格式选择解析/生成库，必要时增加 Python 进程 | “能读取、能生成下载、保留原格式、在线编辑”分别评估，不把文本预览当 Office 能力 |
| 接口与发布 | HTTP/OpenAPI＋SSE 进度；Docker、试点 Compose；CI＋接口测试＋Playwright | 开发/测试/生产分开；后续按规模升级部署方式 |

后端比较与选择依据见[多端架构与技术栈确认](多端架构与技术栈确认-V0.1.md)。PostgreSQL 提供[行级安全策略](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)，[pgvector](https://github.com/pgvector/pgvector)提供向量检索。这些是能力核验，尚非本项目安装和兼容性验证。

主路线已确定，NestJS/FastAPI 留作历史比较。引擎及文件处理的语言不受主后端限定；ORM、前端请求库等普通实现细节由开发选择并记录。

## 6. 按依赖推进的开发批次

| 批次 | 待办 | 验收证据 |

| B3 引擎可迭代与 9POP 验证 | 引擎/方法版本、评估案例、回退；9POP 管理场景的数据映射和目标配置 | 相同基础引擎用于新场景；管理判断有依据，指标口径明确；新旧版本比较质量/耗时/成本 |
| B4 群力团队试点 | 多成员使用、共享维护、职责协作、选定业务连接或应用能力 | 员工产生和复用成果；多角色授权与并发版本有效；不因发布成果开放私人对话 |
| B5 持续深化 | 扩大主动范围、方法库、梦境维护、应用生成和更多连接/客户端 | 每项按真实场景独立确认并验收 |

试点管理、用量、备份、告警和恢复从 B0 开始设计，在第一批真实使用前达到相应要求，不留到最后补。B3/B4 是建议顺序，用户尚未确定具体启动时间。

任务状态建议采用排队、运行、待补充/待确认、取消中、成功/失败/已取消；最终细节随切片确认。成功必须有真实产物/业务写入。队列只负责调度，事务、幂等键、唯一约束及可补发事件保障重试一致性，见[BullMQ 幂等任务说明](https://docs.bullmq.io/patterns/idempotent-jobs)。

基础验收覆盖：权限丢失时中止新的读取/写入；确认绑定明确方案版本；重复执行不重复发布；历史画报来源固定但访问实时检查；数据库策略不替代对象存储、工具、缓存、日志的授权；备份必须实际还原。共享检索前先过滤权限，结果交付时再核对受众。

具体周期在首项工作、文件范围及 Harness 原型后估算，本轮不编造已通过检查或固定交付日期。
