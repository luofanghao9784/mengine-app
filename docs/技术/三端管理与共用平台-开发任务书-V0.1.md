## 1. 三端分工与角色关系

输入、处理、输出描述工作如何完成；三端描述不同使用者从哪里开展工作和管理。一个板块可以涉及三个端，同一人也可以具有多个入口的资格。业务负责人在客户端使用 AI，并不因此必须成为系统管理员；进入总台也不自动获得全部技术发布权。

| 入口 | 主要职责 | 典型使用方式 |
| --- | --- | --- |
| 客户端 | 完成工作，查看、纠正和维护本人及获准空间的内容 | 会话、目标与任务、画报、资料与成果、经验和偏好维护 |
| 企业管理端 | 配置本企业如何使用 AI，管理组织、授权和运行 | 成员与空间、企业档案、数据与能力接入、AI 工作配置、本企业运行与变更 |
| 平台总台 | 开通企业、维持平台运行，管理通用能力与技术发布 | 企业生命周期、通用规则/模型/工具/方法版本、兼容和评估依据、平台运行 |

表中是职责归属，不是给现有管理员整列新增权限。具体人员、服务身份和动作授权在后续细化；同一有权者可以承担多种职责，不要求每项动作由不同人批准。网页优先及后续 App 顺序不变，自进化不新增第四个端。

## 2. 各板块管理对象的归属

下表汇总需求，不表示所有对象已有实现或都要成为顶级菜单。企业与空间的维护者按对象授权确定，不按职务名称推断。

| 对象 | 客户端承接 | 企业管理端承接 | 平台总台承接 |
| --- | --- | --- | --- |
| 成员、组织和工作空间 | 当前企业/空间、本人工作身份及获准协作 | 本企业成员、组织、空间元信息及权限配置 | 企业开通/状态和已允许的初始管理员流程 |
| 企业事实与用户档案 | 本人的企业内工作档案、偏好及纠正；获权维护企业/空间事实 | 企业档案的责任、适用范围、默认配置与确认状态 | 通用结构和能力版本；不汇集客户档案正文 |
| 普通资料与外部业务数据 | 上传、获准批量导入、资料版本、来源缺口和纠正 | 来源授权、连接状态、同步范围、字段映射与业务口径的维护分工 | 通用连接器/解析能力、兼容及不含客户内容的技术状态 |
| 目标、持续委托与执行能力 | 目标沟通、计划及任务状态、补充、停止和获准重试 | 企业默认职责、工具可用范围、委托与资源策略及管理状态 | 通用执行能力、模型/Harness/工具版本和技术运行 |
| 资料库与经验库 | 获权内容维护、适用性反馈、经验使用和纠正 | 本企业内容维护分工、入库/使用范围、分类与专属配置 | 库结构、检索/索引方法和获准通用经验；客户经验不自动外流 |
| 成果、画报与反馈 | 阅读、编辑、明确发布、两类反馈及本人呈现偏好 | 企业默认交付要求、发布范围、站内提醒策略及获准汇总 | 通用排序、呈现与站内交付能力的版本和运行 |
| 评估、异常与资源 | 本人或获准任务的结果、影响、补充及恢复动作 | 本企业评价维护分工、获准业务证据、运行汇总及资源策略 | 通用样例/工具、技术评价、平台运行和资源状态 |
| 方法变更及后续自进化 | 与本人工作有关的变化说明、纠正及获准内容维护 | 企业/空间的采用策略、实际生效范围、停止和恢复 | 通用候选、评估、发布及平台技术处置；不越过企业采用授权 |

空间资料、经验正文和业务目标的维护优先复用客户端对象详情；集中核查、跨空间冲突、企业正式口径及维护策略优先在企业管理端的对应工作区处理。经验维护采用第 11.7 节的双入口建议，按工作场景选择，不将同一动作强制限定在某一端。两端可复用同一对象、编辑组件和版本记录，管理页在具备内容及动作权限时也可直接承载编辑，不要求全部跳回客户端。“避免重复建设”不等于禁止管理端编辑。能维护空间内容不等于能给成员授予权限；能读共享成果不等于能读反馈人的私人会话。

普通索引更新、明确偏好维护、正常经验归档和任务恢复属于基础系统；自进化后续改进这些维护方法，不接管基础能力的日常运行。资料库是否复用 WeKnora 等组件按输入任务书核验，不把第三方管理界面直接当作企业管理端。

## 3. 每项管理能力先明确什么

在安排页面前，为实际交付的管理对象说明以下事项。它们是设计检查项，不要求所有对象强行放进同一张表或万能配置模型。

| 检查项 | 需要回答的问题 |
| --- | --- |
| 对象与来源 | 管的是业务事实、目标、偏好、方法、授权还是运行状态；原始记录由哪个模块负责 |
| 生效范围 | 作用于平台通用、某企业、某空间、某企业内的个人或当前任务；是否影响共享依赖 |
| 可执行动作 | 可看状态、读内容、维护、授权、执行、发布、采用、停止或恢复中的哪些动作 |
| 决定资格 | 谁能确认业务含义、取舍和交付要求；谁能配置或执行；依据什么有效授权 |
| 可见证据 | 为完成该动作确实可读哪些字段、比较和来源；没有正文权限时能判断什么 |
| 当前状态与变更 | 当前实际版本、待生效差异、覆盖范围、失败/未知部分、后续观察及退出条件 |

界面明确当前企业、对象及实际生效范围。跨端跳转、切换企业或恢复未完成操作时重新校验目标与当前身份；不能把上一个企业的配置草稿、偏好或候选带入另一个企业。服务端仍逐动作核验，页面隐藏和入口地址不能承担授权。

## 4. 权限与决定不能混为一项

建议采用少量常用角色组合承接明确动作，首版不要求企业编写权限表达式或从零设计角色体系。以下是动作区别，具体授予谁仍需后续收口。

| 动作 | 所需依据 | 容易混淆的情形 |
| --- | --- | --- |
| 查看运行/管理状态 | 对应范围的管理查看权及允许字段 | 状态、文件名、接收名单、错误摘要也可能含受限信息 |
| 读取资料和评价证据 | 内容及用途授权、当前成员/来源状态 | 管理头衔或评测需要不产生读取权 |
| 维护事实、目标和方法 | 对应对象的维护权；业务含义需有权者确认 | 能修改配置不代表能改变财务口径或业务承诺 |
| 授予权限或预授权 | 对应范围内可授予的动作和委托边界 | 自身有某权限不自动等于可以转授；管理员任命及自授权继续待定 |
| 执行任务或试验 | 任务、数据、工具、副作用、资源及期限的有效授权 | 读取资料不自动允许写入系统，评测通过也不产生执行权 |
| 发布版本或共享成果 | 对应技术发布权或目标空间发布/维护权 | 通用方法发布与客户内容发布不是同一动作 |
| 在范围内采用 | 有效采用策略或有权者对具体影响的决定 | 平台可用版本不等于全部企业正在使用 |
| 停止和恢复 | 具体对象及范围的控制权、当前版本和可恢复条件 | 停止优化不自动撤销业务效果；恢复不覆盖后来的人工作业 |

例如，更换检索方法需要技术比较和采用依据；改变“营业收入”的计算口径还涉及业务定义。企业管理员可以管理接入配置，但不能仅凭此身份决定新口径是否正确。需要内容判断时由获权业务维护者处理；没有合适决定者时只等待相关变更，无关获准工作继续运行。

上述区分不建立统一逐次审批层。已有授权覆盖且条件满足时，人或 AI 均通过相同的受控操作继续；需要新增决定时再呈现具体差异、证据、范围及后果。AI 可以协助生成、解释配置，不能通过会话获得更多权限或直接把任意文字变成系统指令。

总台首期没有客户内容入口、代入员工或临时支持授权，这是既有决定。客户提示词、样例、反馈原文、原始错误及小范围汇总不能变成内容旁路；去敏本身也不授权跨企业复用。企业管理端同样没有自动的私人内容读取权。FDE 是服务职责，当前不新增特殊全量访问角色。

## 5. 页面组织建议

页面按使用目的组织，算法和内部流程按需要下钻。以下工作区可以合并或以详情页呈现，名称、数量和路由尚未冻结；随真实能力交付增加入口，不先展示空白自进化菜单。

### 5.1 客户端保留工作主线

会话至少与画报同级，工作空间继续组织资料、成果及协作。个人档案/偏好可放在个人设置；空间资料、目标和经验维护放在相应空间或对象详情，具体导航随后续交互收口。任务等待、失败、待补充及交付提醒关联原任务和成果，不迫使用户去后台找自己的工作。

本人的普通偏好、成果纠正和获准空间业务维护不集中交给企业管理员审批。维护者保留自己的个人及业务工作空间，集中维护职责通过单独入口按需处理；拥有维护权不代表默认承担全企业维护任务。涉及持续目标、新执行授权或共享发布时展示对应影响；当前一句临时要求不自动改变整个企业配置。

### 5.2 企业管理端围绕五类管理问题

| 建议工作区 | 核心问题与操作 | 复用位置 |
| --- | --- | --- |
| 企业与成员 | 企业事实和组织如何维护，谁加入、停用、交接 | 企业设置、成员与邀请；档案事实按对应维护权 |
| 空间与授权 | 谁可查看、维护和执行哪些工作 | 现有共享空间及查看/维护授权，后续补动作范围 |
| 数据与能力 | 接了什么来源，是否正常，允许 AI 使用什么 | 来源连接/更新状态、能力范围；业务口径由有权者维护 |
| AI 工作配置 | 关注什么、可做到哪里、怎样交付、采用哪些方法 | 默认目标、工具/资源/交付策略、当前生效配置及方法采用 |
| 运行与改进 | 是否稳定、有什么问题、效果依据是什么、谁改过配置 | 运行概览、质量/异常和变更记录；后续接自进化建议与控制 |

默认提供可用配置，只在需要时修改。常用页面表达业务目的、允许范围及交付要求；高级方法差异供获权维护者按需查看。无需企业逐家复制主模型整份规则文件，仍沿共用基础规则、企业/空间差异和个人偏好的组合设计。

### 5.3 平台总台围绕三类内部工作

| 建议工作区 | 管理内容 | 边界 |
| --- | --- | --- |
| 企业与服务 | 企业开通/状态、初始管理员邀请、服务可用情况 | 不进入客户私人工作；套餐和计费另按商业范围确定 |
| 引擎与通用能力 | 模型/Harness/连接器/规则/经验方法、版本依赖、通用评估及发布依据 | 凭据由受控配置机制持有；发布与企业采用分开，新增执行权单独定义 |
| 平台运行 | 健康、聚合用量、异常影响、资源、发布/恢复及管理记录 | 状态基于真实记录；未知用量不填零，技术上限不冒充货币预算 |

自进化接入后，在相关能力详情中查看候选、比较、采用范围和停止/恢复；企业侧查看自身实际采用。两端引用同一变更及分范围结果，不各造一套互相矛盾的“发布成功”。共享组件故障或旧版本不受支持时，呈现真实影响与可用方案，不承诺企业永远可独立保留任意版本。

## 6. 共用平台需要提供的支撑

共用平台指三端和各业务模块共同使用的能力，不新增一套万能管理系统或新的生产运行中枢。主模型规则文档负责指导模型使用能力；可信授权、调度状态、版本和回执仍由平台及相应执行组件负责。

| 共用能力 | 本轮建议的增量 | 责任边界 |
| --- | --- | --- |
| 身份、作用范围与动作授权 | 在已有企业/空间隔离上补实际新增动作、授权来源及有效期限 | M2 联动各对象；权限由服务端、数据和工具层执行 |
| 配置与方法版本 | 能查看有效组合、来源、待生效差异、适用范围和兼容依赖 | 各模块保留自身语义；不把事实/偏好/权限混成任意覆盖文件 |
| 变更与采用记录 | 人工维护和后续自进化共用真实差异、授权、评估关联、分范围生效和恢复依据 | 复用正常发布/变更能力；不为每个端或板块另建实验平台 |
| 任务、资源与运行证据 | 复用任务/尝试、回执及用量，关联异常、评估和实际方法 | M4 及原模块维护执行事实，M7 维护观测/比较；不复制调度器 |
| 管理与工作交互 | 共享控件、作用域提示、版本冲突/未知结果呈现、获权详情跳转 | 复用三端风格；客户端处理本人工作，管理端处理对应管理状态 |
| 保留、导出、删除和恢复 | 按资料、独立企业副本、反馈、评估证据、审计等分别确定策略与动作 | 复用输入/成果/运行规则，不用一个全局开关承诺清除或恢复一切 |

同一配置中，正式业务要求、默认表达偏好、当前任务要求和访问授权具有不同含义；不能用“企业层总覆盖个人层”解释所有冲突。页面应能说明实际采用的依据，不要求把所有规则和日志展示给普通用户。

版本检查和权限复核与实际写入/采用衔接，重复提交不重复生效；回执未知先核对，旧候选不能覆盖新修复。管理摘要不可用可以延后展示，必要授权或关键执行事实无法确认时停止受影响动作。自进化未部署或停用时，这些基础维护能力仍可正常使用。

首个代表闭环只实现其必需的共用能力，随后逐步复用。首版不以完整工作流设计器、自定义权限语言、统一审批中心、商业计费或独立实验门户为前提。

## 11. 工作与维护入口及企业自进化分工

用户追问维护职责是否干扰员工本职工作、现有客户端能否承载，以及企业自进化在企业管理端还是总台管理。本节修正首轮“日常业务维护留在客户端”的宽泛表述，提出更细的分工；具体页面、维护角色和托管策略尚待确认，未新增实际权限或运行授权。

### 11.1 按操作性质安排维护入口

判断入口不能只看“属于业务内容还是系统内容”，还要看操作规模、频率、责任和影响范围。同一份资料可以在日常使用时纠正，也可以在集中核查中处理，仍是同一业务对象。

| 操作性质 | 示例 | 建议入口 |
| --- | --- | --- |
| 本人工作与轻量维护 | 更新资料版本、修改本人文稿、反馈当前画报、纠正本人偏好 | 客户端原对象旁，按权限显示必要动作 |
| 共享空间内的局部维护 | 修正一条获准经验、澄清空间目标、处理当前资料的问题 | 对应空间/对象详情的维护操作；不使所有成员进入管理模式 |
| 企业范围的集中维护 | 批量待核实内容、跨空间冲突、正式业务口径、来源接入、经验入库策略、评估标准和采用策略 | 企业管理端相应工作区，按对象开放给获授权维护者 |
| 通用技术运行维护 | 解析器/检索方法升级、通用模型或工具兼容、平台容量和故障 | 平台总台及受控工程发布流程 |

“空间目标”也需按实际影响判断：在工作中澄清本空间已授权目标可留在客户端；改变企业正式目标或扩大部门交付承诺，需要进入相应决定流程。日常上传与错误纠正不因放在客户端就被认定为系统管理员工作。

### 11.2 同一员工如何兼顾自己的工作

维护职责附加在企业成员身份和明确范围上，不替代这个人的个人空间、会话或日常业务职责，也不要求专门创建一个空的“系统维护工作空间”来装管理功能。确有团队协作需求时可以使用普通共享空间，但该空间不会自动获得管理权限。

建议默认进入日常工作；有权维护时在对象详情显示轻量动作，需要集中处理时再进入企业管理端相应工作区。维护者只获得职责所需入口，例如资料质量和经验维护，不必同时获得成员停用、管理员任命或其他企业配置权。这需要补细粒度管理能力及入口校验，现有只允许企业管理员进入管理端的规则不能不经设计就扩大。

维护事项应有责任范围和处理依据，不能把全企业问题自动推给所有有维护权的员工。可自动完成的获准检查和维护由系统处理，需要人判断的冲突或业务含义再交给相关维护者；有权限不等于被分配全部维护义务。集中批量操作与日常会话分开呈现，只有影响当前任务时在工作入口提示必要信息。

跨端跳转应保留当前任务定位及已保存草稿，返回后可继续工作；企业或权限变化时按当前权限恢复，不能为保留上下文继续展示已撤权内容。维护耗时、待处理积压、无效提醒和对本职工作的打断可作为后续评价依据，不能只用系统质量提升掩盖转移给员工的维护成本。

### 11.3 现有页面可以复用什么

2026-09-30 静态核对：[真实资料页](../../src/material/Library.tsx)已有按维护权呈现的上传、目录及版本操作；[真实工作端](../../src/identity/AccessApp.tsx)有会话、画报、资料库及个人/共享空间入口，空间主页主要列获权空间并进入资料库。它们能为原对象轻量维护提供基础。

当前真实页面尚无完整的空间目标/经验维护、批量核查、维护责任队列或企业自进化管理。[Demo 空间页](../../src/pages/Workspace.tsx)中的空间设置和[Demo 导航](../../src/components/Sidebar.tsx)中的个人设置不能当作真实服务已具备这些能力。

因此本轮建议保留客户端的工作主线，同时扩展原对象的必要操作，并在企业管理端增加集中维护能力；不能直接宣称当前页面无需调整。两个入口共用对象、版本、动作接口及可复用编辑组件，根据权限取得内容，避免各自保存副本或出现两种生效状态。具体抽屉、详情页及导航数量留待交互切片确认。

### 11.4 企业自进化分为执行能力与管理入口

建议共用优化机制，按企业/空间的授权执行优化任务，按需使用模型和资源。企业专属优化指目标、证据、候选、授权及采用范围属于该企业，不意味着每家企业必须维护一套算法、常驻模型或独立自进化引擎。是否拆分实例、队列或物理部署由后续容量和隔离需求决定。

| 层面 | 建议归属 | 实际处理什么 |
| --- | --- | --- |
| 优化执行 | 后端共用优化能力，在获准范围内运行 | 观察、生成候选、组织评估、按策略采用及持续观察；管理页面关闭不影响已授权任务 |
| 通用能力与技术运行 | 平台总台 | 优化机制和工具版本、兼容、通用评估、技术故障及资源状态 |
| 企业优化政策与效果 | 企业管理端的获权角色 | 哪些对象/数据可参与、允许动作和资源、采用条件、本企业效果及停止恢复 |
| 具体业务判断与纠正 | 有对应内容和业务权限的维护者，按工作性质进入客户端或企业维护工作区 | 评价是否解决实际问题、维护标准、处理超出既定策略的业务取舍 |

总台提供统一技术运行视图，不成为全量客户优化内容的汇集点。企业任务的执行器可以在被授权的数据用途和范围内处理内容；这不赋予总台人员查看客户提示词、样例、候选正文或原始错误的权限。通用改进只使用获准通用证据，企业专属案例/方法不自动转为平台资产。

### 11.5 企业侧可以采用托管方式

企业管理端保留控制入口，不意味着客户需要日常调算法、训练模型或逐条审核候选。建议提供易理解的默认托管方案，由有权者确定优化范围、数据用途、资源条件、业务标准、允许采用的类型和退出方式；这些条件成立后，AI 按有效授权自行推进，企业主要查看效果、异常和需要决定的事项。

托管是后续交互与服务设计建议，不是本轮已确认的自动类别或授权。企业专属方法可在本企业范围完成评估与采用，不必每次升级为平台通用版本；涉及共用代码、组件或结构时仍进入平台技术发布流程，企业采用政策不能替代共享依赖的发布资格。平台技术故障处置也不能借此改写企业业务标准。

例一：平台改进通用经验检索方法，通过获准通用样例验证并发布，各企业依有效采用策略更新，总台和企业端分别显示可用版本及实际采用状态。

例二：某企业销售周报遗漏既定要求中的业务分类，获准企业优化任务可比较检索、上下文或呈现方法，在原业务标准与采用条件内改善；它不能自行改写销售额定义、扩大读取权限，或把企业样例共享给其他客户。客户无须关心内部检索参数，但可以知道改了哪些行为、对本企业有何效果，以及怎样停止。

两端引用同一优化任务/变更的获准信息与分范围状态，避免分别运行两套互不关联的优化流程。企业停止相关优化后，不再启动相应新工作或采用，已有方法仍由基础系统运行；在途试验、未知结果、恢复和共享组件限制沿自进化任务书处理。

### 11.6 对后续任务与验收的补充

1. 在角色专题定义内容维护、业务决定、采用策略和技术运行的具体能力组合；能使用部分企业维护功能不等于成为全权企业管理员。
2. 在客户端保留个人/业务工作，新增必要的原对象维护入口；企业端承接集中处理，验证上下文返回、权限变化及同一对象跨入口版本一致。
3. 让维护事项只进入相关责任范围，评估维护负担；自动维护沿基础能力实现，自进化后续优化其方法。
4. 后接入自进化时，验证共用执行能力处理企业专属任务、企业托管策略和总台技术视图能够协作，且总台无客户内容旁路；停用本企业的相关自进化能力，不影响其他企业及本企业仍获准的基础工作。

以上均为拟开发及验收内容。本轮仅更新设计，不新增菜单、管理角色、客户数据访问或后台优化任务；第 12 节继续细化组织角色及授权生命周期，承接本节新增的部分管理入口权限。

### 11.7 部门与跨部门经验维护采用两个入口

用户进一步提出：企业可以有多个部门及各自维护负责人，部门负责人在客户端维护经验符合工作习惯；企业管理端也应能集中维护，方便跨部门负责人。用户随后要求继续下一步，双入口方向按 DEC-092 接续：同一套经验资产和维护能力提供两个操作入口，具体角色授予、页面及批量操作规则仍待细化，未进入实现。

| 入口 | 主要工作场景 | 建议交互 |
| --- | --- | --- |
| 客户端的工作空间/经验详情 | 部门或业务维护者处理本范围经验，与实际任务、资料和使用反馈结合 | 查看与修订经验、补充适用条件、处理待核实事项及失效反馈；只呈现本人获权动作 |
| 企业管理端的经验维护工作区 | 获权维护者集中处理一个或多个部门/空间的经验 | 按空间、业务分类、负责人、状态等筛选；查看使用/问题记录，直接编辑单条或对选定范围批量维护 |

两个入口按使用目的组织，同一维护者可选择适合当前工作的入口。企业端可以直接编辑单条经验，客户端也不因“轻量”定位而禁止本范围内合理的维护操作；具体批量交互随对象和风险设计，不把入口分工变成互相排斥的权限规则。

共同约定如下，作为后续设计与验收依据：

1. **同一经验、同一版本与状态。** 企业端展示各获权范围内的经验，不因集中展示复制成另一个库或自动转成全企业共享经验；两端编辑共用服务和记录。
2. **范围绑定实际业务对象。** 部门可以关联多个空间，空间也可以有跨部门协作；维护权落在明确空间/经验范围和动作上，不强制部门与空间一一对应。跨部门管理员也只处理其获权范围，私人经验不因管理角色自动纳入。
3. **使用入口不改变权限。** 查看、修改、发布/扩大复用范围分别核验；经验维护职责不自动产生成员管理权或源会话读取权。集中维护可以只开放相应管理能力，无须赋予全权企业管理员。
4. **集中处理不抹平业务差异。** 相似经验可能在不同部门有不同适用条件；先比较依据，再决定关联、修订或形成可共享版本。跨部门维护权不自动产生业务裁决权，正式口径或职责冲突按对应业务授权处理。把部门经验推广到更大范围属于单独的发布/授权动作，不由企业端编辑自动完成；引用或独立发布继续遵守各自来源和撤权规则。若经验包含 Skill、脚本等可执行方法，内容修订与方法发布/采用分别记录，不直接改变在途任务的方法版本。
5. **修改不互相覆盖。** 两端指向同一当前版本，提交旧版本时提示冲突并保留尚未提交的修改供有权者核对；批量操作逐对象检查范围与版本，明确已完成、未完成和待核对结果。
6. **负责人保留自己的工作。** 原个人空间、会话和业务任务照常使用，维护待办按责任范围呈现。已有权限允许的维护直接完成，不因有两个入口增加“部门先审、企业再审”的固定流程。

后续验证至少覆盖：部门负责人从客户端更新经验，获权跨部门维护者能在企业端看到同一新版本；企业端更改同一经验后客户端反映实际状态；未获权部门/私人经验及源会话不出现在集中视图；两端同时修改不会静默覆盖，编辑部门经验不会自动扩大其发布范围。本轮仅记录设计，不代表这些场景已验收。

## 12. 组织角色与授权生命周期

本节沿经验维护双入口方向，提出任命、授予、调整、停用和交接的具体方案。[总任务书第 11.2 节](开发任务书-V0.1.md#112-授权与角色的首版推荐)进一步推荐首版主要授权负责人、显式共享自授权、失联核验及存量责任确认路径，仍待用户确认；当前代码中未开放的动作保持原状态。本轮没有授予真实权限或修改账号、任务及数据。

### 12.1 部门关系与工作空间分开表达

企业成员可有部门、岗位和业务职责；工作空间承载实际资料、成果和协作范围。一个部门可使用多个空间，一个空间也可服务跨部门业务。部门主管、空间内容维护者、成员授权者及业务决定者可以由同一人兼任，但不因职务名称自动相互包含。

建议首版只提供实际场景所需的组织关联和少量职责组合，不建立完整人事系统或自定义权限语言。部门调整提供需要复核的权限清单，不将原部门所有权限自动带到新部门，也不因组织树上的上下级关系开放下属私人资料。

### 12.2 建议采用的职责组合

| 职责 | 典型能力 | 授权范围 |
| --- | --- | --- |
| 普通成员 | 本人工作、获准内容使用及个人偏好 | 本企业成员身份、本人空间及明确共享授权 |
| 业务/内容维护者 | 维护指定资料、经验、目标或评价依据，处理对应问题 | 一个或多个空间/对象；部门及跨部门维护者复用同一能力组合 |
| 企业配置管理员 | 成员邀请/状态、空间配置、来源/能力及企业使用配置中被授予的管理动作 | 本企业及明确可管理的对象/动作，不默认包含所有业务决定或内容 |
| 企业授权负责人 | 确定管理员任命、授权政策和责任交接，指定可代为授予的范围 | 企业已具备的合法授权范围；不产生私人内容、他企业数据或平台权限 |

“企业授权负责人”是建议明确的一项责任，可由企业指定人员兼任，并非另建高于所有内容规则的超级账号。同一人可以承担全部适用职责；大企业可分工，单人企业不强制增加第二人。业务目标或口径的决定权还需按实际业务职责确定，不要求再为每一种业务建立一个系统角色。

部门维护者在客户端或企业端使用同一获权维护能力；仅因需要企业端的经验工作区，不授予成员停用、角色任命等无关管理功能。平台角色继续独立，不能通过上述企业职责代入客户业务。

### 12.3 管理员任命与初始责任的建议

建议企业指定的授权负责人可以任命、调整和撤销企业配置管理员；普通配置管理员默认不具有任命同级管理员或任意转授权的能力。确需委托他人处理任命时，明确可授予的职责与范围，实际操作按有效委托执行，不为每次常规任命增加平台审批。

未来新企业开通时，在初始管理员安排中同时明确由谁承担授权责任，接受相应身份后生效；可由同一人兼任。存量企业不能仅凭“原来是管理员”或数据库中的 owner 字段批量升级为授权负责人，需在迁移方案中明确责任归属及原权限映射。新增身份能力的迁移不扩大内容权限，也不无依据撤掉既有合法访问。

授权责任转交应先确认接任者为有效企业成员并接受职责，再解除原负责人的相应职责，避免企业失去有效管理主体。可以预先安排备用责任人，但首版不强制多管理员或多人联签；责任人数量、委托期限和身份恢复方式在相关交互前收口。

无法联系或登录唯一负责人的恢复流程仍需独立设计，核实企业侧身份及授权依据；总台现有“更换尚未接受的初始邀请”不能用于替换已加入的管理员。平台不自行裁决企业内部接班人，不通过代入账号或读取私人内容解决交接。

### 12.4 共享空间自授权的建议

建议采用“默认没有内容权，有明确授权资格时可显式取得指定共享权限”的方式。授权负责人可在企业有权管理且允许其取得权限的共享范围内，为自己明确授予查看或维护权，并记录范围、动作及生效依据；可在创建空间流程中一起表达该决定，但不能因创建者字段隐式获得权限。

普通配置管理员默认不能自行决定增加本人内容权。若企业已有有效政策明确允许其取得相应权限，可据此操作；否则由有权者决定。这是可执行授权的资格区别，不要求单人企业为自己额外找一个审批人，也不把“管理员不能自授”设计成永久绝对禁令。

具体边界建议如下：

- 自授权只覆盖明确的共享范围和动作，不能进入他人的个人空间、私人会话或取得源会话访问；外部来源附带的用途/转授限制仍有效。
- 为本人取得“查看”不自动取得“维护”，取得内容维护不自动取得成员授权、发布扩大范围、工具执行或业务决定权。
- 服务端检查授予人资格、接收人资格、对象范围及权限上限；不能通过管理员 A 授给 B、B 再授给 A，绕过对管理员本人取得内容权的规定。
- 若某共享空间要求限制管理者访问，应同时约束其授予他人、再转授及修改授权政策的能力。只禁自授权按钮，却允许间接制造自己的读取资格，不能保证该限制。
- AI 只能执行明确获准的授予动作，不能从部门头衔、维护任务、错误排查或候选内容中推断新的授权。

共享内容的授权操作与读取仍分开记录；页面应让有权者知道实际增加了哪些范围。现有自授权接口继续关闭，以上仅为本轮推荐，须与具体角色/范围方案确认后实施。

### 12.5 成员变动时如何处理权限和工作

| 变化 | 权限与身份建议 | 工作和资产建议 |
| --- | --- | --- |
| 加入企业 | 获得企业成员身份及明确授予的职责/空间权；岗位信息不自动开放所有资料 | 保留本人工作入口，按获权范围使用经验与工具 |
| 调整部门或职责 | 复核原职责、新职责及需保留的协作权，分别记录撤销/新增 | 业务维护责任按对象接续，不强制搬迁资料或复制经验 |
| 临时停用成员 | 该企业身份暂不可用，保留但不使用原授权；恢复时仅使用仍有效且未撤销的授权 | 核对受影响任务状态，不因恢复身份自动重试失败或重复已发生动作 |
| 长期离职或明确撤权 | 终止对应成员访问，处理其个人委托、能力授予及待交接责任 | 企业共享资产按原规则保留；私人资料/会话不随岗位自动转移 |
| 转交授权或维护责任 | 接任者取得明确职责和必要权限；原角色及不再需要的授权分别撤销 | 保留历史操作者和版本，不改写旧回执或把所有对象换个 owner 就当完成 |

离职不应等待资料交接完成才切断不再有效的访问。相反，关闭访问也不等于业务责任和任务已完成交接。临时停用与长期离职若采用不同恢复政策，需要明确原因和状态，不能用同一个“恢复”动作悄悄重建永久撤销的权限。

持续任务按授权来源处理：本人请求或依赖私人资料/个人凭据的任务，在相关权限失效后停止受影响的新动作；不能简单更换负责人继续读取。已形成独立有效企业委托、使用企业获准资料和执行能力的任务，可在该委托持续有效且责任明确时继续，或按原策略交接；若只能依赖离职者账号执行，需补企业委托机制，不能伪装成已有独立身份。

企业授权和已发布政策也不因最初操作人离职而全部失效：要区分已独立生效的企业授权，与仍依赖该个人权限的委托链。前者按自身期限/撤销状态继续，后者重新核验，不以一刀切保留或删除代替判断。自进化预授权同样按实际授权主体、范围及有效条件处理。

对未开始、正在执行、已终结和结果未知的任务分别展示处理结果。新动作使用当前有效身份/授权；已提交动作先核对真实结果，避免重复。恢复身份不是新的业务请求，积压任务是否继续还需核对原委托是否有效、是否过期及是否已被替代，不统一补跑所有历史动作。

企业共享经验/资料和已明确发布的独立企业副本按各自规则保留。个人工作空间和会话继续遵守原内容权限，交接职务不自动移交账号、密码、私人会话或私人资料；确需交付的业务成果通过明确发布/共享处理，非自愿离职后的个人资料处置政策仍待专门确认，不由管理员获得内容的需要反推权限。

### 12.6 已有实现与本轮新增的区别

本轮只读核对源码与既有记录，未执行测试或修改运行代码：

- 当前企业身份只有 `TENANT_ADMIN` 与 `MEMBER`，见[身份契约](../../contracts/public-api/identity.ts)；没有本节建议的独立授权责任、部分管理工作区角色或任务接任机制。
- [企业管理服务](../../apps/api/src/main/java/com/dreamcore/workspace/identity/TenantAdminService.java)继续拒绝本人新增查看/维护权，[管理接口](../../apps/api/src/main/java/com/dreamcore/workspace/identity/TenantAdminController.java)没有管理员任命/降级入口。
- 最后一名有效管理员保护已经用于成员停用路径，以账号、成员均有效且角色为管理员计算；不能据此声称角色降级、全局账号停用和新授权责任转交都有同等保护。全局账号停用等历史场景使用数据库夹具，见[撤权记录](../交接/M2-D1撤权与停用验证-2026-09-23.md)。
- 现有成员停用保留空间授权，恢复不重建已撤销授权；企业恢复不启用单独停用成员，沿原验证范围理解。
- 当前任务使用请求人的身份，复核当前权限并在发现失权后拒绝；失败/取消/中断需要明确重试。但停用成员/企业没有统一取消队列或持久标记“这些旧任务须重新恢复”。仍为排队状态的任务可能在身份恢复后被正常领取，短暂停用也不保证每个运行任务都观察到该变化。相关行为见[会话服务](../../apps/api/src/main/java/com/dreamcore/workspace/conversation/ConversationService.java)及[企业状态管理](../../apps/api/src/main/java/com/dreamcore/workspace/identity/PlatformAdminService.java)，不把本节新生命周期要求写成已有实现。

若采用本节方案，应补明确责任/授权来源、授予资格及范围、停用影响与恢复条件、管理端部分入口、跨端权限复核和迁移验收。任务状态/调度仍由处理及原执行模块负责，管理端呈现和调用同一事实，不另建任务系统。

### 12.7 拟验收与接续

1. 一个企业有多个部门和跨部门空间，维护者只取得指定范围，既能在客户端工作，也能进入获准的企业经验维护页面；部门上级没有自动的私人内容权。
2. 企业授权负责人任命管理员，接任和撤销按当前资格生效；管理员自行任命同级或通过旧页面、互授权限扩大内容范围时被拒绝。
3. 单人企业负责人可按明确决定取得合法共享空间权限，系统无须第二人审批；私人空间/会话及受限来源仍不可越权取得。
4. 转交授权职责或停用成员与并发操作交错，最终仍有合法管理途径，已撤销权限不会经恢复复活；不可使用的账号不能被当作有效接任者。
5. 企业持续委托与个人任务分别经历离职：获准企业工作可按委托和责任安排继续，个人权限依赖被识别；未知副作用先核对，不复制账号或无条件重试。
6. 两端维护同一经验时保留版本/权限一致；既有企业授权和独立发布成果不因原操作者离职被误删，私人内容不因交接被转授。

这些场景均待实施验收。本轮给出管理员任命和受限自授权的推荐，尚未改写旧实现或视为全部确认。下一专题讨论企业初始化和 AI 工作配置：哪些信息开通时必需、哪些可由使用中补齐，默认职责/主动范围如何生效，并承接本节待确认的角色安排。全局汇总前继续跟踪，依赖具体权限的功能须在实施前收口。

## 13. 企业初始化与 AI 工作配置

本节把[输入冷启动背景](输入板块-开发任务书-V0.1.md#88-系统目标与冷启动的跨板块补充)、[处理侧目标与冷启动](处理板块-开发任务书-V0.1.md#4-任务从哪里开始)及站内输出要求落实到三端使用流程。默认方案、启用范围及交互仍为建议；[总任务书第 11.3 节](开发任务书-V0.1.md#113-默认主动工作的首版推荐)进一步提出按范围一次启用及自主工作的初值，尚待确认；第 12 节管理员任命、自授权和责任制度仍保持待定。本轮没有开通企业、保存实际调度计划或启用模型/自进化。

### 13.1 可以开始工作不等于全部配置完成

建议把初始化设计为可逐步补齐的使用过程。企业无需先填完整组织图、岗位画像和经营目标，也无需先建成经验库或接通 ERP；只要当前任务所需的身份、能力、授权和输入条件成立，就可以开始对应工作。需要企业事实的分析仍必须有足够依据，不能将“可以使用会话”宣传为“全部经营分析已准备好”。

| 何时需要 | 必要信息或条件 | 可以后补的内容 |
| --- | --- | --- |
| 企业开通及身份使用 | 企业识别信息、有效初始管理联系人/成员安排、企业状态及服务可用条件 | 完整部门结构、所有成员、行业画像及全部业务目标；新授权责任按第 12 节另行确认 |
| 开始一次具体工作 | 当前成员/空间和动作权限、所需能力及资源、可取得的任务输入 | 与当前任务无关的档案字段；简单提问不要求先建工作计划 |
| 启用某范围的主动辅助 | 有权者、范围/用途、允许行为、资源与退出条件，实际可用的触发能力 | 算法权重、完整行业模型及所有后续关注；产品提供可理解的初值 |
| 建立持续交付 | 有效职责或明确委托、资料及更新责任、接收范围、触发/时区/期限、资源及保存成功的计划 | 未涉及的业务来源和其他部门配置 |

模型、解析或某工具的运行配置由对应平台能力提供，客户通常选择可用能力及使用范围，不必自行配置供应商密钥、维护主模型规则或填写 Token 参数。实际启用前平台必须有可执行的资源限制，不能以数值留待设计为由按无限资源运行；具体额度与服务承诺在全局范围和运行条件具备后确定。

配置是否必需以当前动作判断。例如，缺少企业行业信息可能降低主动建议的针对性，但不应阻止用户修改一份已上传的文稿；建立每周报表计划时，时间、来源周期和接收范围才成为必要条件。明确且已有效的信息直接复用，不要求用户重复录入或确认同一授权。

### 13.2 建议的首次使用流程

1. **总台开通并交给企业侧管理。** 沿现有企业/初始管理员流程，展示真实服务状态，不把开通企业等同于所有成员已加入、所有空间已授权或自进化已启用。
2. **企业侧补最少背景。** 可用自然语言简述主营业务、空间用途或当前关注；目标尚不明确时可跳过。已有资料可作为带来源背景，AI 提取与人工确认分别记录，文字中的“负责人”不产生平台权限。
3. **选择一个实际起点。** 直接发起会话；选择获准资料完成一项工作；或在指定空间启用基础工作辅助。界面只提供已可用的能力，并呈现缺失条件，不强制依次走完三条路径。
4. **形成首个可用成果。** 输出能够核实的结果、范围和关键限制；需要补充时说明具体缺什么以及影响哪部分。成果在原会话/任务中直接可找，只有适合推荐时再进入画报，不为完成初始化强行生成卡片数量。
5. **通过使用校准。** 用户纠正当前结果、表达明确偏好或提出持续关注，分别交给对应机制维护。没有反馈不会自动形成永久目标，明确且获准的持续委托也无需再走一套重复确认表单。

员工加入已配置的企业后，复用其获权范围内的有效配置，补本人的必要职责或偏好即可，不让每位员工重做企业初始化。开通过程的服务/授权前提与可选业务补充分别呈现；允许跳过画像不等于跳过执行所需的权限、输入或资源条件。

### 13.3 推荐提供基础工作辅助方案

建议产品提供可按范围启用的默认方案，帮助客户从有限主动工作开始，而非要求客户先设计所有任务和算法。有权者看到对象范围、会做什么、交付给谁、资源条件和停止方式后，可以通过一次有效设置启用；启用后范围内的工作自主推进，不逐候选请求许可。

| 工作类型 | 建议默认行为 | 启动及停止依据 |
| --- | --- | --- |
| 明确任务 | 直接完成分析、检索、起草及获准动作；发现缺口时先推进独立部分 | 用户请求及当前有效授权，沿原任务取消/重试规则 |
| 基础资料维护 | 按导入/来源规则解析、索引、维护可重建关联及获准明确偏好 | 既有输入和维护授权；不与“主动发现”开关绑定 |
| 有限主动发现 | 在纳入范围内核查缺口、变化和与工作相关的问题/机会，形成有依据的发现、草稿或候选 | 已生效的辅助策略及实际资料就绪/变化或获准检查安排；有结束条件，可无新发现而结束 |
| 持续关注与交付 | 跟进有效职责或明确委托，按已保存计划处理 | 目标、计划、运行身份、资源及期限持续有效；无变化也履行约定交付 |

推荐初始主动范围围绕当前工作及明确纳入的共享空间/来源，选择范围时说明包含哪些现有内容及后续新增内容。读取权限与主动处理用途分别核对：能读一个空间，不自动意味着后台可持续分析它；范围一旦有效，AI 可在其中自主选材，无须逐文件再问。

新增空间不能仅因属于同一企业就自动纳入既有探索范围。私人空间按本人及既有用途规则处理，企业开通不代替全员授权扫描私人资料。一次上传可以触发既有输入维护，也可触发已经启用且覆盖该来源的分析；上传动作本身不建立新的永久关注。

默认成果先交付本人或有效策略指定的获权接收者，首版限站内。共享发布、写入业务系统和更大受众传播按其自身授权处理，不由“基础工作辅助”名称一并授予。已有明确执行授权仍可正常使用，不因默认初始方案以分析为主就要求所有业务动作逐次重问。

“停止主动发现”“暂停某项持续关注”“取消本次任务”和“关闭提醒”分别表达。停止一般探索不撤销明确任务及已承诺交付；关闭提醒不停止后台工作，关闭某计划也不停止输入的正常解析维护。独立自进化不在初始方案中，仍在基础版本完成后接入测试。

### 13.4 没有业务系统或数据不完整时如何起步

| 当前条件 | 可以完成的初始工作 | 需要如实表达的限制 |
| --- | --- | --- |
| 只有少量业务背景 | 整理工作方法、准备模板、提出带适用条件的调查方向；公开检索在已有能力与授权内使用 | 不能声称已发现该企业的经营异常或核实不存在的问题 |
| 有导出表格、文档等资料但无 API | 沿上传和版本链路分析实际资料，必要时登记持续来源及人工更新责任 | 没有接口不妨碍当前文件任务，但不能承诺自动得到后续业务数据 |
| 有资料但没有明确重点 | 在有效辅助策略中核查少量相关变化/缺口，形成有依据的初步结果，再通过反馈校准 | 无需先设完整经营目标；行业经验只是方法参考，不替代企业证据 |
| 来源可连或文件已解析，但当前期资料不齐 | 交付能够核实的部分，说明覆盖、口径和补充需求 | 技术成功不等于业务数据完整，未知不填零，不以缺数据报告“一切正常” |
| 没有业务系统且关键事实从未记录 | 结合目标选择最小记录表及负责方式，说明哪些工作当前不可做 | 完整 ERP/CRM 建设仍是额外业务；是否能承担持续服务按数据可得性判断 |

冷启动可使用少量经核对的通用/行业方法，不等待本企业积累大量成功会话，也不要求首版覆盖所有行业。方法没有足够适用依据时可以回到基础分析或说明缺口，不虚构“行业最佳案例”。

### 13.5 AI 工作配置呈现业务选择

配置按企业默认、空间差异和本人偏好使用；当前任务要求在其范围内生效。以下是页面内容分组建议，不要求创建五张独立配置表或五个菜单。

| 配置内容 | 使用者需要看懂和调整的事项 |
| --- | --- |
| 工作目的与职责 | 当前有效目标、职责来源、适用空间/场景及维护责任；哪些是已生效要求、默认建议或候选理解 |
| 资料与能力范围 | 可用来源、工具及动作，哪些范围纳入主动辅助；连接、资料覆盖及待补条件 |
| 主动发现与持续工作 | 已启用范围、关注事项、真实计划、后续触发条件、暂缓/停止及影响 |
| 成果与站内交付 | 交付对象、形式、必要内容和提醒偏好；普通表达偏好与正式交付要求分开 |
| 资源与当前生效情况 | 可理解的资源方案/技术限制、当前使用与未知部分、受阻原因、配置版本和变更范围 |

AI 可协助解释已有配置、从获准内容形成草案和提出推荐。普通低风险明确偏好沿已确认维护原则生效，正式职责/权限或会改变业务承诺的设置按对应资格处理；配置写入及计划被平台接受才算生效，不能用模型说“已经安排”代替回执。

无需客户编辑完整规则文档。主规则保持共用的行为与能力使用原则，具体背景、目标和配置按需装配。企业正式要求、企业默认样式、空间差异、个人偏好及当前请求具有不同含义，不能使用一条“企业设置覆盖一切”规则；例如个人可选择更简洁的呈现，但不能借此删去正式交付必需的风险说明。

建议页面能查看“当前实际生效什么、来源于哪里、可修改哪部分”，高级方法和详细版本按权限下钻。草案未保存不影响运行；并发更改核对版本，普通配置更新按适用规则影响后续任务，权限撤销或关键缺陷立即按对应边界处理。关闭页面或刷新后从真实状态恢复，不重新创建配置、重复运行首次分析或补造历史发现。

### 13.6 初始化的状态与跨端分工

不以一个“企业初始化完成”勾选代替所有可用性判断。至少区分：企业/成员及授权可用，来源接收/解析/覆盖状态，某项任务的能力和输入是否满足，后续计划是否实际保存，以及成果是否真实交付。某来源故障只影响依赖它的工作，其他获准任务仍可运行。

客户端呈现与本人任务有关的资料选择、初次成果、必要补充和后续关注；企业端集中呈现档案、来源/能力、基础工作辅助及计划的有效范围与维护责任；总台呈现企业服务、通用能力及允许的技术状态。企业配置者没有正文权限时，只显示获准元信息，需要业务判断的部分交给有内容权和决定资格的维护者。

示例：销售部门上传两期报表，没有 ERP 接口。若当前请求或有效基础方案覆盖这些资料，AI 可以核对周期和口径后分析变化，缺少成本数据则不计算未经支持的利润结论。用户明确要求每周跟进时，复用已有设置或补齐缺少的更新责任、触发时间和接收范围，保存真实计划；后续仍需人工交表时明确说明。当周资料未到就保留缺口和对应待办，不宣称已完成完整检查，也不反复调用模型空等。全过程不依赖自进化。

### 13.7 拟开发任务及验收

任务仍沿 M2/M3/M4/M5/M7 分工：补按能力展示的初始化入口、档案与配置草案/生效记录、可按范围启用的基础方案、真实来源状态、持续关注/计划关联及首次成果到反馈的真实交互。身份/任务/资料事实复用原模块，三端不另建初始化调度器。

现有企业开通、邀请、个人/共享空间、文件上传和会话是复用基础；完整档案配置、主动辅助及持久关注计划仍需增量实现。真实云模型与实际业务效果继续按接入授权验收，不以目前的本地合成流程或新向导页面证明冷启动效果。

拟验收场景：

1. 仅有企业基本身份和少量背景时，可开展获准的准备工作；不强制 API、完整画像或既定经营目标，不伪造企业发现。
2. 上传部分历史资料后，接收/解析状态与业务覆盖分别显示；已有范围内可分析，不自动产生无限探索或长期委托。
3. 启用限定空间的辅助方案后，AI 可在范围内自主核查；新建空间、私人资料、超出用途的工具和共享动作不自动纳入。
4. 资料补齐后按有效任务/计划继续，关联原依据与新版本，不重复已完成动作；保存计划失败不能显示“已安排”。
5. 企业默认、空间差异、个人偏好和当前要求按性质组合，两个企业不串用；档案中的职位文字不改变权限。
6. 明确周期交付即使无新变化仍履行约定；未取得数据与已核实无变化分别呈现，关闭提醒不取消任务。
7. 草案修改、重复提交、页面关闭和并发保存不重复启用或运行；撤权/暂停后旧入口与迟到触发按当前状态处理。
8. 首次成果在站内可找到，反馈只影响相应对象及范围；自进化未部署时上述使用、维护及计划机制仍成立。

本轮没有运行这些验收。默认启用方式、首批场景及行业方法、资源/频率、角色授予和首次交付标准需在相关切片前收口；本节为具体推荐，不产生当前企业的后台工作授权。

下一专题将运行与改进工作区、待处理事项和跨端交互串起来，明确用户、维护者、企业管理者及平台技术人员如何分别处理缺资料、评价、异常和方法变更；随后收口必要的数据保留/删除/导出与管理阶段汇总，再进入全局任务整合。

## 14. 运行与改进工作区及待处理流程

本节将[日常观测与异常恢复](评估与运行观测-开发任务书-V0.1.md#12-第三轮讨论日常观测异常处理与资源边界)、[站内交付](输出板块-开发任务书-V0.1.md#11-本轮讨论交付和推送)、[两类反馈](输出板块-开发任务书-V0.1.md#12-本轮讨论画报反馈与会话反馈)及方法变更映射到三端。页面分组、责任流转和具体动作仍为设计建议；前文未决角色和默认策略不因本节继续讨论而自动生效。

### 14.1 先让使用者知道有什么需要处理

建议三端展示同一业务事实的不同获权视图，并提供与当前问题相符的操作。普通用户主要处理自己的工作，维护者集中处理职责内问题，总台处理技术运行；不将所有日志、反馈和模型建议都转换成人工待办。

| 使用入口 | 建议呈现 | 能做什么 |
| --- | --- | --- |
| 客户端会话、任务与相关对象 | 与本人工作有关的缺口、失败、待决定或更正说明；必要时提供“需要你处理”的汇总入口 | 补充资料、澄清要求、查看结果、提出纠正、按权限继续或取消 |
| 企业端运行与改进工作区 | 本企业获权范围内的运行概况、待处理事项、评价/反馈问题及方法变更 | 按空间/责任/原因筛选，处理来源或配置问题，进入原对象维护，查看实际恢复与采用情况 |
| 总台平台运行及引擎工作区 | 允许的服务/组件状态、技术异常影响、资源和通用方法变更 | 排查通用技术问题，执行获准运维及发布动作，查看分范围技术结果 |

企业端可先按“运行概况、待处理、改进与变更”组织列表或详情，名称和导航仍可调整。客户端不必增加一整套运维后台，可在原任务提供操作，再按需汇总本人待处理事项；方法/评测详情向相应维护者开放，不让员工处理内部技术参数。

用户已决定将待办卡片放在智能画报板块内，采用可折叠区域：概览最多显示两排，支持完全展开和完全收起（DEC-093）。第 14.8 节维护该设计，与原任务、企业端集中处理共用状态；此前独立待办视图建议被本决定替代。

运行概况继续说明统计范围、时间窗口、最近检查及未知数据。任务执行、内容质量、使用反馈及方法比较分别表达；不能用一个“健康分”或关闭事项数量证明系统有效。方法变更在基础阶段承接人工维护和正常发布，自进化接入后再接其候选及试验记录，不提前展示虚构的优化结果。

### 14.2 问题如何分流

| 问题或信号 | 优先处理者及入口 | 怎样判断取得了进展 |
| --- | --- | --- |
| 资料缺失、过期或口径不清 | 当前任务使用者、来源责任人或获权业务维护者；客户端原对象或企业待处理列表 | 所需周期/范围资料已补齐，或已明确可完成部分及仍缺条件；上传成功本身不算问题解决 |
| 当前内容错误或关键遗漏 | 当前任务/成果的获权处理者；共享内容交其维护者 | 依据核对、确切更正版本和必要复核可关联；私人原稿更新不冒充企业副本已更正 |
| 重复、不相关或表达偏好反馈 | 系统先按有效反馈/偏好策略处理；需人时交对应维护者 | 实际偏好或呈现调整及范围可查；低分不自动引发无限重做或停用通用方法 |
| 技术故障、资源受阻或执行结果未知 | 系统按已有策略恢复；超出范围再交相应企业配置者或平台技术维护者 | 原动作回执、恢复检查及受影响工作可核对；未知结果先查明，不默认提供一键重跑 |
| 需要业务取舍或新授权 | 对应范围的有权决定者 | 具体决定及影响已记录，并通过原对象接口生效；指派给某人不自动给其决定权 |
| 方法改进候选或采用后退化 | 具备该范围评估、发布、采用或停止权限的维护者，或已获准的自动流程 | 比较、实际采用及后续效果各有状态；评测通过、版本发布和企业生效不混为一项 |

已授权的安全重试、补资料后继续、明确低风险偏好维护等可直接执行，保留记录；无需先生成让人点击确认的卡片。向人提出事项时，至少说明发生了什么、影响什么、已有依据、缺少什么，以及当前可执行的下一步。原因不确定时标为待核对，不让 AI 推断直接成为已证实根因。

没有明确需要人采取的动作时，可保留为运行记录、获准汇总或改进线索，不占据所有人的工作队列。正常等待、权限正确拒绝及用户取消也不自动认定为事故。确有未解决责任但暂时找不到处理者时，保留缺口并按已有责任分工升级，不悄悄关闭或自动发给全体管理员。

### 14.3 处理记录关联原业务对象

“待处理事项”用于组织责任、下一步和处理依据，可以关联任务、资料版本、反馈、评测及变更。原模块仍维护实际执行、内容和采用状态；不以新增事项系统复制另一套任务事实，也不要求每次反馈或每个任务都额外创建一条事项。

建议区分三类信息，而非只有一个通用“已处理”按钮：

| 信息 | 示例 | 生效含义 |
| --- | --- | --- |
| 个人提醒状态 | 已读、稍后提醒、关闭本人的一般提醒 | 影响该人的告知，不改变其他人的职责、原任务或业务截止时间 |
| 处理进展 | 待接手、处理中、等待资料/决定、待复核、已结束 | 表达责任和处理过程，具体字段随实现确定；结束可因修复、误报、重复、被替代或有权决定不再处理 |
| 实际结果依据 | 已补交、已更正、检查恢复、确认线下完成、仍未知 | 引用原对象状态、真实回执或有权人员确认；只代表其具体覆盖范围 |

不同结束原因不能全部计为解决成功。有权者确认“线下已完成”可作为业务状态证据并注明来源，不要求伪造系统工具成功；相应失败回执仍保留。暂不处理或接受某项取舍，要记录其适用范围及仍存在的影响，不写成技术故障已修复。

点击操作调用原模块，取得实际结果后再更新处理进展；网络丢失回执时保留待核对，不先将事项关闭。用户已从另一入口补交资料或完成修订时，相关待办按真实状态更新，不能要求重复上传或继续催办。原问题解决后仍有必要质量验证或业务后果处理的，保留具体未完成部分。

### 14.4 责任与内容权限分别核对

处理责任优先来自原任务、来源、空间、有效业务职责或已配置维护范围；AI 可以提出分流建议，但不能仅凭职称推断责任或授权。涉及多人协作时明确各自需要完成的部分及当前承接者，不把同一动作同时要求每个人各做一次；指派、转交和接手方式在相应角色方案确认后落实。

指派责任不会授予读取、执行或业务决定权。缺少权限时呈现具体阻碍，交给具备所需资格的人在原范围处理，或由有权者另行决定共享必要信息；不能为方便排障把私人会话、反馈原文或受限资料自动附给管理员。可见摘要、标题、来源名称和小范围统计同样遵守内容边界。

部门负责人可以在客户端接手其维护范围的事项；跨部门维护者可以在企业端集中处理相同事项。两端共用对象及处理记录，只返回当前使用者获准看到的部分。人员调岗、离职或失权后，责任分配和可做动作重新核对，旧链接不能继续授予权限；缺少接任者时保留受影响工作及责任缺口。

跨企业共用组件故障可由平台关联为同一技术事故，但企业侧保留各自受影响工作及业务复核。总台取得允许的技术标识、原因和影响汇总，不据此读取各企业的任务正文、文件名、反馈和样例，也不获得代用户运行任务的权力。

### 14.5 合并提醒和并发处理

同一事项重复触发或同一故障影响多个任务时，可以按真实来源和因果关系合并提醒，并保留不同对象、版本和新增影响。不能仅凭文字相似合并不同部门的业务结论，也不能因为已经有一条事项就丢掉后续新证据。

处理顺序综合当前阻碍、有效截止时间、实际影响范围、等待时长及证据确定程度。模型标记“紧急”不自动改变业务承诺或绕过资源限制；也不把普通探索永远排在所有工作之前。仅有建议处理时间时明确其性质，不伪装成企业已承诺的时限。

两端或多人同时操作时复核当前权限、对象版本及处理进度，重复提交引用同一真实动作。界面可以提示有人正在处理，但协作提示不能代替服务端检查；批量处理逐项核对并呈现成功、失败、冲突和未知部分。迟到的旧反馈或动作结果不能覆盖后来的人工作业。

再次提醒应有未完成责任、实质变化或有效约定，原事项已完成、被替代或转交后停止旧对象的重复催办。一人关闭个人提醒，不影响其他责任人的待办；一人完成本部门部分，不自动结束整个跨部门事项。无反馈不算完成或接受建议，用户撤回某条评价也不自动删除其他独立证据支持的纠错事项。

首版业务提醒全部在系统内，沿 DEC-088。提醒策略不要求常驻模型或持续监视员工屏幕，也不把系统外异常推送借此纳入首版。

### 14.6 示例与完成依据

例一：销售周报缺当期数据。任务中显示具体缺失周期；若存在有效来源责任，相关维护者可从客户端或企业端补交。平台核对新资料和任务条件后按授权继续，处理记录显示“已补交，分析待完成”，而非直接认定报告交付成功。完成后关联真实报告版本，用户关闭页面也可返回查看。

例二：用户指出共享报告数字错误。系统关联该反馈对应的报告版本，获权维护者核对来源，明确是资料问题还是处理问题；依据不够时保留待核对。修正私人草稿、更新企业副本及告知原接收者分别按实际授权处理，不因一次差评自动改源数据。即使反馈者撤回评价，已独立核实的问题仍可继续修复。

例三：模型服务故障影响多个企业。平台在技术视图处理服务，企业侧看到各自获准工作受影响的状态；服务检查恢复后记录技术恢复。失败任务是否重试、是否曾产生结果以及已交付报告是否要复核，继续逐项处理，不能将所有企业业务统一标为已完成。经有效策略可以自动处理的恢复继续自主执行。

例四：出现经验检索方法改进候选。企业或平台维护者按其范围查看比较及限制，已有采用策略覆盖时可以自动采用；需要新的业务决定时才进入对应待处理事项。候选不采用也可正确结束，但不能据此宣布已经提升效果。自进化后续加入相同流程，基础阶段的人工更新及正常维护不依赖它。

### 14.7 可复用基础与拟开发验收

本轮静态核对：[运行概览](../../src/operations/OperationsPanel.tsx)和[运行接口](../../apps/api/src/main/java/com/dreamcore/workspace/identity/OperationsController.java)已有真实聚合读取，当前异常仅统计窗口内目前失败/中断的任务，重试恢复后会移出；无指派、处理进展或关闭回执，不是完整历史异常列表。[客户端任务操作](../../src/conversation/Conversations.tsx)有本人任务取消/重试及版本校验，不能据此认定管理员可以接任或代处理。

[真实画报契约](../../contracts/public-api/briefing.ts)已有关注、隐藏和尺寸偏好，完整有用/没用及原因交互主要在 Demo，不能当作服务端反馈闭环已实现。当前未形成真实异常处置或方法改进面板；本文没有启动服务或运行测试。

拟增量包括：原业务对象与处理依据的关联、按责任和权限呈现的待处理视图、必要的协作/等待记录、实际操作与状态同步，以及正常方法变更的管理呈现。M2 负责对应管理授权，M3/M4/M5/M6 维护原对象和执行，M7 提供观察与评价；不以完整工单产品、统一审批中心或新的调度平台为前提。

拟验收至少覆盖：自动处置不增加无意义人工确认；跨入口补交/纠正后旧待办更新；关闭个人提醒不结束业务责任；线下完成不伪造工具成功；部分恢复和未知结果不被批量关闭；重复/并发操作不重复执行；责任转交不扩大内容权限；平台技术恢复与企业业务复核分开；反馈撤回或迟到不误删独立问题证据；无自进化时基础处理和正常方法更新仍可运行。

后续观察应包含真正受阻时长、按期处理情况、问题复发、错误关闭、重复提醒和人员维护负担，保留统计范围及未覆盖部分；不以事项数量、关闭率或员工排名单独衡量价值。具体字段、责任委托、提醒例外及首版处理类别仍待交互/全局收口。

下一专题收口资料、经验、反馈、评价证据和运行记录的保留、删除、导出与恢复边界，再形成三端管理阶段汇总。当前继续只整理任务书，未新增页面、分派真实任务或启用任何后台处理。

### 14.8 智能画报内的可折叠待办卡片

2026-09-30，用户明确决定将待办卡片设计在智能画报板块内，可折叠、最多显示两排，并支持完全展开和完全收起（DEC-093）。本条替代此前“画报 / 待办”切换或相邻独立待办视图的建议；当前只更新任务书，未调整页面。

已确认的展示结构如下。“最多两排”适用于概览状态，完全展开时可查看超过两排的待办；完全收起时隐藏全部待办卡片。

| 展示状态 | 卡片范围 | 交互责任 |
| --- | --- | --- |
| 两排概览 | 最多显示两排；不足两排时按实际数量呈现 | 可完全展开，也可完全收起 |
| 完全展开 | 可查看当前责任和权限范围内的全部待办 | 可返回两排概览，也可完全收起；数量较多时可按需加载，不遗漏后续事项 |
| 完全收起 | 不展示待办卡片 | 保留重新展开方式；不结束、删除或忽略待办责任 |

以下为配套交互建议，不扩大为用户已确认细节：待办区可放在智能画报靠前位置；首次进入建议采用两排概览；完全收起后建议只保留“待办＋数量＋展开按钮”的紧凑栏。可记住用户的展开偏好，新事项到达不默认强行展开。具体位置、默认/记忆策略、筛选和空状态在页面设计时落实，AI 会话继续保持既有主要入口。

“两排”按当前屏幕宽度和实际卡片排布计算，不等同于固定卡片数量；窄屏也应提供查看全部事项和完全收起的操作。建议使用高度协调的紧凑卡片，避免第二排内容被截断。待办区在智能画报内汇总工作事项，普通内容推荐继续采用其自己的呈现规则；不让兴趣排序、低点击或普通画报已读折叠删除待办。用户可以随时收起整个待办区，再展开时按当前真实状态读取。

卡片只在存在真实处理需要和责任依据时形成，不能把每个后台任务都转成人工待办。AI 正在执行、系统正在自动恢复、普通成果已生成等通常在原任务展示；需要用户补资料、作决定、纠正或履行已明确职责时形成待办。可阅读其他部门资料不自动意味着需要承担该部门的待办；已接手但正在等待条件的事项与需要本人立即处理的事项区分呈现，具体筛选名称仍待页面设计。

待办卡片建议呈现：问题标题及空间、需要本人做什么、当前状态、必要影响/依据、真实截止时间（存在时），以及一个主要操作和原对象详情入口。优先使用紧凑、稳定且状态清晰的布局，不要求每张卡配图或按视觉空位改变工作优先级。

例如，一张缺资料卡片可展示“销售周报缺本周报表”“资料补齐后继续分析”，并提供“补交资料”和“查看任务”。补交回执只证明资料已提交，实际覆盖检查和任务继续状态随后从原对象取得，不能立即把整份报告标记为完成。决定卡片先提供可审阅的方案、依据和影响，再执行获准动作，不因复用画报样式把重要决定压缩为不明含义的按钮。

卡片交互沿第 14.3—14.5 节，补充以下约定：

- 折叠、阅读、点赞、隐藏普通推荐或取消关注均不完成待办；稍后提醒也不更改业务截止。待办主操作使用“补充资料”“查看并决定”“核对更正”等与事项相符的表达，避免统一套用普通画报的有用/没用按钮。
- 两排概览仅限制可见数量，不删除超出部分；完全展开后可查完整的当前待办范围。待办排序可考虑真实截止、阻碍、影响及等待，不能仅按推荐兴趣；一般推荐开关不删除待办区的重新展开方式。筛选及完成归档不等于删除责任。
- 会话、智能画报待办区及企业端引用同一事项与原业务对象。在一处完成后，其余入口按实际状态更新；重复曝光不重复创建事项或统计处理次数，重复操作及版本冲突仍由服务端处理。
- 个人提醒与共同事项分开，一人已读或完成自己的部分不结束其他人的责任；等待或结束原因保持可查看。指派、转交、取消及批量操作按相应权限执行，不从卡片增加权限。
- 标题、预览、来源、附件和待办数量均按允许范围展示；点击卡片复核当前内容及动作权限，不能借待办读取已撤权资料或私人源会话。完全收起后保留的数量同样遵守权限。

用户此前暂时隐藏会话类型画报及“正在跟进”分组的决定继续保留。新待办依据真实处理动作设计，不批量恢复旧会话卡或旧分组；历史合成待办和 Demo 交互也不自动迁为正式企业责任。企业管理端继续支持获权范围的集中维护，与客户端画报待办区共用事项和处理结果。

拟验收：概览最多两排且不裁断卡片；完全展开可访问超出两排的所有获权待办；完全收起时没有待办卡片、仍可再次展开，业务状态不变；已读、普通推荐关闭或无推荐曝光不删除未完成事项；无须人处理的后台运行不增加人工待办；同一事项跨入口同步且不重复执行；补交与报告完成分别呈现；越权或撤权卡片及数量不能泄露内容；企业端集中处理获权范围，客户端仅呈现与本人责任相关的事项。具体视觉稿和真实接口接入在统一执行阶段完成，下一专题仍为数据保留/删除/导出/恢复。

## 15. 数据保留、删除、导出与恢复

本节承接输入第 9.5、10.3 节、处理第 8.3 节、输出第 12.6 节及评估第 12.5 节，将数据生命周期落实为共用能力和三端动作。用户随后认可按对象治理、分清停止使用与删除、三端职责及基础维护独立运行的方向（DEC-094）；具体期限、删除/导出职责、企业退出承诺及其他细化方案仍待确认。2026-10-01 已在[总任务书第 12 节](开发任务书-V0.1.md#12-数据保留与退出的首版具体方案)提出具体默认值及职责，作为本节后续推荐的统一出处，仍待确认；本节不另复制一份期限表。当前没有执行删除、导出、备份或恢复，也未新增内容采集。

### 15.1 按数据用途确定保留方式

建议区分原始内容、正式资产、处理证据及可重建数据。经验积累的目标是保持可用和可验证，不以保存全部历史或不断增加条目作为效果指标。

| 对象 | 建议保留方式 | 到期、失效或删除的影响 |
| --- | --- | --- |
| 原始资料、业务数据及版本 | 保留当前使用版本和有明确业务用途的必要历史；注明来源、所属空间及实际适用期 | 旧版本可以停止新分析，历史查看按权限和保留规则；正文删除后引用说明不可用 |
| 私人会话、草稿及随来源权限的成果 | 按本人在当前企业中的权限和已生效政策管理；业务交接通过明确共享成果完成 | 删除与退出不自动把私人内容交给管理员；相关摘要、上下文及私有派生内容一并检查 |
| 明确发布的企业成果、可用经验方法及案例 | 按发布范围、版本、适用条件和独立保留依据维护；定期核对有效性 | 停用、替代、归档和删除分别处理；独立发布不代表永久保留，也不随私人源内容删除一律消失 |
| 经验候选、原始反馈、评测样例 | 为明确维护或比较目的保存必要内容；候选有积压上限，原文与提炼资产分别管理 | 无价值候选和到期资料按政策清理；已撤回反馈不继续作为有效支持，独立核实问题仍可处理 |
| 授权、执行回执、版本采用及必要管理记录 | 保留支撑当前责任、去重、结果核对和后续维护的最小记录；正文另设保留规则 | 到期按政策清理；仍有未决执行或责任时按明确依据延长必要部分，不以审计名义永久保存全文 |
| 解析片段、索引、缓存、临时导出及诊断产物 | 从有效来源派生，设有限期限/容量；允许在权限及资源内重建 | 来源删除或用途终止时清理或失效；重建不能恢复已删除内容或已撤销资格 |

每种政策至少说明用途与范围、保留起算点、期限或持续保留条件、到期动作、可恢复窗口及负责角色。临时产物、候选、详细诊断和备份需要明确有限期限；正式业务资产可按持续有效的业务条件保留并复核。具体数值在统一执行前随首批场景、存储成本和交付范围收口，不把未填期限解释为永久保存。

企业可在平台实际支持的范围内选用保留政策。变更政策时说明新旧数据分别受何种影响，不能通过悄悄缩短期限清空在用依据；有权者可一次授权明确范围的到期清理，无需逐文件重复审批。延长保留也不自动扩大读取者或模型用途。

### 15.2 把用户动作及实际影响讲清楚

| 动作 | 应实现的含义 | 界面需要说明的边界 |
| --- | --- | --- |
| 隐藏或折叠 | 调整本人展示，包括画报待办区 | 业务事项和资料仍按真实状态存在 |
| 归档 | 转入历史管理并减少日常干扰 | 是否仍可检索/分析由有效性和用途决定；归档本身不撤权 |
| 停止使用 | 阻止指定来源、版本或方法参与受影响的新工作 | 历史依据可按权限保留；在途任务的后续读取和交付另作核对 |
| 撤销访问 | 终止某个身份或范围的后续访问 | 不删除企业资产，也不承诺收回已下载字节 |
| 移入回收站 | 撤出正常使用并在明确窗口内允许获权恢复 | 回收期内实际仍有保存，不能显示为已彻底清除 |
| 彻底删除 | 按授权范围清理正文及需随之清理的派生内容 | 显示实际完成范围、失败项、备份处理方式及可能保留的最小记录 |

建议普通可编辑资料/草稿提供可恢复删除；错误或失权内容先停止使用，避免回收或清理过程继续提供给 AI。具体哪些类型进入回收站、谁可彻底删除、是否允许按有效策略跳过回收期，作为业务配置收口；本节不授予所有维护者同等销毁权。

删除前呈现获准看到的影响范围：目标对象/版本、直接派生数据、相关任务和独立发布对象的处理差异。现有授权覆盖的明确删除请求直接执行；新增范围或缺少决定时再交对应责任者。共享使用和历史引用需要处理影响，但不应成为无限阻止有效删除要求的理由。

### 15.3 关联内容及在途工作怎样处理

删除不能只删资料列表中的一行。建议原模块维护资料版本与派生对象的必要关系，共用操作记录协调各存储和索引的处理；无需先建立覆盖全系统的复杂关系平台。

1. **解析、索引、缓存和模型上下文：** 阻止已删除或停止使用内容继续被新检索、旧链接或缓存返回；处理保存的摘要、提取片段和任务快照，不能借“摘要”继续保存应删除的正文。已发送给外部模型的内容不能承诺收回，供应商保存范围须在真实接入前核实并明确。
2. **随来源权限的私人派生成果：** 延续当前来源检查，撤权后不继续提供旧结果；来源正文已删除时标明依据不可访问，按具体删除要求处理内部副本。不能让历史版本、导出缓存或评价详情绕开该规则。
3. **明确发布的独立企业副本：** 沿 DEC-066 由目标空间及独立发布依据管理，删除私人来源不自动删除企业成果。若问题是发布内容本身错误或含有需要清除的信息，另对相应副本执行有权更正/撤回/删除，不能以独立副本为由永久保留所有内容。
4. **经验与评测：** 原始会话、经验候选、正式方法和案例证据分别判断。有效发布且可独立使用的方法可按自身政策保留；仅依赖已失效证据的案例应复核、缩小结论或停止使用，受限原文摘录按要求清理。去敏不自动授予新用途，也不必因删掉一次使用记录就删除所有无关方法。
5. **在途任务及迟到结果：** 后续读取、保存、发布和自动归档核对当前对象状态，防止删除完成后旧任务把内容重新写回。已发生的业务动作按真实回执记录；需要缺口处理或更正的事项关联原任务，不伪造已撤销的事实。

删除记录应区分请求已接受、停止后续使用、在线内容已清理、派生组件仍待处理及备份按政策到期等真实阶段。局部失败可幂等重试，但保持访问限制；必要最小记录也有明确内容和期限，不保存原文作删除证明。

例如：销售表已经生成私人分析和明确发布的企业周报。删除原表后，原件、检索片段和缓存按范围清理，私人分析按来源规则受限；独立企业周报按目标权限继续维护。如果原表是错误数据，需同时标出受影响周报并完成获权更正，单纯删除原表不能证明周报已被修复。

### 15.4 三端管理入口与数据导出

| 入口 | 建议承接的操作 | 权限边界 |
| --- | --- | --- |
| 客户端 | 在资料、经验、成果和本人记录中查看状态，执行获权归档/停用/删除/恢复及导出 | 读、维护、删除、批量导出分别核对适用授权；本人身份不绕过企业资产政策 |
| 企业管理端 | 在数据与能力管理中集中维护获权资产、查看容量/清理状态及配置政策，按授权组织企业资产导出 | 管理政策不自动开放私人正文；企业导出明确空间、对象类型、版本和负责者 |
| 平台总台 | 管理存储健康、清理失败、备份覆盖、技术恢复及企业退出执行状态 | 仅呈现必要技术信息，不提供客户正文浏览、全实例下载或代用户导出入口 |

尽量在原资料/经验/成果页面增加生命周期动作，企业端按需要提供集中处理；不增加第四个端。企业端与客户端继续共用对象及状态。基础设施持有备份的技术权限需单独控制，不能将“没有总台下载按钮”等同于备份本身已受充分保护。

日常原件下载和成果导出复用现有权限。新增批量或企业级导出需要明确授权范围，按对象检查，文件清单、名称、摘要和来源链接也遵守权限。生成、暂存和下载各阶段复核当前权限及有效期；生成时可读不代表撤权后仍可下载。

导出包建议附上所选范围、内容版本、格式、生成时间、未包含项及原因。部分导出不能标为完整迁移；当前版本导出与全部历史导出分别说明。内容导出文件与能重建运行环境的备份分开设计，不把 PDF/Word 或资料压缩包称为完整系统备份。临时包按期清理；已下载到用户设备的副本由其后续保存行为决定，不承诺远程收回。

### 15.5 恢复与企业退出

回收站恢复、历史版本恢复和灾备恢复分别处理。前两者在原对象范围内核对权限、版本、名称冲突和当前有效性；恢复旧版本应形成可追溯状态，不静默覆盖后来的修订。恢复内容也不自动重新启用已停用经验、恢复已撤销授权或继续旧业务任务。

备份按明确用途、保留窗口和保护方式维护，记录实际覆盖对象及最近还原验证。若备份不能即时逐条删除，应明确其隔离、到期清理方式和实际时间，不宣称在线删除等于所有历史备份已清空；备份不用于日常检索、模型分析或后台经验提取。

恢复旧备份前后要能够核对备份点之后的删除、撤权、停用及有效配置变更；正式开放读取和重建索引前重新落实有效状态。相关依据应有独立可靠的恢复路径，具体采用操作记录补齐或其他机制随部署方案确定。依据不足时保持受影响范围隔离，不能直接把旧权限快照当作现行授权。恢复记录不触发重复执行、重复发布或补发所有旧通知，结果未知的动作先核对真实结果。

企业停用、终止服务、数据导出和最终清理应有各自状态。建议企业退出时按已约定方案停止新增工作、处置在途任务，允许获权主体在明确窗口取得约定资产，再执行到期清理并给出实际覆盖回执；窗口结束不等于仍有未决清理的组件都已完成。保留窗口、费用及退出导出范围需要在交付约定中收口，不能从现有企业停用按钮推定已经支持。平台不因此获得私人内容阅读权，账号在其他企业的身份也不被一并删除。

### 15.6 日常维护与自进化的边界

到期清理、索引失效、已授权删除、临时导出清理和备份管理属于基础运行，自进化未部署或停用时照常执行。AI 可在生效范围内做候选去重、过期识别、保留建议和依赖影响分析；确定性期限和明确权限由平台执行，不要求每次清理都调用主模型。

未来自进化可优化分层存储、索引重建、候选压缩、采样及维护调度，比较检索质量、重要证据覆盖、存储/计算成本和维护负担。修改保留政策本身仍属于有范围和影响的变更；不能为降低成本删除必要反例，或为未来优化任意延长私人内容保留、扩大数据用途。

评价依据到期或撤销后，可按政策保留最小历史结论与方法版本，并标明无法重新取得的证据和受限覆盖；不得声称仍可完整重放，也不能静默删除失败样例后沿用原比较结论。正常的政策清理不要求永久保存全部评价正文。

### 15.8 后续交付与验收

拟由 M2 承接对象操作授权及政策配置，M3/M4/M5/M6 分别维护原对象、版本和派生关系，M7 承接必要操作证据、清理观测与备份恢复。先围绕资料及其任务成果实现代表闭环，再复用到经验、反馈和评价；不以完整企业迁移平台作为开始交付的前提。具体对象范围和依赖在下一轮管理阶段汇总及全局任务书收口。

拟验收场景包括：

1. 隐藏、归档、停用、撤权和删除表现不同；待办收起不完成任务，归档不自动开放权限或删除数据。
2. 原件删除后旧索引、缓存、私有导出和迟到任务不使内容重新出现；部分清理失败保持限制并能核对实际进度。
3. 私人来源删除或原作者离职后，明确发布的企业副本按目标权限处理；需要清理副本内容时有实际动作及回执。
4. 企业政策管理者和平台技术人员不能通过回收站、导出包、备份页或清理记录读到未授权私人内容；批量导出前后撤权仍有效。
5. 恢复资料时当前权限、删除记录及后续版本有效；恢复备份不会自动启用旧计划、重放已完成动作或突破企业隔离。
6. 删除正文后必要记录遵守最小范围，历史评价准确标明复核限制；反馈撤销不误删独立核实的问题，也不继续提供旧有效评价。
7. 经验候选和临时产物按政策清理，少用但必要的反例不被简单按点击淘汰；无自进化时清理和恢复仍可工作。
8. 企业停用、退出导出和清理分别有真实状态；业务导出缺项、备份未覆盖和外部已下载副本均不被承诺为已完整处理。

本轮未运行这些验收。需要在相应实现前确定的业务选择包括：首批各类数据的具体期限/回收窗口、共享资产彻底删除及企业批量导出角色、离职私人内容处置、退出窗口及导出范围。存储方案、备份覆盖和恢复目标随部署条件确认。第 16 节及总任务书第 10 节已形成阶段/全局整合；具体期限和退出推荐见总任务书第 12 节，存储和恢复目标继续随资源方案核对。未决项集中跟踪，不以本节成文视为全部确认。

## 16. 三端管理阶段汇总与全局衔接

本节汇总第 1—15 节，作为后续全局任务整合的管理依据。三端保留与管理职责方向沿 DEC-080、DEC-087，经验维护双入口沿 DEC-092，画报内可折叠待办沿 DEC-093；用户认可第 15 节数据生命周期方向，记为 DEC-094。具体角色资格、菜单名称、自动策略、期限、首版对象及交付拆分仍按待定或建议状态管理。本轮仅完成文档汇总，不新增运行权限或开始编码。

### 16.1 三端页面与工作归属

下表是页面组织建议；工作区可复用现有菜单、对象详情或抽屉，数量不等于新增顶级菜单数量，也不要求先搭齐所有页面再接业务。

| 端 | 建议组织 | 用户能完成的工作 | 关键约束与依据 |
| --- | --- | --- | --- |
| 客户端 | AI 会话、智能画报、工作空间及其资料/成果/经验、个人设置 | 提出任务、查看交付、补充与反馈、维护本范围资产和偏好 | 会话至少与画报同级；工作空间兼容部门、持续业务和项目；原对象按权限提供维护动作 |
| 客户端画报待办区 | 智能画报内的可折叠卡片区域 | 处理本人需要补资料、决定或纠正的事项 | 概览最多两排，可完全展开或完全收起；折叠不结束工作，不恢复旧会话类型及“正在跟进”分组 |
| 企业管理端：企业与成员 | 企业档案、组织关联、成员、邀请及交接 | 维护企业背景、人员和对应责任 | 部门/职位不直接授予内容权；任命、自授权和责任交接资格须单独收口 |
| 企业管理端：空间与授权 | 工作空间及对象/动作的授权 | 配置谁能查看、维护、执行和发布 | 配置权、内容权和业务决定权分别落实；不自动开放私人空间及源会话 |
| 企业管理端：数据与能力 | 来源状态、获权资料/经验的集中维护、能力范围及生命周期 | 接入和维护来源、处理跨空间资产问题、按政策清理与导出 | 客户端与企业端编辑同一资产/版本；来源连接管理不等于内容读取 |
| 企业管理端：AI 工作配置 | 默认职责/主动范围、持续委托、工具/资源和交付要求、有效方法组合 | 看清 AI 要做什么、可以做到哪里、当前采用什么 | 提供可用默认方案，按需修改；不让每家企业维护整份主规则文档 |
| 企业管理端：运行与改进 | 运行概况、待处理、评价/反馈问题、方法变更 | 核对实际效果，处理业务问题，查看本企业变更及采用 | 基础阶段承接正常维护与更新；后接入自进化再增加优化策略、候选、效果和停止恢复 |
| 平台总台：企业与服务 | 开通/状态、初始管理员流程及技术服务状态 | 维持企业服务可用，按约定处理退出状态 | 套餐/计费不自动进入范围；没有客户内容、员工代入或客户资料导出入口 |
| 平台总台：引擎与通用能力 | 模型/Harness、连接器、规则及方法版本、通用评价与技术发布 | 维护可替换通用能力及兼容关系 | 平台发布与企业实际采用分别记录；共用组件更新不能绕过范围及依赖检查 |
| 平台总台：平台运行 | 健康、用量、异常、存储/备份、发布恢复及管理记录 | 排查技术运行问题并核对恢复情况 | 只呈现获准技术信息；真实消耗、未知值和效果分开，备份不成为客户内容旁路 |

同一成员保留自己的日常工作入口，也可按职责进入企业端的部分维护功能。两端维护共用数据、版本、编辑能力和状态，不复制经验库或增加固定双重审批；已有授权覆盖的动作直接办理。相关职责和授权建议见[第 11 节](#11-工作与维护入口及企业自进化分工)及[第 12 节](#12-组织角色与授权生命周期)。

### 16.2 基础阶段拟交付的管理能力

基础阶段应能支持约定场景的输入、处理、输出、经验维护、日常评价和运行恢复。以下是后续任务包建议，沿用既有模块编号，全局整合时再划分新切片，不重命名或重复交付已有切片。

| 拟交付任务包 | 主要归属与依赖 | 可审阅的交付结果 |
| --- | --- | --- |
| 身份、维护职责与跨端授权 | M2；各对象落实动作权限 | 维护者仍能开展自己的工作；仅进入获准维护区；任命、撤权、交接及存量角色映射按已确认规则运行 |
| 企业初始化、档案与 AI 工作配置 | M2 联动输入/处理/输出 | 必需条件与可后补资料分开，当前生效配置及来源可查；可从普通任务起步，持续/主动工作按有效范围开展 |
| 来源与资料生命周期 | M2 原件/版本，M3 解析/索引，相关任务与成果联动 | 更新/缺口/错误状态真实；在选定对象上贯通停用、删除、派生清理、获权恢复和导出 |
| 经验维护双入口与反馈处理 | M2 授权，处理经验机制、M4/M5 反馈、M6 相关成果 | 同一经验两端可维护，修订不扩大复用范围；候选、发布、实际可用和使用后维护有真实状态 |
| 任务、成果与画报待办衔接 | M4 任务/计划，M5 画报/站内交付，M6 成果 | 需要人处理时显示真实卡片；会话、画报和企业端共用处理状态；两排/展开/收起交互接真实数据 |
| 运行、质量、资源与问题处理 | M7 复用各模块记录，M2 管理可见范围 | 可分别核对运行状态、任务质量、用户反馈及方法比较；异常关联实际修复和未解决部分 |

| 保留政策、清理与备份恢复 | M2 动作与政策，各原对象处理，M7 运行证据 | 明确所覆盖对象、期限及恢复范围，清理失败/部分完成真实可见；恢复不复活已撤权内容或重复业务动作 |

其中生命周期与清理为同一组共用能力的不同对象任务，不能分别建设输入删除系统、经验删除系统和管理端删除系统。界面消费原模块的真实对象状态；任务、成果和方法各保留自己的业务语义，不统一压成一个万能状态机。

### 16.3 基础交付与后续自进化的分界

| 阶段 | 本阶段需要具备 | 接续条件 |
| --- | --- | --- |
| 约定的基础交付版本 | 输入/处理/输出、正常资料及经验维护、真实反馈/评价、三端管理、必要运行与恢复；方法可替换、版本和依据可追溯 | 全局明确范围，并对约定范围完成端到端及异常验收；一个切片通过不等于整个基础版本完成 |
| 独立自进化后接入 | 在有效范围内自主观察、形成候选、组织试验、按预授权采用、观察效果及停止恢复 | 基础版本完成后选择有可靠基准的对象，补实际资源/数据/采用授权，复用评估与正常发布能力 |
| 后续产品或交付扩展 | App 及系统外触达、更广连接器/行业经验、复杂协作与企业迁移等 | 按既有分期和真实需要另行收口；不作为所有自进化验证都必须等待的条件 |

自进化接入前，正常索引维护、偏好更新、经验整理、到期清理和工程升级已经可以运行。后接入增加自主改进的组织能力，两端相应增加管理交互；不先展示虚构的候选/收益或搭空后台。

企业优化可由共用能力按企业授权执行；企业管理端管理本企业范围、策略、采用和停止，总台管理通用能力和技术运行。企业默认托管及具体自动类别仍需收口，管理入口不要求企业逐条调算法或人工批准所有候选。首个优化对象依届时证据选择，检索示例不等于已选实验。

首版业务交付与提醒限定系统内（DEC-088）；身份邀请/账号安全流程继续按其独立范围处理。普通资料的授权批量扫描上传方向保留（DEC-085），Web 能力验证及必要 App 承接按输入和多端分期落实，不在本次汇总中提前承诺 App。

### 16.5 串联三端的代表验收流程

建议以“一个企业、两个业务空间、若干不同职责成员”的合成场景先证明协作与权限行为，再按约定开展真实模型及业务验收；该例不是指定首个客户或新增真实调用授权。

1. 平台开通企业，企业侧明确必要责任、空间和允许的 AI 工作范围；有限配置即可开始一个真实有资料的任务。
2. 员工上传获准资料并提出分析要求；缺少数据时形成原任务缺口及画报待办，补交后按真实状态继续，折叠和重复点击不改变执行事实。
3. AI 交付有来源的结果，员工在原任务反馈或按授权明确发布成果；私人来源与企业副本按各自权限维护。
4. 有复用价值的材料进入获准经验候选，按既定策略整理及发布；部门维护者从客户端修订，跨部门维护者在企业端看到同一版本，并发修改不会相互覆盖。
5. 企业侧查看获权的质量、资源、问题与方法采用；总台只见允许的技术状态。需要更正时沿原对象处理，无须人处理的后台动作不增加人工待办。
6. 补充撤权/停用、晚到结果、导出中撤权、删除后索引/缓存失效和恢复等场景，核对跨入口状态、实际完成范围及没有重复业务动作。
7. 在完全未部署独立自进化的环境中完成以上约定流程；后续另行接入其完整改进闭环，分别证明机制可靠性和实际收益。

此流程便于检验接口及职责是否贯通，但不能替代基础版本其余约定场景。具体数量、性能、样例覆盖和质量指标进入全局验收表；当前未执行上述流程。
