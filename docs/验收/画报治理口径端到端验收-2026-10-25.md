# 画报治理口径端到端验收（2026-10-25）

验证 PR #86（方案 A）在真实画报任务中的实际行为：治理发布里的列含义、单位、UNKNOWN 标记是否注入画报数据集上下文，以及是否守住"仅提示、不改计算、缺失时降级"三条边界。

**结论：通过。** 治理口径确实送达画报任务的工具结果；非画报任务不注入；治理不可见时降级为 `source=NONE` 且不影响数据读取；模型在最终回复中使用了口径措辞，同时没有自行计算金额。

## 一、先前"未验证"的真实原因

`.local/trial` 实例原来的 `api.jar` 构建于 `e451706`，而画报治理口径的代码在 `013f98c`（PR #86）。也就是说，**缺口不是"本地没有数据集"，而是本地实例运行的后端根本不含这段代码**——`GovernedFieldContext.class` 并不在旧 jar 内。

本次先重新构建后端（`mvnw package -DskipTests`，构建后 jar 内含 `BOOT-INF/classes/com/dreamcore/workspace/context/GovernedFieldContext.class`），再启动实例做验收。

> 这条对后续所有"本地验证 #86 之后的功能"都适用：本地实例的 jar 不会自动跟随仓库最新提交。

## 二、环境与数据

| 项 | 值 |
|---|---|
| 实例 | 本地 trial，`agentMode=live`，模型 `deepseek-flash` |
| 验收租户 | `画报治理口径验收企业`（独立新建，不触碰既有账号与数据） |

治理发布中三个字段的口径：

| 列 | meaning | unit | status |
|---|---|---|---|
| 门店 | 收银发生的门店名称 | — | SOURCE_DOCUMENTED |

治理发布不是直接改库塞进去的假数据，`Package/Item/DatasetField` 的结构与真实投放入口一致；`GovernedFieldContext` 读取的字段名（`column/meaning/unit/status`）与 `DatasetField` 定义逐一对齐。

## 三、验收结果

### 1. 画报任务能拿到治理口径 —— 通过

做法：通过公开接口 `POST /api/v1/tenants/{tenant}/briefing/generation` 发起真实画报，由调度器创建真实任务并交给引擎；任务执行结束后，用它自己的 attempt 令牌调用内部接口 `POST /internal/v1/agent-access/{task}/context`（`action=dataset_search`），取平台真实返回。

返回的该项数据集带有：

```json
"governedFields": {
  "authority": false,
  "source": "NATIVE_GOVERNANCE_RELEASE",
  "releasedAt": "2026-10-25T07:51:30.644396Z",
  "usage": "人工发布后确认的字段口径，仅用于解读，不改变计算规则。status=SOURCE_DOCUMENTED 表示已核对；UNKNOWN 表示口径未确认，不得据列名推断金额、单位或业务状态，也不得因此拒绝计算。",
  "fields": [
    {"column": "门店", "meaning": "收银发生的门店名称", "unit": "", "status": "SOURCE_DOCUMENTED"},
    {"column": "收款金额", "meaning": "门店当日收款合计；人工核对确认以分为单位存储", "unit": "分", "status": "SOURCE_DOCUMENTED"},
    {"column": "收款状态", "meaning": "原始状态码含义尚未确认，不得据列名推断到账或退款", "unit": "", "status": "UNKNOWN"}
  ]
}
```

要点：

- `source=NATIVE_GOVERNANCE_RELEASE` 说明命中的是治理发布，不是部署字段定义
- `authority=false` 与 `usage` 文案确认它是**提示性**的
- UNKNOWN 列**照常返回**，没有被拦截或过滤

### 2. 非画报任务不注入 —— 通过

同一任务、同一数据集，摘掉 `briefing_generation_batches` 关联后再取一次：`governedFields` 为 `null`。与代码中 `if (briefing)` 的分支一致，普通会话载荷不受影响。

### 3. 治理不可见时降级，不报错 —— 通过

把治理发布的 `recipient_id` 临时改成另一个真实账号（即"发给别人"），同一任务再取：

```json
"governedFields": {
  "authority": false,
  "source": "NONE",
  "usage": "该数据集尚未发布治理口径；字段含义与单位以部署定义为准，不得据列名推断金额或业务状态。"
}
```

接口正常返回数据行，没有异常、没有阻断。这与 `GovernedFieldContext` 的"降级为显式未治理标记"设计一致。

### 4. 模型确实使用了口径 —— 通过（行为证据）

本次真实画报任务的最终回复原文（节选）：

> 收款状态是原始状态码，**含义尚未确认，不能当成已到账或已退款来解读**；金额以分存储。……这只是部分记录的登记值，**未被核验计算**，不能作为门店合计结论。

"到账/退款"这一措辞只出现在治理发布的 UNKNOWN 字段里；部署字段定义对该列只写"收银系统原始状态码"，而代码中的 `businessReading` 分支要求同时存在"收款状态"和"收款类型"两列才会注入——本数据集没有"收款类型"，分支未触发。因此该措辞可归因于 `governedFields`。

同时模型明确拒绝自行计算金额，符合方案 A"不改变计算规则"的边界。

### 5. 画报未成功出卡（与本次改动无关）

两条画报任务都以 `PARTIAL` 结束，批次 `FAILED / TASK_PARTIAL`，原因是 `BRIEFING_GOAL_UNAVAILABLE`：验收租户没有填写岗位目标/治理目标，选题规划被拒；另有"数据集没有已发布指标，服务端算不出金额"。

这与治理口径注入是两件事：**注入发生在数据集读取层，已经验证；失败发生在规划与计算层，属于验收租户数据不完整**。若要验收"一张完整画报卡上的口径标注"，还需补岗位目标并发布对应指标。

## 四、方法说明与可复现性

- 画报任务由公开接口真实创建、调度器真实派发、引擎真实调用模型，不是模拟。
- `governedFields` 的抓取使用了任务自身的 attempt 令牌调用真实内部接口。由于抓取时任务已进入 `PARTIAL`、租约失效，为完成读取，临时把任务与批次状态恢复为可执行的 `RUNNING`，取完立即还原；**读取走的仍是生产代码路径与真实鉴权，没有绕过权限或改代码**。
- 脚本与中间产物在 `dreamcore-workspace/.local/verification/`（已被 `.gitignore` 覆盖），包括造数、登录、触发画报、口径探针四个脚本。
