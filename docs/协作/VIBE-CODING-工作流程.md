# Vibe Coding 工作流程

> 适用对象：项目负责人（不需要懂代码），配合 AI 完成日常维护与更新。
> 与仓库既有规则的关系：Git 主线、凭据边界、部署与推送的区分仍以 [AGENTS.md](../../AGENTS.md) 和 [COLLABORATION.md](../../COLLABORATION.md) 为准；本文件补充"人 + AI 怎么配合"的部分。
>
> **两人共同维护时**，先读 [协同规范](协同规范.md)，里面的认领制、分支与合并规则优先适用。

---

## 一、核心思想：把风险分级，把验证前移

所有工作分成四级。级别决定需要谁确认、需要验到什么程度。

| 级别 | 做什么 | 例子 | 需要的确认 |
|---|---|---|---|
| **L0 只读** | 查看、解释、分析 | "这个功能怎么实现的" | 无需确认，随时可做 |
| **L1 本地改动** | 改代码、改文档，跑本地实例 | "让画报支持导出 Excel" | 说清楚要改什么即可 |
| **L2 部署** | 把改动发布到线上服务器 | "把这次改动上线" | 必须明确说"部署"，并确认回滚方案 |
| **L3 数据/权限/密钥** | 改数据库、改权限、换密钥 | "给新同事开账号" | 单独确认，先备份 |

**默认停留在 L0 和 L1。** 任何跨到 L2/L3 的动作，AI 必须先停下来问。

## 二、一个任务的六个步骤

```
① 说清目的  →  ② AI 先出方案  →  ③ 你确认方案
                                        ↓
⑥ 记录归档  ←  ⑤ 提交   ←  ④ 改 + 本地验证
```

### ① 说清目的
用一句业务语言描述，不需要技术词。

> ✅ "客户问报销标准时，AI 现在只能回答文字，我想让它能附上表格截图"
> ❌ "改一下 briefing 的 render pipeline"

### ② AI 先出方案，不直接动手
AI 需要先读相关代码，回答三件事：
- 打算改哪些地方（用业务语言说）
- 有什么风险（会不会影响已有功能）
- 怎么验证改对了

### ③ 你确认方案
三种回答都行：
- 「按你说的做」
- 「第 2 点不对，改成……」
- 「先只做第一步」

### ④ 改 + 本地验证（**这一步不能省**）
改完必须在本地实例上真的点一遍，不是"编译通过就算完成"。

### ⑤ 提交
一次任务一个提交，说明**为什么**改，不只是改了什么。

### ⑥ 记录
在 `docs/变更记录/` 写一条，模板见 [`docs/变更记录/_模板.md`](../变更记录/_模板.md)。

## 三、验证门槛（提交前必须全过）

### 通用三件套

```bash
# 前端 + 类型检查
npm run build

# 后端（改了 Java 才需要）
./apps/api/mvnw -B -f apps/api/pom.xml -DskipTests package
```

### 关键路径手测清单

改动涉及以下任一项时，必须在本地实例上实际走一遍：

- [ ] 能登录三端（客户端 / 企业管理 / 总台）
- [ ] 能上传一份资料并解析成功
- [ ] 能发起一次 AI 对话并拿到带出处的回答
- [ ] 能生成一张画报
- [ ] 权限收回后，对方确实看不到内容

### 数据库改动的额外要求

- 迁移脚本先在本地 trial 实例跑通，再考虑线上
- 线上执行前必须有备份
- 迁移是**只增不改**：已执行的脚本不再修改

## 四、AI 协作的五条硬规则

这五条会写进 `CLAUDE.md`，每次会话自动生效。

1. **一次只做一件事。** 想改三个地方，分三次做，不要一次全改。
2. **先读后写。** 不确定现有实现时，先看代码再动手，不猜。
3. **不对生产写操作。** 部署、改配置、改数据、重启服务，都要你明确说"改服务器"才执行；只读核验（看日志、看状态）经你授权可做。
4. **密钥不进对话。** 需要凭据时，AI 只说文件路径，不输出内容。
5. **说清楚怎么验证。** 每次改完，AI 要告诉你"怎么确认它真的好了"。

## 五、提交规范

```
<类型>: <一句话说明为什么>

可选：补充背景、验证方式、影响范围

Co-Authored-By: ...
```

类型只用五种：

| 类型 | 用于 |
|---|---|
| `feat` | 新增功能 |
| `fix` | 修问题 |
| `docs` | 只改文档 |
| `refactor` | 不改行为的整理 |
| `chore` | 依赖、构建、杂务 |

**一个提交一件事。** 不要把"修 bug"和"改样式"混在一个提交里——出问题时无法单独回滚。

## 六、部署流程（L2）

部署不是 `git push`。这个项目的代码推送与线上运行是分开的。

```
本地验证通过
   ↓
确认线上版本与回滚包（当前运行版本要能退回去）
   ↓
更新代码 → 构建 → 替换产物 → 重启服务
   ↓
线上验证（登录、上传、问答各走一遍）
   ↓
出问题立刻回滚
```

**任何时候都要能回答：如果现在出问题，怎么退回上一个版本？**
回答不了就不部署。

## 七、上下文管理

| 情况 | 做法 |
|---|---|
| 一个任务做完 | 更新 `续接说明.md`，可以开新会话 |
| 任务做到一半、上下文快满 | 让 AI 先写进度摘要，再开新会话 |
| 换季/换人接手 | 读 `续接说明.md` + 本文件即可接上 |

**建议：一个任务一个会话。** 会话开头的第一句固定为：

> 读一下工作区根目录的 `续接说明.md`（本仓库上一级，仓库外，克隆后需另行获取），然后我们继续。

## 八、你可以直接用的句式

不需要懂技术，说清楚意图就行：

| 场景 | 你可以说 |
|---|---|
| 想加功能 | 「我想让 XX 能 YY，先告诉我大概要改什么，别急着写」 |
| 遇到问题 | 「XX 页面点了没反应，帮我查一下是什么原因，先别改」 |
| 想发布 | 「本地验证过了，可以部署到线上吗？先告诉我回滚方案」 |
| 不确定影响 | 「改这个会影响哪些已有功能？」 |
| 想自己验证 | 「告诉我怎么在本地确认这个改动生效了」 |
| 上下文快满 | 「先把当前进度写成文件，我要开新会话」 |

## 九、每周/每月的固定动作

**每周**
- 跑一次完整构建，确认没有悄悄坏掉的部分
- 检查服务器磁盘、备份是否正常

**每月**
- 更新一次 `续接说明.md`（现状、缺口、待办）
- 检查依赖是否有安全更新
- 回顾一次变更记录，看有没有反复出现的问题

## 十、这张流程解决什么

| 常见问题 | 本流程怎么防 |
|---|---|
| AI 一次改太多，出问题找不到原因 | 一次一件事 + 一个提交一件事 |
| 改完不知道有没有坏 | 强制本地验证 + 关键路径手测 |
| 部署出问题退不回去 | 部署前必须能说清回滚方案 |
| 换了会话接不上 | 续接说明 + 变更记录 |
| 不知不觉动了线上 | L2/L3 必须显式确认 |
| 密钥泄露 | 只写路径不写内容 |
