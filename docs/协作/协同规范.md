# 两人协同规范

> 适用：两位维护者（都不写代码、主要靠 AI），只有一人持有线上部署权。
> 配套：[VIBE-CODING-工作流程](VIBE-CODING-工作流程.md) · [任务看板](任务看板.md) · [变更记录模板](../变更记录/_模板.md)

---

## 一、为什么两人的流程不一样

一个人维护时，最大的风险是"改错了"。
两个人维护时，最大的风险变成**"两个 AI 同时改了同一处，谁都不知道对方做了什么"**。

这不是靠沟通能解决的——人会说"我改一下画报"，但 AI 动手时改的可能是同一个文件的另一段。所以必须用机械的方式隔离：**各自独立的副本 + 先认领后动手 + 合并前必须验证**。

---

## 二、三条铁律

### 铁律一：各自独立克隆，绝不共用目录

```
你：  ~/Desktop/mengine/dreamcore-workspace
同事：~/项目/dreamcore-workspace          ← 完全独立的另一份
```

**为什么**：两个 AI 在同一个目录里工作时，一个在跑构建、另一个在改文件，产物和源码会互相污染，出问题无法判断是谁造成的。

**推论**：`.local/`（本地数据库、模型密钥、试用数据）各自独立，不共享、不同步。

### 铁律二：先认领，再动手

任何超过"看看代码"的改动，先在 [任务看板](任务看板.md) 登记一行并推送到远端。**推送成功才算认领。**

**为什么**：Git 是唯一可靠的协调方式。口头说"我做画报"没有约束力；看板上一行 + 推送记录，对方一拉就知道。

**发现已被认领**：换一个任务，或在看板里标注"等待对方完成"。

> **唯一的直推例外**：合并完成后，把 `docs/协作/任务看板.md` 的状态从「待合并」改为「已合并」这类**纯状态记账**，可以直接提交到 `main`，不必再开 PR。仅限状态字段；内容改动仍须走分支 + PR。

### 铁律三：`main` 必须随时能跑

合并进 `main` 之前，必须满足：

- [ ] 本地构建通过（`npm run build`，改了后端再跑一次 Maven）
- [ ] 关键路径在本地点过一遍（登录、上传、问答、画报，按改动范围选）
- [ ] 变更记录已写好

**为什么**：`main` 是两人共同的起点。它一旦坏了，对方第二天开工就卡住。

## 三、首次准备（只做一次）

### 账号与权限

| 角色 | GitHub 账号 | 仓库权限 |
|---|---|---|
| 你 | `luofanghao9784` | Write（可推分支、可开 PR） |
| 同事 | `dimmm1125-coder` | Admin（仓库所有者） |

**不需要再发邀请**——同事本来就是仓库所有者。你要做的是确认双方各自用自己的账号，不要共用。

`CODEOWNERS` 已把所有文件指向 `@dimmm1125-coder`。注意：只有在分支保护里勾选 `Require review from Code Owners` 后，PR 才会**强制**要求同事审查；未开启前它只是一份声明，不会自动拦截合并（实测开 PR 时也不会自动把同事加为 reviewer）。

### 你这边

1. 确认同事**不需要** SSH 接入包——对方没有服务器权限，部署只有你能做
2. 给同事一份**独立的**模型 API Key，不要共用你现在这把

### 同事那边

```bash
git clone https://github.com/dimmm1125-coder/dreamcore-workspace.git
cd dreamcore-workspace
npm ci
npm run build
```

用**自己的** GitHub 账号克隆和推送，不要共用在用的账号凭证。
然后照 [续接说明](../../../续接说明.md) 里的方式装好本地环境，模型密钥写进自己的 `.local/model-private/`。

> 暂时没有第二把 key 时，可以先跑无模型模式（`run-trial.sh` 不带 `--live`），界面和资料功能照样能验证，只是 AI 对话不可用。

### 建议开启的分支保护（管理员操作，一次即可）

目前 `main` **没有任何保护**，"不直推 main"只能靠自觉。建议由管理员在
GitHub → Settings → Branches → Add branch protection rule 设置：

- Branch name pattern：`main`
- ✅ Require a pull request before merging
- ✅ Require approvals：`1`
- ✅ Require review from Code Owners（让 `CODEOWNERS` 真正生效）
- ⬜ Do not enforce on administrators（保持开启，保留紧急修复能力）
- ✅ Do not allow force pushes

开启后，任何人都无法直接推送 `main`，必须走 PR。管理员在紧急情况下仍可绕过。

## 四、每天开工（五分钟）

```bash
git checkout main
git pull --ff-only origin main      # 拉取对方昨天的合并
git status                           # 必须是干净的
```

然后看两处：

1. [任务看板](任务看板.md) —— 有没有别人在做的任务、有没有需要你接的
2. `docs/变更记录/` 最新一条 —— 对方昨天改了什么

**如果 `git status` 不干净**：先处理完手上没做完的事，不要直接 pull——可能覆盖未保存的工作。

## 五、一个任务的完整流程

```
① 看板登记          填一行：任务、认领人、涉及范围
② 推送认领          git add 看板 && git commit && git push    ← 成功才算认领
③ 开分支            git checkout -b feat/画报导出excel
④ AI 干活           说目的 → AI 出方案 → 你确认 → 改
⑤ 本地验证          构建 + 实际点一遍
⑥ 提交并推送分支    git push -u origin feat/画报导出excel
⑦ 开 PR             描述用变更记录模板
⑧ 对方合并          看"改了什么/怎么验证"，通过就合并
⑨ 更新看板          状态改成"已合并"，删除分支
```

第 ⑦ 步的 PR 描述就是交接材料。对方不写代码，但能看懂"改了什么、为什么、怎么验证"——够了。

## 六、冲突了怎么办

| 情况 | 现象 | 怎么办 |
|---|---|---|
| **认领撞车** | 推送被拒绝 | 拉取看对方认领，换任务或等对方完成。**不要强推** |
| **同一文件两人都改** | 合并时提示冲突 | 停下，两人确认谁保留哪部分；由后完成的一方差量重做 |
| **迁移版本号撞车** | 两个 V169 | 后到的一方改成 V170，并在看板登记 |
| **main 被打断** | 拉下来构建不过 | 立刻告诉对方；在修复前不要再往 main 合并 |

**主动预防**：认领时写清"涉及范围"（改哪个端、哪个功能）。看到对方改了同一块，先约顺序再动手。

## 七、部署闸（只有你能过）

同事的改动合并到 `main` 后**不会自动上线**。部署由你单独决定。

```
同事改动 → 合并进 main → （等待） → 你择机部署
```

部署前你自己要确认三件事：

1. `main` 上现在的构建能过
2. 有可用的回滚包（上一个线上版本）
3. 知道这次改了什么、影响哪个端

**部署是你的专属动作**，同事不参与、也不需要他的确认。

## 九、AI 使用的约定

两人的 `CLAUDE.md` 都在仓库里，克隆下来就自动一致，不需要口头传达。

需要两人共同遵守的：

1. **AI 不得直接推 `main`** —— 只推自己的任务分支
2. **AI 说"改完了"不算数** —— 要有人实际点过
3. **一次只让 AI 做一件事** —— 同时改三个地方，出问题定位不了
4. **AI 不碰线上** —— 它没有服务器权限，也不要给它
5. **每次让 AI 写清"怎么验证"** —— 这是对方合并时的判断依据

## 十、一周节奏

| 时间 | 动作 |
|---|---|
| 每天开工 | pull + 看板 + 看昨天的变更记录 |
| 每天收工 | 推送分支（未完成也推），更新看板状态 |
| 每周一次 | 两人各跑一次完整构建，确认 main 健康 |
| 每月一次 | 更新 `续接说明.md`，清理已合并分支 |

---

## 十一、一句话总结

**各干各的副本，先认领再动手，main 永远能跑，部署只有一个人说了算。**

这四件事做到了，两人协作就不会乱；做不到，技术再好也会互相踩。
