# 两人协同规范

> 适用：两位维护者（都不写代码、主要靠 AI），线上部署权只在 `luofanghao9784`（下称「部署负责人」）一方。
> 配套：[VIBE-CODING-工作流程](VIBE-CODING-工作流程.md) · [任务看板](任务看板.md) · [变更记录模板](../变更记录/_模板.md)

> **规则放在哪：** 两人使用的 AI 不同，读取的规则文件也不同。
> `AGENTS.md` 给 Codex 等读取 AGENTS 约定的代理，`CLAUDE.md` 给 Claude Code。
> 两份文件都把协作要点指向本规范——**本规范是唯一权威版本**，改动时三处需同步。

---

## 一、为什么两人的流程不一样

一个人维护时，最大的风险是"改错了"。
两个人维护时，最大的风险变成**"两个 AI 同时改了同一处，谁都不知道对方做了什么"**。

这不是靠沟通能解决的——人会说"我改一下画报"，但 AI 动手时改的可能是同一个文件的另一段。所以必须用机械的方式隔离：**各自独立的副本 + 先认领后动手 + 合并前必须验证**。

## 二、三条铁律

### 铁律一：各自独立克隆，绝不共用目录

```
你：  ~/Desktop/mengine/dreamcore-workspace
同事：~/项目/dreamcore-workspace          ← 完全独立的另一份
```

**为什么**：两个 AI 在同一个目录里工作时，一个在跑构建、另一个在改文件，产物和源码会互相污染，出问题无法判断是谁造成的。

**推论**：`.local/`（本地数据库、模型密钥、试用数据）各自独立，不共享、不同步。

### 铁律二：先查重，再认领，再动手

任何超过"看看代码"的改动，先在 GitHub Issues 里搜一遍有没有人已经认领同一功能；**确认没有重叠后**，再开一个 Issue 认领：标题写「认领：<任务>」，正文写**认领人**和**涉及范围**（改哪个端、哪个功能），并把 Issue 指派给自己。**Issue 开出并指派成功，才算认领。**

**为什么先查重**：Issue 在双方共用的仓库里即时可见，搜一下就知道有没有人在做。先认领再查重，等于先占位置再看有没有撞车——那时冲突已经发生了。

**发现已被认领**：换一个任务，或在对方 Issue 下留言"等待完成"。

> **认领只开 Issue，不推 `main`**：Issue 在 GitHub 上直接创建；真正的代码改动仍走任务分支 + PR。

### 铁律三：`main` 必须随时能跑

合并进 `main` 之前，必须满足：

- [ ] 本地构建通过（`npm run build`，改了后端再跑一次 Maven）
- [ ] 关键路径在本地点过一遍（登录、上传、问答、画报，按改动范围选）
- [ ] 变更记录已写好

**为什么**：`main` 是两人共同的起点。它一旦坏了，对方第二天开工就卡住。

## 三、首次准备（只做一次）

### 账号与权限

| 角色 | GitHub 账号 | 仓库权限 |
|---|---|---|
| 你 | `luofanghao9784` | Write（可推分支、可开 PR） |
| 同事 | `dimmm1125-coder` | Admin（仓库所有者） |

**不需要再发邀请**——同事本来就是仓库所有者。你要做的是确认双方各自用自己的账号，不要共用。

`CODEOWNERS` 已同时登记 `@dimmm1125-coder` 与 `@luofanghao9784`。它只表明"谁有资格审查"，**不强制两人都批准**——审查按"一名非作者批准"执行。

### 你这边

1. 确认同事**不需要** SSH 接入包——对方没有服务器权限，部署只有部署负责人能做
2. 给同事一份**独立的**模型 API Key，不要共用你现在这把

### 同事那边

```bash
git clone https://github.com/dimmm1125-coder/dreamcore-workspace.git
cd dreamcore-workspace
npm run setup:git
npm ci
npm run build
```

用**自己的** GitHub 账号克隆和推送，不要共用在用的账号凭证。
然后照 [本地启动指南](../交接/本地启动指南.md) 装好本地环境并跑起来，模型密钥写进自己的 `.local/model-private/`。

> 暂时没有第二把 key 时，可以先跑无模型模式（`run-trial.sh` 不带 `--live`），界面和资料功能照样能验证，只是 AI 对话不可用。

### 分支保护：受套餐限制，暂靠本地钩子 + 流程

当前仓库是**私有仓库**，GitHub 免费套餐**不提供分支保护功能**——要开启必须升级到 GitHub Pro / Team，或把仓库设为公开。**不要为了开保护而公开商业仓库。**

在分支保护可用之前，"不直推 main"靠两层：

1. 本地 `pre-push` 钩子（`.githooks/`，克隆后执行 `npm run setup:git` 启用）默认拦截直接推 `main`
2. 流程自觉：只推任务分支，由对方审阅后合并

升级套餐后，再由管理员按 GitHub 文档开启分支保护（Require a pull request、至少 1 人批准、禁止 force push）。管理员在紧急情况下可绕过；开启保护后，任何人（含管理员）默认都必须走 PR。

## 四、每天开工（五分钟）

```bash
git checkout main
git pull --ff-only origin main      # 拉取对方昨天的合并
git status                           # 必须是干净的
```

然后看两处：

1. GitHub Issues —— 有没有别人在做的任务、有没有需要你接的
2. `docs/变更记录/` 最新一条 —— 对方昨天改了什么

**如果 `git status` 不干净**：先处理完手上没做完的事，不要直接 pull——可能覆盖未保存的工作。

## 五、一个任务的完整流程

```
① 查重              先在 GitHub Issues 搜一遍，确认没人认领同一功能
② 开认领 Issue      标题「认领：<任务>」，正文写认领人和涉及范围，assignee 指派自己
③ 开分支            git checkout -b feat/画报导出excel
④ AI 干活           说目的 → AI 出方案 → 你确认 → 改
⑤ 本地验证          构建 + 实际点一遍
⑥ 提交并推送分支    git push -u origin feat/画报导出excel
⑦ 开 PR             描述用变更记录模板，并在 PR 里链上认领 Issue
⑧ 对方合并          看"改了什么/怎么验证"，通过就合并
⑨ 关 Issue           合并后关闭认领 Issue，删除任务分支
```

第 ⑦ 步的 PR 描述就是交接材料。对方不写代码，但能看懂"改了什么、为什么、怎么验证"——够了。

## 六、冲突了怎么办

| 情况 | 现象 | 怎么办 |
|---|---|---|
| **认领撞车** | 开 Issue 前发现已有人认领同一功能 | 换任务，或在对方 Issue 下留言等对方完成 |
| **同一文件两人都改** | 合并时提示冲突 | 停下，两人确认谁保留哪部分；由后完成的一方差量重做 |
| **迁移版本号撞车** | 两个 V169 | 后到的一方改成 V170，并在认领 Issue 登记 |
| **main 被打断** | 拉下来构建不过 | 立刻告诉对方；在修复前不要再往 main 合并 |

**主动预防**：认领时写清"涉及范围"（改哪个端、哪个功能）。看到对方改了同一块，先约顺序再动手。

## 七、部署闸（只有部署负责人能过）

同事的改动合并到 `main` 后**不会自动上线**。部署由部署负责人（`luofanghao9784`）单独决定。

```
同事改动 → 合并进 main → （等待） → 部署负责人择机部署
```

部署负责人部署前要确认三件事：

1. `main` 上现在的构建能过
2. 有可用的回滚包（上一个线上版本）
3. 知道这次改了什么、影响哪个端

**部署是部署负责人的专属动作**，同事不参与、也不需要他的确认。

## 九、AI 使用的约定

两人的 `CLAUDE.md` 都在仓库里，克隆下来就自动一致，不需要口头传达。

需要两人共同遵守的：

1. **AI 不得直接推 `main`** —— 只推自己的任务分支
2. **AI 说"改完了"不算数** —— 要有人实际点过
3. **一次只让 AI 做一件事** —— 同时改三个地方，出问题定位不了
4. **AI 不对生产写操作** —— 生产服务器、生产数据库、生产配置上的写操作（部署、改配置、改数据、重启服务）只由部署负责人执行，代理不持有该权限。只读核验（看日志、状态、目录清单）经部署负责人授权后可做，但同样不把密钥交给它。
5. **每次让 AI 写清"怎么验证"** —— 这是对方合并时的判断依据

## 十、一周节奏

## 十一、一句话总结
