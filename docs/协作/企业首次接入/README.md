## 打开和生成

在项目根目录运行：

```sh
python3 docs/协作/企业首次接入/build.py
python3 docs/协作/企业首次接入/build.py --check
python3 -m http.server 5198 --bind 127.0.0.1 --directory docs
```

浏览器打开 `http://127.0.0.1:5198/协作/企业首次接入/index.html#onboarding`。统一从 `docs` 提供预览，使看板、图册和研判页的相对链接均可打开；已有该预览时直接访问，无需重复启动。若端口已占用，先确认现有服务，不要误停业务进程；可另选端口。同事拉取仓库后在自己的电脑运行。localhost 不是同事可远程访问的共享网址。生成的 index.html 也可直接打开阅读，handoff 相对链接要求目录文件完整。

| [handoffs/](handoffs/) | 每个节点一份 Markdown；JSON 区块是该节点开发状态唯一来源，下方记录上下文、代码范围、接口约定、验证和更新历史 |

## 右栏任务分类

每个节点右侧分别显示两张卡片；窄屏下移到节点下方。两张卡片分别统计任务、完成数和“不需开发”数，详情只显示所选类别的任务。空类别明确提示尚无独立任务，不代表该节点没有接入操作或系统已经完备。

| 卡片 | JSON `workstream` | 归类依据 |
|---|---|---|
| 绿色 · 业务对接任务 | `business` | 围绕具体企业整理资料、明确问题和口径、核对配置、组织真实用户验证、编写使用说明与交接 |
| 蓝色 · 系统开发任务 | `system` | 核查或补齐可复用的页面、接口、权限、适配器、数据处理和运行机制 |

每项任务在原 handoff JSON 中填写 `workstream` 与 `classificationReason`；构建拒绝未知分类或空依据。按任务主要交付内容归类，不按所在六阶段、FE／BE 后缀或负责人的岗位推断。原任务 ID、验收和状态保持独立；分类不会自动认领或批准开发。

例如 ONB-04-02-FE 整理接入方式说明属于业务对接，ONB-04-02-BE 核查适配器属于系统开发；ONB-05-02-BE 用真实角色验证本次授权属于业务对接，ONB-02-03-BE 核查通用权限机制属于系统开发。客户连接配置和资料确认属于业务接入，开发通用连接器属于系统能力。一个任务若后续发现兼有独立的业务交付与系统改造，应在确认范围后拆分并保留原 ID 的追溯关系。

初始 60 项仍是核查／候选调整；本次分类为业务对接 19 项、系统开发 41 项。系统开发卡片包括“能力核查”，不等于都需要新写代码。节点整体实现／验证／部署记录在详情中单独标明，不作为任一类别或客户验收的完成状态。

## 已有代码核查

系统开发任务可在原 JSON 内增加 `implementationReview`，记录 `result`（代码已实现／新基线已有／部分实现／待核实）、`surfaces`（总台／企业端／员工端／部署工具／服务层）、已有内容、剩余限制、完整基线 SHA、核查人和带时区时间，以及报告、源码和测试依据。构建会检查这些字段、报告和源码路径。卡片显示结论与涉及端，详情显示证据和待接续事项；接入流程总览从同一份 handoff 汇总，不另存进度数据。

“代码已实现”指 2026-10-17 核查时运行目录的工作树已存在对应能力；“新基线已有”指当时协作代码中已包含、运行目录的工作树尚未包含。当前源码已迁入统一项目，这两个结论保留原日期与基线，不因文档合并自动重做业务验收。二者均不自动证明运行产物、真实模型或客户验收完成。`status` 继续记录任务状态，节点的实现／验证／部署字段单独显示为本轮改造记录；只做已有代码核查不会将其批量改为实现完成或已部署。

本轮记录见[系统开发实现核查](系统开发实现核查-2026-10-17.md)。按用户指定，确认已有实现的任务负责人登记“罗方豪”，表示接续责任，不推断原代码作者；实际业务链路尚待复验的保留“待验证”。部分实现与待核实项不自动认领。核查更新不授权新增业务规则或生产部署。

## 认领与接续

1. 先拉取并查看目标节点 handoff、当前流程和已有变更，检查该任务是否已被认领。
2. 将任务 owner 写为实际执行人；节点不另设负责人角色，不填写节点级 owner。填写 updatedBy、带时区 updatedAt、真实状态、代码范围和共享接口约定；追加更新记录。不要冒用另一位开发者的身份。
3. 初始 60 项是前后端核查／候选调整，不是 60 项已批准改造。核查无缺口填“不需开发”并给依据；有缺口写清复现、范围和验收，细节未确认填“待确认”。经确认的任务再进入开发。可以将候选拆为更细任务，但保留已使用的任务 ID，不复用或重编号。
4. 在 dependsOn 中填写具体任务 ID；blockers 写待谁处理什么。跨节点任务尽量引用原任务，不重复建立同一能力。构建检查不存在的依赖与循环依赖。
5. 更新 handoff 的接续说明、实际代码文件、提交或 PR、验证命令及结果。已完成／不需开发必须填写 evidence。实现、验证、部署分开记录，不能只因代码写完便标全部完成。
6. 运行 build.py 及 --check，提交业务改动、对应 handoff 和生成的 index.html。按明确路径暂存，避免带入他人文件或凭据。不要把真实客户资料、账号或连接配置放进看板。

推荐状态：待核查 → 待确认／待开发 → 开发中 → 待验证 → 已完成；也可以转阻塞或不需开发。右栏完成数按任务计算，排除项单列；不是已部署百分比。字段校验不能替代人工审查证据。

## 修改流程本身

修改 flow.json，保持 nodeId 不变；序号是展示顺序，nodeId 是身份。增加节点时使用新 ID 并增加对应 handoff。调整节点边界或验收时增加 revision，在 CHANGELOG 追加更新人、时间、原因、节点及影响。

旧 handoff 的 flowRevision 不自动升级，右栏会提示“流程已修订，请复核任务范围”。负责人检查任务与验收是否仍成立后更新 flowRevision；不受影响的节点也要明确检查后同步。删除节点前先处理任务迁移／归档，避免静默遗失 handoff。

历史讨论仍在 template.html 折叠区；如调整历史文本要保留历史含义，不把尚未采纳的新页面方案混回当前操作流程。

## 多人 Git 协作边界

双方各用独立克隆，克隆内顺序工作，main 集成；不同时修改同一个共享工作目录，不创建新 worktree。先推送认领，再开始授权范围内的开发。共享文件与接口重叠先协调；认领记录不是分布式锁。具体操作以《双方 Codex 协作约定》为准。

节点 handoff 独立文件可以降低冲突。生成的 index.html 冲突时，先合并 flow.json、template.html 和 handoff，再重新构建，不手工合并生成 HTML。没有自动发布或推送；发布业务系统仍走原授权与验收流程。

已包含：固定节点／任务编号、负责人、更新人、时间、任务状态、依赖、阻塞、验收证据、流程版本提醒，以及独立的实现／验证／部署状态。暂不增加评论、搜索、在线编辑、通知或复杂权限。后续可按需要把 build.py --check 接入 CI，或关联现有 GitHub PR；本轮未配置外部服务。
