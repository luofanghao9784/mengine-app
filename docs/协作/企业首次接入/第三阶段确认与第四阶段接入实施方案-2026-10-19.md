## 一、历史关联：先生成归属证据，再分发

逐表草案已有40表直接store_id、1表门店主数据、50表关联候选、15表尚无获准字段内可证明的归属路径。完整表名、字段与候选路径保留本地私有映射JSON。

| 类别 | 具体处理 | 放行条件 |
|---|---|---|
| 40表直接门店 | 保留原store_id，区分五店与总部；遇缺失或未登记门店先隔离 | 门店值和业务归属一致；不能仅凭字段名推定口径 |
| 门店主数据 | 用stores.id建立五店/总部字典 | 不把总部拆成两个源门店，不把默认日期当真实开业日期 |
| 50表关联候选 | 逐表固定关联键、有效期、行粒度；形成每条来源记录的历史归属与证据 | 同一记录跨店、多对多或孤儿必须显式处理；禁止按员工当前门店回填历史 |
| 15表其他 | 区分全局参考规则与敏感关系数据，分别确定适用范围 | 无归属不能默认全员；先留获准受限范围，不发店长 |

15表中：产品/销售规则版本、费率和公告/手册可研究版本适用范围；accounts、会员请假、薪酬锁定、财务联签、备付金政策、对账批次及历史汇总需要专项归属，不能当公共字典。

重点核对课时与会员转店的历史生效时间、收退款对应交易门店、费用跨店分摊及冲销、工资所属期间/计算依据、分红权益与现金发放。候选外键链仅是技术线索，不是已验证的业务规则。

产物：逐表关系配置、主键与基数约束、版本/有效期规则、孤儿与歧义清单、来源ID到店/总部的映射。先用合成跨店、历史调岗、一对多、冲销、无关联样例验证；实际取数获准后再检查真实记录，不提前宣称通过。共用中心汇总引用同一来源，不将多空间副本重复计数。

## 二、分页容量：先完整，再发布

当前旧三表采集器上限10000行；完整采集器每表100000行、每批2000000单元格/64MiB、每页1000行。它们是整批失败边界，不是截断后交付的窗口；本轮未读取行数，不知道实际是否达到上限。

1. 先在本地为原三表准备与完整采集器一致的v2读取适配，保留46列及源身份校验；不强制继续旧10000行实现。源码仍只在本地维护，后续可通过SSH标准输入执行受控只读程序，不在源机安装/改写文件；凭据只在源机进程内读取。
2. 每批固定投影在同一只读一致性事务内读取计数、结构、稳定主键排序的全部页面；校验页数、重复主键、总数、摘要及字节/单元格上限。无稳定唯一键或非事务表先列缺口。
3. 事务内完整性检查失败时整批不发布，保留旧版本；断线重试重新开启整批事务，不拼接两个时点的页。多个批次保留独立时间，不伪称106表同一时点。
4. 超限先依据业务稳定边界设计分片；原始父来源与分片覆盖清单一起保存，验证不漏不重，再进入目标服务。消费者尚不支持完整分片时列开发任务，不能只改MAX_ROWS或偷偷截取最近记录。
5. 手工全量刷新也须识别修改、删除与撤销：新完整快照验证后原子替换；权限变化先执行撤权。成功读取时间不当业务覆盖截止。

先测试空表、跨页、并发变更、恰好上限、超限、断线、重复键、NULL/精度、源删除及失败回退。完整取数证据在04形成；本轮不执行计数或容量探测。

## 三、本地连接安装：先准备，不启用

链路：本地固定来源入口 → 受控SSH → 源机只读程序及既有私有凭据 → 标准输出返回 → 本地私有暂存/完整性校验 → 数据基座 → 按来源权限和七空间路由使用。

| 步骤 | 交付内容与约束 |
|---|---|
| 1 核对身份 | 新本地企业、连接、数据集、来源版本和空间ID逐项固定；显式绑定允许的源端旧身份，不关闭tenant检查，不复制云端旧企业注册 |
| 2 本地安装 | 0600私有配置，固定主机、命令、字段及批次；登记到本地来源适配器，禁止浏览器/模型传SQL；不执行旧extract.py，因为它会在云端落快照 |
| 3 扩展完整清单 | 保留已有两个历史provider和十项路由；新真实来源以独立身份先验证。完整manifest遗漏会撤下，必须对照全量清单后再应用 |
| 4 权限与内容 | 门店投影、薪酬/分红名单、总部范围分别落实；发布权不扩大普通维护。敏感原件未提供且禁下载；资料类型若不能独立禁止下载，先不发布该原件，另列系统缺口 |
| 5 人工试取 | 仅04后续明确执行时触发，不在本轮安装后自动运行；关闭周期更新和外部模型自动工作 |
| 6 切换与回退 | 新来源验明后再明确替换旧历史样例的使用路由，保留版本证据；失败保持旧数据，不在汇总中同时计算新旧两套 |

已确认的使用范围不是对云端变更的授权。若姓名列或新受控投影需要源侧增权/安装，先报具体缺口；优先沿现有权限完成，不自行改云端。业务方只需解释仍未知的业务口径，不需要决定分页或接口实现细节。
