# 部署 Codex 作业规范

状态：分工方向已认可；具体企业的用途、范围和权限分别确认。本规范用于第三阶段接入准备，并向 02.3 和第四阶段交接，不是新的业务系统功能，也不授予任何真实环境的访问或部署权限。

## 角色和完成标准

| 角色 | 职责 |
|---|---|
| 部署人员（实名认领） | 确定本次环境和授权边界、审核 Codex 输出、协调缺口、对交付负责 |
| 部署人员的 Codex | 在已有授权内整理、只读调查、比对来源和配置、形成方案及验证建议，维护文档 |
| 企业业务负责人 | 确认首批用途、资料必要性、业务口径和可用标准 |
| 来源负责人／技术对接人 | 确认提供方式、允许接入的字段、记录、期间、更新要求及技术条件 |
| 有资格的授权者 | 确认实际使用者，以及阅读、维护、下载、AI 使用、共享的范围 |

同一人可以兼任，但确认记录需注明其资格和确认范围。Codex 的执行结果不替代业务确认，部署人员的技术审核也不替代有资格者授权。既有明确授权和业务决定持续有效，不反复要求确认；新范围或证据冲突才交对应人员处理。没有依赖的工作继续推进。

完成本阶段要求：部署人员审核清单；每项来源和用途可追溯；获准项有确认依据和配置映射；未决项有责任人和下一步。编写规范、代码测试通过或清单草稿生成均不代表某家企业已经完成接入。

## 开始前给 Codex 的输入

- 本次项目、企业、目标环境、部署负责人姓名；已存在时提供 tenant／workspace／connection／dataset 标识。
- 首批工作目的、访谈记录、预期成果与明确不做的内容。
- 获准读取的文档、代码、源系统结构、只读环境及必要的脱敏样例；明确允许的操作和范围。
- 已有接入配置摘要、授权决定、可用页面及历史缺口。
- 本次清单保存位置、资料密级和可否提交 Git。

缺少 ID 不得编造；未获准连接源系统时先整理已有资料，并列出需要提供的证据。凭据由私有环境或密钥管理注入，不要求粘贴进提示词，不输出到文档、日志或 Git。仓库看板仅保存去敏规范和协作状态，真实企业清单保存在该企业获准位置；入库前确认可共享性。

先阅读仓库 AGENTS.md、[数据基座部署技能](../../../.agents/skills/deploy-data-foundation/SKILL.md)和[部署协议与字段解释](../../技术/数据基座部署协议与字段解释.md)，再读目标节点 handoff。不要把旧运行版本或历史核查当成当前代码事实。

## 03.1：整理清单

1. 从首批工作反推需要的数据、企业背景、制度、口径和样例。逐项写用途，避免“先把所有数据接进来”。
2. 分别核对人工资料来源、数据库数据集、治理同步资产，不把其中一种目录当作所有来源。
3. 保存现有 ID 和可定位证据：文档章节、代码位置、结构版本或已获准的核查回执。区分“已存在”“需新增”“暂不需要”“待调查”。
4. 标记事实、推断和未知；提出需要业务负责人确认的问题，由部署人员审核并协调确认。

输出：接入清单草稿及缺口表。不创建产品内工作任务，不实际采集数据。

## 03.2：把范围映射到可执行配置

1. 核对提供人、接入方式、网络／TLS、已有适配器、更新需求和必要数据量。
2. 逐项记录表／视图、列、记录范围和业务期间；区分获取时间与数据覆盖时间。
3. 将每项限制对应到实际实现位置：受限源视图、只读账号、固定列投影、独立数据集或专用适配器。
4. 对列含义记录 SOURCE_DOCUMENTED、DEPLOYMENT_INFERRED、UNKNOWN 及证据；业务口径确认状态独立记录，不能因为代码有定义就视为企业已确认。
5. 产出部署建议，由来源负责人确认允许范围、部署人员审核技术方案。安装、采集和配置变更留到已获准的第四阶段执行。

注意：文字范围不会自动变成行过滤，accessSummary 不是权限规则。现有采集器已支持固定 rowScope，须由部署人员配置并验证；复杂关联归属不自动推导。不同员工需要不同数据范围时，先判断受限视图、拆分数据集和空间是否足够；不能默认为已有动态行列权限。

## 03.3：整理使用授权表

1. 按人员／岗位和具体资源列出阅读、维护、下载、AI 使用与成果共享需求，不将这些动作合并成“可以使用”。
2. 标明源端人员权限是否实际同步、目标空间权限如何配置。源系统采集账号的读取资格不能转授为所有员工的读取资格。
3. 区分工作空间撤权和外部来源撤权：治理同步路径有同步周期和授权有效期，不能承诺所有来源即时撤权。
4. 由有资格的业务授权者确认，保存确认人、日期、依据位置和范围版本；部署人员审核配置映射。
5. 已确认的人员／空间范围交 02.3；已确认的接入范围和源权限要求交 04。邀请加入企业可先做，未确认业务范围不附带空间。

阅读权限不自动证明所有派生成果可以共享。后续验证应覆盖目录、预览、AI 任务、历史引用和撤权结果，并明确下载与共享的实际支持边界。

## 输出模板

每次交付包含以下四张表；可用普通 Markdown，不新增业务系统页面。空缺填“待确认”，不能默认同意。

|---|---|---|---|---|---|---|---|

确认记录必须能定位原始决定，不能只写“已确认”。遇到范围变化保留旧版本，重审受影响项，不把旧授权套到新增字段或新用途。

## 什么才算系统开发

- 访谈整理、目录核对、权限建议、已有功能配置：部署业务任务，执行者可为 Codex。
- 现有机制具备但尚未证明：能力验证任务，不自动记为缺功能。
- 现有适配器无法读取获准来源、无法落实必需限制，或实际复现了权限／状态缺陷：候选系统开发，附复现、影响、替代方案和验收要求，确认范围后另建任务。
- 统一审批平台、通用行列权限引擎、实时外部撤权等未确认需求不自动进入本期。上一轮建议的范围展示与同步状态展示仍为候选，不因本规范获认可就视为已批准开发。

第三阶段现有六项任务保留 ID，归为业务梳理／配置准备；其历史 FE／BE 后缀不决定当前分类，旧实现核查保存于 handoff。后续新增系统任务用新的稳定 ID，不复用旧 ID 表示另一项功能。

## 交接和复用提示词

handoff 写明：实际负责人、Codex 执行者、输入版本、完成内容、证据、确认记录位置、未决事项、下一步及运行／部署状态。真实企业信息不能因需要协作就自动写入公共或共享仓库。任务“已完成”要求其验收条件成立，不用代码验证代替具体企业授权。

可给部署 Codex 以下提示词，并填入本次上下文：

> 按本项目《部署 Codex 作业规范》完成第三阶段接入准备。部署负责人是【姓名】，执行者是你。企业／环境为【标识】，首批用途为【用途】，获准输入和只读范围为【位置及范围】，输出保存到【获准位置】。先检查现有文档、代码和授权决定，按 03.1—03.3 整理接入清单、范围配置映射、使用授权表和缺口表。区分事实、推断、未知和业务确认，不编造来源、人员、ID 或授权。已有授权内的核查继续完成，不重复确认；实质业务决定交部署负责人协调有资格者确认。这里只准备和只读核查，不安装连接、不实际采集、不修改权限、不部署。确有系统缺口时先记录证据和建议，不自行扩大开发范围。完成后更新对应 handoff，注明实际验证边界和接续事项。

## 真实资讯首次接入

资讯须登记真实公开来源并由企业选用，使用产品共用读取器发现候选、读取原文，保留URL、发布时间、检索时间和正文哈希。不得向外发出企业背景或经营数据；内部分析不能冒充资讯。首轮作者可由Codex承接，但交付必须通过来源有效性与原有权限检查。固定来源读取和通用搜索供应商分别验证，首次成功不等于自动维护已启用。操作和验收见[真实资讯首轮](股东经营画报与真实资讯首轮-2026-10-20.md)。
