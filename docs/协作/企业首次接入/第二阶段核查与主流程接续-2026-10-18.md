## 本期决定

用户明确：本期不接真实手机号验证系统，使用假／模拟验证码走通主流程；真实验证放在系统上线前开发。模拟邀请与验证码沿已有本地机制使用，不能描述为真实短信已送达或手机号已完成真实核验。此决定不授权在生产开启模拟验证，不增加正式手机号渠道作为本期阻塞。

本期闭环：总台开通 → 模拟邀请／验证码 → 负责人明确接受职责 → 员工加入 → 按已确认范围进入空间 → 核对未授权内容不可读。身份、企业隔离、授权边界和原子激活不能为简化流程而绕过。

邀请时勾选初始空间会在接受后实际授予权限（InvitationWorkspaceAccess.apply → TenantAdminService.grant），不是单纯组织登记。授权未确认时先不附带业务空间；确认后按范围配置。业务接入任务与系统能力检查分开登记，不以功能存在替代本企业接入完成。

### 实际调整

- 总台开通表单提醒先人工核对已有企业，避免将请求重试幂等误认为企业主体自动查重。
- 员工邀请表单明确：授权范围未确认时不选择业务空间；加入后再按确认范围授权。本地模拟邀请不会发送真实短信。
- 修复三组 API 测试中旧身份域预期：没有对应端会话返回 401；已登录但跨企业或没有权限仍返回 403；资料不可见按现有契约返回 404。没有放宽服务端控制。
- 修复浏览器测试的“用户名或手机号”定位。
- 新增 `scripts/verify-onboarding-stage2.ts` 和 `npm run test:onboarding-stage2`，使用独立临时数据库、真实 API、构建后的页面和三个隔离浏览器身份；不 mock 业务接口，不接短信或模型。运行完成会关闭本轮服务并删除临时数据库，结果摘要与截图位于忽略目录 `.local/onboarding-stage2/`。

### 已实际跑通的链路

1. 总台初始化使用本地模拟验证码；总台页面“企业管理 → 开通企业”生成待激活企业。同一请求重放复用原企业。
2. 新负责人打开邀请，在页面填写姓名、密码并读取本地模拟验证码，点击“接受并开通企业”；真实接口原子激活，负责人身份成立。
3. 当前接管后默认进入企业数据入口，点击“全部管理功能”进入完整企业管理；在“成员与空间”配置人员和空间。不是直接落到旧版成员列表。
4. 负责人通过真实 API 建立两个共享空间，在页面邀请新员工，不勾选初始空间。员工在独立浏览器中使用本地模拟验证码加入，仅看到个人空间。
5. 模拟业务授权已在线下确认后，负责人通过“共享空间 → 管理空间 → 添加成员 → 确认添加”授予一个空间只读访问。另一个空间仍不可读；员工不能管理企业、访问其他企业或使用总台接口。
6. 通过真实 API 撤销访问后，原员工会话立即失去该空间访问；重放接受邀请不会恢复被撤销权限。加入、授权、撤权没有依赖浏览器重新登录。

这里验证的是系统接入能力；具体企业的主体核对、负责人确认和 03.3 授权依据仍是业务接入任务，不因合成场景通过而标为完成。03.3 的确认由业务人员提供依据，现有系统没有因此新增审批对象或自动审批工作流。
