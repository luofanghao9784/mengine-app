# 双方 Codex 协作约定

2026-10-17：用户授权双方围绕看板节点分别开发，通过 Git 与 handoff 交接。本约定只扩展此看板节点协作范围；不授权其他并行项目、部署、生产数据修改或跨会话发消息。

## 工作目录和主线

- 双方各用自己的本地克隆，每个克隆内顺序工作；不要同时操作同一个共享目录，不新建开发 worktree。`main` 为共同集成主线。
- 每次开始先读根目录 AGENTS.md、COLLABORATION.md、本目录 README 和本约定，再查看最新流程与目标 handoff。
- 先检查 `git status`，再 `git fetch origin main`。干净且可快进时用 `git pull --ff-only origin main`；若有未提交内容或分叉，先核对归属与影响，不 reset、不覆盖、不自动 stash 他人的内容。
- 此前“单目录顺序开发”的约定在各自克隆内继续生效；本次允许双方按节点分工，不代表可以同时修改同一组共享文件。旧规则与本节点范围冲突时，以本约定及用户最新指令为准。

## 共同代码与数据库基线

以包含[基线整合记录](../../交接/代码基线整合与迁移兼容-2026-10-17.md)的最新 `origin/main` 开发，handoff 记录实际 HEAD。旧本地 `56966018` 与旧远端 `37a7721e` 不再分别作为后续开发起点。只保留历史迁移链，V150 起新增迁移统一放 `apps/api/src/main/resources/db/migration-common/`；先在任务认领中登记版本与涉及表，避免双方占用同一版本。不得对另一种历史执行 Flyway repair、清库或覆盖校验和。线上升级另行核查与授权。

## 认领与范围

1. 先从远端最新 handoff 查看 owner、status、依赖、阻塞与记录。任务初始为核查／候选，不代表用户批准所有改造。
2. 选定任务 ID，填写实际负责人和更新人、带时区时间、代码文件范围、接口约定和本次基线提交。只在 tasks 中填写任务 owner，不设置节点级 owner；多人做同节点不同任务要分别登记。
3. 先提交并推送认领记录及重新生成的看板，再开始业务改动。推送成功后才视为认领共享成功。不要依赖未推送的本地标记。
4. 两人同时认领导致推送拒绝时，重新 fetch，阅读对方认领。不得强推、不得盲目重放覆盖 owner；保留对方认领，另选任务或由用户协调。Git 记录是协调方式，不是自动锁。
5. 不同节点仍可能改同一文件、接口或数据库迁移。认领时列出共享范围；有重叠先约定顺序或接口负责人，阻塞方可做不依赖该改动的工作。
6. 先核查已有能力。无缺口标“不需开发”并写依据；有明确缺口且在授权范围内才实施；未确认业务规则、新入口或权限变化标“待确认”。实现不自动升级需求确认状态。

## 完成与交接

- 每个有意义的交接点更新对应 handoff：实际改动、代码位置、接口变化、验证命令及结果、剩余问题、下一步、依赖与证据。
- 维护 JSON 的 updatedBy、updatedAt、任务状态及实现／验证／部署状态；在文档末尾追加更新记录，不覆盖历史。
- 运行 `python3 docs/协作/企业首次接入/build.py` 与 `--check`。业务任务按实际改动进行验证；看板检查不能代替业务验证。
- 仅明确路径暂存；先检查 staged diff，再提交、推送。未获授权不部署、不改生产数据、不发外部通知。需要提交号自引用时，在后续交接补记；本次提交以 Git 历史关联 handoff，不伪造 SHA。
- 推送前 fetch 检查共同主线变化。非快进时不 force；检查冲突，必要时合并远端并复验受影响范围。生成 index.html 冲突先解决源文件与 handoff，再重新构建。
- 接续方拉取后先读 handoff 和实际 diff，不仅看“已完成”标签。完成必须有验证证据；实现、部署和业务验收互不替代。

## 流程变更

流程节点的说明、边界和顺序在 flow.json 维护，新增节点使用新 ID。业务含义改变时增加 revision，追加 CHANGELOG.md；开发进展只更新 handoff。展示修复无需让所有节点业务方案重新确认。

旧 flowRevision 会提醒复核。负责人确认任务仍适用后更新该值，不自动批量升级。删除或合并节点前明确任务迁移；不得丢弃未完成任务。

## 向用户汇报

每次交接说明：节点／任务 ID、已做与未做、验证结果、提交号和推送结果、阻塞及下一位应做什么。没有执行生产发布时明确未部署。双方通过仓库同步，本约定不授权自动向另一会话发消息。
