## 两种数据库历史如何汇合

历史上双方重复使用了相同 Flyway 版本号但内容不同。简单复制远端 SQL 到旧本地库会触发 checksum 错误；改版本号或 repair 也不能证明数据库已正确升级。

| 数据库来源 | 加载路径 | 本次补齐 |
| --- | --- | --- |
| 新建库、原远端标准迁移链（至 V133） | 默认 `db/migration` + `db/migration-common` | 保留原 V1–V133 字节；V134–V138 补本地能力，V139 修正历史来源授权。 |
| 旧本地开发迁移链（至 V140） | 显式 `migration-local` profile：`db/migration-local` + `db/migration-common` | 保留旧本地全部历史字节；V141–V147 补远端 V127–V133，V148 修正历史来源授权。 |
| 汇合后的新增功能 | `db/migration-common` | V149 为汇合标记；**下一项迁移从 V150 开始，只在此目录新增。** |

`migration-local` 是旧数据库兼容路径，不是长期开发分支。以后两边执行相同 V150+ 迁移，禁止再次分别扩展历史目录。

本轮按 Git 原件逐字节比对：远端 128 个历史 SQL、本地 126 个历史 SQL 未修改。文件数和最高版本号不同，历史本来存在版本空档。

### 开发者操作

1. 拉取共同主线前检查工作区；干净且可快进时使用 `git pull --ff-only origin main`，分叉或存在他人改动时先核查，不 reset、不强推。
2. 新克隆执行 `npm run setup:git`。新建本地库使用默认迁移路径，通常 `SPRING_PROFILES_ACTIVE=local`。
3. 已有本地数据库先只读检查 `flyway_schema_history` 的 version/script/checksum，确认属于哪条原历史。**不能只根据最大版本号猜测。**明确属于旧本地链时，使用 `SPRING_PROFILES_ACTIVE=local,migration-local`，保持既有数据库连接与私有存储位置。该配置会执行迁移，应先备份本地数据。
4. 历史混杂或存在手工 overlay 时停止启动，记录真实历史后另做兼容检查。禁止 `flyway repair`、改 checksum、清库或重置 baseline 来绕过错误。
5. 任务认领时登记计划迁移版本、涉及表和接口；双方不得同时占用 V150 等同一版本号。第二位开发者先拉取，再分配下一个版本。

线上曾使用增量 overlay；本记录的两条标准历史验证**不代表线上数据库历史已匹配**。生产升级需另行只读核查、备份与授权，本轮未执行。
