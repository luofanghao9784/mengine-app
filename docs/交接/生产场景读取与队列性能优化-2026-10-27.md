# 生产场景读取与队列性能优化实施记录

关联 [Issue #202](https://github.com/dimmm1125-coder/dreamcore-workspace/issues/202)。按 `superpowers:executing-plans` 在本分支逐项实现，结束后独立审查。

目标：降低企业整理队列的重复权限计算，解除场景读取的全局串行等待，为意外 500 提供不含业务内容的定位编号。实现决定不代表生产部署完成。

## 证据与范围

2026-10-27 只读巡检发现：企业整理队列无待运行任务时，仍反复查询约 4.4 万知识分块；查询计划与进程采样显示该查询占用一个 CPU 核，单次持续数十秒。同一资料版本的权限被逐分块重复检查。其他简报、推荐查询也有 CPU 消耗，本次不声称解决所有数据库热点。

`SceneService.dispatch` 使用实例全局锁，所有企业的读取和写入共用同一锁。慢查询或桥接等待会阻塞后续读取。生产内部代理等待上限为 120 秒；未取得生产线程转储，不能量化每次 504 的锁等待占比。

知识页面 500 的历史来源事务回滚问题，主线已包含 PR #143（`cec9855d`），生产部署的旧包尚未包含该修复。本次不重复实现，保留其回归验证。

## 实现约束

- 只修改本地代码与文档；生产写入、部署、服务重启由部署负责人执行。
- PostgreSQL 查询内复用权限结果，不做跨请求或跨权限版本缓存。领取任务、发布结果原有权限复核继续执行。
- GET 读取共享公平读锁，允许多次读取并行；写入、同步与路由变更共用排他写锁，保留原有读写互斥。桥接侧权限变化独立于 Java 企业成员身份，不能仅凭响应前成员复核去掉读写互斥。
- 意外错误只记录服务端生成的编号、异常类型和有限代码位置，不记录异常消息、SQL、请求体、URL 参数或凭据。

## 审查重点

当前代次失败时不能回退到旧代次；首分块为空不能隐藏后续有效内容；撤权与恢复必须在下次查询生效；不同企业的读取互不阻塞且不能越权；异常链不能泄露消息或无限展开。

## 发布与恢复边界

本分支基于当前主线，生产仍在较早版本。部署负责人应决定验证完整主线发布，或在生产基线上另做经测试的补丁发布，不能把本 PR 等同于可直接覆盖旧生产包。数据库迁移编号须按实际发布基线协调。

V187 仅新增发现专用视图，不修改业务数据和旧视图。应用回滚后旧发现语句继续可用，多出的视图可保留；如需移除，应在停止新代码使用后由负责人执行新的前向迁移，不修改已应用迁移的校验和。历史来源 500 修复也必须包含在实际发布包中。

上线验收应比较相同业务时段的数据库 CPU、队列发现查询耗时及调用量、scene 接口 P95/P99 与 500/504 比例，并复核权限与队列状态。合成测试的性能数字不能当作生产降幅承诺。

## 验证记录

旧实现的合成回归先复现：4,001 分块触发 4,001 次权限判断，慢 GET 阻塞另一企业 GET，意外 500 没有定位编号。修复后同一视图查询仅 1 次权限判断；4,001 条 CANCELLED 记录经过真实 discover 三条语句后，共 2 次权限判断且全部正确恢复 QUEUED。次数只代表这些测试数据和查询，不代表所有生产查询耗时等比例缩短。

独立审查发现并修正两项边界：共享视图物化使单分块查询从 1 次权限判断变为 7 次，故改为发现专用视图，领取和重试保留旧视图；无锁 GET 允许桥接权限写入越过在途读取，故改为公平读写锁。两项都补了先失败的测试。慢写入仍会阻塞读取；本次只移除不必要的读读互斥，不能承诺所有 504 消失。

物化仅在单条查询中复用结果；PostgreSQL 同时指出物化会限制外部筛选下推，故必须将全库发现与定向查询分开：[官方文档](https://www.postgresql.org/docs/18/queries-with.html#QUERIES-WITH-CTE-MATERIALIZATION)。

最终相关后端回归 83 项通过，0 失败，API 打包成功；前端构建及生产入口资源检查通过。覆盖队列领取、失败重试、来源撤权、桥接治理、路由与历史来源 500 回归；未进行浏览器人工点击或生产写入。独立代码审查复核通过。本地私有日志位于 `.local/work/production-performance/`，不提交日志或任何生产业务内容。
