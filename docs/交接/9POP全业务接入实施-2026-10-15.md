# 9POP 全业务接入实施

## 已确认范围

用户明确授权 [106 表范围](../调研/9POP全业务数据盘点与接入范围-2026-10-15.md)：全部门店、全部源库现存历史；先补完整取数，按基础经营链起逐批取数、首轮治理、知识初始化，验证服务器模型接续后上线。原三表保持 ID 与原投影，新增 103 表。C/D 类仍按清单排除或按需确认，不把业务授权扩大为原件、私人健康/会话或凭据读取。

## 技术决定与实施边界

- 新的 `full_collector.py` 读取部署固定投影。计划阶段只估算页数；真实数量、结构和全部页面在同一个 InnoDB REPEATABLE READ / READ ONLY 事务读取，并最终 ROLLBACK。稳定主键排序分页；增长超过计划、缺页、重复主键、内容摘要/数量不符或超限，整份拒绝。源数据没有写操作。
- v2 上限每表 100000 行/100 列，每次来源响应 64MiB/2000000 单元格；这是失败边界，不是截断窗口。v1 保留原上限。采集输出先受子进程文件大小约束，验明完整后才发布，失败保留旧版本。
- 每次采集响应中的多表同一事务一致；引擎按表拉取，因此各次调用及各表持久化回执的读取时刻仍独立保留，不宣称一组或 106 表在同一时点。跨表分析必须检查对应来源时间与业务日期。
- 新来源由独立列级只读账号读取；已核验成员电话列、鉴权表和 UPDATE 拒绝。新增来源已逐批验收并激活，原三表继续使用原采集账号与来源。
- 新增 `restrictedContent` 受限来源标记：即使另一位企业管理员也不自动取得正文、AI、治理或自授权资格；仅来源所有者或明确内容授权可读。当前没有经核验的其他财务/人事账号映射，不自动批量授予权限。
- 中央 Scene 目前会将输入归入同一共享空间，因此受限来源及其派生知识不自动导出到该空间。它们由获权负责人在企业管理端数据基座/知识库使用并由服务器模型维护；普通共享空间只接非受限来源。未来要在员工工作空间开放受限明细，须先实现并验证对应专属空间映射，不能靠提示词隔离。
- 首轮口径明确区分源码/结构事实、部署推断、尚未确认。未知含义字段保留原值并显示治理提示，不进入模型统计。余额、日快照及需要方向/冲销规则的字段使用禁止无条件求和约束，防止错误统计进入知识。

### 大表统计性能修正

线上课债批次确认逐字段重复解析全量记录会延长首轮检查。改为同一次同步统计内复用一次不可变的记录读取，不跨请求缓存、不降低新鲜度或权限检查。与已完成的真实课债/财务 12 表统计逐项比较，所有事实一致，本地全组统计耗时 949ms；Wiki 201 项回归再次通过。此修正先完成验证，再用于跨批次关联与后续服务器模型维护。

### 正常同步后的关联接续修复

最终线上扫描发现旧关联指纹包含目标表数据摘要，正常行更新会导致 15 处“关联规则失效”。已改为结构指纹绑定，保留旧格式只用于兼容；正常记录和更新频率变化不失效，字段结构变化仍拒绝。重新验证并绑定本轮 106 表的关系，回归覆盖行更新成功、真实结构变更拒绝。此项是验收发现的实现问题，不归咎于源业务数据。

### 合法空字符串与 NULL 分离

`CourseProductRules.validateTrialCourse` 在源码第 183 行明确设置 paymentMethods 为空字符串，V94 体验官固定产品也使用空字符串。之前将 SQL NOT NULL 等同于非空文本，造成 4 条产品及其下游关系误报。固定投影新增 `allowEmptyColumns=[payment_methods]`，字段仍保留 required/NOT NULL 约束；仅允许空字符串，sourceNullFields 标记的 SQL NULL 仍检查失败，不补造 `full` 或金额。类型与字段投影不变，重新取数并按新结构版本绑定受影响的关系；对应中央数据定义由内容指纹生成新 ID，保留旧版本。测试覆盖空字符串通过、NULL 拒绝和未声明例外仍拒绝。最终状态以线上验收结果为准。
