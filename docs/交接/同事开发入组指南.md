# 同事开发入组指南

更新：2026-09-22。适用于“系统＋前端”和“梦核引擎”两条开发线。日常规则以 [COLLABORATION](../../COLLABORATION.md) 为准；技术和实现状态以 [README](../../README.md)、[开发启动说明](开发启动说明.md) 及实际代码为准。

流程：**提供本人 GitHub 用户名 → 接受仓库邀请 → 克隆并启动 → 确认负责范围 → 任务分支开发 → PR 审查 → 合入主线。**

## 1. 负责人先做什么

收集同事的 GitHub 用户名、负责方向、第一项任务及审查人。每人使用自己的账号和本机认证，不共享仓库所有者的密码、令牌或 SSH 私钥。

仓库为 [dimmm1125-coder/dreamcore-workspace](https://github.com/dimmm1125-coder/dreamcore-workspace)。负责人进入：

**Settings → Access 下的 Collaborators → Add people → 选择同事账号 → 发出邀请。**

同事接受邀请后获得仓库访问权。添加协作者无需为了本项目购买套餐；GitHub Free 支持私有仓库协作。依据：[GitHub 邀请说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository)。

当前是个人账号名下的私有仓库，协作者获得整个仓库的读写能力，不能只给某个目录权限。两组源码互通已经确认；内部开发和成本文档也在仓库内，邀请前应确认同事可阅读这些资料。更细的团队角色以后需要时再迁移到组织，不是现在入组的前置条件。依据：[个人仓库权限](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository)。

成员确定后再将真实负责人登记到任务与代码责任清单；`CODEOWNERS` 不等于访问控制，也不能在当前条件下强制双方审批。当前尚未邀请新成员，本指南不代表已经授予任何人权限。

## 2. 同事准备自己的电脑

当前先准备 Git、Node.js **24.20.0**（以仓库 `.node-version` 为准）和编辑器。使用下面的 GitHub CLI 登录方式时还需安装 `gh`；Windows 命令示例可在 Git Bash 执行。

如果自己的电脑已经有可用的 GitHub 认证，可继续使用。尚未认证时执行：

```bash
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
gh auth status
```

按 GitHub 页面登录自己的账号并授权；确认当前账号与收到邀请的账号一致。也可使用本人已配置的 SSH 认证，但无需为了入组切换连接方式。GitHub 的命令行认证与浏览器会话分别管理，见[认证说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github)。

目前可运行工程是 React 前端 Demo，Spring Boot 平台和独立引擎的具体工程入口尚未建立。JDK、构建工具及引擎依赖在对应工程落地后按其 README 配置，不凭未来规划猜测安装或启动命令。

## 3. 克隆和首次启动

接受邀请后，在自己电脑的开发目录执行：

```bash
git clone https://github.com/dimmm1125-coder/dreamcore-workspace.git
cd dreamcore-workspace
npm run setup:git
npm ci
npm run dev
```

打开 `http://127.0.0.1:5173/`。`setup:git` 启用本仓库的防误推钩子和快进拉取设置；每个新 clone 都要执行一次。

另开终端进入同一项目，设置自己的提交身份。以下文字需要替换；邮箱使用本人 GitHub 验证邮箱或账号设置提供的 noreply 邮箱：

```bash
git config --local user.name "你的姓名或开发署名"
git config --local user.email "你的提交邮箱"
```

提交署名与 GitHub 登录认证是两件事；填写 `user.name` 不会获得仓库访问权。

首次环境检查：

```bash
npm run build
npm test
npm run test:git
npx playwright install chromium
npm run test:e2e:konggu
```

这些是现有项目命令。每位同事须以自己机器上的实际输出为准，不能引用其他电脑的旧结果作为本人已通过。运行时不需要另一人的 localStorage 或官网仓库，当前 Demo 也不需要生产数据库和模型密钥。

## 4. 开发前先对齐责任

| 开发方向 | 负责内容 | 开工先对齐什么 |
| --- | --- | --- |
| 系统＋前端 | 网页、业务平台、身份权限、资料与任务、成果 | 当前页面/业务需求、负责文件、验收场景 |
| 梦核引擎 | 上下文、分析与策略、方法、模型/Harness 适配 | 与平台的输入输出、模拟样例、错误和任务状态 |
| 双方共同部分 | 引擎契约、相关样例、跨模块联调 | 谁负责修改、双方审查人、兼容范围 |

两组克隆同一个仓库。分工写在任务和目录责任里，不建长期“系统分支”和“引擎分支”。未来目录按照实际工程建立；当前 `engine/` 等目标目录尚未存在。

第一项任务尽量小且完整，例如一项已明确的页面调整或一组接口样例，不以“把整个引擎开发完”作为第一张任务单。共享接口、根依赖和公共配置由一名负责人整合，另一方审查。

## 5. 每项任务的操作顺序

在干净的工作目录里从最新远端主线开任务分支。以下分支名是示例，替换为自己的真实任务；平台任务与引擎任务二选一：

```bash
git status --short --branch
git fetch origin
git switch --no-track -c codex/engine/EN-001-task-contract origin/main
```

系统与前端使用 `codex/platform/<任务号>-<主题>`，引擎使用 `codex/engine/<任务号>-<主题>`。已有未提交工作时不要直接切换或覆盖，先保存本任务工作，或按协作规则建立独立 worktree。

修改后执行相关检查，并检查 `git diff`。用 `git add -- 文件路径` 逐项暂存本任务文件，不使用 `git add .` 混入他人工作；随后检查并提交：

```bash
git diff --cached --stat
git diff --cached --check
git diff --cached
git commit -m "feat(engine): describe the actual change"
git push -u origin HEAD
```

提交说明替换为真实改动。到 GitHub 为该任务分支发起 **Pull Request，目标分支选择 `main`**；说明解决的问题、涉及接口、实际测试和需要另一组配合的部分。初期由项目负责人协调审查与 squash 合并，契约变化由双方审查。

主线新增了自己依赖的变化或发生冲突时，先 `git fetch origin`，在任务分支合入 `origin/main` 并处理冲突，重跑相关检查。共享分支不擅自 rebase 或强推。

PR 合并后，下次任务从最新 `origin/main` 开新分支。单任务目录要更新本地 `main` 时，先确认当前工作已保存，再执行 `git switch main`、`git pull --ff-only`。不要用 reset/clean 丢弃尚未保存的修改。

## 6. 当前需要知道的两个限制

1. **远端 CI 尚未启用。** CI 草案保留在维护者的本地待授权分支。普通克隆、分支和代码推送不需要先解决它；每个 PR 暂时由开发者运行本地检查并提供结果，由审查人核验。
2. **没有服务端强制主线保护。** 本地钩子帮助防误推，但可被绕过；个人仓库协作者本身有写入和合并能力。因此“统一由负责人合并”目前是团队协作约定。需要平台强制审查时再开通相应保护能力，不能把当前约定当作已启用的技术限制。

当前仓库包含已提交并推送的版本。维护者电脑上尚未提交的修改、其他本地分支和浏览器资料不会随 clone 分发；入组前应将同事需要的已确认说明和任务基线提交到可访问分支。

## 7. 可转给同事的开工说明

> 请先接受 dreamcore-workspace 的仓库邀请，使用自己的 GitHub 账号克隆项目。按 AGENTS.md、COLLABORATION.md、README.md 和开发启动说明补齐上下文，执行 `npm run setup:git` 并确认当前 Demo 能构建和启动。你本次负责【系统＋前端 / 梦核引擎】，任务为【编号与具体目标】，负责文件为【路径】，接口依赖为【契约或另一组任务】，审查人为【负责人】。从最新 origin/main 建立本任务分支，按实际路径提交，推送后向 main 发起 PR；记录实际验证结果，不直接推 main、不改写其他任务的工作，也不把模拟执行当作真实模型或业务执行成功。

方括号内容由负责人在分配真实任务时填写。本指南只说明入组流程，没有自动发出邀请或创建任务。
