# 云端模型接入（2026-10-11）

用户要求接入当前服务器版本，选择沿用本机百炼配置，并授权开发助手直接操作。本次在主目录 main 顺序处理，云端仍是现有数据副本，不代表本机最新业务数据已完成最终切换。

## 范围与实现

- 既有 API V108 接独立引擎 0.19.0，模型 `qwen3.7-plus-2026-05-26`；凭据通过 SSH 标准输入转移，未写入仓库、命令行参数或输出。
- 引擎仅监听 `127.0.0.1:18482`，API 使用内部令牌鉴权；模型 Key 仅注入引擎和一次性连接验证进程。API 原有网络限制保留。
- Node 24.20.0 从官方发布地址下载并核对 SHA-256，安装到 `/opt/dreamcore/`，不替换宿主 Node 20。引擎生产依赖按 lock 安装且禁用安装脚本。
- `TASK_CONCURRENCY` 控制单 API 进程会话执行槽位，默认仍为 20，允许 1—20，非法配置拒绝启动；本云端单实例设为 2，超额任务继续排队。账号既有五路业务限额不变；标题生成仍有独立单路，不将 2 路宣称为所有模型请求的总并发。
- 引擎资源上限 640MiB / 0.5 核，API 原有 1280MiB / 0.75 核保留。自动画报、持续计划、企业信息分析、经验提炼、采集、联网和新文件解析保持原关闭状态；本轮验证手动会话。

## 部署与回退

部署脚本：[enable-cloud-model.py](../../scripts/deploy/enable-cloud-model.py)。这是针对当前 V108 实例的一次性受控接入，不是通用安装器。

- 运行目录 `/var/lib/dreamcore/model-live-20261011/`，配置 `engine.env` 仅 root 可读；systemd 为 `dreamcore-model-engine.service`，以 dreamcore 用户运行。
- 证据与旧产物 `/var/lib/dreamcore/deploy-evidence/model-live-20261011/`，包含新产物 SHA、旧 API 配置/JAR、连接测试回执和切换前数据库快照。备份含敏感配置，不放公网。
- `prepare` 仅部署引擎并检查连接；`activate` 停 API、复核无活动任务、备份、切换后再启动。健康检查失败自动恢复原 API 配置与 JAR，停止引擎。
- 回退命令：服务器 root 运行 `python3 /var/lib/dreamcore/deploy-evidence/model-live-20261011/enable-cloud-model.py rollback`。只恢复配置与旧产物，**不覆盖数据库**。启用后已有新任务时先保全并核对其执行状态，停机不能当成供应商未收费。
- 本次不改变现有整机重启恢复策略；模型服务故障会自动重启，是否开机启动以 systemd 实际状态为准。

## 端到端验收发现与修正

首次正文任务 `32751beb-d7f6-429c-a1ee-70dd0ffa9a43` 及定位复验 `6d402805-2ef7-4437-b0f5-8944a49f5f77` 返回 RESULT_UNKNOWN；标题生成成功（227 输入 / 5 输出 token），正文没有模型请求记录，不能把供应商直连通过当成整个会话成功。新增引擎失败诊断只记录路由类别和安全错误码，不记提示词、响应、密钥或授权头，4 项服务/传输检查通过。

诊断时，独立数据库容器持续触及 0.4 核 CPU 限额；同一条真实任务权限校验查询在新连接下 `jit=on` 执行 12114.578 ms，`jit=off` 执行 827.562 ms。通过 API PostgreSQL JDBC URL 的 `options=-c%20jit%3Doff` 只关闭该应用连接的 JIT 编译；保留原 SQL、权限校验、回调超时和宿主数据库配置。此前尝试 Hikari `connection-init-sql` 遇到已启动池配置密封导致启动失败，已移除此配置，采用连接建立参数。此测量支持回调超时的诊断，但未据此将用户最初全部 499 归因为 JIT。

## 最终通过结果

- JIT 关闭后，0.4 核数据库仍在回调时触发 2505 ms 的 REMOTE_UNAVAILABLE。仅将 `dreamcore-app-check-20261010` 数据库容器 CPU 上限提升至 1 核，内存仍 512MiB；原 0.4 核配置已记录供回退。宿主当时 4 核、约 3.2GiB available、负载约 0.8；这是初始部署配置，不代表负载验收完成。
- 回调正常后发现本次打包遗漏 `engine/catalog/`，在模型调用前由 TrustedCatalog 读取目录失败。最终引擎包补齐 catalog、workers、许可文件；以实际服务账号逐项核验 4 个技能文件摘要通过，prepare 增加同项检查。源码层保留安全错误码、耗时与代码位置诊断，不输出异常消息、业务正文或授权头。
- 限流/兼容性 11 项、引擎 Harness/服务/传输 24 项均通过；没有重新声明全仓库全量测试通过。
- 北京时间约 15:22，正式 HTTPS 客户端会话 `b295966d-5bc6-4b94-a50c-1320eff88d08` 中任务 `6310d459-d510-4e80-ada9-aa4b91449d57` 成功，页面显示“云端模型连接正常”。数据库状态 SUCCEEDED、模型 qwen3.7-plus-2026-05-26、model_calls=1；用量回执 RETURNED，6797 输入 / 4 输出 token。该任务的完整上下文含系统规则，不能把输入 token 说成只有测试消息。
- 之前 6 次诊断任务均未获得成功回执，保留原 RESULT_UNKNOWN 记录，不伪造完成、不删除或重写历史；其中未查到正文模型请求记录。首次标题生成、供应商连接检查与最终正文调用分别有独立用量，不能将总费用报为零。
- API 与引擎均运行，数据库迁移版本仍 V108；ai、coach、boss HTTPS 均 200、TLS 校验成功。没有重启同机 9POP。截图在本机 `.local/cloud-deploy-prep/model-live-20261011/client-success.png`。
